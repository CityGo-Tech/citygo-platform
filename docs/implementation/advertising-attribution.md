# CG-ADS-001 · Измерение рекламных переходов

Подготовка от `main 854148e`, 8 ноября 2026 года. Это изменение Web и
документации: без миграций, включения рекламы, обновления сервера или изменения
публичных флагов аналитики.

## Метрика: исправление отчётов по источникам

Публичный лендинг сохранял четыре проверенные UTM-метки для регистрации, но
удалял query до загрузки Метрики. Явный `hit` содержал только чистый адрес,
поэтому источник и кампания не попадали в него.

Теперь collector публичного лендинга получает snapshot из существующего
контракта атрибуции. В явном `hit` передаются только `utm_source`, `utm_medium`,
`utm_campaign` и `utm_content`; такие же значения доступны в параметре
`campaign` целей лендинга. Каждое значение — строчный ASCII slug до 80 символов.
Snapshot должен соответствовать версии и точному пути лендинга. Адрес браузера
очищается по-прежнему, а неизвестные поля, поля контактов, поисковые фразы,
referrer, click ID и произвольный query не передаются. Метки остаются
недоверенными публичными ярлыками, не доказательством рекламного перехода.
Допустимый синтаксис сам по себе не распознаёт персональные данные: оператор
не должен помещать в UTM контакты или другие сведения о пользователе.

Пример ссылки:

```text
https://pilot.xn--c1ajazlh.xn--p1ai/landing/v1?utm_source=vk&utm_medium=cpc&utm_campaign=v1_moscow_202611&utm_content=family_01
```

Для Avito используется `utm_source=avito`; разные креативы получают разные
заранее заданные `utm_content`. Разделение между источниками проверяется на
новом экземпляре collector: предыдущая кампания не переносится на другой визит.

Основная цель — `citygo_registration_completed`, после успешного ответа API
подтверждения email и создания аккаунта. Submit формы и принятый запрос письма
остаются отдельными этапами. Регистрация сохраняет версию лендинга; её цель
связывается с посещением средствами счётчика. Продуктовые URL остаются чистыми,
а обычные события кабинета не наследуют произвольные campaign-поля.

Источник аккаунта также сохраняется в `user_acquisition` в транзакции его
создания; это не гарантирует доставку браузерной цели. Блокировщики, DNT, GPC,
отказ от аналитики, недоступное хранилище и admin-сессия могут исключать визиты.
Нельзя делить все регистрации БД на посетителей, видимых только Метрике.

## VK и Avito: точные ID, интеграция ещё не включена

Владелец предоставил публичные идентификаторы:

| Площадка  | ID        | Планируемая цель                |
| --------- | --------- | ------------------------------- |
| VK Ads    | `3812681` | `citygoRegistrationCompleted`   |
| Avito Ads | `3496456` | `citygo_registration_completed` |

Эти ID не являются секретами. В этом изменении их SDK **не устанавливаются**:
нет скрытого изображения, `noscript`, placeholder-пикселя, новых build-флагов
или кода, создающего видимость работающей интеграции. Цели в кабинетах не
созданы, получение событий площадками не проверено. Метрика не заменяет
платформенный счётчик для оптимизации рекламы на конверсию.

Подтверждённый контракт VK/Top Mail описан в
[JS API](https://top.mail.ru/help/ru/api/jsapi),
[целях](https://top.mail.ru/help/ru/settings/goals) и
[инструкции SPA](https://top.mail.ru/help/ru/code/ajax).
После отдельной интеграции и создания соответствующей JS-цели вызов должен
происходить только по факту подтверждённой регистрации:

```js
_tmr.push({
  id: 3812681,
  type: "reachGoal",
  goal: "citygoRegistrationCompleted",
  url: "https://pilot.xn--c1ajazlh.xn--p1ai/",
  referrer: "",
  title: "CityGo",
});
```

Контракт Avito приведён в
[инструкции счётчика](https://ads-help.avito.com/external/pixel-avito-ads).
После загрузки утверждённого счётчика и настройки соответствующей цели:

```js
_apxl.sendEvent({
  type: "reachGoal",
  goalName: "citygo_registration_completed",
});
```

Счётчик Avito автоматически отслеживает SPA-переходы; дополнительные ручные
pageview могут дублировать просмотры. Удаление тега `script` не является
остановкой уже выполненного SDK. Перед включением нужна проверенная архитектура
жизненного цикла, прекращающая его работу при отказе, смене сессии, неизвестной
роли и входе в admin. Нельзя подменять её недокументированным `destroy` или
считать класс `ym-hide-content` защитой для других поставщиков.

Новых галочек регистрации эта подготовка не добавляет. Будущая интеграция
должна учитывать действующий выбор аналитики, не передавать содержимое кабинета
и иметь отдельно проверенный безопасный переход к новому документу/контексту.

## Проверка перед запуском

1. Выпустить проверенный код с исправлением UTM по обычному процессу.
2. Для каждого источника проверить новый обычный визит с контролируемой меткой;
   admin-визит не используется как доказательство доставки.
3. Проверить в Метрике источник, кампанию, лендинг и подтверждённую регистрацию
   в одном окне измерения. Локальная проверка payload не подтверждает реальную
   доставку в кабинет.
4. Отдельно закончить безопасный жизненный цикл VK/Avito SDK и проверить новые
   пиксели: загрузку, одну действительную конверсию, отсутствие дублей, отказ,
   admin и смену аккаунта. До этого оптимизация по их целям не считается готовой.

Три режима ИИ, тарифы, постоплата, чеки ЮKassa, телефон и подарок 500 ₽ не
изменяются. Платных вызовов, импортов клиентских контактов и рекламного запуска
в проверках нет.

## Локальная проверка подготовки

- 36 целевых unit/lifecycle-тестов: безопасные метки, отдельные источники,
  неизменяемый snapshot, границы путей и версии, admin/DNT/GPC/отказ.
- Web lint и typecheck, lint изменённого E2E: пройдены.
- Production build: пройден, включая отдельную локальную сборку с явными
  параметрами fake collector; публичные флаги сервера не менялись.
- 26 desktop/mobile E2E для обоих лендингов: пройдены с синтетическими API и
  подменённым SDK. Подтверждены чистый адрес, UTM в явном hit, разделение VK и
  Avito, OTP-версия и исключение приватных полей. В первой попытке 25/26 прошли;
  оставшийся сбой был завершением image-proxy фикстуры после конца теста.
  Ожидание network-idle перед disposal исправлено; повторный прогон — 26/26.

Полный релизный Linux-прогон, Container smoke и реальная доставка событий в
рекламные кабинеты этим набором проверок не подтверждаются. Merge и выпуск
относятся к отдельным этапам.
