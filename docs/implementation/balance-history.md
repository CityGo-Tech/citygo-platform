# История баланса CityGo

Экран `Баланс и пополнение → История баланса` продолжает Figma `6:65` и использует существующие Manrope, карточки, цвета и кнопки. Из истории можно вернуться к пополнению, выбрать «Все операции», «Подарок», «Пополнение», «Списание» или «Возврат», загрузить следующую страницу и обновить список. Только необходимая пользователю информация: тип операции, дата и точная сумма.

## Источник и границы

`GET /v1/ai/credit/history?filter=all&cursor=…` возвращает максимум 20 операций и 16 КиБ. Фильтр применяется в SQL **до** LIMIT: скрытые служебные hold/release больше не вытесняют старые пользовательские операции. Суммы передаются целыми микрорублями без округления, идентификаторы bigint — строками.

- Подарок, подтверждённое пополнение, фактическое списание: `ai_credit_entries` bonus/topup/settle, включая фиксированную плату режима «Минимум» через существующее завершение ledger.
- Возврат: только `payment_refunds.status=succeeded` вместе с settled allocation той же точной суммы и первым неизменяемым `provider_observed` с `providerStatus=succeeded`. Возврат **уменьшает** баланс CityGo: деньги возвращены покупателю, это не новое пополнение. Повторные наблюдения не создают второй строки. Резерв, pending, неизвестный результат, ответ create и отменённый возврат не объявляются успешным возвратом.
- Это история завершённых операций, не выписка о доступном остатке: незавершённые операции по-прежнему отражает текущий баланс.

Сортировка — время с точностью до микросекунд, источник и bigint ID. Курсор содержит снимок максимальных ID обоих источников и ключ последней строки; новые проводки и поздно завершившиеся возвраты появляются после явного обновления. HMAC связывает курсор с сессией, владельцем и фильтром. Подмена, другая сессия/владелец/фильтр отклоняются; через 30 минут нужно обновить историю. Доступ проверяется внутри транзакции под SHARE-блокировками account-security → active user → действующая session, включая временный пароль и сохранённое согласие для сервиса. Read-only: новые аккаунты/проводки/согласия/аудит не создаются. Ограничение SQL — 5 секунд, без повторов.

Миграция `0043_balance_history.sql` добавляет только два индекса: видимая история по user/kind/time/id (по одной ограниченной ветви на вид), первое успешное наблюдение по refund/sequence. Старый `(user_id,id)` не обеспечивает одновременно фильтр вида и хронологический keyset. Для возвратов сохраняется owner-фильтр и существующие индексы владельца/связей. Роли и финансовые алгоритмы не меняются.

## Приватность и совместимость

Экран скрыт от записи содержимого Метрикой (`ym-hide-content`). Финансовые записи не пишутся в local/sessionStorage, браузерный адрес или события аналитики. API-курсор служит только пагинации; он не содержит суммы, номера платежа, контакты, ключи или провайдерские идентификаторы. Смена фильтра/владельца/сессии, выход и размонтирование исключают публикацию запоздавшего ответа. Ошибки доступа очищают список; ошибки сети допускают ручной повтор, без вывода внутренних ошибок.

Endpoint аддитивный: прежние Web/API/Expo продолжают работать. Три режима, резерв 5 ₽, тарифы, списания ×10, платёжный магазин/чеки, телефон и подарок 500 ₽ не меняются. Обновление сервера и автодеплой не выполняются этой доработкой.

## Проверки

Целевые contract/client/resource, PGlite/API и opt-in PostgreSQL тесты покрывают фильтр до пагинации, tie keysets, точность микрорублей, владельца/сессию/блокировку, подмену курсора, возвраты и отсутствие денежных записей при чтении. Браузерный сценарий проверяет экран, фильтры, следующую страницу, ошибки, клавиатуру, узкую ширину и отсутствие внешних вызовов/мутаций. Полный релизный прогон выполняется отдельно на интегрированном SHA; наличие тестов не означает выпуск на сервер.
