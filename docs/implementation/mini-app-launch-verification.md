# Серверная проверка запуска мини-приложения

`POST /v1/mini-apps/telegram/verify` и `POST /v1/mini-apps/max/verify` принимают
строку `Telegram.WebApp.initData` или `window.WebApp.initData` в теле
`text/plain; charset=utf-8`. Используются обычные заголовки контракта API CityGo.
Параметры запроса в URL запрещены. `initDataUnsafe`, адрес страницы, внешние
параметры запуска и JSON-обёртки в этот контракт не входят.

Токены `TELEGRAM_MINI_APP_BOT_TOKEN` и `MAX_MINI_APP_BOT_TOKEN` доступны только
API. Каждый маршрут включается своим токеном. Для двух маршрутов нужны разные
токены. Пустые настройки отключают маршруты, текущие профили развёртывания
не изменяются.

## Валидация

Оба адаптера вычисляют HMAC-SHA-256 над декодированными парами `key=value`,
отсортированными по ключу и разделёнными LF. Из расчёта исключается `hash`.
Ключ HMAC выводится из константы `WebAppData` и токена выбранного бота.
Telegram-поле `signature`, если оно пришло, остаётся в сообщении HMAC.
Отдельная процедура Telegram с Ed25519 предназначена для третьих лиц.

Граница входа — 8192 байта и 32 пары. Проверка отклоняет повторяющиеся
декодированные ключи, управляющие символы в значениях и ошибки URL-декодирования.
Применяется форм-декодирование `+` как пробела и `%2B` как литерального плюса.
Сырые значения не пересобираются из JSON перед сравнением подписи.
CityGo требует однозначный числовой `user.id` и у MAX непустой `query_id`.
Числовой идентификатор проверяется без округления. Поля профиля не извлекаются
в результат. Для внешних подписанных полей, которые CityGo не использует,
сохраняется участие в HMAC.

`auth_date` — Unix-время в секундах. CityGo принимает возраст до пяти минут
и допускает расхождение часов до 30 секунд вперёд. Telegram делегирует выбор
окна приложению, MAX рекомендует интервал в один час. Подписанный `start_param`
определяет назначение запуска. Поддерживаются `housing`, `coordinator` и обычный
гостевой запуск без этого поля. Любое другое значение отклоняется.

## Граница полномочий

Ответ содержит `verified: true` и `purpose`. Повтор свежего запуска даёт тот же
результат: проверка не создаёт аккаунт, сессию, привязку или одноразовый допуск.
Тело передаётся только в обработчик проверки. Содержимое, подпись, идентификаторы
и контактные поля не записываются в БД, логи или аналитику и не возвращаются.

При добавлении операции, которая меняет состояние, её обработчик должен заново
проверять запуск, сопоставлять подписанное назначение с ожидаемым и атомарно
фиксировать потребление запуска в той же транзакции, что и изменение.
Для уникальности подходит отпечаток проверенной подписи в контексте
провайдера и конкретного бота. Повтор должен остановиться до изменения состояния.
Приём всего `initData` в публичном URL или хранение его целиком для контроля
повторов в этот контракт не входят.
