# CG-011A — основа постепенно накапливаемой базы знаний

Решение владельца от **18 октября 2026**: CityGo начинает без заранее наполненной
базы городов. По мере обращений помощник сначала проверяет доступные знания;
при пробеле нужно ограниченное исследование публичных источников. Полезные
проверенные сведения сохраняются для следующих ответов. Это отдельная база,
**не обучение весов модели на переписках пользователей**.

Эта итерация от `main` после PR #82 (`6a900d7`) добавляет только строгие контракты
и детерминированный offline-planner. Она не зависит от неслитых PR #86/#87,
не включает research, не меняет API, БД, сервер, деньги или Figma. Нет созданного
каталога реальных городских фактов; тестовые записи вымышлены.

## Как будет работать накопление

1. Из разговора строится минимальный предметный запрос без персональных данных:
   тема и применимость к городу либо направлению. Сейчас это ещё не реализовано;
   planner получает уже заданный редакционный `factKey`, а не свободный вопрос.
2. Сначала проверяются опубликованные актуальные версии базы.
3. При `miss`/`stale` можно предложить research. Сам planner не вызывает ни сеть,
   ни модель, ни очередь. Перед этим нужны допуск, отдельный бюджет и лимиты.
4. Исследование формирует **кандидата**, а не общедоступную истину. Утверждение
   связано с точной версией источника, подтверждающей цитатой и областью действия.
5. Проверка качества, прав использования, даты и применимости предшествует
   публикации. Схема сейчас допускает только editorial review, но не проверяет
   полномочия редактора: это обязанность будущих серверных команд и аудита.
6. Позднее retrieval-first использует эти сведения повторно. Скорость, стоимость,
   точность и долю повторного использования нужно измерять, не обещать заранее.

Публичные знания о городах и личная память клиента — разные хранилища и допуски.
Переписка, контакты, адрес человека, его бюджет и персональная рекомендация не
должны автоматически попадать в общий каталог. Исключение полей `userId`,
`messages` и подобных из контракта **не является PII-detector**: личные сведения
всё ещё могут оказаться внутри строки и требуют отдельной проверки.

## Контракты и состояния

Модуль [knowledge.ts](../../packages/contracts/src/knowledge.ts) независим от
legacy-таблицы `knowledge_sources` и кандидатного `r1SourceSchema` из CG-008.
Их записи не преобразуются в новую форму автоматически.

| Объект      | Назначение                                                                                                                                     |
| ----------- | ---------------------------------------------------------------------------------------------------------------------------------------------- |
| Source      | Неизменяемая версия URL, заголовка, ограниченного фрагмента, происхождения, применимости, даты получения и заявленного основания использования |
| Fact        | Отдельное утверждение с редакционным ключом вопроса, происхождением процесса и ссылками на точные версии источников/цитаты                     |
| Publication | `candidate` с датой предложения; `published` с проверкой/публикацией/сроком; `withdrawn` с датой отзыва                                        |
| Scope       | `global`, конкретный `city`, либо направленный `route` от города к городу                                                                      |
| Query       | Ключ вопроса, область, явное `asOf`, предел 1–20 результатов                                                                                   |

Схемы строгие, без произвольных payload и скрытых полей. ID — ограниченные
ASCII-ключи, ревизии — положительные safe integers, URL — HTTPS без credentials.
Такой URL **не является разрешением fetch**, доказательством публичности,
доступности, доверенности домена или проверкой SSRF.

Кандидат не требует выдуманной даты проверки. Для публикации нужны корректный
порядок дат, редакционный reviewer и рассмотренное основание повторного
использования. Это записанные заявления, не автоматическое юридическое заключение
или подтверждение фактического ревью. Проверка формы не доказывает истинность.

Одна запись не более 8 источников, фрагмент источника до 16 000 символов,
утверждение/цитата до 4 000; вход не более 1 000 source- и 1 000 fact-версий.
Это ограничения чистого модуля, не замена будущим HTTP/body/time/token limits.

## Правила offline-planner

[planKnowledgeLookup](../../packages/content/src/knowledge.ts) принимает `unknown`
и проверяет boundary через общие contracts. В `content` не добавлена прямая
зависимость от Zod. Нет чтения часов: время всегда передаётся явно. Нет I/O,
callbacks, URL-fetch, вызовов модели, изменения входа, платного действия или записи.

| Статус     | Значение                                                                                                                    | Действие planner                                                            |
| ---------- | --------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------- |
| `hit`      | Все выбранные записи опубликованы, актуальны, однозначны и имеют допустимые точные источники                                | Возвращает ограниченные факты/цитаты/URL/ревизии; `researchNeeded=false`    |
| `miss`     | Нет записи, публикации или источника; версия отозвана либо синтетическая                                                    | Возвращает причину без текста фактов; `researchNeeded=true` — только сигнал |
| `stale`    | Срок истёк либо источник заменён новой ревизией                                                                             | Не выдаёт старый текст за текущий; только сигнал обновления                 |
| `conflict` | Некорректный snapshot, будущая дата, разные содержания одной ревизии, неоднозначные утверждения или неверная цитата/область | Не запускает research; сначала проверка целостности/редактора               |

Особенности консервативной политики:

- Для каждого ID выбирается старшая ревизия. Даже новая candidate-версия блокирует
  прежнюю опубликованную версию; отзыв не позволяет вернуться к старому тексту.
  Production-хранилище позднее может отделить revision от publication head,
  но должно сохранить явное, протестированное правило отзыва.
  «Старшая» здесь означает только старшую в переданном snapshot: чистая функция
  не может обнаружить скрытую от неё новую/отозванную запись. Будущий repository
  обязан давать полный согласованный текущий head и повторно проверять его
  перед ответом; список, присланный клиентом, не является авторитетной базой.
- Точная city/route-запись имеет приоритет над `global`. Если она непригодна,
  нельзя незаметно подменить её общим утверждением. `route A→B` не равен `B→A`;
  city-факт не применяется к направлению автоматически.
- Область каждого источника должна точно совпадать с областью факта. Нельзя
  расширить локальный источник до другого города одним полем в рекомендации.
- Нужна именно указанная ревизия источника и его текущий head. Цитата должна
  буквально входить в сохранённый фрагмент; источник опубликован до проверки
  факта. Это **не семантическая проверка**, что цитата поддерживает утверждение.
- Эффективный срок — самый ранний срок факта и всех его источников. На самой
  границе срока ответ уже `stale`. Будущее получение/ревью/публикация/отзыв
  относительно `asOf` блокирует snapshot; будущий `validUntil` допустим.
- Разные тексты одного применимого `factKey` считаются неоднозначностью, даже
  если человек позже признает их равнозначными. `limit` не скрывает конфликт.
- Разные содержания одного `(id, revision)` блокируют весь snapshot, включая
  нерелевантные записи; точные дубликаты допустимы. Для одного fact-ID `factKey`
  и scope неизменяемы между ревизиями; для source-ID неизменяем scope. URL,
  заголовок, фрагмент источника и текст утверждения могут изменяться в новой
  ревизии, но смена вопроса/географии требует нового ID. Нарушение identity
  даёт `conflict/version_conflict` до query-фильтрации, независимо от порядка
  входа: нельзя спрятать прежний точный факт сменой scope/key и получить
  глобальный fallback. Порядок ответа стабилен.
- Если одна выбранная запись непригодна, surviving-запись не скрывает проблему.
  Нет stale fallback. Синтетический источник не даёт реальный `hit`.

Тексты источников остаются недоверенными данными. Planner не исполняет содержащиеся
в них инструкции и не превращает их в tools/system messages. Это не полноценная
защита downstream-промпта; перед подключением LLM нужны отдельные guardrails.

## Следующие поставки и допуски

1. **CG-011B:** PostgreSQL-версии кандидатов/публикаций, редакционные команды,
   права, CAS, уникальность, audit, отзыв/повторное ревью и чтение текущего head.
   Новая миграция, не правка применённой `0001_initial.sql`.
2. **CG-023/CG-050A:** ограниченный research gateway, SSRF/redirect/content limits,
   источники/цитаты, минимальная проекция запроса, контроль личных данных.
3. **CG-050B:** очередь с lease/retry/dedup, защита от повторного исследования
   одного пробела, бюджет, квитанции и измерение стоимости проверки/переиспользования.
4. Подключение к admission и ответам помощников; источники/дата в разговорном
   интерфейсе нового Figma, без анкет и без требования заранее заполнить профиль.

Кто оплачивает общий research, какие категории можно проверять автоматически,
кто публикует спорные/правовые сведения и сроки повторного ревью — отдельные
решения. Не списывать фоновое общее исследование со случайного клиента без
принятого правила. Нельзя обойти consent/provider budgets новым research path.

Vector DB, embeddings и fine-tuning не нужны для этого инкремента. Здесь нет
полнотекстового или семантического поиска: редакционный ключ и scope задаются
явно. Переход к ним — после измерения качества и требований среды.

## Проверки

Контрактные и content-тесты используют только вымышленные данные и `.example`
URL. `primary` в положительном unit-тесте моделирует классификацию реального
источника, но не означает настоящего издателя или реальную редакционную проверку.
Отдельная отрицательная проверка запрещает `synthetic` source для `hit`.

Проверяются пустая база, границы схем, состояния/даты, город/направление,
неизменяемые ревизии, точные ссылки/цитаты, отзыв, expiry, конфликты, повторяемость
и отсутствие мутации входа. Даже зелёные тесты не доказывают работающий research,
PII detection, семантическую достоверность или готовность запуска пилота.

В этой отдельной ветке проверено закреплёнными Node 24.11.1 / pnpm 10.15.0:

- contracts: **89/89**, в том числе 6 новых knowledge-проверок; content: **16/16**;
- typecheck и ESLint обоих пакетов;
- ESM/DTS-сборки contracts и content;
- Prettier изменённых файлов, `git diff --check`, 38 относительных ссылок в трёх
  изменённых документах без отсутствующих целей.

Workspace-зависимость добавлена обычным pnpm; в lockfile только локальная связь
`content → contracts`, без новых npm-пакетов/версий. Установка выполнена из
существующего cache строго offline, с `--frozen-lockfile --ignore-scripts`.
GitHub CI, полный Web/Expo build, PostgreSQL, живой поиск и вызовы моделей этим
списком не подтверждаются.
