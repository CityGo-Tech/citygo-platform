# CG-012A — хранение частичных ответов и истории брифа

Дата: **4 октября 2026**. Первый ограниченный инкремент CG-012, подготовленный
на базе `main` [`4b4b33f`](https://github.com/CityGo-Tech/citygo-platform/commit/4b4b33fd2248566fc6512d683ec2c6ab540890aa).
Статус: **кандидат отдельной ветки для ревью; не слит в main и не развёрнут**.
Полная CG-012 и пилот R1 этим изменением не закрываются.

## Что это даёт

Пользователь сможет отвечать постепенно, пропускать вопросы и исправлять
решения, не теряя предыдущий контекст. В этом инкременте подготовлено только
хранение: пустой черновик, явные ответы человека и неизменяемые версии.
Экран, полезные карточки и публичные API-команды появятся отдельно.

Основа — [принятые правила CG-010](cg-010-housing-criteria.md). Ни бюджет,
ни дата переезда, ни тип жилья не обязательны для создания этого черновика.
Например, можно сохранить только верхнюю границу аренды или месяц переезда.
`unasked`, `undecided`, `declined` и `known` различаются; для необязательных
полей допускается `not_applicable`. Отказ отвечать не требует объяснения.

Важное ограничение: хранилищу нужен **уже существующий собственный текущий
план**. Оно не создаёт план, профиль или квест и не включает обход старой
анкеты. Создание первого плана без полной анкеты — ещё не реализовано.
Тест без профиля использует синтетический план и не доказывает готовность
такого пользовательского пути в приложении.

## Модель хранения

| Таблица                      | Назначение                                                                                  |
| ---------------------------- | ------------------------------------------------------------------------------------------- |
| `r1_housing_briefs`          | Постоянный ID черновика, владелец и точная пара plan ID/version                             |
| `r1_housing_commands`        | Команда, серверное событие, нормализованный запрос, старый/новый ответ, ссылка на результат |
| `r1_housing_brief_revisions` | Неизменяемый полный снимок черновика с номером ревизии                                      |

Журнал и снимок связаны в обе стороны по **точному событию, ID брифа и
ревизии**. Отложенный внешний ключ не позволяет зафиксировать команду без
её результата или сослаться на результат другой команды. Составные внешние
ключи защищают связь плана и владельца. Индексы поддерживают owner-scoped
чтения и связи. `UPDATE` трёх таблиц отклоняется триггером.

Это не криптографический аудит и не защита от администратора БД. JSON-поля
проверяет доверенное хранилище; SQL-права, ownership и внешние ключи не заменяют
проверку всех смысловых инвариантов JSON. Само наличие `user_stated` в
произвольном JSON не доказывает действие человека.

Миграция только добавляет таблицы, индексы и триггеры. Она не переносит
старые анкеты, не меняет планы, XP, денежные записи или согласия. Старые
миграции не переписываются. Схема не содержит блокировки любого `DELETE`:
правила экспорта/удаления и сроков хранения относятся к CG-018 и ещё требуют
реализации. Эта история не обещает вечного хранения персональных данных.

## Как выполняются команды

1. Строгая схема проверяет ID, UUID, диапазоны, тип поля и форму ответа.
   Клиент не может передать actor, provenance, новую ревизию или системное
   предположение вместо пользовательского ответа.
2. Короткая транзакция блокирует владельца. Для новой записи проверяются
   принадлежность брифа и плана, текущая версия плана и допустимое состояние.
   Порядок блокировок согласован с существующими командами: user → plan.
3. Изменение требует точных `brief.revision` и `expectedFieldRevision`.
   При конфликте возвращается 409 `REVISION_CONFLICT`; изменения не теряются
   из-за незаметного перезаписывания. Чужой ресурс возвращает общий 404.
4. Сервер создаёт event UUID, увеличивает ревизию изменённого поля и брифа,
   сохраняет команду и новый снимок в одной транзакции. Остальные поля
   остаются прежними. При ошибке откатываются обе записи.
5. Тот же `commandId` и нормализованный payload возвращают **исходную
   сохранённую ревизию**, даже после дальнейших правок или замены плана.
   Другой payload/action с тем же ID внутри пользователя даёт конфликт.
   UUID команды в этом узком API общий для create/stateAnswer; будущие
   confirmation/completion имеют отдельные контракты идемпотентности CG-010.

Новые записи разрешены только для текущего собственного плана со статусом
`active` или `completed`, как в текущем выборе плана CG-009. Исторические
owner-scoped чтения и точные повторы успешных команд не требуют активного
плана. Нет AI-вызовов или других сетевых операций внутри транзакции.
Достигнутый предел INT4 ревизии даёт конфликт, а не сброс нумерации.

## Границы включения и совместимость

- `citygo_api` и `citygo_worker` не получают доступ к новым таблицам.
  Существующий `grants.sql` сохраняет этот запрет; backup-роль получает чтение
  через своё существующее правило для всех таблиц. Права deployment не менялись.
- Нет backfill из профиля: `monthlyBudget` не становится бюджетом аренды.
- Черновик с предложениями или `starterPlan` отклоняет простую команду
  изменения: до реализации правил зависимостей нельзя молча потерять
  предложения или оставить устаревший результат актуальным.
- Создание отдельного черновика получает новый ID. Это не создание нового
  плана/квеста и не восстановление права на XP. Привязка результата к точному
  user quest и определениям ещё не реализована.
- Старые Web/Expo, анкета, чат, completion и XP не переключаются на эту схему.
  Отсутствие AI-согласия в тесте означает лишь отсутствие модельной операции;
  это не готовая политика обработки данных для пилота.
- После будущего merge обычный pipeline может применить **неактивную схему**.
  Выпуск всё равно требует принятого PR и штатных миграционных проверок;
  наличие этого документа не разрешает deploy.

## Проверки

Проверки используют только синтетические данные; модельные ключи и рабочая БД
не используются. Результаты относятся к локальному diff, не GitHub CI.

- 17 целевых сценариев на PGlite и отдельной PostgreSQL 17.11: частичные
  ответы, отказы, исправления, история и серверное событие, чужой владелец,
  текущий/старый план, точные повторы и коллизии ID, конкурентные изменения
  и создание, переполнение, откат транзакции, неизменность SQL и upgrade.
- Полный `pnpm check` — PASS: lint, typecheck, unit/integration, тесты
  контейнерных и релизных scripts, build и startup. В обычном memory-прогоне
  остаётся штатный skip старого PostgreSQL-only теста API CG-009; это не skip
  новых 17 сценариев CG-012A. Пакет БД — 55/55.
- `pnpm mobile:export` — PASS: собраны Android и iOS. APK/устройство и
  новый UI этим не проверены; пользовательские экраны не менялись.
- Prettier изменённых файлов, `git diff --check` и относительные ссылки — PASS.
- Полный локальный Docker smoke — PASS: миграции и replay, production-роли,
  сохранение данных, API/Worker drain, реальный guarded upgrade 9 → 12,
  отказ при drift/lock/SQL/ACL ошибках и транзакционный откат. Подтверждены
  отсутствие runtime-доступа к новым таблицам и чтение backup-ролью.
  Также прошли синтетические dump/age/restore, два закрытых выпуска,
  восстановление после прерывания commit, закрытый graceful restart,
  TLS/maintenance/SSE. Внешние AI-запросы и cloud не использовались.

Docker-проверка выполнена через отдельный Linux-runner на Docker Desktop,
со снимком текущего diff, без `.env`, ключей и пользовательских данных.
Только локальный override: Web на loopback-порту 48977, один jobs build для
идентичных worker/migrator; исходные deploy-файлы не изменялись. Все восемь
изменённых code/test/migration-файлов после прогона сверены по SHA-256.
Этот результат не является GitHub CI, проверкой целевого Cloud.ru-сервера,
проверкой устройства или разрешением на открытие пилота. Нового Web E2E
пока нет: новый пользовательский путь ещё не подключён.

Для повторения в чистом окружении сначала установите закреплённые зависимости
и соберите зависимости `@citygo/db`; затем:

```sh
pnpm --filter @citygo/db exec tsx --test src/housing-answers.test.ts
pnpm check
pnpm mobile:export
```

Для PostgreSQL первый тестовый entrypoint читает `TEST_DATABASE_URL`:
используйте только изолированный тестовый кластер, где разрешено создавать
и удалять временные базы. Каждый тест создаёт собственную базу `cg012_test_*`.
Никогда не передавайте URL production. Без переменной используется PGlite.
Docker smoke запускается отдельно по существующему runbook/CI в disposable
окружении, а не поверх работающего приложения.

3. CG-013 — постепенный Web-путь с паузой, исправлениями и понятными состояниями.
4. CG-014 — атомарное содержательное завершение, scope-награда, XP, unlock и
   outbox по принятой CG-010. До этой защиты нельзя включать пересоздание
   награждаемых планов/квестов. Затем совместная E2E-приёмка.

Для проектирования БД применены рекомендации Postgres Best Practices:
составные связи владельца, индексы внешних ключей, короткие транзакции и единый
порядок блокировок. Механизмы проверены по официальной документации
[ограничений PostgreSQL 17](https://www.postgresql.org/docs/17/ddl-constraints.html)
и [блокировок](https://www.postgresql.org/docs/17/explicit-locking.html).
