# Восстановление сверки ответа и событий воронки

## Инцидент — 28 октября 2026

На публичной схеме 36 один прерванный запрос «Максимума» оставил резерв
5 ₽ CityGo без окончательной сверки. Это не недостаток баланса: защита от
нескольких неподтверждённых расходов блокирует следующие платные запросы.
Отказ происходил уже после создания реплик и расходования квоты, поэтому
повторные попытки добавляли в историю неисполненные вопросы.

Read-only проверка связала резерв с точной генерацией RouterAI. В кабинете
и API видна нулевая текущая стоимость, но ответ API не содержит признака
окончательности, а upstream не указан. Это не доказательство окончательной
нулевой стоимости. Нельзя подменять `response_complete`, придумывать квитанцию
или автоматически освобождать такой резерв по одному тайм-ауту.

Отдельно внутренний журнал действий CityGo содержал события пользователя,
но их доставка в Метрику терялась. Внешний referrer блокировал SDK на весь
визит; события до получения identity и загрузки SDK не ожидали отправки.
Сброс сессии после регистрации также мог удалить ещё не переданные цели.

## Исправление допуска к следующему вопросу

При явной отправке нового сообщения API сначала проверяет текущие условия,
режим, владельца открытого диалога и повтор request ID. Для единственного
завершённого, но ещё не сверенного ответа выполняется один GET стоимости
с ограниченным временем ожидания. Используются сохранённые модель, upstream
и тариф исходной попытки. Модель повторно не вызывается.

Если стоимость не подтверждена, новый вопрос не сохраняется и квота не
расходуется. Проверка повторяется внутри обычной транзакции допуска под
блокировками пользователя и диалога; действующая аренда другого диалога
закрывает гонку до появления денежного резерва. Обращение к человеку сохраняет
свой прежний бесплатный путь. Фоновый опрос, повтор генерации и освобождение
прерванной попытки по предположению не добавляются.

Ошибки чтения стоимости получают структурированный диагностический код
`AI_CHARGE_COST_PENDING`. Тексты вопросов, ответы провайдера, ключи и
идентификаторы клиента в эти сообщения не включаются.

## Метрика

Исправления жизненного цикла и регистрации описаны в
[наблюдении за пользовательским путём](customer-observability.md).
Разрешён HTTP(S)-referrer, сокращённый до origin, без credentials, пути,
query и hash. События ожидают identity и исполнение SDK в ограниченной
очереди в памяти текущей сессии. Успешная регистрация переносит только
фактически наблюдавшиеся этапы того же flow к тому же обычному пользователю.

Администраторы, приватные URL, DNT/GPC и отказ от аналитики по-прежнему
исключаются. Переписка, контакты, OTP и план остаются скрыты от Метрики.
Прошедшие события не создаются задним числом. Browser-проверки используют
поддельный SDK и синтетические API; настоящие цели счётчика не вызываются.

## Проверка и выпуск

Для нового SHA нужны целевые проверки завершённой и прерванной попытки,
чужого владельца, повторного ID, отмены, гонки двух диалогов и отсутствия
новых записей при отказе. Полный Linux/Docker-прогон и browser-сценарии
с включённым тестовым счётчиком сохраняются отдельными доказательствами.

Схема остаётся 36. Резерв 5 ₽, RouterAI ×10, фиксированные 3 ₽ за успешный
«Минимум», существующая ЮKassa с чеками, телефон и подарок 500 ₽ не меняются.
PR не является разрешением на выпуск; автодеплой остаётся выключенным.
Адресное исправление старого зависшего резерва требует отдельной честной
операторской записи, не подменяющей доказательство стоимости провайдера.
