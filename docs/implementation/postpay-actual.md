# Оплата завершённых ответов без денежного резерва

Новый профиль включается только через `AI_CUSTOMER_BILLING_MODE=postpay_actual_v1`. Значение по умолчанию — `legacy`; миграция не меняет конфигурацию и не включает расходы. Для выпуска нужны отдельные проверенные execution/pricing identity, три режима, тариф CityGo ×10, схема46 и runtime v14. Старые профили v1–13 и существующие удержания продолжают работать по исходным условиям. Эта ветка содержит финансовые изменения44→45→46 без визуального стека PR174–178.

## Денежное поведение

При допуске RouterAI проверяется положительный доступный баланс не менее10 микрорублей CityGo; для Минимума — не менее3 ₽. Снимок делается под блокировкой пользователя/счёта. Реальный операторский допуск RouterAI равен целой части баланса CityGo/10. Сохраняются лимиты входного контекста/выходных токенов, административный стоп и операторские дневные/общие квоты. Это мягкий допуск, а не гарантия остановки внешнего провайдера на данной сумме; неподдерживаемый параметр `max_cost` не отправляется.

`postpay_open` с нулевой суммой — только неизменяемый идентификатор принятой попытки. Он не увеличивает `held_micros`, не резервирует источники средств и не показывается старому клиенту как денежное удержание. Название технического wire-поля `creditReservationMode=fixed5_overdraft` остаётся совместимым с APK0.2.3, но новый сервер не удерживает5 ₽. Публичный ответ дополнен необязательным `billingPolicy`; старые enum истории остаются прежними.

После успешного terminal-события, сохранённого ответа и положительной валидной стоимости RouterAI производится одно списание `floor(costRub × 10 × 1_000_000)` микрорублей CityGo. Десятичная цена рассчитывается точно, без умножения binary float. Даже если фактическая стоимость превысила снимок допуска, известный расход списывается автоматически один раз; допускается отрицательный баланс. Такой случай не выключает глобальный бюджет и не требует ручного подтверждения администратора.

Минимум стоит3 ₽ за успешный сохранённый ответ GigaChat. Ошибка/обрыв не создаёт списание. Ограниченная аренда аккаунта Ultra сохраняется, в том числе защитная пауза после неоднозначного dispatch. Бесплатная себестоимость GigaChat не подменяется вымышленным счётом RouterAI.

Расходы используют свободные подарочные средства, затем прежние невозвратные средства, затем оплаченные источники FIFO. Удержания старых попыток, зарезервированные возвраты и уже возвращённые деньги не расходуются. Непокрытая часть отражается отдельным долгом; последующие пополнения/разблокировки средств погашают единую FIFO очередь старых и новых долгов. Платёжные поручения, чеки, телефон и подарочные права не переписываются.

## Стоимость и завершённость — разные доказательства

Официальный [RouterAI OpenAPI](https://routerai.ru/api/openapi.json) для GET `/v1/generation` документирует `id`, `model`, `api`, `session_id`, `provider`, `total_cost` и usage, но не terminal/finality-флаг и не гарантию неизменности нулевой цены. Поэтому цена0 после успешного SSE пока остаётся наблюдением, а не окончательным бесплатным счётом. Положительная цена прерванного ответа тоже остаётся наблюдением для оператора: она не превращает обрыв в завершённый ответ и не списывается с пользователя.

Сохраняются generation ID, UUID попытки/reference, frozen mode, execution/policy/protocol/model/upstream, снимок тарифа и баланса, привязанный к запросу ID сохранённого ответа и наблюдение цены. Нельзя заменить ответ другим сообщением или повторно использовать доказательство старого запроса. Неизвестная стоимость не блокирует все последующие сообщения; одна реальная активная генерация на аккаунт по-прежнему защищена user→thread блокировками до записи квот и вопроса. Истёкший lease позволяет восстановление после аварии процесса.

## Автоматическая сверка и её границы

API запускает не блокирующий readiness планировщик: до10 identity-bound GET за пакет, не более одного пакета одновременно, deadline15с и GET timeout5с. База выдаёт атомарные leases с `SKIP LOCKED`. Для каждой попытки действует backoff до6ч, максимум64 фоновые проверки и возраст до7дней; успешные terminal-ответы обслуживаются раньше прерванных. После исчерпания окна запись остаётся честно pending и не мешает чату. Если generation ID не был получен, документированный GET по ID невозможен: автоматический повтор POST и вымышленное нулевое завершение запрещены. Изменившийся execution/profile также не используется как прежний профиль сверки.

Параллельные after-answer GET, пакетная сверка и повторное чтение одного счёта сходятся к одному settlement за счёт блокировок и unique resolution. Повторная иная подтверждённая цена отвергается. Обрыв/ошибка не требуют отправлять запрос модели повторно. Предельные конечные размеры денежного журнала остаются fail-closed: слишком большой расход не публикуется как некорректный баланс, а сохраняет pending-доказательство.

## Миграция и обслуживание

0046 добавляет3 таблицы без новых последовательностей, zero-valued admission kind и отдельный billing discriminator Miniмума. Она не переписывает старые charge/receipt/debt строки и включает новые долги в прежние conservation-проверки. Readiness проверяет receipt0045/0046 и физические новые поля/таблицы; запуск нового кода на44/45 отклоняется. Обновляются только явно проверенные API grant-права; worker не получает финансовые таблицы/изменение admitted identity. Закрытые reset-инструменты сохраняют новый журнал и отказывают в стирании его доказательств.

Legacy-режим сохраняет5 ₽ и прежние правила. Для него административный UI/API теперь отвергает операторский ceiling вне0,5–6 реальных ₽ до CAS/аудита/записи. Это устраняет ситуацию, когда настройки принимались, а пользовательский запрос затем отклонялся несогласованным лимитом. Новая политика postpay имеет отдельную authority и не наследует этот legacy product cap.

## Проверка

Покрытие включает три режима без held, точное позднее списание и перерасход, zero→positive, interrupted positive без списания, не блокирующую pending-стоимость, protected refund, replay/владельца/идентичность сообщения, отказ при billing review, PostgreSQL race двух соединений, ограниченную API роль и сохранение старой схемы API. Финальные результаты CI/Container smoke публикуются отдельно по точному коммиту; этот документ сам по себе не является разрешением на выпуск.
