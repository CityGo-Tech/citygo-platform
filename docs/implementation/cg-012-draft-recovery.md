# CG-012B: восстановление черновика и совместимость истории

Дата: 4 октября 2026. База: `main` после
[PR #79](https://github.com/CityGo-Tech/citygo-platform/pull/79), `0f09650`.
Предыдущий инкремент: [CG-012A](cg-012-answer-history.md).

Реализован внутренний слой чтения. Он позволяет найти собственные брифы по
точному плану, восстановить единственный черновик и читать историю страницами.
Исторический JSON проверяется закреплённой схемой его версии. Это закрывает
ограничения M2/M3 на уровне репозитория, но **не включает новый API или экран**.
Runtime-роли по-прежнему не имеют доступа к таблицам R1; миграции, grants,
CI/deploy и текущие completion/XP в этом инкременте не меняются.

## Что это даёт человеку в будущем интерфейсе

После паузы не потребуется заново сообщать бюджет и остальные условия.
Восстанавливается сохранённое состояние, включая «не спрашивали», «не решил»,
«пропустил», частичные ограничения и исправления. Неизвестные бюджет, срок и
тип жилья не запрещают чтение черновика. Новых предположений о человеке нет.

Если в плане уже несколько брифов, система не выбирает последний за человека
и не объединяет ответы автоматически. Она требует явного выбора существующего
ID. Порядок списка — только навигация, не признак предпочтительного брифа.
Это важно: CG-012A разрешает несколько брифов с разными `commandId`.
Ограничение «один бриф на план» здесь не вводится задним числом.

## Методы внутреннего репозитория

Вызовы принадлежат `HousingAnswers` из `@citygo/db`. `owner` должен поступать
из проверенной сервером сессии; эти методы не предназначены для вызова LLM,
оператором от лица пользователя или прямого использования браузером.

| Метод                                | Назначение и результат                                                                                      |
| ------------------------------------ | ----------------------------------------------------------------------------------------------------------- |
| `listForPlan(owner, plan, options?)` | Для точных `plan.id/version` возвращает страницу `{id, revision, plan}` без текста ответов и `nextBeforeId` |
| `recoverForPlan(owner, plan)`        | Ни одного брифа → `not_found`; один → `recovered` с последним снимком; несколько → `selection_required`     |
| `get(owner, id, revision?)`          | Последний либо точно указанный исторический снимок выбранного собственного брифа                            |
| `history(owner, id, options?)`       | Исторические снимки по убыванию ревизии и `nextBeforeRevision`                                              |

Восстановление не создаёт бриф, план, вопрос, событие или награду. При
`selection_required` потребитель запрашивает список, предлагает выбор и
вызывает `get` с выбранным ID. При `not_found` создание — отдельная явная
команда по прежним правилам CG-012A, не побочный эффект чтения.

Чтение собственного архивного плана разрешено. Это не разрешение писать в него:
новые команды по-прежнему требуют текущего плана. Нет автоматического переноса
ответов, подтверждений или XP в новый план. Создание нового награждаемого плана
остаётся закрытым до защиты CG-014.

### Доступ, страницы и конкурентные операции

- Владение проверяется SQL-условиями до разбора JSON. Чужой или отсутствующий
  ресурс даёт одинаковый общий 404; версия и повреждённое содержимое чужого
  брифа не раскрываются. Неверная версия собственного плана также даёт 404.
- Вход строгий: ID — каноническая положительная int8-строка; version/revision —
  положительный int4. Coercion, неизвестные ключи и некорректные курсоры дают 400.
- `limit`: по умолчанию 20, минимум 1, максимум 50. Продолжение исключительное:
  `id < beforeId` или `revision < beforeRevision`; сортировка числовая, не строковая.
  Следующий курсор — последний возвращённый элемент, либо `null` в конце.
- Это живая keyset-навигация, **не** замороженный снимок всей истории.
  Новые записи выше курсора видны после обновления первой страницы, не сдвигают
  продолжение и не дублируют старые элементы. Курсор — граница, не разрешение
  читать ресурс с этим ID. Все запросы сохраняют ограничения владельца/плана.
- `recoverForPlan` берёт ту же короткую блокировку пользователя, что create/
  stateAnswer: поиск и чтение единственного кандидата не разрываются новой
  командой создания/редактирования. Возвращённая ревизия не гарантируется
  последней навсегда; последующее изменение требует прежних CAS-проверок.
- Используются существующие индексы владельца/плана и PK `(brief_id, revision)`.
  Новая миграция не требуется. Лимит страницы не заменяет будущую квоту хранения;
  нагрузочная приёмка большой истории здесь не выполнена.

## Версионированное чтение

Исходный контракт CG-010 перенесён без изменения правил в
[`housing-v1.ts`](../../packages/contracts/src/housing-v1.ts), включая вложенные
валидаторы и нормализацию. Публичный `housing.ts` пока переэкспортирует v1;
явные `r1HousingBriefDraftV1Schema`, обе схемы команд v1, ID/revision и
`createR1HousingAnswersV1` закреплены за этим модулем.
Читатель [`housing-history.ts`](../../packages/db/src/housing-history.ts)
выбирает схему по сохранённому `schemaVersion`, а не по текущим правилам ввода.
Его используют `get`, `history`, восстановление и идемпотентный replay.

Поддержана **только версия 1**. Новую версию нужно реализовать отдельно,
добавить явную ветку reader и новые fixtures. Ужесточение нового ввода не должно
менять v1. Исторический снимок не переписывается, не преобразуется в новый DTO
и не нормализуется молча при чтении. Писатель CG-012A уже сохраняет нормализованный
JSON; reader дополнительно требует точное совпадение результата разбора с ним
(порядок ключей объекта не важен). Это не реализация hashes/receipts CG-010.

Неподдерживаемая версия либо повреждённый/неканонический JSON приводят к
`HousingStoredDataError` с причиной `unsupported_version` либо `invalid_content`.
Это **серверная ошибка данных**, не Zod/400 и не отказ пользователя отвечать.
Сообщение не содержит сохранённый текст, payload, Zod issues или cause.
Будущий HTTP-слой должен сохранить общий 500; существующий общий error handler
уже отличает такую обычную Error от Zod/DomainError, но нового маршрута здесь нет.

Нет fallback к предыдущей «хорошей» ревизии: повреждённый последний снимок нельзя
выдать за актуальный. Более раннюю поддержанную ревизию всё ещё можно запросить
по точному номеру. Если повреждён элемент возвращаемой страницы истории,
вся страница отклоняется; элементы не пропускаются незаметно. Lookahead нужен
только для следующего курсора, не является возвращаемым/подтверждённым снимком.
Метаданные списка доступны без декодирования текста: это способ найти ID,
не обещание исправности или пригодности результата.

Структурное чтение не доказывает подлинность provenance, полезность starterPlan,
готовность подробного поиска или право на completion/XP. Проверки событий,
владельца источников, критериев и receipt остаются отдельными задачами CG-012/014.

### Запись и replay v1 после независимого ревью

Замечания N1/N2 закрыты на уровне этого репозитория: `create`/`stateAnswer`
разбирают команды схемами **v1**, создают ответы helper v1 и записывают содержимое
валидатором v1. Их поведение не зависит от будущих unversioned-экспортов фасада.
Replay по-прежнему сверяет нормализованную команду целиком и возвращает исходный
снимок; переиспользование `commandId` с другим действием/телом остаётся 409.

Писатель поддерживает только v1. Даже если в будущем reader получит поддержку
v2, этот писатель должен отказать в её редактировании как `unsupported_version`,
а не преобразовать версию молча. Внутренняя ошибка построения содержимого —
`HousingStoredDataError`, не клиентская Zod/400. Новые версии требуют отдельного
модуля и явного протокола команд/писателя; менять правила `housing-v1.ts` нельзя.

Регрессионный тест запускает отдельный процесс, **подменяет реальные публичные
экспорты** до загрузки reader/репозитория, ужесточает обе схемы команд, меняет
текущий draft на v2 и запрещает старому писателю использовать текущий helper.
После этого проверяются create, частичные ответы/исправление, get/history/
recover и replay исходного результата после правок и архивации плана.
Это заменяет прежний недостаточный тест с отдельным `schema.refine` (N8).
Флаг Node `--experimental-test-module-mocks` действует только в дочернем тестовом
процессе; runtime и CI-конфигурация не меняются.

Отдельно закреплён SHA-256 **исходного модуля валидаторов v1** с LF-окончаниями,
не только положительных fixtures. Ослабление правил также меняет digest;
запрещено обновлять его ради введения v2. Даже изменение комментариев/формата
требует осознанного ревью pin. Digest не фиксирует код Zod, Node или ICU и не
доказывает подлинность снимков/receipt.

### Ограничения среды выполнения и допуска runtime

N3 не объявлен воспроизведённым или закрытым. Для уже назначенных символов
Unicode гарантирует стабильность нормализации; исключение относится к символам,
не назначенным в используемой версии Unicode. См.
[UAX #15: Versioning and Stability](https://www.unicode.org/reports/tr15/#Versioning_and_Stability).
Сохраняем строгий reader без молчаливой нормализации, перезаписи и fallback.
При обновлении Node/ICU/Zod необходима отдельная проверка совместимости истории;
до открытия API нужно принять устойчивую политику для ранее неназначенных
символов. Ни pin исходного TS, ни три fixtures не решают этот риск сами по себе.
Локальная среда доработки: Node 24.11.1, ICU 77.1, Unicode 16.0. Production Docker
использует `node:24-bookworm-slim`: точная версия ICU этим PR не закрепляется.

Остальные замечания остаются условиями CG-012C, не готовыми возможностями:
диагностика повреждённых строк без текста (N5), метаданные для осмысленного выбора
(N6), квоты и проверка индекса на нагрузке (N7), HTTP-контракт/права.
`FOR UPDATE` требует UPDATE на `users`; у существующей `citygo_api` это право уже
есть, но доступа к R1-таблицам нет. Grants этим PR не меняются. N4 проверяется
реальными конкурентными соединениями PostgreSQL, а не PGlite.

## Проверки

Литералы [fixtures v1](../../packages/db/src/fixtures/housing-v1.json) не создаются
текущими helper/schema. Закреплён SHA-256 JSON после разбора и повторной
сериализации: форматирование можно менять, значения и порядок ключей fixture
нельзя заменять ради прохождения новой схемы. Это не canonical hash для receipt.
Это синтетические примеры, не выгрузка production. Расширенный fixture с
предложениями/import служит проверке старой **формы**, не свидетельством уже
реализованных команд принятия предложений или импорта профиля.

Сценарии покрывают пустое/единственное/неоднозначное восстановление, точный план,
архивный план, пагинацию через границу ID `9 → 10`, новые записи между страницами,
отказы/исправления, 404 для чужого владельца, строгие лимиты, повреждённые версии
и replay исходного результата после правок. Добавлены точная граница `limit`,
курсор с ID чужого брифа и настоящий повреждённый lookahead: корректная первая
страница возвращается, но следующая страница с повреждением отклоняется без
незаметного пропуска записи. Проверяется реальная замена публичного фасада.

PostgreSQL-only тест проверяет четыре порядка: create → recover, recover →
create, stateAnswer → recover, recover → stateAnswer. Первый участник удерживает
настоящую блокировку пользователя; `pg_stat_activity`/`pg_blocking_pids`
подтверждают ожидание второго на том же SQL `users FOR UPDATE`, затем проверяются
результат на границе команды, количество событий/снимков и отсутствие XP.
На PGlite этот тест явно **SKIP**, не доказательство сериализации.

Для повторения после установки закреплённых зависимостей:

```sh
pnpm exec turbo run build lint typecheck test --filter=@citygo/db --filter=@citygo/contracts
pnpm check
```

PostgreSQL-проверку запускайте только с `TEST_DATABASE_URL` отдельного тестового
кластера, где разрешены временные базы/роли; без переменной используется PGlite.
Через `turbo run test --filter=@citygo/db` переменная передаётся по существующему
allowlist. Ни production URL, ни `.env`/модельные ключи тестам не нужны.
