# Метка версии лендинга до аккаунта

Реализация от 7 ноября 2026 года. Новая миграция —
`0050_landing_attribution.sql`; миграции 1–49 не изменены.

`LandingAttribution` — необязательная публичная метка с `landingVersion`
(`v1` или `v8`) и необязательными `source`, `medium`, `campaignId`, `content`.
Значения этих четырёх полей — ASCII slug длиной 1–80: строчные латинские
буквы, цифры, точка, дефис и подчёркивание; первый символ — буква или цифра.
Другие ключи, URL, referrer и raw query не принимаются. Это недоверенные
клиентские сведения, которые не дают прав и не подтверждают конверсию.

Клиент передаёт последний необязательный аргумент:

```ts
client.beginEmailRegistration(email, password, consents, landingAttribution);
client.auth("register", email, password, consents, landingAttribution);
```

Старые вызовы продолжают работать. Если браузерный выбор приватности
отключает аналитику, Web не передаёт метку. Сервер не делает вывод о таком
выборе из согласия на email-рассылку и не отправляет метку внешнему счётчику.

При OTP-регистрации метка фиксируется в `email_registrations` до отправки
кода. Повторная отправка не меняет snapshot. Только успешное подтверждение
создаёт `user_acquisition` в одной транзакции с пользователем, согласиями и
сессией. Регистрация без OTP использует такую же привязку при создании.
Если метки нет, для нового аккаунта фиксируется SQL NULL. Вход, подтверждение
кода и resend не принимают новую метку; существующая запись не обновляется.
У старых аккаунтов миграция не создаёт выдуманную атрибуцию, у старых pending
метка остаётся NULL.

Таблица содержит только `user_id`, `landing_attribution`, `created_at`.
Первичный ключ запрещает повторную запись; SQL-триггеры запрещают изменение
метки pending и атрибуции аккаунта. Вставка допускается в транзакции создания
пользователя. API имеет SELECT/INSERT, Worker доступа не имеет. Операторские
процедуры очистки учитывают новую таблицу; финансовая история не меняется.

Readiness требует миграцию 50, физические поля pending/account attribution и
два включённых защитных триггера. Запись о миграции без рабочей структуры не
делает API готовым к регистрации.

Проверки покрывают границы контракта, совместимый транспорт, оба HTTP-пути,
OTP/resend/replay, конкурирующие pending, SQL-ограничения и откат транзакции,
переход 49→50 со старым pending. Базовые тесты используют вымышленные данные и
PGlite. Отдельный `apps/api/src/landing-attribution.pg.test.ts` при явном
`TEST_DATABASE_URL` создаёт собственные случайно названные тестовые БД и роли,
проверяет ожидание блокировки между двумя PostgreSQL backends, реальные ACL,
атомарный откат обоих способов регистрации и readiness. Проверено на
одноразовом PostgreSQL 17.11; фикстуры удаляют свои БД и роли. Внешние отправки,
обращения к модели и production не используются.
