# CG-010 Критерии жилищных результатов R1

Дата: 4 октября 2026. База: main 2c22d4e после PR #74 (CG-009).
Ветка: codex/cg-010-housing-criteria, рабочая копия citygo-codex-cg009.

**Продуктовый критерий принят владельцем. Повторное ревью Cursor не выявило
блокирующих дефектов в коде контрактов; уточнения спецификации N1/N2 внесены
после ревью, R1 не включён.** Принятие критерия не разрешает merge/deploy.
Изменяются контрактный модуль, его тесты и спецификация. API, БД, Web/Expo,
провайдеры, текущий completion, XP и сервер не изменены.

## Принятое решение: польза до полной анкеты

Первый результат — полезный сохранённый стартовый план поиска жилья, который
учитывает хотя бы одну явно названную пользователем ситуацию, цель или ограничение.
Неизвестное остаётся неизвестным. Пользователь выбирает следующий шаг из
предложенных и явно подтверждает именно показанную ревизию результата.
Это основание для первых 60 XP после будущих серверных проверок, не награда
за заполнение полей.

Бюджет, срок, состав домохозяйства и тип жилья **не обязаны быть известны**.
Не нужно сначала рассмотреть каждый вопрос или нажать «не знаю» у всех полей.
Пустой черновик, одни системные предположения или открытие карточки не дают
основания для награды. Заполненная строка сама по себе не доказывает полезность:
содержательный результат проверяется отдельно от структуры.

Вторые 60 XP — за подготовленный и подтверждённый чеклист просмотра, не за
фактически состоявшийся просмотр. Частичных XP и новых наград нет.

После повторного ревью владелец дополнительно подтвердил:

- Каждая из двух наград выдаётся один раз на пользователя в рамках пилота R1,
  независимо от пересоздания плана, user quest или изменения версии определения.
- Чеклист можно подтвердить заранее. Завершение второго квеста — отдельное явное
  действие после первого, с повторной проверкой актуальности, без auto-award.

| Возможность                  | Что нужно                                                              | Чего не нужно                                  |
| ---------------------------- | ---------------------------------------------------------------------- | ---------------------------------------------- |
| Первая помощь                | Контекст обращения и применимые правила доступа                        | Полная анкета, готовый бриф, завершённый квест |
| Сохранить черновик           | Владение ресурсом и допустимая структура                               | Известные бюджет и срок, все ответы            |
| Получить стартовый результат | Пользовательская ситуация/цель и полезное содержание                   | Подробный поисковый бриф                       |
| Подготовить чеклист          | Общие вопросы, при наличии — подтверждённые факты                      | Первый award, найденная квартира               |
| Получить XP                  | Точная ревизия, действие пользователя, серверные критерии и транзакция | Право модели объявить успех                    |

Первая помощь может быть чатом **или сохранённой карточкой**, в том числе без AI.
AI-согласие требуется для соответствующего AI-вызова, не для всей помощи.
Нельзя маскировать полную анкету последовательностью обязательных вопросов.
Один релевантный вопрос → полезный результат → следующий добровольный шаг.
«Ещё не решил» ведёт к объяснению/сравнению, а не к повтору того же вопроса.

Полный путь CityGo шире: решение о переезде, деньги, работа, жильё, билеты/вещи,
приезд, городские сервисы и окружение. Этот кандидат охватывает только основу
жилищного R1 для Москвы, не добавляет остальных специалистов/интеграций.
Цены, маршруты, зарплаты и меры поддержки нельзя выдумывать: нужны подходящие
источники, дата и область применимости в последующих задачах.

## Состояния и частичные ответы

r1HousingAnswersSchema — **серверный снимок**, не обязательная форма ввода.
createR1HousingAnswers() создаёт поля как unasked с revision 1, без придуманных
причин. Будущий API CG-012 принимает изменения отдельных полей с ожидаемой
версией; заполнять все поля пользователь не обязан.

| Статус         | Значение                                                                                            |
| -------------- | --------------------------------------------------------------------------------------------------- |
| unasked        | Ответ ещё не зафиксирован; факт показа вопроса проверяется отдельно, утверждений о пользователе нет |
| undecided      | Не знает/не решил; его заметка необязательна                                                        |
| declined       | Пропустил/отказался; объяснение не требуется                                                        |
| known          | Сообщил или явно принял конкретное значение/ограничение                                             |
| not_applicable | Явно указал отсутствие применимого требования; только для необязательных предпочтений/дороги        |

Ошибка разбора моделью — **не** undecided/declined пользователя. Подтверждённый
снимок при ней не меняется; UI предлагает проверить распознанное.
Система не перезаписывает ответы без отдельного действия пользователя.

Known означает известную часть данных, не исчерпывающую готовность:

- «До 60 000» → {max: 60000}, без выдуманного min = 0.
- «От 40 000» → {min: 40000}, без выдуманного потолка.
- Месяц → {kind: "month", month: "2026-11"}; также on/before/after/range.
  Неоднозначное «после десятого» требует уточнения месяца, не догадки.
- Место работы и допустимое время дороги — независимые поля.
- Списки имеют completeness: open | complete, включая пустой открытый список.

Отдельного статуса partial нет: частичность хранится в типизированном значении.
Нельзя трактовать любой known как «всё выяснено». Для подробного поиска/подбора
потребуются отдельные версионированные серверные критерии; search_ready
в этом кандидате не реализован.

Поля: stage, priority, monthlyRentRub, upfrontBudgetRub, moveTiming, household,
housingType, preferredAreas, commuteDestination, commuteMaxMinutes, mustHave,
niceToHave. Stage/priority удобны для начала, но не обязательны:
«переезжаем семьёй» тоже может быть основой первого результата.

r1HousingQuestionCandidates(answers, alreadyAsked) исключает поля с ответами
и уже доставленные вопросы, даже если ответа не последовало. AlreadyAsked берётся
из серверного журнала вопросов, не из флага клиента. CG-013 хранит идентификатор
поля, время/число доставок и состояние текущего вопроса; резервирование перед
отправкой и подтверждение доставки должны предотвращать дубли при конкурентных
ходах. При смене темы статус слота может оставаться unasked, но автоматически
повторять вопрос нельзя. Повтор/повторная доставка после сбоя — отдельная политика
CG-013 с идемпотентным ID вопроса, не очистка истории на каждом ходе.
Потребитель выбирает максимум следующий релевантный вопрос. Declined/undecided
возвращаются через явное «помоги разобраться»/«изменить ответ», не автоматическим
циклом. Свободные openQuestions/nextQuestion больше не дублируют состояния.

### Происхождение и предположения

Предложения системы отдельны: pending / accepted / rejected, ID UUID, ревизия,
типизированные field/value и объяснение. Предложение не заполняет ответ.
Принять конкретное предложение — отдельное действие с CAS. «Результат просмотрен»
не означает принятия всех pending-предложений.

У всех статусов, кроме unasked, обязательно серверное происхождение с eventId
(канонический UUID события явного пользовательского действия):

- user_stated — значение сообщил пользователь;
- accepted_suggestion — ID/ревизия явно принятого предложения;
- profile_import — ID/ревизия профиля и явное подтверждение пользователя.

Accepted_suggestion применим только к known: предложения содержат конкретные
значения, а не решения «отказался»/«не применимо». Для undecided, declined и
not_applicable допустимы user_stated или явно подтверждённый profile_import.
В unasked происхождение не допускается. UUID источников нормализуются в lowercase.

Это **доверенный серверный DTO**, не payload прямой записи клиента или LLM.
CG-012 сверяет существование события, пользователя, тип действия, точные
field/status/value и ревизию источника. UUID события и user_stated сами по себе
не доказывают происхождение. Нельзя присвоить отказ по таймауту/смене темы.
Принятые предложения сохраняются в истории; правка ответа не переписывает
факт принятия. Повторное применение требует нового действия.
Старый общий monthlyBudget нельзя автоматически превращать в арендный бюджет.

Draft и Prepared проверяют внутреннюю связность: каждый текущий accepted_suggestion
ссылается на присутствующее accepted-предложение с теми же ID, revision, field и
нормализованным value. Порядок ключей объекта не важен, порядок массива важен.
Это не заменяет проверку пользовательского события.

Suggestions внутри текущего снимка — **проекция, не накопительная история**:
до 20 pending и до 12 accepted, на которые ссылаются текущие ответы.
Rejected и accepted, заменённые поздней правкой, остаются в отдельном неизменяемом
журнале CG-012 и старых ревизиях, но не переносятся в новый снимок.
Историческое принятие не требует, чтобы текущий ответ по-прежнему совпадал с ним.
Сервер атомарно пишет события и строит новую проекцию; клиент не удаляет историю.
CG-012/013 используют журнал отклонений: повторное предложение того же
нормализованного (field, value) не создаётся без изменившегося релевантного
контекста или явного запроса пользователя вернуться к варианту. Причина повтора
фиксируется; удаление rejected из проекции не означает забывание отказа.
При 20 pending новое предложение не добавляется в активную очередь до освобождения
места; это не препятствует сохранению/исправлению ответов. Число прошлых отказов
не ограничено размером текущей проекции. Persist/retention здесь ещё не реализованы.

### Технические ограничения

Деньги — целые рубли 0…1 000 000; верхняя граница аренды, если задана, > 0;
хотя бы одна граница, min ≤ max. Это ограничения пользователя, не цены рынка.
Дорога — целые 1…240 минут, не вычисленный маршрут. Даты 1900…2199, календарные
и упорядоченные; прошлые снимки читаются. Для уже приехавшего человека прошедшая
дата сама по себе не блокирует помощь/award. Актуальность будущей операции
проверяется её правилами, не глобальным запретом.

Текст NFC + trim, до 500 Unicode code points (проверено на закреплённом Zod 4.5.4).
До нормализации/trim отклоняются управляющие символы категории Cc, включая NUL,
табуляции и переводы строк, и непарные суррогаты Cs; корректные emoji разрешены.
Это короткие текстовые поля, не многострочные документы. Проверка Cc/Cs не
гарантирует однострочность или отсутствие bidi/format-символов: Zl/Zp и некоторые
Cf внутри видимого текста проходят текущую схему (N4). Невидимое содержимое
само по себе недопустимо. До 20 уникальных после нормализации элементов
предпочтений. Сравнение точное, чувствительное к регистру; семантические дубликаты,
ПДн, injection и ложные заявления этим не проверяются.

## Черновик, подготовленный результат и подтверждение

Экспорты намеренно разделены:

- r1HousingBriefDraftSchema: starterPlan может быть null.
- r1HousingBriefPreparedSchema: брендированный тип с непустым starterPlan;
  summary, хотя бы одна актуальная информативная known-основа, зависимости по полям и 1…5
  разных следующих действий. Среди зависимостей может быть неопределённость;
  все указанные ревизии должны совпадать.
- r1ViewingChecklistDraftSchema: 0…7 разделов, можно без вопросов.
- r1ViewingChecklistPreparedSchema: брендированный тип, все семь разных
  разделов, 1…8 непустых уникальных вопросов в каждом.
- r1HousingArtifactDraftContentSchema и r1HousingArtifactPreparedContentSchema:
  отдельные union и назначения.

Prepared — **только структурный кандидат**, не сохранение, semantic PASS,
подтверждение или award. Бессмысленная summary/ложная provenance может пройти
структуру, но не серверную приёмку. Экспорты публичны внутри workspace,
но не разрешают подключить их к completion до CG-012/014 и release-проверок.

Структурно информативная основа: непустой список; для аренды заданный потолок
либо положительная нижняя граница; для остальных known — валидное значение.
Пустой список и {min: 0} допускаются как данные Draft, но не как единственная
основа Prepared. Явно названные {min: 0, max: 1000000} и нулевой бюджет первых
расходов не объявляются фиктивными: первое содержит потолок, второе — существенное
ограничение человека. Подлинность события и полезность результата проверяет сервер.
Например, {min: 1} и housingType = flexible структурно допустимы, но сами по себе
не доказывают полезность стартового результата; это проверка CG-014, не Zod.
Brand — ограничение TypeScript, не security boundary; приведение типа не даёт
права на подтверждение. Эта оговорка также стоит рядом с экспортом пакета.

Семь разделов чеклиста: budget_and_payments, authority_and_documents,
condition_and_utilities, terms_and_handover, area_and_commute,
personal_requirements, next_steps. Это темы подготовки, не одобренные экспертом
тексты, проверка договора или доказательство безопасности сделки.
Viewed/passed/legallyVerified не предусмотрены; свободный текст тоже требует
проверки. Название UI: «Подготовка к просмотру».

Общий чеклист может не иметь housingBrief и персональных зависимостей.
Персонализированный обязан ссылаться на бриф и его исходную ревизию,
**не обязательно подтверждённую для XP**. Первый квест — только
awardPrerequisite второго, не барьер получения/подтверждения чеклиста.

### Раннее подтверждение и явное завершение

Состояние user quest locked означает запрет completion, а не работы с артефактом.
CG-012 разрешает создание/подтверждение чеклиста при locked, если выполнены
owner/graph/Prepared/semantic проверки. Receipt сохраняется, XP не выдаются.
Состояние пригодности receipt вычисляется сервером, не записывается клиентом:

| Событие                                                                                                 | Состояние пригодности / действие                                                        |
| ------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------- |
| Чеклист подтверждён до завершения первого квеста текущего плана                                         | confirmed_waiting_prerequisite; receipt сохранён, 0 XP                                  |
| Первый квест завершён, прежний receipt и зависимости актуальны                                          | confirmed_ready; доступна кнопка завершения, начисления нет                             |
| Изменились используемые ответы, версия самого чеклиста или план                                         | stale; показать изменения, обновить результат и подтвердить заново                      |
| В исходном брифе добавлено/отклонено pending-предложение, используемые ответы и сам чеклист не менялись | Пригодность receipt чеклиста не меняется; предложения не входят в его digest            |
| Явная команда завершить второй квест                                                                    | Повторная проверка плана, графа, receipt, зависимостей и prerequisite; затем транзакция |

Prerequisite — завершённый первый квест **текущего плана**, не обязательное новое
начисление +60: при уже использованной награде completion первого может вернуть
0 XP и всё равно открыть второй. При замене плана старые receipts не переносятся
автоматически. Никакого worker, фонового auto-award или начисления при unlock.
Если пользователь исправил используемый ответ исходного брифа после раннего
подтверждения, прежний receipt остаётся историей, но не основанием для нового
completion. Изменения неиспользуемых полей и непринятых предложений исходного
брифа не сбрасывают подтверждение неизменившегося чеклиста.

## Исправления и зависимости

CG-012 хранит неизменяемые ревизии артефакта и журнал изменения ответа:
actor (пользователь/система/оператор), серверное время, источник команды,
старое/новое значение либо ссылки; причина пользователя необязательна.
Модель предлагает правку, но не присваивает ей авторство пользователя.

Revision поля монотонна внутри постоянного ID брифа: новый снимок артефакта
не сбрасывает её к 1. Любое изменение значения, статуса или происхождения
увеличивает revision; переполнение int4 — явный конфликт, не wrap/reset.
createR1HousingAnswers() применяется лишь при создании нового ID брифа.
Пересозданный бриф имеет другой ID и требует перепривязки зависимостей, даже
если номера ревизий совпадают. ID нельзя повторно использовать.
Known → undecided/declined разрешён. Затрагиваются только используемые зависимости:
niceToHave не устаревает раздел, построенный только на monthlyRentRub.
r1ViewingSectionsNeedingUpdate() принимает currentBrief с ID, revision и answers.
Чужой ID, отсутствующий источник или ревизия старее исходной приводят к ошибке,
а не к пустому списку устаревших разделов. Для общего чеклиста без источника
возвращается пустой список. Сравнение одинакового ID не является owner check.
Изменение значения без повышения revision запрещается серверной командой/CAS;
CG-012 обязан покрыть этот случай интеграционным тестом. Сам helper не имеет
прошлого значения и не может доказать корректность истории.
Зависимости рассчитывает и проверяет сервер; неполному списку LLM доверять нельзя.

HousingBrief.revision — неизменяемый исходный снимок чеклиста. Более новая ревизия
брифа допустима без пересборки чеклиста **только** при неизменности использованных
полей, том же брифе и проверенных graph/owner. Для стартового плана действует
такое же правило basedOn. Удаление/замена исходного артефакта делает зависимый
результат непригодным для нового подтверждения.

Подтверждается только последняя ревизия самого подтверждаемого артефакта.
При гонке: «Результат обновился — посмотреть изменения», не auto-confirm latest.
Выданные XP и исторические receipts сохраняются; правка не даёт новой награды.

| housing-viewing | Подготовленный чеклист      | 1 / 1 / 1 / 1                         | 60  | housing-brief      |

Это неизменяемые **кандидатные** определения, не DB seeds; версия 1 не выпускалась.
Литералы intent выводятся из определений. Следующий после первого —
housing-viewing; после второго следующего нет.

Оба определения содержат awardScope = r1-pilot и completionMode = explicit_command.
Ключ однократной награды: (user_id, award_scope, quest_slug), независимо от
plan_id/user_quest_id и версий definition/criteria/reward. Нельзя автоматически
менять scope при регенерации плана или смене провайдера. Это **требование CG-014**,
а не уже установленное ограничение в БД.

Новые ссылки — канонические положительные int8-строки до 9223372036854775807.
012, 0x1f, latest и переполнение отклоняются без coercion.
Version/revision — положительный int4 до 2147483647.
Старые общие protocol/platform schemas этим PR не меняются.

CG-012/014 хранят **у user quest при создании** snapshot: slug, definitionVersion,
criteriaVersion, rewardVersion, confirmationCopyVersion, xpReward, awardScope,
completionMode. Для профиля profile_import нужна явная привязка нового int8 ID
к сохранённому профилю; непрозрачные ID раннего r1.ts нельзя произвольно привести.
Snapshot после создания неизменяем на уровне хранения, не только TypeScript.
При award версии и xpReward читаются только из него, не из текущего каталога
quests/последних определений. Миграция 0011 защищает идентичность user quest,
но не реализует это требование к новым snapshot-полям; защиту и тест отказа
от UPDATE добавляют CG-012/014 до активации нового пути.
Definition.ref в r1.ts — ID записи и её storage revision, не alias definitionVersion:
нужна явная связь с неизменяемой записью и версиями. Plan.ref.revision из раннего
r1.ts нельзя просто переименовать: нужна проверенная связь с persisted
plan.id/version CG-009. Этот кандидат ранние metadata DTO не мигрирует.

Intent включает UUID команды, plan.id/version, questId, artifact.id/revision,
questSlug, четыре версии, contentSha256, unresolvedFieldsSha256 и два явных true:
reviewedResult/preparationOnly. Для первого квеста нужен selectedNextStepKey:
пользователь выбирает из nextSteps **этой** ревизии, не модель/сервер автоматически.
Для второго квеста такое поле не принимается.

Hashes возвращает сервер со снимком. Они связывают намерение с контентом,
но **не доказывают чтение**. Receipt фиксирует серверные owner/time, версии,
hashes, acknowledgements и выбранный шаг. CopyVersion связывает неизменяемую
редакцию текста действия/пояснения; это не AI-согласие.

### Явные команды: точная цель и границы транзакций

Ниже — требования к будущим командам CG-012/014, не новые экспорты, endpoints
или уже реализованные DTO. Одинаковый completionMode = explicit_command
не означает одинаковое число пользовательских действий:

1. **Первый квест — confirm_and_complete_housing_brief.** Пользователь выбирает
   следующий шаг и одним явным действием подтверждает показанную ревизию и
   завершает квест. Команда использует intent первого квеста с точными plan,
   questId, artifact, hashes и версиями; существующего receipt ещё нет и ссылка
   на него не требуется. Сервер в одной транзакции проверяет intent, создаёт
   неизменяемый receipt, фиксирует completion, award (60 либо 0 по scope),
   unlock и outbox. Ответ содержит созданный receipt и результат команды.
2. **Второй квест — confirm_viewing_checklist.** Intent второго квеста сохраняет
   receipt точной ревизии, включая раннее подтверждение до prerequisite.
   Эта команда всегда выдаёт 0 XP и не завершает квест, даже если первый уже
   завершён. В ответе — точная ссылка на receipt и вычисленная пригодность.
3. **Второй квест — complete_housing_viewing.** Отдельное явное действие после
   первого квеста передаёт requestId (UUID), plan.id/version, questId,
   questSlug = housing-viewing, receipt.id/revision, artifact.id/revision,
   contentSha256, unresolvedFieldsSha256, definitionVersion, criteriaVersion,
   rewardVersion и confirmationCopyVersion. Это значения сохранённого receipt,
   показанного пользователю, не указатель latest. Сервер сверяет весь набор
   с receipt, snapshot user quest, артефактом, текущим планом и зависимостями.
   После проверки prerequisite completion/award/unlock/outbox атомарны.

Receipt не редактируется на месте. После необходимого переподтверждения
создаётся новый receipt; сервер не подставляет его в старую команду завершения.
При несовпадении цели, hash, версии или актуальности — «Результат обновился —
посмотреть изменения», без auto-confirm/auto-complete по более новому результату.
Если только prerequisite ещё не выполнен, completion отклоняется, но актуальный
ранний receipt сохраняется. Auth/owner проверяются до раскрытия конфликтов.
Повтор уже успешно обработанной команды с тем же payload возвращает сохранённый
результат по правилу идемпотентности ниже, а не заново завершает текущий артефакт.
Разные действия имеют разные command_kind и requestId; это не отменяет общий
ключ однократной награды. Ни одна команда не выполняет AI-вызов в транзакции.

### Обязательства CG-012/014, не реализованные здесь

1. Проверить авторизацию/владельца **до** конфликтов с currentVersion.
   Чужой ID не раскрывает наличие/версию ресурса.
2. Проверить активность плана и текущую plan.version; user quest принадлежит
   этому плану/владельцу. Artifact.plan/quest/owner совпадают;
   metadata.kind = content.kind = definition.artifactKind.
3. Artifact.revision последняя, содержимое неизменно. HousingBrief у чеклиста —
   именно бриф того же владельца/плана, соответствующего housing-brief user quest,
   не другой чеклист. Исходная ревизия существует; used field/revision актуальны.
   Проверить provenance/пользовательское принятие, не доверять JSON.
4. Применить Prepared и содержательные критерии полезности/безопасности.
   Показать неизвестные/ограничения, не заставляя ответить на каждый вопрос.
   Проверить hashes, copyVersion, принадлежность выбранного шага.
5. Для первого квеста подтверждение точной ревизии и completion — одна явная
   команда и транзакция. Для второго сохранить подтверждение без completion,
   в том числе в ожидании prerequisite; отдельная команда завершения закрепляет
   точный receipt и повторно проверяет evidence, hashes и awardPrerequisite.
   Прогресс, XP, unlock и outbox фиксируются атомарно по правилам команд выше.
6. Помимо защиты от дубля user quest, нужна общая уникальность
   (user_id, award_scope, quest_slug) для старого **и** нового пути.
   Пересоздание плана не восстанавливает право на XP. При уже использованной
   награде валидный completion нового квеста обновляет его прогресс/unlock,
   но возвращает awarded: 0 и не пишет второй положительный XP event.
   Scope-claim, ledger и прогресс фиксируются атомарно; ошибка/откат не должны
   «съесть» награду. Гонки между двумя планами/командами проверяются в CG-014.
   Идемпотентность команды: (user_id, command_kind, requestId) + hash
   канонического payload; тот же hash возвращает сохранённый результат,
   другой даёт конфликт лишь в пределах пользователя/команды.
   Другой command_kind не обходит уникальность award.
7. При активации новых критериев старый boolean completion не обходит evidence:
   для этих квестов вернуть понятное EVIDENCE_REQUIRED/обновление UI.
   Завершённые legacy-квесты не переоцениваются и не получают выдуманные receipts.
   Незавершённые legacy-квесты не менять автоматически: до релиза CG-014 нужен
   отдельный проверенный переход с согласованием владельца.
   Пока переход не реализован, новые определения к ним не применяются.
   До включения общей политики существующие XP events сопоставляются со slug
   и отмечают scope-награду уже использованной, без выдуманного receipt, нового
   начисления или удаления старой истории. Неоднозначная историческая запись
   блокирует активацию до разбора; нельзя обойти её новым user quest.
8. Ни один путь создания повторного плана или повторного user quest с тем же
   награждаемым slug не включается до общей DB-уникальности scope-награды,
   согласования legacy XP и защиты обоих путей completion. CG-012 можно выпустить
   без активации таких путей, но нельзя полагаться лишь на последующий CG-014.
   Старый complete() требует сообщение модели и не подходит для подтверждённого
   результата без AI: новые команды не наследуют этот барьер. Общие механизмы
   ledger/идемпотентности переиспользуются только с новыми evidence-проверками,
   атомарностью и общей политикой награды.

Для hashes CG-012 реализует/тестирует единый canonical JSON: после валидации
и нормализации рекурсивная сортировка ключей объектов, отсутствующие optional-поля
опущены, порядок массивов сохранён. Сериализация — JSON с корректным экранированием
строк, затем UTF-8 без форматирующих пробелов, SHA-256 lower hex. Входные строки
уже проверены на корректный Unicode/Cc. Content hash — всё содержимое ревизии.

### Набор неопределённостей version 1 для обоих kind

Точная оболочка: {schemaVersion: 1, artifactKind, sourceBrief, fields, pendingSuggestions}.
SourceBrief — {id, revision} либо null. Fields — массив {field, answer} с полным
нормализованным снимком ответа, включая revision/provenance; порядок полей как
в r1HousingFieldSchema. PendingSuggestions — массив {id, revision}, упорядоченный
по нормализованному ID (ASCII), затем revision. Включаются только pending.
Дубликаты до хеширования отклоняются.

- Бриф: artifactKind = housing_brief, sourceBrief — ссылка на сам подтверждаемый
  сохранённый бриф. Рассматриваются все его answers и pending-предложения.
- Общий чеклист: artifactKind = viewing_checklist, sourceBrief = null,
  fields = [], pendingSuggestions = []. Это фиксированный пустой набор version 1,
  а не неизвестные поля чужого или случайного текущего брифа.
  UI явно пишет «Общий чеклист; ваши условия не учтены», не «Всё известно».
- Персонализированный чеклист: sourceBrief равен housingBrief из содержимого
  чеклиста (историческая ссылка на источник). Сервер проверяет того же владельца,
  ID брифа и неизменность используемых версий. Рассматривает объединение полей
  basedOn всех разделов без дублей; берёт их из актуального брифа.
  PendingSuggestions = []: непринятые предложения модели не являются ответами
  пользователя и не входят в digest чеклиста. Несовпадение использованных
  field/revision — stale, не молчаливый расчёт по новым данным.

Из рассматриваемых полей в fields входят unasked/undecided/declined и known с
открытой границей аренды, неточной датой (month/before/after), completeness=open.
Not_applicable не неизвестное, но требует проверенного пользовательского события.
Пустой набор допустим. Для брифа pending-предложения входят в его собственный
снимок: их изменение создаёт новую ревизию брифа и требует подтверждения нового
результата перед новым completion первого квеста. Для любого чеклиста
pendingSuggestions всегда пуст: добавление, изменение или отклонение непринятого
предложения в исходном брифе само по себе не меняет hash/пригодность receipt
чеклиста. Явное принятие, изменившее используемый ответ и его revision, делает
чеклист stale по обычному правилу зависимости. Изменение содержимого/ревизии
самого чеклиста также требует переподтверждения. Несвязанные ответы исходного
брифа не меняют hash чеклиста.
Чтение источников и проверка hashes/CAS атомарны, без сетевого/AI-вызова в транзакции.
Receipt дополнительно сохраняет фактически прочитанную актуальную ревизию источника
для аудита. UI отображает серверный набор, не строит свой digest.
Частичный потолок остаётся пользовательским ограничением, даже попав в fields.

Receipt фиксирует оба hashes и версию алгоритма/снимка. Сам алгоритм, receipt,
owner/CAS/ledger и UI **не реализованы в CG-010**. Нельзя логировать/эхом возвращать
свободный текст, секреты и произвольный payload в ошибках. Семантика, ПДн, ссылки,
injection — отдельные CG-019/024/026; unit PASS не заменяет их приёмку.

## Разбор замечаний Cursor

- M1/M2: строгие ID/int4; требования snapshot и явного mapping ранних metadata.

### Итог повторного ревью Cursor и уточнения N1–N11

Cursor не обнаружил блокирующих дефектов в коде контрактов. Два блокирующих
неоднозначных места спецификации устранены в этой редакции документа:

- N1: pending-предложения исключены из digest любого чеклиста; таблица состояний,
  зависимости и правила hashes согласованы. В собственном снимке брифа они остаются.
- N2: для первого квеста описана одна команда подтверждения/завершения; для второго —
  подтверждение без XP и отдельное завершение по точному receipt, артефакту,
  hashes и версиям. Автоподстановка нового receipt запрещена.
- N6/N7/N11: добавлены требования к памяти отказов, неизменяемому snapshot награды
  и порядку активации повторных планов/новых completion. Это работа CG-012/013/014,
  не выполненные миграции или runtime-защита.
- N4/N8: явно указаны границы Unicode-фильтра и структурной информативности.
  Дополнительные ограничения схем и тесты из необязательных N3–N5/N9/N10
  в этом документальном уточнении не реализованы. Решения о более строгой
  семантике не подменяются молчаливым изменением принятого контракта.

Будущие приёмочные проверки CG-012/014 (здесь не выполнены):

1. Новое/изменённое/отклонённое pending-предложение в исходном брифе не делает
   неизменившийся чеклист stale. Принятие с изменением используемого ответа — делает.
2. Изменение самого чеклиста, плана или используемой ревизии ответа требует нового
   подтверждения; подмена переданного receipt более новым не допускается.
3. Сбой первой объединённой команды откатывает receipt, прогресс и награду;
   идемпотентный повтор успешной команды не создаёт ни новый receipt, ни новые XP.
4. Раннее подтверждение второго квеста даёт 0 XP. Завершение первого лишь открывает
   возможность отдельного completion второго, не запускает его автоматически.
5. Две конкурирующие команды/планы не обходят user/scope/slug; snapshot не меняется
   через UPDATE и изменение каталога quests не меняет награду существующего квеста.
