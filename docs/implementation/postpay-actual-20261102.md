# Postpay actual: подготовка отдельного выпуска — 2 ноября 2026

Статус: реализация и синтетические проверки в ветке `codex/incident-postpay`.
Этот документ не подтверждает обновление сервера. Публикация, миграция и открытие
доступа требуют разрешения на окончательный SHA и фактических результатов
релизного прогона.

## Причина и поведение

Прежний режим использует денежный резерв и сохраняет его при неподтверждённой
стоимости. Новая политика включается явно через `AI_CUSTOMER_BILLING_MODE=postpay_actual_v1`;
обычная конфигурация по умолчанию остаётся `legacy`. В новом режиме попытка
получает неизменяемую запись admission с нулевой суммой, без денежного удержания.
Она хранит исходный баланс, маршрут, версию тарифа и идентичность запроса.

Для RouterAI доступный баланс ограничивает допустимую стоимость исходного
запроса. Пользовательское списание выполняется только после сохранённого
успешного ответа и подтверждённой стоимости: фактическая стоимость ×10.
«Минимум» сохраняет фиксированные 3 ₽ за успешный ответ. Неподтверждённая
стоимость остаётся `pending`; нулевая стоимость вместо неизвестной не
записывается. Если фактическое списание образует обязательство, отдельный журнал
и источники погашения сохраняют точную сумму и исключают повторное погашение.

Фоновый reconciler запускается явно, не блокирует readiness и выполняет
ограниченные GET-проверки сохранённой попытки. Он не повторяет запрос модели,
не придумывает terminal-результат и завершает работу через abort/drain при
остановке приложения. Ошибки и тайм-ауты имеют ограниченную задержку повторной
проверки; одновременно работает один batch.

## Миграции и совместимость

Выпуск с текущей схемы 44 включает два неизменяемых SQL-файла:

- `0045_ai_balance_request_cost_limit.sql` — уже подготовленная миграция
  снимка ограничения стоимости; её текст в этой доработке не переписывается,
  прежние проверки режима `operator_ceiling` сохраняются.
- `0046_postpay_actual.sql` — новые `ai_postpay_attempts`,
  `credit_postpay_liabilities`, `credit_postpay_repayments` и discriminator
  `gigachat_request_fees.billing_mode`. Итоговый inventory: 46 миграций,
  79 таблиц, 23 последовательности.

Прежние записи ledger, удержания, чеки, источники средств и полученные подарки
не удаляются и не превращаются задним числом в postpay. Maintenance сохраняет
новую историю и требует отдельного review перед потенциальной очисткой.
Disposable-фикстуры отката могут удалить только пустые новые таблицы; это
проверка миграций на вымышленных данных, а не команда rollback рабочего сервера.

Действующий APK использует прежние API-контракты. Параметр
`AI_CREDIT_RESERVATION_MODE=fixed5_overdraft` остаётся в новом профиле как
совместимый envelope, а сервер выбирает postpay через отдельный флаг. Три режима
ИИ, маршруты подтверждения телефона, подарок 500 ₽ и фискальные чеки не
получают новых клиентских прав или самостоятельных вычислений денежных сумм.

## Отдельный runtime-профиль

Startup v14: `citygo-api-web-postpay-actual-v1`; маркер контейнера:
`postpay-actual-v1`. Его закрытый JSON содержит точный набор v13 плюс
`AI_CUSTOMER_BILLING_MODE=postpay_actual_v1` и
`AI_REQUEST_COST_LIMIT_MODE=operator_ceiling`. Профили v1–v13 не расширены.
Ошибочные/пропущенные поля и попытка передать эти настройки через ambient
окружение отклоняются.

Прежний closed-release workflow привязывает полный JSON API, миграционное и
startup-разрешения, generation и образы к хэшам. У API один read-only mount;
Web, Worker и migrator не получают API-секреты. `finish` сам по себе сохраняет
закрытые трафик, Worker и restart. Автодеплой этой доработкой не включается.

## Проверки и границы доказательств

Отдельные синтетические проверки scheduler: 12/12; они используют fake clock и
инъецированный callback, без внешних запросов. Windows-проверки нового runtime:
`container-runtime.test.mjs` — 31/31; Python validation start/finish — 30/30.
Новый `PostpayActualCutover` наследует полный набор Linux-проверок защищённого
закрытого cutover, дрейфа секретов, отзыва разрешений и сохранения барьера;
результат их исполнения в Linux нужно приложить к окончательному выпуску.

Полный текущий `pnpm check`, PostgreSQL integration и Container smoke фиксируются
отдельными фактическими логами для окончательного SHA. Предыдущий batch8 и его
проверки не заменяют проверку нового финансового кода. Реальные SMS, модель,
платёж или операции рабочего сервера не требуются для этих тестов.
