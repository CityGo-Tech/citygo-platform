# Исправления по независимому ревью разрешений R1

**CG-018B–F, 5 октября 2026. Локальные изменения поверх `34f0295`, не поставлены в main.**

Исправлены два блокера независимого ревью: повторное включение снятой версии
уведомления и недостаточная проверка указателей при POST. Усилены восстановление
клиента, классификация ошибок записи и проверка прав тестовой роли. Все изменения

## Версия уведомления не возвращается к жизни

[Хранилище](../../apps/api/src/r1-permission-store.ts) проверяет сохранённую
историю конфигураций под общей блокировкой runtime. Версия не может снова стать
выбранной `approved_fixture`, если её сняли через `withdrawn_fixture`, убрали из
выбора, заменили другой версией или понизили из approved в draft. Возврат через
draft не обходит правило. Отказ — `NOTICE_VERSION_RETIRED`, без новой записи.

Первая подготовка draft → approved разрешена: ещё не утверждённый черновик не
считается ранее действовавшей версией. Для замены снятой версии создаётся новая
версия словаря. Старый grant не переносится на неё, требуется явное новое действие.
Текст под прежней областью/версией по-прежнему неизменяем; status сам по себе
не входит в хеш текста и не удостоверяет согласие или законность обработки.

## Чтение и запись проверяют одни инварианты

GET, POST и доверенная замена конфигурации сверяют runtime с вершиной истории,
а указатели решений — с максимальными ревизиями собственного журнала. Проверяются
точные связи owner/scope/event/command; чужая история не разбирается. Для маршрута
сверяется максимальная историческая ревизия, чтобы откат high-water mark не
допускал повторного использования старой ревизии.

Проверки выполняются до replay. Поэтому идентичный повтор не обходит повреждение
указателя, но при исправном хранилище возвращает историческую квитанцию даже после
отзыва или смены маршрута. Она не является актуальным grant или допуском AI.

Отзыв не требует принятия или разбора тела новой политики. Он, как и read-only
поиск команды, сохраняет проверки указателей/собственного журнала; если метаданные
маршрутов нечитаемы из-за повреждения policy-body, эти две операции не требуют
восстановления тела. Получение текущего снимка, новый grant и замена конфигурации
при таком повреждении отклоняются. Это ограниченный путь отзыва/чтения квитанции,
не fallback к ранее одобренному уведомлению.

## Отказ до записи и неизвестный COMMIT различаются

Локальный wrapper хранилища опирается на контракт `Database.transaction`:
COMMIT вызывается только после успешного завершения callback. Не менялись
общий DB-driver или его интерфейс.

- Ошибка проверки или ограничения целостности до завершения callback означает,
  что команда не дошла до COMMIT. Повреждение/SQLSTATE класса 23 возвращает
  безопасный `rejected / STORED_DATA_INVALID`; иной технический отказ до COMMIT —
  `rejected / WRITE_NOT_COMMITTED`. Оба ответа не содержат SQL-диагностику.
- После успешного завершения callback ошибка COMMIT или потеря его подтверждения
  остаётся `unconfirmed / STORAGE_UNAVAILABLE`, `retry: same_command`.
  Даже код класса 23 на этой стадии не превращает неизвестный исход в обещание
  отката. Повтор использует прежние UUID и содержимое.

Если клиент уже потерял исходный ответ, последующий однозначный отказ не
доказывает, что первая попытка не записалась. Контроллер не очищает такую pending
команду автоматически и не создаёт вместо неё новую.

## Поиск квитанции и восстановление checkpoint

Новый тестовый маршрут:

```text
GET /v1/synthetic/permissions/commands/:scope/:requestId
```

Он доступен только через прежний явный test-only opt-in, с настоящей тестовой
сессией. Owner берётся из auth, query-параметры запрещены. Ответ проверяется
строгой схемой, имеет `Cache-Control: no-store`; запрос не создаёт событий и не
расходует квоту записей. Совпавшая собственная квитанция возвращается как
`synthetic_recorded`, `replayed: true`, даже если grant впоследствии отозван.

`not_recorded_at_read` означает только отсутствие записи в момент чтения.
Старый POST может всё ещё ждать блокировки и позже завершиться. Поэтому такой
ответ **не отмена, не fencing и не разрешение бросить команду**. Readiness/повреждение
хранилища также не дают разрешения автоматически очистить неопределённость.

[Offline-контроллер](../../apps/api/src/r1-permission-recovery.ts) предоставляет
`beginLookup` / `acceptLookup`. Только совпавшая owner/scope/command квитанция
переводит pending в `recorded_need_refresh`. Перед новым действием нужен свежий
GET; старая квитанция не меняет текущую проекцию.

Для восстановленного grant `retryCommand` требует свежий собственный снимок,
точное совпадение expectedRevision/notice/route и явное подтверждение этих условий
с исходным request ID. Вызывающий код должен сначала показать полный текст и
маршрут. Подтверждение в offline-модуле не удостоверяет, что пользователь их
действительно увидел: интеграция и проверка UI остаются отдельной задачей.
Если условия сменились, поиск прежней квитанции позволяет проверить её без POST
со старым grant. Восстановленный revoke не требует новой политики.

Tickets привязаны к экземпляру по идентичности объекта. `close()` остаётся
терминальным локальным закрытием; это не серверный отзыв, отмена запроса или
удаление checkpoint. Контроллер не импортируется в Web/Expo/server, не делает
сетевых запросов и не запускает модели.

## Доводка N1 и N4

[Readiness](../../apps/api/src/r1-permission-access.ts) требует плоских grants:
у effective-role нет ни одного прямого членства в других ролях. Проверка читает
`pg_auth_members` по OID `current_user` и не зависит от `INHERIT` или `SET`.
Поэтому отвергаются и NOINHERIT-членство в чужом writer/`pg_write_all_data`,
и членство с `SET FALSE`. Это сознательно строгое правило маленькой фикстуры,
не универсальная политика для production с групповыми ролями.
Наследование и переключение — разные способы получить права
([PostgreSQL 17](https://www.postgresql.org/docs/17/role-membership.html)); каталог
хранит оба флага отдельно
([pg_auth_members](https://www.postgresql.org/docs/17/catalog-pg-auth-members.html)).

В каждой из пяти таблиц проверяется `has_any_column_privilege(..., 'REFERENCES')`,
а не только право на всю таблицу. В `cg018_synthetic` допустима ровно одна routine:
`keep_history()` без аргументов, возвращающая trigger, invoker, с ожидаемым
`search_path`, без EXECUTE у effective-role и без членства в её владельце.
Три history-триггера должны ссылаться на её точный OID. Лишняя функция, процедура
или перегрузка закрывает readiness даже при отозванном EXECUTE; доступные
SECURITY DEFINER-функции не пропускаются. Тело функции и прочие схемы этим
инвентарём не удостоверяются — полный DDL/security-аудит не заявлен.

В [общую регрессионную фикстуру](../../apps/api/src/r1-permission-review.fixture.ts)
добавлены три предметных сценария N1 и расширены прежние проверки N4:

- non-owner writer, встроенная `pg_write_all_data` и членство с `SET FALSE`;
- колоночный REFERENCES отдельно на каждой из пяти таблиц; тест подтверждает,
  что table-level право отсутствует, а column-level присутствует;
- лишняя SECURITY DEFINER-функция с EXECUTE, та же функция без EXECUTE и
  перегрузка `keep_history(integer)`;
- NOINHERIT-членство во владельцах схемы и функции истории;
- точный replay уже успешного grant/revoke и lookup при откаченном указателе;
  lookup при пропавшем решении и replay grant при configuration/route rollback.
  Недостающие повторы и прямые владельцы из следующего ревью добавлены в N7 ниже.

Небезопасные права отклоняют POST, текущий GET и lookup одинаковым безопасным
`STORE_NOT_READY`, без изменения счётчиков событий. После снятия лишних прав
или удаления созданной тестовой routine обычное чтение и replay снова доступны;
повтор возвращает сохранённую квитанцию, не новую запись.

Привилегированный login synthetic harness по-прежнему способен выполнить
`RESET ROLE`. Guard проверяет effective-role внутри операции и не является
изоляцией от произвольного SQL или доказательством безопасности login пула.
Перед реальным запуском нужна отдельная ограниченная login-роль и её аудит.

N2 пока не менялся: подтверждение checkpoint не доказывает показ текста;
проверка UI остаётся отдельной работой. N3 — безопасная лишняя неопределённость
при сбое COMMIT транзакции, уже выбравшей отказ без записей; оптимизация не
внесена. N5 — полное чтение истории конфигураций, ограничение сохранено.
Z1/Z5 также не закрываются этой доводкой.

## Доводка N6 и N7

N6 усиливает только структуру трёх history-триггеров. В дополнение к имени,
типу событий, включённому состоянию и точному OID функции требуются
`tgqual IS NULL` и `cardinality(tgattr::int2[]) = 0`. Эти поля описывают условие
`WHEN` и колонки `UPDATE OF`
([каталог PostgreSQL 17](https://www.postgresql.org/docs/17/catalog-pg-trigger.html)).
Проверки тела `keep_history()`, прочих DDL-путей и production не добавлялись.

Один новый общий сценарий по очереди заменяет триггер у `commands`,
`configurations` и `notices` на условный либо колоночный: всего шесть отрицательных
вариантов. Тест подтверждает, что прежние `tgtype=27`, включённое состояние и
OID функции сохранены; меняется только `WHEN` или список колонок.
POST, GET и lookup получают `503 STORE_NOT_READY` без новых событий.
Каждый триггер восстанавливается в `finally`, затем доступны обычное чтение,
lookup и replay с прежней квитанцией.

N7 расширяет проверки уже успешных grant **и** revoke. После удаления строки
`decisions`, отката указателя конфигурации и отката route high-water mark обе
исходные команды повторяются без изменения UUID/содержимого. Также проверяются
новые команды, текущий GET, lookup записанных и отсутствующей команды: всегда
`503 STORED_DATA_INVALID`, без изменения счётчиков commands/decisions/consent/AI/XP.
В конфигурационном сценарии теперь две сохранённые команды, не одна.

Добавлены три независимых сценария прямого владения effective-role: схема,
таблица `commands` и функция `keep_history()`. Членств в других ролях нет.
После передачи владельца схема сохраняет только USAGE без CREATE; таблица —
точные SELECT/INSERT grants без лишних прав и записи `recorded_at`; функция —
без EXECUTE. Тесты явно проверяют эти права и OID владельца, поэтому ранний
membership/ACL guard не маскирует проверку владения. Обычные права владелец
может отозвать у себя, но владение остаётся отдельным полномочием
([права PostgreSQL 17](https://www.postgresql.org/docs/17/ddl-priv.html)).
Все три HTTP-пути отклоняются без записей. В callback восстановления возвращаются прежний
владелец и узкие grants API. N8 ниже дополнительно восстанавливает исходные
права владельца и проверяет полный снимок ACL.

Readiness и общая фикстура — единственные изменённые исходники N6/N7.
SQL-фикстуры, grants-файл, оба harness, store, recovery, HTTP, контракты,
runtime/deploy и сервер не менялись. Проверки не расширяют прежние границы
Z1/Z5/N2/N3/N5 и не являются полной приёмкой CG-018.

## Доводка N8 и N9

N8 устраняет утечку состояния после трёх проверок прямого владельца. Перед
передачей владения сохраняются `nspowner/nspacl`, `relowner/relacl`, `attacl`
всех живых колонок `commands` и `proowner/proacl` функции `keep_history()`.
В callback восстановления возвращаются владелец, его прежние полные права и точные узкие
grants API; колоночные ACL таблицы очищаются и выставляются заново.
Снимок после восстановления должен точно совпасть с исходным. Сортируется
только порядок ACL-записей: grantor, значения и различие NULL/пустого списка
сохраняются. Это восстановление известной фикстуры, не общий инструмент
восстановления произвольной production-политики.

[Очистка HTTP-фикстуры](../../apps/api/src/r1-permission-http.fixture.ts)
проверяет все переданные имена до первого удаления. В принятом N8 принадлежность
случайных `cg018_http/worker/backup_<32 hex>` своему списку обеспечивал вызывающий
код; N11 ниже делает это обязательной проверкой приватного реестра. Существующая роль
должна быть NOLOGIN и не совпадать с `current_user`. Сначала выполняется
`REASSIGN OWNED … TO CURRENT_USER`, затем `DROP OWNED … RESTRICT` и `DROP ROLE`;
CASCADE не используется. Переназначение владения не удаляет прежние grants,
поэтому очистка grants выполняется отдельно
([REASSIGN OWNED](https://www.postgresql.org/docs/17/sql-reassign-owned.html),
[DROP OWNED](https://www.postgresql.org/docs/17/sql-drop-owned.html)).
Отсутствующая роль пропускается; ошибка одной роли не прерывает попытки для
остальных. Закрытие приложения, очистка ролей и закрытие принадлежащей фикстуре
PGlite также выполняются независимо; ошибки собираются, не скрываются.

Один новый общий сценарий намеренно оставляет схему, таблицу и функцию у
временного владельца после сбоя callback восстановления. Затем инъекция
отказывает на его REASSIGN: проверяется, что другая созданная роль всё равно
удалена, а чужая fixture-роль не затронута. Повтор настоящей очистки возвращает
владение, удаляет оставшуюся роль, сохраняет полный ACL-снимок, счётчики и
квитанцию. Повторная очистка безопасна, имя вне допустимого шаблона отвергается.
Сценарий прошёл на PGlite и PostgreSQL. Он не обещает успешную очистку при
недоступной БД: такой сбой остаётся явной ошибкой teardown.

N9 сохраняет квитанцию первого успешного ответа. После восстановления каждого
из шести вариантов триггера и трёх прямых владельцев replay **и** lookup
сравниваются с этим оригиналом, а не только друг с другом. В сценарии
повреждения указателя явно проверены `200` исходных grant и revoke до
повреждения. Дублирование безопасной проверки владельца функции не удалялось.

В N8/N9 изменены только `r1-permission-review.fixture.ts`,
`r1-permission-http.fixture.ts` и документация. Readiness, SQL/grants-фикстуры,
оба PostgreSQL runner, store, recovery, HTTP-обработчик, контракты, общий
DB-driver, runtime/deploy и сервер не менялись. N8/N9 приняты независимым
read-only ревью Cursor в заявленных границах; прежние ограничения остаются.

## Доводка N10 и N11

N10 заменяет `try/finally` в трёх direct-owner сценариях и внешней очистке
сценария оставшегося владельца на `withReviewRestoration`. Восстановление
выполняется и после ошибки основной проверки. Одна ошибка возвращается как
тот же исходный объект; при двух ошибках `AggregateError.errors` содержит
сначала первичную, затем ошибку восстановления. Сравнение ACL и cleanup больше
не подменяют первичную причину. Новый общий диагностический сценарий проверяет
порядок вызовов, идентичность обеих `AssertionError`, каждый одиночный сбой
и успешный путь. Намеренный отказ восстановления в сценарии N8 также требует
точной исходной ошибки, а не любого отказа с похожим сообщением.

N11 заменяет свободный cleanup-хелпер на `syntheticPermissionRoleFixture`.
Каждый экземпляр хранит собственный приватный Set имён: имя добавляется только
после успешного `CREATE ROLE … NOLOGIN` через его метод `create`.
Перед чтением каталога и удалением проверяются **все** выбранные имена:
допустимый шаблон и принадлежность этому Set. Похожее имя роли соседней
фикстуры не подходит. Принадлежность не может быть добавлена публичной
регистрацией чужого имени. При повторной очистке уже удалённая собственная
роль по-прежнему безопасно пропускается. NOLOGIN/current_user guard,
REASSIGN → DROP OWNED RESTRICT → DROP ROLE, отсутствие CASCADE и независимые
попытки очистки других собственных ролей сохранены.

Второй новый общий сценарий проверяет четыре отказных пути:

- собственная допустимая роль вместе с недопустимым именем;
- собственная роль вместе с допустимым именем роли другой фикстуры;
- собственная роль, временно изменённая на LOGIN;
- собственная NOLOGIN-роль, являющаяся текущей ролью запроса.

В первых двух случаях нет даже чтения каталога; в последних разрешено только
проверочное чтение, ни один REASSIGN/DROP не вызывается. `current_user`
проверяется настоящим `SET LOCAL ROLE` в транзакции, не поддельным результатом
каталога. Проверяются тип/код ошибки, сохранность обеих ролей, полного ACL-снимка
и счётчиков. Затем каждый экземпляр очищает только свои роли, остаток — ноль.
Тест использует NOLOGIN-роли без паролей; LOGIN включается временно без пароля,
доступ к БД извне не создаётся.

В N10/N11 изменены только те же две тестовые фикстуры и документация.
Readiness, store/recovery/HTTP, SQL/grants-фикстуры, оба PostgreSQL runner,
контракты, общий DB-driver и runtime не менялись. Старые `finally` для
`cg018_notice_owner_*` и `cg018_review_writer_*` не переводились на новый
реестр; их отказ может оставить роль в тестовом кластере. Недоступность БД,
неизвестный исход создания роли, произвольные DDL/races или production-изоляция
этой доводкой не решаются. N10/N11 приняты независимым read-only ревью Cursor
в заявленных границах; CG-018 не закрыт.

## Наблюдение за транзакциями в N12

В отрицательном сценарии N11 `observedBase` теперь явно оборачивает три метода:
`query`, `exec` и `transaction`. Счётчик транзакций увеличивается при входе в
метод, до делегирования в исходную БД. Поэтому попытка cleanup перейти к SQL
через транзакцию до отказа больше не останется незамеченной.

Безопасная проба с callback без SQL проверяет возврат того же объекта
и прирост только счётчика транзакций на один. Само делегирование проба
не доказывает: оно подтверждено чтением `return f.base.transaction(work)`
в обёртке. Это уточнение N13, без изменения кода или новой проверки делегирования.
После неё смешанный недопустимый список и роль другой фикстуры не меняют ни
один счётчик. LOGIN/current_user допускают одно проверочное чтение, но не
вызывают `exec` или `transaction` через cleanup-facing обёртку.

Внутренний `SET LOCAL ROLE` в обёртке `query` по-прежнему использует исходную
`f.base.transaction`: он нужен для настоящего current_user и не считается
действием cleanup. Это явная граница observer, не утверждение об отсутствии
всех физических транзакций. Сохранность ролей, ACL и счётчиков проверяется
как прежде. Набор остаётся из 19 общих сценариев для PGlite/PostgreSQL.

N12 меняет только `r1-permission-review.fixture.ts` и документацию.
Реализация очистки, readiness, store/recovery/HTTP, SQL/grants, runner,
контракты и общий DB-driver не менялись. N12 принят независимым read-only
ревью Cursor в заявленных границах, без блокеров.

лимитом. Это маленькая synthetic-фикстура, не масштабируемое production-хранилище.
