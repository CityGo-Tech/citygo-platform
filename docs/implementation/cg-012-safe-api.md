# CG-012C: безопасный API частичных ответов — синтетическая подготовка

Дата завершения локальной подготовки: 5 октября 2026. База — `main` после
[PR #80](https://github.com/CityGo-Tech/citygo-platform/pull/80),
[`a2b3803`](https://github.com/CityGo-Tech/citygo-platform/commit/a2b380361116f98cee6a4a411e95bd4b90ad3b46).
Предыдущие этапы: [хранение A](cg-012-answer-history.md),
[восстановление B](cg-012-draft-recovery.md).

Подготовлен HTTP-слой для изолированных тестов: создание пустого брифа,
отдельный ответ/исправление, поиск, восстановление и история. Он использует
настоящие сессии и проверки владельца, но **не включён у пользователей**.
Web/Expo, создание первого плана, полезные карточки, подтверждения и XP
не подключаются этим изменением. Вся CG-012 не закрыта.

## Почему только синтетический режим

У CG-018 пока нет принятой политики сроков хранения/удаления новой истории.
У B остаётся открытым N3 — совместимость исторических Unicode-данных.
Технические квоты не решают эти продуктовые вопросы. Поэтому:

- `R1_HOUSING_API_MODE=disabled` — значение по умолчанию: маршрутов нет, 404.
- `synthetic` — только изолированное development/test-окружение с вымышленными
  данными и специально ограниченной ролью БД. Это не режим пилота.
- `NODE_ENV=production` с любым режимом, кроме `disabled`, отклоняется при
  чтении конфигурации и при создании API даже с готовым объектом config.
- Production grants, deployment, CI, миграции и текущие клиенты не изменены.
  Переменная передаётся только API; worker/migrator/build/клиенты её не получают.

Не переключайте работающий сервер в development ради обхода запрета.
Test-фикстуры не предназначены для настоящих пользователей, их аккаунтов и данных.
Хранение обычных ответов и отправка их модели — разные операции: будущая
не-AI помощь не должна требовать AI-согласия, но для реальных данных нужны
отдельно принятые основания обработки и lifecycle CG-018.

## Маршруты и данные

Все перечисленные маршруты существуют **только в synthetic**. Владелец
определяется сервером из действующей сессии, не из запроса или admin-прав.
Используются прежние cookie/bearer, wire-версия 1 и `Cache-Control: no-store`.

| Метод | Маршрут                                              | Результат                                                                                                                        |
| ----- | ---------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------- |
| POST  | `/v1/housing/briefs`                                 | Создать пустой бриф по явной команде v1: `{commandId, plan: {id, version}}`                                                      |
| POST  | `/v1/housing/answers`                                | Изменить одно поле по команде v1: `commandId`, `plan`, `brief: {id, revision}`, `change: {field, expectedFieldRevision, answer}` |
| GET   | `/v1/housing/briefs?planId=…&planVersion=…`          | Список для явного выбора: ID, ревизия, точный план и серверные даты; без текста ответов                                          |
| GET   | `/v1/housing/briefs/recovery?planId=…&planVersion=…` | `not_found`, `recovered` со снимком либо `selection_required`                                                                    |
| GET   | `/v1/housing/briefs/:id`                             | Последний собственный снимок; `?revision=…` — конкретный исторический                                                            |
| GET   | `/v1/housing/briefs/:id/history`                     | Страница снимков по убыванию ревизии                                                                                             |

Снимок: `{id, revision, plan, content}`. `content` проверяется закреплённой
схемой v1, не будущим фасадом текущего ввода. Новые HTTP DTO находятся в
[`housing-api.ts`](../../packages/contracts/src/housing-api.ts), маршруты —
[`housing.ts`](../../apps/api/src/housing.ts).

ID — каноническая положительная int8-строка; query version/revision —
каноническая положительная int4-строка. `01`, дроби, экспоненты, массивы,
повторные ключи, неизвестные поля и переданный `ownerId` не принимаются.
`limit` по умолчанию 20, максимум 50. Список принимает `beforeId`, история —
`beforeRevision`. Следующий курсор — `null` в конце. Это живая keyset-навигация,
не замороженная выгрузка и не право доступа к ресурсу курсора.

`createdAt` — время создания брифа; `updatedAt` — время его последней ревизии.
Они помогают различать черновики, но не означают качество/предпочтительность
результата. Несколько брифов не объединяются и последний не выбирается
автоматически. Старый внутренний `listForPlan` сохраняет прежний DTO без дат;
HTTP использует отдельный `listSelectionForPlan`.

## Постепенный ввод и атомарность

Для создания пустого брифа не нужны заполненный профиль, бюджет, дата переезда,
тип жилья, баланс AI, AI-согласие или модель. Нужен уже существующий собственный
текущий план: этот инкремент **не создаёт его без полной анкеты**. В тестах план
создаётся синтетической фикстурой, не новым пользовательским endpoint.

Состояния `unasked`, `undecided`, `declined`, `known` сохраняются различными.
Частичный ответ не дополняется предположениями. Исправление затрагивает только
явно указанное поле; происхождение и новая ревизия задаются сервером. Клиент
не может прислать actor/provenance или принять предложение системы этим маршрутом.

Команды используют существующие блокировку владельца, проверку текущего
плана и CAS брифа/поля. Журнал команды и снимок записываются одной транзакцией.
Конфликт не перезаписывает историю. Точный replay возвращает **исходный** снимок
после дальнейших правок, архивации плана и исчерпания квот. Повторное использование
того же ID с другим действием/телом — 409. Автоматических retries нет.

Чтение архивного собственного плана разрешено; новые записи в него — нет.
Recovery без брифа ничего не создаёт. Никакой маршрут не создаёт AI attempt,
receipt, completion, XP, unlock или новый user quest. Бриф с результатами или
предложениями нельзя редактировать этим писателем без будущих правил зависимостей.

## Квоты: ограниченное хранение, не удаление

Это предложенные **технические потолки синтетической реализации**, а не принятая
политика пилота. Конструктор хранилища допускает меньшие значения для тестов,
но не превышение этих максимумов. Публичного endpoint/переменных для повышения
потолков нет.

| Ограничение                                        | Максимум и default |
| -------------------------------------------------- | ------------------ |
| Брифы одного владельца, включая архивные планы     | 100                |
| Брифы точного плана/версии                         | 10                 |
| Команды одного владельца, включая архивную историю | 1 000              |
| Ревизии одного брифа, включая первую               | 250                |
| Нормализованный JSON команды в UTF-8               | 16 384 байта       |
| Полный JSON сохраняемого содержимого в UTF-8       | 65 536 байт        |

Количество проверяется после owner lock и проверки replay; сканирование
ограничено нужным префиксом, а не полным `count(*)` растущей таблицы.
Параллельные команды одного владельца не занимают последний слот дважды.
Квоты считаются в БД, не в памяти отдельной API-реплики. Нулевые количественные
лимиты запрещают новые записи, но не чтение или точный replay.

Отказ — 409 `HOUSING_STORAGE_LIMIT`, `retryable: false`, без раскрытия счётчиков
и содержимого. Не путать его с HTTP rate limit 429 или денежным бюджетом AI.
Существующий IP limiter API сохранён; общий account/IP limiter CG-033 не реализован.
История не очищается, старые снимки не перезаписываются, счётчики не сбрасываются.
Согласованные retention/export/delete и работа с backup остаются CG-018.

## Readiness и минимальные права

[`verifyHousingReadiness`](../../packages/db/src/housing-access.ts) — только
проверка, не исполнитель миграций или grants. Каждый новый HTTP-запрос проверяет
свежие права; `/ready` дополнительно вызывает её только в synthetic. В disabled
прежний readiness не получает новой зависимости от 0012.

Проверяется точный SHA-256 LF-нормализованной неизменённой миграции
`0012_housing_answer_history.sql`, наличие используемых колонок и эффективная роль:

- нет superuser/CREATEROLE/CREATEDB/BYPASSRLS и CREATE в `public`;
- SELECT на `users`/`relocation_plans`; UPDATE хотя бы одной колонки этих таблиц
  для существующих `SELECT FOR UPDATE`;
- отдельно SELECT **и** INSERT на каждой из трёх R1-таблиц;
- нет UPDATE даже отдельной колонки R1, нет DELETE/TRUNCATE;
- USAGE на identity sequence брифа, без UPDATE/setval.

Нехватка или избыток проверяемых прав, повреждённая запись миграции или отсутствующая
колонка дают общий 503, без SQL/имени роли. Успех проверки не является аудитом
всего сервера, его роли-подключения, владельцев таблиц или произвольных функций БД.

[`housing-synthetic-grants.sql`](../../packages/db/src/fixtures/housing-synthetic-grants.sql)
используется **только тестовой фикстурой** поверх существующих grants с уникальными
временными ролями. Его нельзя применять в production. Рабочие API/worker по-прежнему
не получают R1-права; backup-доступ сохраняется. Не расширяется общий USAGE/UPDATE
всех sequences и не выдаются R1 UPDATE/DELETE/TRUNCATE ради успешного теста.
Прикладные методы остаются trusted server code: SQL-права не заменяют их owner scope.

Основание проверки: [PostgreSQL 17 — функции информации о правах](https://www.postgresql.org/docs/17/functions-info.html),
[GRANT](https://www.postgresql.org/docs/17/sql-grant.html). Список прав в одном
`has_table_privilege` означает «хотя бы одно»: обязательные SELECT/INSERT
проверяются раздельно; запрет DELETE/TRUNCATE — отрицанием проверки списка.

## Ошибки и диагностика

Повреждённое собственное содержимое, неподдерживаемая версия или ошибка построения
серверного снимка — общий HTTP 500 `INTERNAL_ERROR`, не Zod/400. Нет fallback к
предыдущей «хорошей» ревизии. Чужой повреждённый бриф остаётся обычным 404 до
декодирования, как отсутствующий ресурс.

Событие `HOUSING_DATA_ERROR` содержит только фиксированную причину/операцию,
проверенные ID/ревизию брифа и серверный requestId. Содержимое строки, free text,
Zod issues, raw SQL error/cause и credentials туда не передаются. Клиент не
получает этот диагностический контекст. Это не полная политика всех HTTP-логов:
реальные данные и внешние системы журналирования требуют отдельной приёмки CG-018.

## Проверки и ограничения

В новых тестах используются вымышленные аккаунты, настоящие session записи и
роль API без права изменять R1-историю. Проверяются отсутствие маршрутов по
умолчанию, запрет production, cookie/bearer, CSRF, отозванная сессия, блокировка
аккаунта, чужие ID, строгий ввод, история, явный выбор, CAS, replay, квоты,
readiness, безопасный 500 и отсутствие новых XP/AI/согласий.

DB-набор на одноразовом PostgreSQL **17.11** — **87 PASS, 0 FAIL, 0 SKIP**
в каждом из двух финальных последовательных прогонов на одном тестовом кластере.
После каждого прогона оставшихся тестовых/runtime-ролей — **0**.
Реальное ожидание owner lock проверено для гонок последнего слота и восстановления.
`EXPLAIN (ANALYZE, BUFFERS)` на 3 001 синтетическом брифе/множестве владельцев
подтвердил существующие индексы списка/квот/истории без принудительных настроек
планировщика. Это проверка формы доступа, не нагрузочная приёмка CG-063 или SLA.

API-набор на отдельном одноразовом PostgreSQL **17.11** — **128 PASS,
0 FAIL, 0 SKIP**, включая восемь новых HTTP-сценариев с ограниченными ролями.
Readiness-тест также проверяет отсутствие миграционной записи, совпадающий
checksum при отсутствующей колонке и роль с лишним CREATEDB. Изменение прав
обнаруживается следующим запросом, не требует перезапуска API.

На PGlite DB-набор — **78 PASS, 3 SKIP, 0 FAIL**: пропущены только реальные
гонки восстановления, последнего слота квоты и проверка планов PostgreSQL.
Contracts — **66/66**, config — **13/13**. Эти memory skips не выдаются за
доказательство блокировок или выбранных индексов.

Полный `pnpm check` — PASS: lint/types, unit/integration, окружения,
контейнерные/release scripts, сборка всех приложений и startup. В общем
memory/Windows-прогоне пять ожидаемых skips: три DB PostgreSQL-only, один API
CG-009 PostgreSQL-only и один Linux-only env. API на PGlite — **127 PASS,
1 SKIP, 0 FAIL**; env — **17 PASS, 1 SKIP, 0 FAIL**; контейнерные scripts —
**38/38**, release scripts — **23/23**, startup — **5/5**.
Prettier всех изменённых/новых TS/JS/Markdown-файлов, `git diff --check` и
**222 относительные ссылки семи Markdown-файлов** — PASS.

Использованы Node **24.11.1**, pnpm **10.15.0**, очищенное окружение без ключей.
Временные PostgreSQL-контейнеры имели loopback-порты, tmpfs и никаких host mounts;
после прогонов удалены только эти контейнеры с вымышленными данными.

Для повторения на установленном закреплённом toolchain:

```sh
pnpm exec turbo run build lint typecheck test --filter=@citygo/contracts --filter=@citygo/config --filter=@citygo/db --filter=@citygo/api --concurrency=3
pnpm check
```

Без `TEST_DATABASE_URL` используются PGlite и явные PostgreSQL-only skips.
Для DB/API проверок настоящего PostgreSQL задавайте только URL **отдельного
одноразового тестового кластера** с разрешёнными временными базами/ролями,
после подготовки build зависимостей. Нельзя передавать URL рабочей БД.
Модельные ключи и пользовательские `.env` не требуются.

Полный Docker image smoke, Playwright, Expo/устройство, live AI и серверная
проверка в этот инкремент не входят. Миграция/модуль v1/fixtures v1 не менялись,
новых зависимостей нет. GitHub checks и deployment нельзя считать пройденными
по локальному результату: их оценивают отдельно по опубликованному SHA.

## Дальнейшая работа

До реальной активации: принять policy CG-018 и Unicode N3, оформить рабочие
минимальные права и release gate, согласовать лимиты/допуск/нагрузку.
Далее — первый план без обязательной полной анкеты и без повторного награждаемого
плана, связи user quest, полезный starterPlan/чеклист, зависимости, предложения,
provenance и подтверждение конкретной ревизии. Затем CG-013/014 и общая E2E-приёмка.
Первую пользу нельзя подменять требованием заполнить все поля брифа.
