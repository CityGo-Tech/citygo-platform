# Синтетическое хранение решений и повторных команд R1

**CG-018D, 5 октября 2026. Локальный инкремент, не поставлен в main.**
Добавлено SQL-хранилище вымышленных решений поверх
[проверяющего слоя CG-018C](cg-018-permission-planner.md). Запись решения и
журнала атомарна; повтор успешной команды возвращает сохранённую квитанцию.
Гонки проверены на отдельном PostgreSQL. Это не новые действующие согласия,
не HTTP API и не допуск пользователя или данных к реальной модели.

## Изоляция от работающего приложения

[Хранилище](../../apps/api/src/r1-permission-store.ts) в CG-018D не импортировалось
`app`, `server` или роутами. Позднее [CG-018E](cg-018-permission-http.md) добавил
явный test-only HTTP harness; обычный server и production его не активируют.
Следующий [CG-018F](cg-018-permission-current.md) добавил согласованное собственное
чтение через `FOR SHARE` и strict snapshot, не использование квитанции как допуска AI.
Актуальные исправления после независимого ревью и общий прогон описаны в
[отдельном отчёте B–F](cg-018-permission-review-fixes.md).
Хранилище требует явного режима `synthetic_only` и
предварительно созданной тестовой схемы. [SQL-фикстура](../../apps/api/src/fixtures/r1-permissions-synthetic.sql)
находится вне каталога миграций; обычные migrate, release и deploy её не применяют.
Нет ссылок на реальные users, AI-согласия, финансовые или жилищные таблицы.
Зависимости, ключи, runtime-настройки и рабочие данные не изменены.

`authenticatedOwnerId` передаёт доверенный вызывающий код, а не тело команды.
Сервис проверяет форму identity и изолирует записи по ней, но **не проверяет
сессию**. Флаг режима и имя тестовой схемы не заменяют auth, безопасное окружение
или ограниченные роли. SQL-фикстура и её привилегированный тестовый пользователь
не предназначены для подключения к production.

## Устройство хранения

| Таблица в `cg018_synthetic` | Назначение                                                                                              |
| --------------------------- | ------------------------------------------------------------------------------------------------------- |
| `notices`                   | Неизменяемый словарь полных тестовых текстов по области и версии; изменение текста требует новой версии |
| `configurations`            | История явно выбранных редакций и маршрута, включая статусы fixtures                                    |
| `runtime`                   | Текущая ревизия конфигурации, максимальная использованная ревизия маршрута и строка блокировки          |
| `commands`                  | Успешные команды, fingerprint, event ID, ревизия результата, ссылка на конфигурацию и время БД          |
| `decisions`                 | Указатель текущего решения отдельно для владельца и области                                             |

Первичный ключ повтора — `(owner_id, scope, request_id)`. UUID нормализуется
по регистру; порядок свойств не меняет fingerprint. Один request ID другого
владельца или другой области не раскрывает и не возвращает чужую квитанцию.
Составной внешний ключ связывает текущее решение с его собственным событием;
уникальность ревизии не допускает двух результатов одной ревизии.

История конфигураций сохраняет полный показанный тестовый текст, а не только
«последнюю политику». Изменение статуса fixture не переписывает текст. Проверка
словаря запрещает менять тело под прежней областью/версией **между** конфигурациями,
а не только внутри одного объекта реестра. Update/delete-триггеры истории —
инвариант disposable-фикстуры, **не** выбранная политика хранения персональных
данных. Удаление всей тестовой БД очищает фикстуру; реальный lifecycle ещё не создан.

## Транзакция и повтор

Команда сначала проходит строгий синтаксический разбор. Затем короткая транзакция
блокирует единственную строку `runtime` через `FOR UPDATE`. Эту же строку первой
блокирует замена тестовой конфигурации: все записи следуют одному порядку.
Внешних запросов или модельного I/O внутри транзакции нет. Свойства PostgreSQL
row locks сверены с [официальной документацией](https://www.postgresql.org/docs/17/explicit-locking.html#LOCKING-ROWS).

Под блокировкой сначала проверяется целостность указателей конфигурации/маршрута
и собственных решений относительно их истории, затем журнал успешных команд.
Совпадающий повтор
возвращает исходные event ID, ревизию и время даже после отзыва или смены маршрута.
Иное содержимое под прежним ключом даёт `REQUEST_ID_REUSED`. Квитанция исторична:
старый grant из неё не означает, что разрешение действует сейчас.

Для новой команды читается актуальное решение, проверяются ревизия и, для grant,
выбранный текст/статус/маршрут. Revoke не требует чтения тела текущей политики или
принятия новой редакции. После проверки журнал и указатель решения записываются
в одной транзакции. Время назначает БД; клиент не может его подставить.
Проверочные отказы не создают событие и не занимают request ID.

Замена конфигурации также использует сравнение ожидаемой ревизии. Новый маршрут
должен получить новую ревизию; отключение и повторное включение не позволяют
переиспользовать старую. Это защита от возврата к старому состоянию с прежней
ревизией, не изменение действующего выбора провайдера.

После независимого ревью также запрещено вновь выбирать approved-версию,
ранее снятую, заменённую или пониженную из approved. Возврат через draft не
обходит запрет. Первая draft → approved разрешена; после снятия нужны новая
версия и явный новый grant, не возвращение прежнего решения.

Если связь с БД потеряна около commit, ответ имеет статус `unconfirmed` и код
`STORAGE_UNAVAILABLE`. Он **не доказывает откат**. Для команды нужно повторить
те же request ID и содержимое; создавать новую команду для «восстановления» нельзя.
Для неподтверждённой замены конфигурации сначала требуется сверить её сохранённое
состояние: отдельного журнала повторов этой доверенной операции пока нет.
Ошибки не включают SQL, строки подключения, тексты политики или входные данные.

В актуальном коде локальный wrapper различает стадии транзакции. До успешного
завершения callback COMMIT не достигнут: ошибка целостности возвращает
`rejected / STORED_DATA_INVALID`, иной технический отказ —
`rejected / WRITE_NOT_COMMITTED`. После завершения callback ошибка COMMIT/ack
остаётся `unconfirmed`, независимо от кода исключения. Общий DB-driver не менялся.

## Выполненные проверки

На этапе D 5 октября общий API-suite выполнен последовательно:
**162 теста, 161 pass, 0 fail, 1 skip**. Пропущен существующий PostgreSQL-сценарий
CG-009, которому нужен отдельный `TEST_DATABASE_URL`; launcher намеренно его
удаляет. Новый CG-018 PostgreSQL opt-in выполнен отдельно, без пропусков.
Typecheck и lint API также прошли. Это проверка совместимости существующего
API и нового внутреннего слоя, не новый HTTP-путь, E2E или live AI.

[Тесты PGlite](../../apps/api/src/r1-permission-store.test.ts) — 17 новых сценариев:
запись и повтор, изоляция, CAS, смена текста/маршрута, отзыв, повреждённые записи,
ошибки до записи, откат после каждого INSERT, потеря ответа после commit,
атомарная конфигурация, внешние ключи и неизменяемость истории.
Они всегда создают БД в памяти и не читают `TEST_DATABASE_URL` или `.env`.

[Отдельный opt-in PostgreSQL-тест](../../apps/api/src/r1-permission-store.pg-check.ts)
не имеет суффикса `.test.ts` и не запускается обычным API-suite. С разрешения
владельца выполнен на `postgres:17-alpine` в контейнере
`citygo-cg018-synthetic-test`, tmpfs и `127.0.0.1:55438`: **9 pass, 0 fail**.
Проверены одновременные одинаковые и несовпадающие повторы, оба порядка
grant/revoke, смена маршрута/снятие политики до grant, grant до смены маршрута,
конкурентная конфигурация и rollback. В восьми гонках отдельно наблюдался
блокирующий PostgreSQL PID; один `Promise.all` не считается доказательством.

Каждый PostgreSQL-тест создаёт и удаляет только новую БД с префиксом
`cg018_case_`. Тестовая авторизация фиксированная и вымышленная, предназначена
только для одноразового локального контейнера. Порт, пользователь и контрольная
БД закреплены в opt-in файле; рабочую строку подключения туда подставлять нельзя.
Контейнер после проверки удалён по проверенным ID/имени/labels. Из tmpfs удалены
только невосстановимые синтетические данные, не пользовательские записи.

Локальные команды через закреплённые Node 24.11.1/pnpm 10.15.0:

```powershell
node .local/handoff/pnpm-safe.mjs --filter @citygo/api typecheck
node .local/handoff/pnpm-safe.mjs --filter @citygo/api lint
node .local/handoff/pnpm-safe.mjs --filter @citygo/api exec node --import tsx --test --test-concurrency=1 src/**/*.test.ts
```

PostgreSQL opt-in запускается отдельно **только после разрешённого создания
точного disposable-контура**:

```powershell
node .local/handoff/pnpm-safe.mjs --filter @citygo/api exec node --import tsx --test --test-concurrency=1 src/r1-permission-store.pg-check.ts
```

Launcher — локальный служебный файл, не зависимость приложения. Тестовые команды
выполнялись вне песочницы из-за ранее проверенного ограничения загрузчика `tsx`;
Docker API также требовал доступ вне песочницы. Настройки Docker не менялись.

## Ограничения и следующий шаг

Одна глобальная блокировка выбрана для маленькой синтетической фикстуры, не для
масштабируемого production-хранилища. Нагрузку, отсутствие starvation и права
runtime-роли эти тесты не доказывают. Нет HTTP, auth/CSRF, rate/storage quotas,
публичного чтения актуального состояния и проверки разрешения перед реальным AI.
Текущие согласия не мигрировали и не переоценивались.

Позднее [CG-018E](cg-018-permission-http.md) локально добавил изолированные
readiness/права и HTTP-команды с настоящими тестовыми сессиями, независимым
отзывом, квотами и безопасной обработкой `unconfirmed`. Это отдельный набор
проверок, не расширение приведённого выше PostgreSQL-отчёта CG-018D.
Перед реальными людьми отдельно нужны принятые тексты/основания,
получатели и lifecycle из [карты обработки](../security/r1-processing-map.md).
Сроки 7/30/24 не приняты и не включены. CG-018, Unicode N3 и CG-028 не закрыты.
Публикация отдельной ветки и PR не активирует реальную обработку.
Слияние, production-миграция и deploy не выполнялись.
