# Синтетический HTTP слой разрешений R1

**CG-018E, 5 октября 2026. Локальный инкремент, не поставлен в main.**
Добавлен тестовый HTTP-обработчик раздельных команд поверх
[хранилища CG-018D](cg-018-permission-store.md): проверка сессии и владельца,
защита cookie-запросов, проверка прав БД и ограничение числа записей.
Это **не действующий endpoint согласий**, не публикация юридических текстов
и не разрешение отправлять реальные данные модели.

Этот документ описывает этап E; актуальные дополнения F и исправления ревью —
в [отчёте B–F](cg-018-permission-review-fixes.md). Числа ниже в разделе проверок
сохранены как результаты этапа E, не последнего общего запуска.

## Как включается тестовый обработчик

[buildApp](../../apps/api/src/app.ts) регистрирует
`POST /v1/synthetic/permissions/commands` только при явной передаче
`syntheticPermissions`, одновременно `NODE_ENV: test` и `testing: true`.
В обычном запуске маршрут отсутствует. Development и production отклоняют
такую опцию даже при переданной напрямую конфигурации. Нет переменной
окружения, переключателя в admin или подключения в server/deploy.

SQL-схема и [отдельные grants](../../apps/api/src/fixtures/r1-permissions-synthetic-grants.sql)
создаются только тестовым harness. Обычные миграции их не применяют.
Существующие сессии, AI-согласия, провайдеры, деньги, XP и жилищные данные
не переопределяются. Передавать сюда production-БД нельзя: имя схемы и флаг
не обеспечивают физическую изоляцию сами по себе.

## Что проверяется при команде

[HTTP-модуль](../../apps/api/src/r1-permission-http.ts) получает identity через
существующий серверный поиск сессии: bearer либо HttpOnly cookie. Просроченные,
удалённые сессии и заблокированные пользователи отклоняются. Owner ID не берётся
из тела, query или пользовательского заголовка. Команда разбирается строгими
схемами; дополнительные owner/timestamp/approval-поля запрещены.

Cookie-запись требует точный настроенный Origin. Заголовок
`x-citygo-client: native` не освобождает её от этой проверки. Bearer-клиент
может не присылать Origin, но явный чужой Origin отклоняется и для bearer.
Это дополнительная защита **нового маршрута**; общий legacy CSRF-hook
не изменён и требует отдельного ревью. Контрактный заголовок, no-store,
ограничение размера тела и обработчик ошибок остаются общими с API.

Подлинная сессия проверяется перед транзакцией команды. Этот инкремент
не вводит атомарную блокировку между отзывом сессии/блокировкой пользователя
и уже допущенной командой. Такой race, как и полноценное управление
сессиями, не считается закрытым.

## Readiness и права БД

[Readiness](../../apps/api/src/r1-permission-access.ts) выполняется без кеша
в той же закреплённой транзакции и под той же effective role, что и запись.
Проверяются таблицы/колонки, точные определения PK/UNIQUE/FK, валидность
индексов и включённые history-триггеры с invoker-функцией. Не проверяется
полный fingerprint всей DDL, CHECK/default/type-семантика или доверие к
владельцу схемы; это не production security-аудит.

Роль не должна быть superuser, иметь CREATE ROLE/DB, BYPASSRLS,
CREATE схемы или любое членство в другой роли, в том числе NOINHERIT и `SET FALSE`.
Это flat-role правило только этой disposable-фикстуры. Дополнительно проверяются
владельцы таблиц, схемы и функции истории. Ей выдаются:

- SELECT пяти тестовых таблиц;
- INSERT колонок команды без клиентского времени и INSERT решения;
- UPDATE только revision/event ID решения;
- UPDATE только id строки runtime для `SELECT FOR UPDATE`, не настроек маршрута.

Блокировка требует UPDATE хотя бы одной колонки таблицы —
[документация PostgreSQL 17](https://www.postgresql.org/docs/17/sql-select.html).
Нет изменения dictionary/configuration/history, удаления, TRUNCATE,
REFERENCES/TRIGGER/MAINTAIN или прямого EXECUTE функции истории. MAINTAIN также
даёт возможность блокировать таблицу, поэтому избыточен для этого обработчика
([права PostgreSQL 17](https://www.postgresql.org/docs/17/ddl-priv.html)).
Колоночный REFERENCES проверяется отдельно на всех пяти таблицах.
Недостаточные **и лишние права из проверяемого списка в этой схеме** дают
безопасный `STORE_NOT_READY` до записи. Это не проверка любых прав во всей БД.

В схеме допускается только одна ожидаемая invoker trigger-функция `keep_history()`
без аргументов и доступного EXECUTE. Проверяются return type, настройки и точный
OID функции у history-триггеров. Лишние routines, SECURITY DEFINER и перегрузки
отклоняются, даже если EXECUTE уже отозван. У всех трёх history-триггеров также
должны отсутствовать `WHEN` (`tgqual IS NULL`) и список `UPDATE OF`
(`cardinality(tgattr::int2[]) = 0`), иначе защита истории условна или неполна
([каталог PostgreSQL 17](https://www.postgresql.org/docs/17/catalog-pg-trigger.html)).
Оба ослабления проверены отдельно на каждой таблице. Прямое владение схемой,
таблицей commands или функцией отдельно отклоняется и при узких обычных правах,
без членства в других ролях. Полный fingerprint тела функции,
доступные функции других схем и все DDL-возможности не проверяются.

Проверяется effective role, а не надёжность login-роли пула. Harness использует
привилегированную связь для создания только вымышленных fixtures и `SET LOCAL
ROLE` для запросов приложения. Для реального запуска нужны отдельный ограниченный
login, аудит членства/владельцев/доступных функций и production-миграция.
`RESET ROLE` привилегированного harness login остаётся возможным; тестовая
effective-role не превращает такой login в безопасный production-пул.

## Квоты и отзыв

Тестовый лимит — по умолчанию **128 новых успешных команд на владельца**,
общий для двух областей, сессий и экземпляров обработчика. В harness можно
явно задать 1–1000. Это не политика хранения, не лимит рублей и не условие
допуска реального участника. Подсчёт выполняется под общей блокировкой runtime
в транзакции журнала/решения; перезапуск обработчика не обнуляет счётчик.

Сохранённый повтор проверяется раньше квоты и не занимает новую запись.
При заполнении квоты нельзя выдавать новые grants, но можно снять уже
выданный grant независимо в каждой области. Для этого оставлены максимум
две дополнительные записи. После снятия повторный revoke с новым request ID
при заполненной квоте отклоняется: история ограничена `лимит + 2`, а не
растёт из бесконечных отзывов уже снятого разрешения. Идентичный повтор
успешного revoke остаётся доступен. Отклонённые команды квоту не занимают.

Отдельный HTTP rate limit — 60 запросов в минуту по IP. Он включает повторы
и отзывы, поэтому временно может задержать их при превышении; резерв записей
не обещает обход защиты от спама. Это процессный limiter существующего плагина,
не общий счётчик между репликами. Общего лимита всех synthetic-владельцев,
нагрузочной проверки и доказательства отсутствия starvation пока нет.

## Ответы и неизвестный результат записи

| Ответ                                                          | Значение                                                                                  |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| 200 `synthetic_recorded`                                       | Записана тестовая команда либо возвращена исходная квитанция; `replayed` различает случаи |
| 400 `INVALID_COMMAND`                                          | Тело не соответствует строгому контракту                                                  |
| 409 с кодом проверки                                           | Конфликт request ID, ревизии, уведомления или маршрута; записи нет                        |
| 429 `STORAGE_QUOTA_EXCEEDED`                                   | Нет разрешённого нового места в журнале                                                   |
| 503 `rejected / STORE_NOT_READY`                               | Guard не допустил запись; роли/схема не готовы                                            |
| 503 `rejected / STORED_DATA_INVALID`                           | Хранилище вернуло некорректные данные; допуск запрещён                                    |
| 503 `rejected / WRITE_NOT_COMMITTED`                           | Технический отказ до завершения callback транзакции; COMMIT не достигнут                  |
| 503 `unconfirmed / STORAGE_UNAVAILABLE`, `retry: same_command` | Результат commit неизвестен; повторить те же request ID и содержимое                      |

Для auth/CSRF, версии контракта, слишком большого тела и rate limit используется
обычная error-envelope API. Новые специфические ответы пока не включены в
Web/Expo API-клиент и не являются новым production-протоколом.
SQL, роль, токены, уведомления и исходные данные в ошибку не включаются.
Квитанция остаётся исторической: повтор старого grant после revoke не означает
актуального разрешения. Публичного чтения текущего решения/уведомлений,
истории и административного переключения конфигурации пока нет.

## Проверки

[HTTP-тесты](../../apps/api/src/r1-permission-http.test.ts) с настоящими
тестовыми сессиями и ограниченной effective role: **13 pass, 0 fail** на PGlite.
Все fixtures создаются в памяти, без `.env`, `TEST_DATABASE_URL` и модельного I/O.
Проверены отсутствие маршрута/production guard, bearer/cookie, истёкшая и
отозванная сессия, блокировка, native-spoof, owner/scope isolation,
отсутствующие/лишние права, прямой SQL-запрет, повреждение ключа/триггера,
общая квота двух сессий, оба отзыва на пределе, replay, потеря ack после commit,
свежесть маршрута и IP rate limit. Нет событий в настоящих consent/AI/XP-таблицах.

Общий API-suite: **175 тестов, 174 pass, 0 fail, 1 skip**. Пропущен прежний
CG-009 PostgreSQL-тест, которому нужен `TEST_DATABASE_URL`; launcher намеренно
его удаляет. Это не live AI и не пользовательский E2E нового R1-пути.
Typecheck, lint, форматирование и `git diff --check` прошли.

С разрешения владельца [отдельный PostgreSQL opt-in](../../apps/api/src/r1-permission-http.pg-check.ts)
выполнен в `citygo-cg018-synthetic-test`, `postgres:17-alpine`, tmpfs,
`127.0.0.1:55438`: **3 новых HTTP-сценария** и повторно **9 сценариев хранилища**
CG-018D, без ошибок. Node отчитал 15 pass, включая три вложенных harness-проверки;
это 12 предметных сценариев, не 15 независимых проверок поведения.
Для новой гонки двух HTTP-команд на последнюю квоту отдельно наблюдалась
блокировка через `pg_blocking_pids`; проигравший получил 429, новая запись одна.
Проверены реальная ограниченная роль, запрет изменения конфигурации/истории,
повтор после отзыва, safe readiness и потеря ack после успешного commit.

Каждый opt-in создаёт и удаляет только новую БД `cg018_case_` и случайные
fixture-роли. Нет чтения окружения/секретов; тестовая строка подключения
содержит фиксированную вымышленную авторизацию disposable-контура.
После проверки осталось 0 тестовых БД/ролей; контейнер удалён по проверенным
ID/имени/labels. Удалены только невосстановимые синтетические tmpfs-данные.
Рабочие БД, сервер, контейнеры и настройки Docker не изменены.

```powershell
node .local/handoff/pnpm-safe.mjs --filter @citygo/api typecheck
node .local/handoff/pnpm-safe.mjs --filter @citygo/api lint
node .local/handoff/pnpm-safe.mjs --filter @citygo/api exec node --import tsx --test --test-concurrency=1 src/r1-permission-http.test.ts
```

Только после разрешённого создания точного disposable-контура:

```powershell
node .local/handoff/pnpm-safe.mjs --filter @citygo/api exec node --import tsx --test --test-concurrency=1 src/r1-permission-http.pg-check.ts src/r1-permission-store.pg-check.ts
```

Тестовый runner выполнялся вне песочницы из-за ранее проверенного ограничения
загрузчика `tsx`; Docker API также требовал доступ вне песочницы. Это не причина
менять toolchain или ослаблять изоляцию данных.

## Следующий инкремент

Сначала — owner-scoped чтение текущего решения и точно выбранного fixture-уведомления, строгие схемы
ответов и отрицательные тесты восстановления клиента. Историческая квитанция
не должна подменять актуальное состояние.

Это продолжение локально подготовлено в [CG-018F](cg-018-permission-current.md):
GET/строгие ответы, offline-контроллер и новые PostgreSQL-гонки. Числа выше
остаются результатами этапа E; свежий общий прогон приведён в отчёте F.
Web/Expo и реальные согласия по-прежнему не включены.

После приёмки N6/N7 локально доведены только тестовые фикстуры N8/N9:
восстановление полного ACL-снимка после direct-owner проверок, очистка
временных NOLOGIN-ролей через REASSIGN перед DROP OWNED RESTRICT и
сравнение replay/lookup с первым успешным ответом. Ошибка закрытия приложения
или одной роли не останавливает остальные попытки очистки; ошибки не скрываются.
Новый сценарий проверяет оставшегося владельца, частичный сбой cleanup и повтор
без потери истории на PGlite и PostgreSQL. Это не изменение HTTP/readiness,
не новая production-политика и не гарантия очистки при недоступной БД.
N8/N9 приняты независимым ревью в заявленных границах. Затем локально доведены
N10/N11: обе ошибки теста/восстановления сохраняются, cleanup привязан к
приватному реестру созданных ролей. Два новых общих сценария проверяют двойной
сбой и запреты для смешанного списка, другой фикстуры, LOGIN и current_user
на PGlite и PostgreSQL. HTTP/readiness и runner не менялись. Старые teardown
для notice-owner/review-writer и неизвестный исход CREATE не исправлялись.
N10/N11 приняты независимым ревью. По разрешению владельца локально исправлен
N12: отрицательный тест учитывает также вход в `transaction` и проверяет
срабатывание observer безопасной пробой без SQL. Очистка ролей не менялась;
N12 принят независимым read-only ревью Cursor в заявленных границах, без блокеров.
По N13 уточнено: проба проверяет учёт входа и возврат результата, а делегирование
подтверждено чтением кода. Это только правка документации. Результаты и ограничения —
в [отчёте исправлений](cg-018-permission-review-fixes.md).

Перед реальными участниками остаются согласованные тексты/основания,
получатели и lifecycle из [карты обработки](../security/r1-processing-map.md),
проверка возраста, отдельное production-исполнение, допуск AI и Web-путь.
Цели 7/30/24 не приняты и не реализованы. CG-018, Unicode N3 и CG-028 не закрыты.
Публикация отдельной ветки и PR не активирует реальную обработку.
Слияние, миграция сервера и deploy не выполнялись.
