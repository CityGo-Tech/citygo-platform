# Статус проекта

## Корректирующая итерация — 18 октября 2026

База кода — `main` после PR #82 (`6a900d7`). PR #82 слился: проверки не получили
hosted runner, а deploy был пропущен. Read-only проверка обнаружила на сервере
версию PR #81 (`34f0295`) и 12 миграций; это не ошибка push и не основание
откатывать миграции или защиту БД.

Принято владельцем: сохраняем серверную основу и переделываем пользовательский
путь по разговорному Figma. В отдельной ветке подготовлены регистрация от 6
символов, роли/смена пароля, закрытый одноразовый bootstrap и диалог без анкеты
для новых Web/Expo-аккаунтов. Миграция 0013 не создаёт пользователей автоматически.

В ветке PR #86 дополнительно подготовлен атомарный закрытый переход: прежние
логины/переписка удаляются, финансовые связи сохраняются с псевдонимизированными аккаунтами,
первый администратор создаётся с обязательной сменой пароля. Это операторский
инструмент с dry-run и blockers, не автоматический сброс при deployment.
[Порядок применения](runbooks/closed-account-restart.md).

Сервер этим изменением не обновлён, старые аккаунты/история не удалены, первичный администратор
не создан. Полный Figma ещё не реализован: нет пользовательских режимов моделей,
избранного, Bubble API и сохранения структурированных результатов из разговора.
[Границы и следующий порядок](implementation/conversation-restart.md).

Принят накопительный подход к знаниям: запуск без наполненной базы городов,
исследование пробелов, затем проверенные публичные факты и retrieval-first.
Политика отбора знаний готовится независимо от PR #86/#87; действующего
интернет-research, автопубликации и чтения такой базы в runtime ещё нет.
PR #87 содержит тарифную основу и план ×10/телефона/ЮKassa, не активные платежи.

## Короткий вывод

Есть работающий Web/Expo-прототип, серверная основа и инструменты эксплуатации.
**Закрытый пилот R1 ещё не завершён.** Следующий основной блок — превратить
принятые правила постепенной помощи в сохранённые результаты, интерфейс и
серверную проверку завершения: CG-012, CG-013, CG-014.

[Первый инкремент CG-012A](implementation/cg-012-answer-history.md) добавляет
частичные ответы и историю ревизий во внутреннем **неактивном хранилище**.
API, пользовательский путь и доступ runtime-ролей к новым таблицам не включены.
Слияние PR и применение миграции сами по себе не активируют этот сценарий;
факт развёртывания проверяется отдельно по релизу и серверу.
Он поставлен в PR #79. [CG-012B](implementation/cg-012-draft-recovery.md), поставленный в PR #80,
дополняет его поиском/восстановлением собственных черновиков и версионированным
чтением истории. Оба слоя остаются неактивными для HTTP/Web/Expo; схемы v1 и
серверное хранилище не означают готового нового пользовательского сценария.
[CG-012C](implementation/cg-012-safe-api.md) добавляет HTTP-слой только для
изолированных синтетических тестов: сессии/owner, readiness, ограниченные права,
квоты, восстановление и безопасные ошибки. Он выключен по умолчанию, запрещён
в production и не создаёт первый план без полной анкеты, полезный результат или XP.

Подготовлены [проект политики CG-018A](security/r1-data-policy-proposal.md)
и [offline Unicode preflight](implementation/cg-012-unicode-preflight.md).
Карта данных/ограничений подготовлена. Владелец принял 18+ и хранение
профиля/ответов/чатов/результатов до 90 дней без активности с более ранним
lifecycle по запросу удаления/концу пилота. Остальные сроки/исключения,
согласование существующей /legal и выполнение требований по уведомлениям открыты
(владелец подтвердил ИП; уведомление Роскомнадзору не подавалось);
export/delete и проверка возраста не реализованы. Совпадение трёх синтетических снимков с локальной
средой не закрывает Unicode N3. Оба допуска для реального API остаются открытыми задачами.

Подготовка CG-018 продолжена [картой потоков/получателей](security/r1-processing-map.md)
и [черновиками уведомлений/действий](security/r1-user-notices-draft.md).
Учтены публичные документы RouterAI. Read-only проверка кабинета Cloud.ru
5 октября подтвердила зону ВМ `ru.AZ-1` и регион API Object Storage `ru-central-1`;
адреса размещения, договорные условия, сроки исключений и тексты ещё требуют проверки/приёмки.
В [CG-018B](implementation/cg-018-permission-contracts.md) локально добавлены
кандидатные DTO отдельных grant/revoke и 11 тестов; обработчики, реестр утверждённых
текстов, export/delete и новые действующие согласия не реализованы.
В [CG-018C](implementation/cg-018-permission-planner.md) добавлены синтетический
реестр точных текстов и проверки отдельных команд: 17 новых unit-тестов,
owner/ревизии/маршрут и отзыв без новой политики. Сам C — чистый проверяющий слой;
позднее D/E/F используют его в synthetic harness, но не в AI admission.
`prepared` не является действующим разрешением.
[CG-018D](implementation/cg-018-permission-store.md) использует проверяющий слой
в отдельном синтетическом SQL-хранилище: решения/журнал, повтор исходной квитанции,
неизменные тексты и 9 прошедших PostgreSQL-тестов гонок/отката.
В самом D нет обычной миграции, runtime-прав или HTTP; последующие E/F добавляют
только тестовые права/HTTP, не допуск реальных данных. При неизвестном результате
commit возвращается `unconfirmed`, а не обещание отсутствия записи.
[CG-018E](implementation/cg-018-permission-http.md) локально добавляет test-only
HTTP-команду с настоящими тестовыми сессиями, owner/CSRF, readiness под той же
ролью и квотой журнала с резервом двух отзывов. В памяти прошли 13 HTTP-тестов;
на отдельном PostgreSQL — 3 новых HTTP-сценария и повторно 9 сценариев хранилища.
На этапе E в общем API-suite было 174 pass, 0 fail, 1 прежний PostgreSQL skip. Нет environment-флага,
включения в обычном server или production, реальных разрешений либо допуска AI.
[CG-018F](implementation/cg-018-permission-current.md) добавляет собственный GET
с точно выбранными fixture-текстами, строгие ответы и offline-восстановление
неопределённой команды. Историческая квитанция не становится текущим grant.
После независимого ревью исправлены B1/B2: терминальные версии уведомлений
и общая проверка указателей при GET/POST. Усилены recovery и проверки прав;
границы исправлений — в [отчёте](implementation/cg-018-permission-review-fixes.md).
Повторное независимое ревью приняло B1/B2/Z3/Z4 и Z2 в заявленных границах,
без блокеров. Следующее ревью приняло N1/Z6 в границах фикстуры и N4 по существу:
flat-role guard, колоночный REFERENCES, строгий инвентарь routines и регрессии.
Следующее независимое ревью приняло N6/N7: структуру триггеров, прямых владельцев
с узкими правами и недостающие повторы при повреждении указателей.
Следующее ревью приняло N8/N9: восстановление полного ACL-снимка, очистку
оставшегося владельца и сравнение с исходной квитанцией.
N10/N11 исправлены и приняты независимым ревью: диагностика двойного
сбоя, приватный реестр созданных ролей и отрицательные пути cleanup.
По разрешению владельца локально исправлен N12: observer отрицательного теста
учитывает `transaction`, проверяет его безопасной пробой и требует нулевого
прироста на отказных путях. N12 принят независимым read-only ревью Cursor
в заявленных границах, без блокеров. По N13 уточнена документация: проба
доказывает учёт входа и возврат результата, делегирование видно из кода.
Код, очистка ролей и runtime/readiness этой документальной правкой не менялись.
Текущий API-suite: **226 pass, 0 fail, 1 прежний skip**; contracts: **83 pass**.
Повторены 34 предметных PostgreSQL-сценария, включая 19 регрессий ревью и
наблюдаемые SHARE/UPDATE-блокировки; 59 TAP pass учитывают вложенные harness-проверки.
Есть 14 GET-тестов, 16 offline-тестов контроллера и 3 сквозных HTTP/PGlite-теста
восстановления. Эти результаты относятся к неизменённому тестовому снимку N12.
Контроллер не подключён к Web/Expo или сети;
снимок не является AI admission. Терминальное `close()` очищает только локальное
состояние экземпляра, не серверное разрешение/данные или внешний checkpoint.
Read-only lookup разрешает неопределённость только при найденной точной квитанции;
отсутствие записи не отменяет ещё работающий POST. Fencing и атомарная проверка
отзыва сессии внутри транзакции не реализованы; CG-018 целиком не закрыт.
Задание Cursor на N12 завершено и сохранено в отчёте F для истории;
N2/N3/N5 остаются ограничениями.
Новый R1-путь и CG-018 целиком не завершены.
Публичный GET RouterAI подтвердил запись `deepseek` с меткой `us`, но документация
неоднозначна о смене получателя на резервной попытке; вопросы поставщику дополнены.

## Что именно завершили CG-009 и CG-010

### CG-009 — принадлежность квеста плану

[PR #74](https://github.com/CityGo-Tech/citygo-platform/pull/74) добавил проверки
связей пользователь → план → квест и миграции `0010`/`0011`. Старые идентификаторы
и XP не заменяются новой историей. Ошибка устаревшего плана не должна обходиться
подстановкой другого ID. Подробности и тесты — [отчёт CG-009](implementation/cg-009-plan-ownership.md).

Это не механизм произвольного пересоздания планов и не готовое хранилище артефактов.

### CG-010 — что считать полезным жилищным результатом

[PR #75](https://github.com/CityGo-Tech/citygo-platform/pull/75) закрепил:

- помощь возможна до полной анкеты; бюджет, срок и тип жилья могут быть неизвестны;
- «не спрашивали», «не решил», «пропустил» и «сообщил значение» — разные состояния;
- предложения системы не становятся фактами без явного принятия;
- подтверждается конкретная ревизия результата, а не автоматически последняя;
- первые 60 XP — за полезный стартовый план с выбранным следующим шагом;
- вторые 60 XP — за подготовленный чеклист, **не за состоявшийся просмотр**;
- каждая награда — один раз на пользователя в рамках R1, даже при смене плана.

Последние правила должны быть реализованы сервером в CG-012/014. Сейчас в
рабочем сценарии защита повторного XP привязана к **экземпляру user quest**,
а не к будущему ключу `(user, awardScope, questSlug)`.

PR также исправил недетерминированную тестовую фикстуру резервного копирования.
У его финального head `3d95841` прошли
[CI](https://github.com/CityGo-Tech/citygo-platform/actions/runs/37184880439) и
[Container smoke](https://github.com/CityGo-Tech/citygo-platform/actions/runs/37184880437).
Это результаты проверок PR, не свидетельство нового production-deploy или
проверки качества жилищных советов. Полная спецификация — [CG-010](implementation/cg-010-housing-criteria.md).

## Что нельзя считать готовым

- Ввод нескольких ответов ещё не заменил старую обязательную анкету в интерфейсе.
- Сообщение AI ещё не является сохранённым брифом с проверенным происхождением.
- Запись handoff не означает, что оператор принял обращение или ответил.
- Имена инструментов в каталоге агентов не означают поиск реальных квартир,
  вакансий, билетов или отправку заявок партнёрам.
- В `main` нет принятого release-набора CG-025. Локальный подготовительный
  результат Cursor не считается поставленным и не закрывает оценку качества.
- Технический допуск провайдера, AI-согласие и общий бюджет — разные условия.
  Режим `routerai_at_cost` не поддерживает списание OpenAI/GigaChat.
- 500 ₽ — **разовый** приветственный бонус после подтверждения участника,
  не ежедневная выдача и не разрешение расходовать общий бюджет.
- Готовые Docker/runbook/CI не заменяют свежую проверку конкретного сервера,
  restore и готовности оператора.

## Как обновлять этот статус

После поставки очередной задачи измените строку таблицы, приложите PR/проверки
и укажите новую дату/базовый коммит. Разделяйте четыре утверждения:
**реализовано в коде → проверено → развёрнуто → принято для пилота**.
Если один из шагов не выполнен, пишите это прямо.

Следующая работа и условия R1: [план разработки](roadmap.md).
