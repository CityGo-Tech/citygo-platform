# Закрытое обновление сервера с 12 до 18 миграций

Цель — обновить схему и API/Web, сохранив сервис закрытым до проверки денег,
аккаунтов и пользовательского пути. Этот порядок **не выполняет обновление**:
конкретный target SHA, image digests, версия доверенного контроллера и approvals
заполняются только после зелёного CI выбранного выпуска.

На 18 октября 2026, 16:20 МСК сервер оставался на
`34f0295a7713c16473eb8409eff40e9304a58043`, с 12 миграциями,
выключенным AI и `autodeploy.enabled=false`. Main после слияния #89–92 —
`8763cda22188bfd88a4abb42158f5527a51f003f`, 18 миграций.
Это исходный снимок, не основание пропустить повторную live-проверку.

Readonly-проверка 18 октября в **16:51 МСК** подтвердила выключенный autodeploy,
отсутствие pending/controller-процессов, прежние IDs/images/StartedAt трёх
healthy-сервисов и свежесть backup. Архив/marker ниже повторно прочитаны из S3
и совпали с квитанцией; штатный monitor завершился успешно в 16:45:03 МСК.
Миграции, конфигурации, данные и расписания при этой проверке не менялись.

## Изменение схемы

| Миграция                      | Назначение                                                                 |
| ----------------------------- | -------------------------------------------------------------------------- |
| `0013_account_access.sql`     | Роли аккаунтов, логин администратора, обязательная смена временного пароля |
| `0014_citygo_credit.sql`      | Тариф ×10, журнал пополнений и сохранённый тариф попытки                   |
| `0015_yookassa_orders.sql`    | Только sandbox-заказы, разделение тестовых платежей и реального AI         |
| `0016_npd_receipts.sql`       | Реестр ручных НПД-чеков, передачи и корректировок                          |
| `0017_credit_source_lots.sql` | Источники средств, gift-first/FIFO, резервы и legacy-средства              |
| `0018_payment_refunds.sql`    | Денежный журнал возвратов и его неизменяемые события                       |

Первые 12 файлов и их checksums не менять. Миграции не сбрасывают данные,
не создают `admin/admin`, не включают бюджет и не начисляют бонусы. Старые
средства переходят в `legacy_nonrefundable`, не становятся оплачиваемыми
возвратными лотами. Сброс старых тестовых данных — отдельное разрешённое действие,
не часть этой процедуры.

## Допуск к подготовке

1. Получить свежие readonly сведения: source/images/StartedAt API, Web, PG;
   полный журнал из 12 миграций; policy off, оба lock свободны, pending отсутствует.
   Не считать успешный GitHub merge подтверждением серверной установки.
2. Проверить штатную зашифрованную копию и monitor; скачать из S3 архив и marker,
   сверить SHA256/размер/receipt. Сохранить доказательства восстановления
   предыдущей копии и доступность исходного age recovery key без вывода его значения.
   В закрытом окне, после остановки пишущих процессов и перед DDL, apply создаст
   новую предрелизную копию под непрерывным lock. Ошибка копирования оставит
   сервис закрытым, а не вернёт его автоматически в работу.
3. Закрепить полный target SHA после этого изменения, зелёные CI/container jobs,
   приватные immutable образы и проверенный release bundle. Никаких `latest`.
4. Убедиться в свободном диске/памяти, совместимости PG17 и отсутствии других
   обслуживающих операций. Не изменять PostgreSQL image/volume/данные хоста.

Последняя проверенная штатная копия в исходном снимке:
`20261018T130646Z-1bbfacbdf8834a1ea82ce276355598e4`,

## Доверенный контроллер

Установленная версия root-контроллера старше нового профиля. Её обновление
готовится отдельно от app bundle; Python кандидата не исполняется как root.
`install-autodeploy.py` предназначен для первой установки и отказывает при уже
существующих policy/user/sudoers — повторно запускать его на этой ВМ нельзя.

Перед заменой оператор должен:

- Проверить исходники и digest новой неизменяемой versioned directory контроллера,
  его unit-тесты и точные entrypoints; сохранить прежние пути, hashes и права.
- Сохранить policy, sudoers, authorized_keys и настройки scheduler без значений
  секретов в отчёте; проверить `visudo` и границы доступа service user.
- Под обоими locks повторить idle/pending/runtime проверки. Изменять только
  заранее определённые ссылки на доверенный controller; не включать policy.
- Оставить `enabled=false`. Новый профиль выбирается независимым startup approval,
  а не молчаливой подменой действующей standing authorization.

Автоматическая смена root-контроллера этим PR не реализуется. До отдельно
проверенной установки нового контроллера live plan/verify для v3 не готов.

## Конфигурация и разрешения

Подготовить новый защищённый API JSON по [профилю ×10](../runbooks/routerai-citygo-10x-profile.md):
`YOOKASSA_MODE=disabled`, без платёжных ключей. Не редактировать mount работающего API.
Предыдущий disabled JSON и вся evidence остаются на месте. Общий бюджет AI не
включать и не подменять его пользовательскими балансами.

Требуются четыре независимых одобрения, привязанные к конкретным байтам:

1. Preparation: current/target manifests, runtime inventory, ingress, проект.
2. Migration: точный переход 12 → 18, шесть checksums, grants и подготовленная копия.
3. Startup **v3**: `citygo-api-web-routerai-citygo-10x-v1`, hash API JSON,
   migration approval и web network; `allow_traffic:false`.
4. Finish: hashes startup/config/generation, закрытые traffic/Worker/restart.

Не генерировать действующие approvals из этой инструкции или синтетических
фикстур. Каждый файл хранится отдельно от request/state/bundles, имеет ограниченный
срок и может быть отозван. Полная схема request и flags —
[операторский порядок](../runbooks/release-operator.md).

## Выполнение после отдельного допуска

Использовать только доверенный `control.py`: `plan`, затем `verify`, затем
явно разрешённый `apply` со всеми пятью flags. `plan/verify` не проверяют live
готовность и не являются разрешением downtime. **Не использовать `autodeploy.apply`**:
он содержит последующее открытие трафика через resume.

Закрытый apply проверяет inventory и approvals, закрывает ingress, останавливает
API/Web и координирует Worker, создаёт зашифрованную копию, выполняет DDL и grants
одной ограниченной транзакцией роли `citygo_migrator`, запускает точные API/Web
образы и проверяет readiness без AI/платежей. После durable config/generation/active
возвращает `closed-release-committed`; ingress остаётся 503, Worker paused,
restart=no. PostgreSQL и сохранённые jobs не заменяются.

Проверить полный журнал из 18 checksums, migration receipt с шестью applied,
новый config/generation и hashes секретов, неизменный PG, API/Web IDs/images,
минимальные ACL, выключенные бюджет/ЮKassa, закрытый HTTPS/Worker и отсутствие
pending. Затем проверить новую резервную копию уже под новым fingerprint.
Открытие сервиса требует отдельного решения и готовности оплаты/аккаунтов.

## Ошибка и граница возврата

Ошибка до COMMIT должна оставить 12 миграций; это подтверждается журналом,
данными и ACL, а не отсутствием успешного вывода. При неизвестном результате
COMMIT не запускать мигратор повторно, не удалять pending и не восстанавливать
старый контейнер автоматически. Сначала сверить историю и сохранённую evidence.

После `0017` старый API PR #81 нельзя возвращать writer-ом: он не учитывает лоты
и allocations. Выбор — закрытый forward-fix либо отдельно разрешённое полное
восстановление согласованной пары БД/config/grants/runtime. SQL down-migration
или удаление новых таблиц на сервере не являются безопасным откатом.

Если прерывание произошло после записи новых config/generation/active, но до
удаления pending, допустим только предусмотренный `inspect-recovery` и новое
независимое разрешение `recover-commit`. Это завершение уже выполненной фиксации,
не повтор DDL, restore, restart или открытие трафика.

## Проверка на синтетических данных

`scripts/release-upgrade-12-smoke.mjs` вызывается только disposable pilot harness
до запуска API. Он проверяет собственные random project/volume и internal network,
единственный PG17 и пустую БД, затем воспроизводит схему из 12 миграций.
Существующий отдельный drill 9 → 18 сохраняется.

Точный drill 12 → 18 создаёт вымышленные auth/session/profile/quest/chat/R1/credit
записи. Поздняя ошибочная выдача прав проверяет rollback всех шести DDL вместе
с данными, журналом и ACL. Успешный production executor проверяет шесть applied
checksums, 18 записей истории, сохранность прежних данных, legacy-лоты и открытый
hold, узкие column ACL API и запреты Worker. Собственные fixture-записи удаляются
до следующих smoke-проверок.

Отдельный production API smoke использует dummy RouterAI key в internal-сети:
готовность, нулевой баланс, недоступные пополнение/подарок и нулевые расходы.
Полный протокол finish/recovery проверяется отдельно на неизменном журнале
18 → 18. Вместе эти проверки не являются live-тестом ключей, боевой оплаты,
полной end-to-end установкой 12 → 18 на сервере или разрешением открыть пилот.

## Результаты локальной проверки 18 октября

На Linux/Python 3.11 прошли 393 unit-теста контроллера; один systemd-тест,
пропущенный в контейнере без systemd, отдельно прошёл в WSL. Проверены новый
approval v3 и неизменность v1/v2, drift секретов до остановки, закрытые
finish/control/recovery и запрет платёжных credentials. JS container-тесты —
39/39, проверки публикации/release gates — 23/23, ESLint/Prettier/diff-check чистые.

На Docker Desktop с Linux-runner отдельно прошли точный PostgreSQL drill
12 → 18 и оба production runtime-профиля. Дополнительные закрытые циклы
выпуска/recovery и graceful restart используют журнал 18 → 18; они проверили
сохранность сессии/истории/XP, зашифрованное резервирование и закрытый ingress.
Хеши всех 15 изменённых code/fixture файлов совпали с тестируемой Linux-копией.
Облако использовалось только для readonly проверки существующей S3-копии;
все миграции и runtime-запуски этой репетиции были локальными и синтетическими.
