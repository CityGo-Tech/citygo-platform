## 1. Что где работает

Публичный адрес стенда: [pilot.ситиго.рф](https://pilot.xn--c1ajazlh.xn--p1ai/).
ASCII-форма домена для DNS/TLS — `pilot.xn--c1ajazlh.xn--p1ai`.
Доступность сайта не означает завершённый R1, включённый AI или разрешение
приглашать неограниченное число пользователей.

```text
Интернет / телефон
    │ HTTPS :443
    ▼
Nginx на Ubuntu ── 127.0.0.1:3000 ── Web (Next.js)
                                        │ /api/* → API :4000
                                        ▼
                                    API (Fastify) ── провайдер AI, если разрешён
                                        │ внутренняя Docker-сеть БД
                                        ▼
                                    PostgreSQL :5432

GitHub Actions ── приватный GHCR + ограниченный SSH ── root-контроллер выпуска
systemd timer ── pg_dump → age → приватное S3; очистка старых проверенных копий
```

ВМ Cloud.ru `citygo-pilot-01`: Ubuntu 24.04, исходная конфигурация Free Tier
2 vCPU / 4 ГБ RAM / 30 ГБ SSD. На хосте — Docker/Compose, Nginx, сертификаты,
контроллеры выпуска/копий и systemd timers. В постоянных контейнерах — Web,
API, PostgreSQL. Мигратор, backup и worker — служебные процессы; наличие
`worker` в Compose не означает включённое расписание его запуска.

ВМ скачивает готовые образы, а не собирает Node-приложение. GitHub runner на
ней не установлен как часть этого контура. PostgreSQL не перезапускается при
обычном обновлении Web/API.

### Сеть и ресурсы

- Внешний вход приложения — 80/443. HTTP перенаправляется на HTTPS.
- Web привязан только к `127.0.0.1:3000`; API 4000 и PostgreSQL 5432 не
  публикуются на хост. Expo/Metro 8081 не является сервером production.
- SSH 22 — административный канал. По решению владельца ограничение по IP
  не включали; ограничение **возможностей CI-ключа** — отдельная защита.
- Базовые контейнерные потолки RAM: PostgreSQL 1024 MiB, Web/API по 768 MiB,
  служебные jobs по 256 MiB. Это не результат нагрузочного теста.
- Docker-логи ограничены ротацией 3 × 10 MiB на сервис. Это не ограничивает
  все host-логи, образы Docker и размер данных БД.

Источники: [Compose-шаблон](../../deploy/compose.pilot.yml),
[PostgreSQL config](../../deploy/postgres/postgresql.conf),
[Nginx template](../../deploy/nginx/pilot.conf.template).
Runtime Compose генерируется контроллером; шаблон нельзя без проверки
подставлять вместо активного файла на сервере.

Не читать секретные JSON через `cat`, `docker inspect` без фильтра или
`docker compose config` в общий лог. Они могут раскрыть пароли, env и mounts.
Примеры ниже выводят только необходимые несекретные поля.

### Почему разные пароли и роли

API работает с данными без прав администратора; мигратор меняет схему;
worker выполняет разрешённое обслуживание; backup читает данные для dump.
Начальная настройка — [init.sql](../../deploy/postgres/init.sql),
runtime-grants — [grants.sql](../../deploy/postgres/grants.sql).
Init выполняется для пустого PG-volume, не при каждом restart.
Нельзя переинициализировать существующий volume ради изменения роли.

Секреты смонтированы только нужному сервису. Compose file secrets — не
шифрование на диске: безопасность зависит также от прав родительской папки
и файлов. Web/Expo/build не должны получать ключи AI или пароль БД.
[Подробное разделение окружений](../runbooks/service-environments.md).

## 3. Что происходит после merge/push в main

| Этап              | Где выполняется                                                              | Результат                                                                                                                       |
| ----------------- | ---------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------- |
| Проверки          | [CI](../../.github/workflows/ci.yml)                                         | Типы до сборки, `pnpm check`, PostgreSQL-тесты, E2E, mobile export, проверка утечки env                                         |
| Проверка поставки | [Container smoke](../../.github/workflows/container-smoke.yml)               | Контейнеры, ограниченные роли, миграции, ingress/drain, registry и Python-контроллеры на изолированных данных                   |
| Сборка кандидата  | `publish-candidate` в [Deploy main](../../.github/workflows/deploy-main.yml) | Ожидает успешные проверки точного SHA, собирает/проверяет три приватных образа, публикует digest и bundle                       |
| Запрос на выпуск  | `deploy` в том же workflow                                                   | Передаёт ограниченным SSH запрос с SHA, run/attempt и artifact ID                                                               |
| Проверка сервера  | Установленный root-контроллер                                                | Сверяет GitHub main, workflow, артефакт, хеши, pins, текущий контур, место и отсутствие незавершённой операции                  |
| Установка         | Сервер                                                                       | Pull образов → maintenance/drain → предрелизная зашифрованная копия → миграция → запуск → health/проверки → фиксация и открытие |

Образы: `citygo-platform-api`, `citygo-platform-web`, `citygo-platform-jobs`
в приватном GHCR организации. Выпуск привязан к immutable digest, не к `latest`.
Миграции выполняются отдельной ролью. Старые миграции не должны меняться.

Выпуски сериализованы (`cancel-in-progress: false`). Новый push не обрывает
начатую миграцию. Ожидающий устаревший SHA не должен подменять актуальный `main`.
Короткое окно недоступности предусмотрено: это не zero-downtime deploy.

Зелёный CI или опубликованные образы — ещё не успешное развёртывание.
Проверяйте job `deploy`, совпадение SHA с серверным аудитом и HTTPS readiness.
Даже документационный merge запускает этот pipeline: path-фильтра для него нет.

### Где настраивается GitHub

В репозитории: **Settings → Secrets and variables → Actions**.

| Тип      | Имя                              | Значение/назначение                               |
| -------- | -------------------------------- | ------------------------------------------------- |
| Secret   | `CITYGO_DEPLOY_SSH_KEY`          | Приватная часть отдельного ограниченного CI-ключа |
| Variable | `CITYGO_AUTODEPLOY_ENABLED`      | `true` разрешает запуск автоматического выпуска   |
| Variable | `CITYGO_RELEASE_PUBLISH_ENABLED` | Разрешение публикации кандидата                   |
| Variable | `CITYGO_PACKAGE_SOURCES_CHECKED` | Подтверждение проверки источников пакетов         |
| Variable | `CITYGO_POSTGRES_IMAGE`          | Точный закреплённый digest образа PostgreSQL      |
| Variable | `CITYGO_DEPLOY_HOST`             | Проверенный адрес ВМ                              |
| Variable | `CITYGO_DEPLOY_USER`             | `citygo-deploy`                                   |
| Variable | `CITYGO_DEPLOY_KNOWN_HOSTS`      | Заранее проверенный SSH host key                  |

Временный `GITHUB_TOKEN` нужен контроллеру для чтения данных выпуска, не
сохраняется как постоянный токен ВМ. Для pull GHCR у сервера свой read-only
credential. Эти два доступа и CI-SSH-ключ — три разных назначения.

CI-пользователь не получает обычную SSH-консоль, PTY, forwarding или Docker socket:
только принудительную команду с узким sudo-допуском. Однако право изменять `main`
всё равно означает право выпускать код приложения и допустимые миграции.
Подробные ограничения и установка — [automatic-main-deployment](../runbooks/automatic-main-deployment.md).

### Что merge не обновляет автоматически

- Установленные root-контроллеры deploy/backup и их systemd units.
- DNS, сертификаты, конфигурацию Nginx и ОС.
- Серверные секреты, срок их действия и закреплённый образ PostgreSQL.
- Политику допуска нового AI-провайдера или бюджет по одному факту наличия ключа.

Изменение таких файлов в Git требует отдельной операторской процедуры.
Например, смена байтов `api.json` без согласованного обновления pins остановит
выпуск. Это защита от незаметного изменения окружения, не повод отключать проверку.

## 4. Резервные копии и место

Рабочая инструкция — [почасовые копии и retention](../runbooks/hourly-backup-retention.md).
Старый `schedule.py` — ограниченный пробный механизм; одновременно его включать
не нужно. Постоянная схема использует `routine.py` и отдельные timers:

- `citygo-backup-routine.timer` — каждый час в `:05`, задержка до 30 секунд.
- `citygo-backup-routine-check.timer` — контроль каждые 15 минут.
- `pg_dump → age → S3 → readback/SHA-256 → complete marker`.
- Очистка только после подтверждённой новой копии. Сохраняется объединение
  24 часовых, 7 дневных и 4 недельных точек UTC: максимум 35, минимум две при наличии.
- Локальные временные шифрованные dumps удаляются по завершении; приватного
  ключа расшифровки на ВМ нет. Оператор должен иметь отдельную офлайн-копию ключа.
- Общий lock не позволяет регулярной копии пересечься с критической стадией deploy.

Предохранители: минимум 8 GiB свободно для backup, до 1 GiB на dump;
регулярная загрузка останавливается при 40 завершённых снимках или 1 GiB уже
занятого префикса. Это не жёсткая квота всего бакета и не ограничение всех
ручных/предрелизных загрузок. Перед pull у deploy есть порог 4 GiB, после pull
требуется запас для backup.

Неизвестные объекты и сомнительные пары автоматически не удаляются. Versioned
objects/delete markers требуют отдельного разбора. Не расширять S3-роль до
администратора ради прохождения проверки. Docker-образы и данные PostgreSQL
этой ротацией не чистятся; за ними нужно следить отдельно.

Email сообщает об ошибке/несвежей копии и восстановлении, без пользовательских
данных. Монитор на той же ВМ не заметит её полного отключения. Readback доказывает
доставку байтов, но не восстановимость БД: нужен периодический отдельный
[restore drill](../runbooks/encrypted-backup.md).

## 5. Проверка состояния без изменения данных

Команды ниже — для уже авторизованной административной SSH-сессии на **нужной
ВМ**, не для CI-ключа. Не публикуйте сырой вывод с данными пользователей.
Здесь нет перезапусков, dump, модельных запросов или ручного запуска деплоя.

```sh
# HTTPS и миграционная готовность API; TLS-проверка остаётся включённой.
curl --fail --silent --show-error --max-time 15 https://pilot.xn--c1ajazlh.xn--p1ai/api/ready

# Сервисы и опубликованные порты, без раскрытия environment.
sudo docker ps --filter label=com.docker.compose.project=citygo-pilot \
  --format 'table {{.Names}}\t{{.Status}}\t{{.Ports}}'
df -h /
sudo docker system df
free -h

# Только несекретные поля активного release config.
sudo python3 -c 'import json; p=json.load(open("/etc/citygo/backup.json")); print(json.dumps({k:p[k] for k in ("source_sha","project","compose_file","compose_env")}, indent=2))'
sudo cat /var/lib/citygo-backup/autodeploy/current.json

# Расписание и последний результат.
systemctl list-timers 'citygo-backup-routine*' --all
systemctl show citygo-backup-routine.service -p Result -p ExecMainStatus
sudo cat /var/lib/citygo-backup-routine/last-run.json
systemctl list-timers certbot.timer --all
```

Ожидается: readiness `status: ok`, три healthy-контейнера, свежий результат копии
и отсутствие накопления временных dumps. Сравнивайте SHA с **завершённым**
`Deploy main`, не с последним коммитом, который ещё проверяется. Контроль диска
должен учитывать и будущий pull, и предрелизную копию.

Для подробной диагностики читайте нужный ограниченный фрагмент `journalctl` или
`docker logs`, предварительно оценив риск персональных данных. Не прикладывайте
полные JSON-конфиги, env или переписку пользователей в GitHub issues.

## 6. Если что-то пошло не так

| Симптом                                  | С чего начать                                                                                         | Чего не делать                                                      |
| ---------------------------------------- | ----------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------- |
| Красный CI/Container smoke               | Открыть упавший шаг для нужного SHA, воспроизвести на тестовых данных                                 | Не пропускать gate и не выкладывать образ вручную «в обход»         |
| Publisher зелёный, deploy красный        | Проверить job deploy и его короткий код отказа; сверить SHA, pending и pins                           | Не считать публикацию образа успешным релизом                       |
| Ошибка до maintenance                    | Старый сайт обычно продолжает работать; после устранения причины возможен полный re-run текущего main | Не перезапускать отдельно deploy с артефактом другого attempt       |
| Pending или ошибка после начала миграции | Проверить `autodeploy/pending.json`, `operation-pending.json`, аудит и receipts; далее ручной runbook | Не стирать маркер и не повторять миграцию наугад                    |
| HTTPS 503                                | Проверить maintenance/состояние выпуска и контейнеров                                                 | Не создавать `traffic-open` вручную, пока контур не проверен        |
| Сайт открыт, AI не отвечает              | Проверить server policy, согласие, routing, баланс/hold и production-допуск                           | Не включать dev, не добавлять ключ в Web, не обходить личный баланс |
| Копия старше двух часов/ошибка очистки   | Таймер, последний результат, lock/pending, диск, срок S3/SMTP credentials                             | Не удалять bucket/prefix по маске и не запускать второй scheduler   |
| Мало места                               | `df`, `docker system df`, размер release bundles и состояния; план адресной уборки                    | Не выполнять `docker system prune --volumes` или `compose down -v`  |
| Сертификат/домен недоступен              | DNS целевого поддомена, 80/443, Nginx и certbot timer                                                 | Не менять основной домен и не отключать проверку TLS                |

Автоматический rollback схемы БД не предусмотрен: предыдущий образ может быть
несовместим с новой схемой. Восстановление выполняется по
[операторскому порядку](../runbooks/release-operator.md), сначала с проверкой
копии в отдельной БД. Цели RPO/RTO не считать гарантией без измеренного учения.

Остановка **новых** выпусков — `CITYGO_AUTODEPLOY_ENABLED=false`; отзыв
серверного допуска — отдельное изменение `/etc/citygo/autodeploy.json` оператором.
Это не отменяет безопасно уже выполняющуюся миграцию. Сначала выясните стадию.

## 7. Как поддерживать документацию

При смене приложения обновляйте [статус](../project-status.md) и соответствующий
runbook. При смене инфраструктуры — эту карту, инструкции восстановления и
новую датированную запись проверки. Фиксируйте SHA, время, успешные проверки
и ограничения, а не секреты. Старые снимки сохраняйте как историю.

Для ежедневной работы достаточно этого руководства и трёх подробных процедур:
[deploy](../runbooks/automatic-main-deployment.md),
[копии](../runbooks/hourly-backup-retention.md),
[ручное восстановление/выпуск](../runbooks/release-operator.md).
