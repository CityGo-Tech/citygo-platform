CI-entrypoint, sudoers, ключей, policy или scheduler. Подготовленный локальный
пакет и четыре черновика не разрешают установку, миграции, запуск контейнеров
или открытие сервиса. Сначала требуется завершить проверку PR #95 и выбрать
окончательный опубликованный выпуск из main.

## Состав нового контроллера

Пакет включает только 13 модулей из `install-autodeploy.MODULES` и
`deploy/postgres/dump.sh`. Файлы читаются как данные, не импортируются и не
исполняются. Каждый файл и итоговый tar имеют SHA256; aggregate вычисляется
тем же алгоритмом, что при первоначальной установке.

По сравнению с установленными байтами в PR #95 меняются четыре файла:

| Файл            | Изменение                                                                                                                                                |
| --------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `start.py`      | Отдельный профиль ×10, approval v3, ЮKassa явно выключена                                                                                                |
| `autodeploy.py` | Распознавание v3; ранее принятые исправления формата opaque token и фиксированного имени lock                                                            |
| `image_gate.py` | Чтение optional Docker Labels у официального PG image; обязательные app labels и digest-проверки сохранены                                               |
| `prepare.py`    | Узкое исключение прежнего 30-секундного stop timeout только для исходного immutable bootstrap image; сам stop всё равно использует полный drain deadline |

Остальные десять файлов, включая `backup.py`, совпадают. Отдельный
`backup-routine` controller, notify, его конфиги, unit-файлы и timers не входят
в новый пакет и не заменяются. Материалы прежнего backup-инцидента сохраняются;
его repair повторно не выполняется.

## Локальный пакет без права установки

`deploy/controller_upgrade_plan.py` создаёт новый выходной каталог, не
перезаписывая существующий. Ему передаются путь к проверенному source tree,
readonly observation без секретных значений и, при необходимости, полный SHA
проверенного источника. SHA источника является утверждением оператора, не
криптографической аттестацией Git.

Создание пакета выполняется обычным пользователем в Linux/WSL, не под root.
Выходной каталог должен находиться в его приватном локальном хранилище.
Привилегированная серверная установка этим инструментом не поддерживается.

```sh
python3 -B deploy/controller_upgrade_plan.py \
  --source /absolute/path/to/reviewed-source \
  --observation /private/path/controller-observation.json \
  --source-sha <reviewed-40-hex-source-sha> \
  --output /private/path/new-controller-preparation
```

Команда не подключается к серверу, Docker, БД, GitHub или платёжным сервисам,
не читает файлы секретов по путям из observation и не создаёт активных approvals.
Пакет — не инструкция распаковать произвольный архив под root. Перед серверной
установкой оператор заново сверяет allowlist, hashes, метаданные и полномочия.

## Установка рядом с прежней версией

Этот этап остаётся отдельным разрешённым действием. До него новая версия не
считается установленной, даже если её локальная упаковка и CI успешны.

1. Сверить актуальные old controller/config/policy hashes и права с observation,
   проверить pending, отсутствие обслуживающих процессов и свежесть копии.
   Под обоими locks повторить проверку. Если работает штатный backup — ждать
   завершения, не останавливать его и не удалять lock/pending.
2. Сохранить защищённую evidence прежних bindings. Новую versioned directory
   создать эксклюзивно, без symlink/подмены предков. Записать только allowlisted
   проверенные bytes: каталоги root-owned 0755, файлы root-owned 0644,
   без group/world write; выполнить fsync и readback всех hashes.
3. Не изменять старую directory/initial-bundle, CI authorized_keys/sudoers,
   backup config, auto current pointer, policy и scheduler. Не создавать users,
   не выполнять `daemon-reload`, не запускать installer или autodeploy.
   При будущей установке отдельно снять и сверить `is-enabled` и symlinks
   включения timers: один `ActiveState=active` не доказывает запуск после reboot.
4. Снова проверить старые bindings/pending. Сохранить receipt с
   `activated:false`, `policy_changed:false`, `release_authorized:false`.
   Ошибка или частично созданная directory требует осмотра; не дописывать её
   автоматически и не переключать указатели ради завершения.

Для ручного выпуска владельцу не нужны новые полномочия CI-пользователя.
`install-autodeploy.py` — одноразовый installer, а не upgrade-инструмент:
он создаёт standing authorization и поэтому здесь не используется.

Ручной `control.py` запускается с проверенными флагами `-E -s -B` из
root-owned directory. Нельзя молча заменить их на `-I`: этот entrypoint,
в отличие от `autodeploy.py`, не добавляет собственную папку импорта.
Не разрешать generic Python или wildcard-команды в sudoers ради обхода.

## Четыре черновика разрешений

План имеет `kind: citygo-closed-release-draft`, `ready:false` и все полномочия
`false`. В каждом blueprint есть `draft:true`, неизвестные pins/время — `null`.
Такие файлы намеренно не принимаются штатными approval-парсерами.
Переименование файла или смена одного `allow`/`ready` не создаёт разрешения.

| Черновик       | Что связывается при последующем независимом утверждении                                                                             |
| -------------- | ----------------------------------------------------------------------------------------------------------------------------------- |
| Preparation v2 | Текущий 12-migration manifest, target artifact/main SHA/manifest/release ID, fingerprint config, реальные image IDs и retained jobs |
| Migration v1   | Hash точных активных байтов preparation, target manifest, config и database network                                                 |
| Startup v3     | Hash активного migration approval, новый API mount и web network; профиль ×10                                                       |
| Finish v1      | Hash активного startup approval, config file и generation; профиль `citygo-closed-release-v1`                                       |

Hashes черновиков не являются будущими pins активной цепочки. Сначала выбирается
конкретный выпуск, проверяются ключи и правила, затем независимо утверждаются
точные bytes и сроки каждого этапа. Последующие hashes пересчитываются по
**активным** предыдущим approvals. Traffic, Worker и restart остаются запрещены.

`control plan` ещё не подходит для пустого черновика: он уже требует три
действующих approvals. `autodeploy.stage_capabilities` тоже не является
планировщиком — он пишет активные полномочия и не используется при подготовке.

## Что блокирует действующие разрешения

- PR #95 ещё должен войти в main; CI и публикация проверяются заново на точном
  итоговом SHA. Прежние образы `8763…` не поддерживают новый marker.
- Нет проверенных target bundle/artifact/image digests и локального image readback.
- Новый контроллер ещё не установлен отдельным защищённым этапом.
- Нынешний API JSON содержит только `DATABASE_URL`. Для ×10 нужен **новый**
  защищённый JSON с реальным RouterAI key, независимо принятыми notice/policy ID,
  корректной DB-ролью, тарифом и `YOOKASSA_MODE=disabled`. Тестовую fixture
  вместо него не использовать; работающий mount не редактировать.
- Inventory/retained jobs/network IDs и окончательный generation hash требуют
  повторной live-сверки после фиксации target. Снимок не заменяет эту проверку.

Выпустить сначала disabled, а затем поменять профиль на том же SHA этим
контроллером нельзя: selection требует разных current/target source SHA.
Не обходить отсутствие нового конфига подменой env.

## После будущего закрытого выпуска

Следовать [порядку 12 → 18](closed-upgrade-12-to-18.md). Боевой ЮKassa transport,
бюджет, подарок, очистка данных и открытие сервиса в это разрешение не входят.

Ручной finish не обновляет `autodeploy/current.json`; прежняя standing policy
содержит disabled-профиль и старые secret pins. Нельзя просто вернуть
`enabled:true` после ручного выпуска. Для будущего автоматического режима
потребуется отдельная согласованная reconciliation/re-enrollment, а пока
policy и CI-точки входа сохраняются выключенными и неизменными.
