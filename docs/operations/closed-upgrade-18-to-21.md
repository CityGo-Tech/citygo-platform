# Закрытое обновление с 18 до 21 миграции

Обновление сохраняет серверную основу и добавляет три миграции для live ЮKassa,
расходов по балансу RouterAI и долговечной очереди уведомлений. Это не повтор
перехода 12 → 18 и не открытие платного пилота. Нужен
[отдельный runtime профиль v4](../runbooks/yookassa-routerai-live-profile.md).

При read-only проверке 18 октября 2026 сервер оставался на `7500266…`:
18 миграций, HTTPS maintenance 503, Worker остановлен, квоты запросов/попыток
нулевые, бюджет AI и ЮKassa выключены, standing autodeploy выключен.
Эта запись не заменяет новую проверку в момент выпуска.

## Точный переход

Первые 18 файлов должны совпадать с текущим manifest побайтно и с журналом
PostgreSQL по каноническим checksum. Разрешён только следующий суффикс:

| Миграция                              | Изменение                                                                  | Что не включается автоматически                              |
| ------------------------------------- | -------------------------------------------------------------------------- | ------------------------------------------------------------ |
| `0019_yookassa_live_orders.sql`       | Live-форма заказа и сохранение разделения test/real по фактическому режиму | Ключи, приём оплаты, снятие карантина                        |
| `0020_ai_budget_provider_balance.sql` | `fixed`/`routerai_balance`, nullable лимиты и безопасная граница счётчиков | Расходы, снятие старых лимитов, пополнение баланса           |
| `0021_payment_notifications.sql`      | Долговечная очередь и узкие права API                                      | Финансовые права Worker, расписание сверки, открытый webhook |

Синтетическая репетиция `scripts/release-upgrade-18-smoke.mjs` встроена в
Container smoke. Она допускает только собственные пустые PostgreSQL/volume/
internal network со случайным тестовым project. Проверяются ровно три миграции,
сохранность истории, заказов, резервов и лимитов, общий транзакционный откат
DDL/ACL/журнала при поздней ошибке и минимальные права ролей. Rewind и очистка
этой фикстуры **не являются командами для рабочего сервера**.

## Подготовка до любых остановок

1. Дождаться зелёных проверок PR #97 и PR с runtime-профилем. После отдельного
   согласования слияния получить точный main SHA, его новые main-проверки,
   manifest и проверенные неизменяемые образы. PR CI не разрешает выпуск.
2. Получить свежий metadata-only снимок текущего **закрытого** выпуска:
   actual manifest и БД на 18 миграциях, active-release профиль и hash API mount,
   выключенный standing policy, контроллер, образы, сеть, locks, сохранённые jobs,
   состояние backup timers. Не заменять actual manifest старым указателем
   standing autodeploy: после ручного выпуска он может относиться к прежнему SHA.
3. Подготовить offline-план явной командой:

   ```sh
   python3 deploy/controller_upgrade_plan.py \
     --transition 18-to-21 \
     --source /local/reviewed-checkout \
     --source-sha <full-reviewed-sha> \
     --observation /local/private/observation-v2.json \
     --output /local/private/new-18-to-21-plan
   ```

   Материализация выполняется непривилегированным POSIX-пользователем в новый
   каталог; исходники кандидата не импортируются. Нужен snapshot **v2** с
   отдельным `current_profile` и API metadata `source=active-release`,
   `matches_active_pin=true`. Значения ключей в снимок не входят. Старый v1
   и опущенный `--transition` не переопределяются: исторический default 12 → 18
   должен отказать на этом состоянии.

4. Отдельно проверить и разместить новый контроллер и API JSON как неактивные
   файлы. Сверить hash, владельца и права; не менять текущий mount, sudoers,
   CI-ключи, автодеплой, ingress или работающую версию на этапе подготовки.
5. Подтвердить штатное резервирование и свежую зашифрованную S3-копию с readback,
   manifest и доступностью восстановления. Копия до предыдущего выпуска
   не подменяет backup внутри нового окна остановленных writers.

План содержит только черновики: `draft=true`, все разрешения false,
`approved_at/expires_at=null`. Его hash не является hash будущих разрешений.
Инструмент не устанавливает контроллер, не создаёт действующие approvals и
не доказывает публикацию указанного оператором SHA.

## Отдельно разрешаемый закрытый выпуск

Нужны новые preparation → migration → startup v4 → finish approvals с точными
hash manifest, конфига, migration approval, API JSON, сетей и generation.
Разрешения 12 → 18 не переиспользуются. Сверить время действия после всех
последних чтений; при дрейфе или истечении остановиться.

Следовать [операторскому CLI](../runbooks/release-operator.md): сначала `plan`,
затем независимый finish approval и `verify`; только после отдельного разрешения
оператора — `apply` с точным набором флагов. В одном окне удерживаются барьеры,
проверяется остановка writers, создаётся backup, выполняются миграции с ACL,
стартуют API/Web и проверяются readiness/401 без создания аккаунтов, платежей
или AI-запросов. Finish сохраняет ingress 503, Worker paused, restart=no.

После выпуска проверить точный журнал 21, роли/ACL, сохранность данных,
профиль/hash mount и выключенный бюджет. Не включать `routerai_balance`,
платёжные операции или public traffic как побочный эффект этой проверки.
При сбое оставить закрытый барьер и собрать evidence; не повторять миграцию
вслепую и не запускать старую версию на изменённой схеме.

Публичный запуск и приёмка живых платежей/возвратов — следующий, отдельно
согласуемый этап. Реестр НПД и наличие ключа сами по себе этот этап не закрывают.
