# Порядок чата и резерв 5 ₽ CityGo

## Принятое решение

Этот шаг заменяет предложение о резерве 2 ₽ и уточняет предыдущую
[калибровку 60 ₽](ai-reserve-2026-10-21.md). Новое правило:

- в начале платного ответа удерживается **5 ₽ CityGo**, не 5 реальных ₽;
- после независимой сверки списывается **вся фактическая стоимость ×10**;
- если средств не хватает, остаток может стать отрицательным;
- новое пополнение зачисляется 1:1 и сначала погашает задолженность;
- подарок, если он отдельно разрешён и действительно выдан, расходуется
  раньше оплаченных средств. Подтверждение телефона этим шагом не подключается.

Пример: 5 ₽ → ответ стоимостью 8 ₽ CityGo → остаток −3 ₽ → подтверждённое
пополнение 100 ₽ → доступно 97 ₽. В журнале пополнение остаётся именно 100 ₽,
а стоимость ответа не списывается второй раз при погашении долга.

Это **частичное предварительное обеспечение с ограниченным долгом**, а не
полная предоплата и не обещание ответа за 5 ₽. Старый режим полного резерва
остаётся по умолчанию. Новое поведение требует явного runtime-профиля.

## Почему помощник отвечал на старый вопрос

`history()` выбирал строковое представление `id::text` и использовал
неквалифицированный `ORDER BY id`. PostgreSQL сортировал выходной текстовый
alias: `1, 10, 11, 2 … 9`. Ошибка влияла сразу на два места:

1. dashboard передавал Web/Mobile неверный порядок отображения;
2. API отбирал последние завершённые сообщения из уже неверно отсортированного
   массива, поэтому новый вопрос мог оказаться не последним в контексте ИИ.

Теперь SQL сортирует **исходный числовой `m.id`**, выбирает последние 100
сообщений нужного потока и возвращает их по возрастанию. API, как и прежде,
передаёт последние 20 завершённых сообщений. ID в контракте остаются строками:
JavaScript-сортировки через `Number` нет, точность bigint не теряется.

Старые сообщения, авторство, содержимое, метаданные и финансовые записи не
переписываются. Исправляется чтение; удалять историю для этого не требуется.

## Денежные ограничения

Новый режим `fixed5_overdraft` работает только с точным тарифом CityGo ×10.
5 ₽ — начальный резерв пользователя, а независимый потолок реальной попытки
сохраняется отдельно. Для нового режима он допускается только в пределах
0,5–6 реальных ₽. При принятом потолке 6 ₽ максимальное учтённое списание —
60 ₽ CityGo, максимальный необеспеченный остаток одной попытки — 55 ₽ CityGo.

Это границы внутреннего допуска и учёта, **не жёсткий лимит внешнего счёта
RouterAI**. При цене выше принятого реального потолка новые расходы
останавливаются; неизвестный результат нельзя объявить бесплатным.

До вызова должны атомарно выполниться проверки денег, источников, технических
квот и бюджета. Для нового запроса требуется не менее 5 ₽ доступного остатка,
погашенный долг и отсутствие незавершённого AI-резерва этого аккаунта. Новый
платный запрос не может накопить ещё один долг, пока предыдущий не сверен.
Это ограничение не отключает бесплатный запрос помощи человека.

Для превышения начальных 5 ₽ введены отдельные append-only записи долга и
погашения. Свободные источники покрывают его сразу: подарок, исторические
невозвратные средства, затем оплаченные лоты FIFO. Недостающая часть ждёт
подтверждённого пополнения. Старые попытки сохраняют прежний режим полного
резерва и собственные снимки тарифа/потолка. Оплаченный лот, сумма возврата и
его выделения никогда не становятся отрицательными.

Повторная квитанция, уведомление об оплате и сверка не создают повторного
списания или погашения. Отмена возврата/освобождение старого удержания сначала
делает освободившиеся средства доступными для уже существующего долга.

## Клиент и совместимость

Кабинет показывает отрицательный доступный остаток и отдельную задолженность,
объясняет, что 5 ₽ не являются окончательной ценой, и ведёт к существующему
пополнению без автоматического платежа. Положительные денежные поля и
проверки возвратов не ослаблены.

Новый Web/Mobile передаёт capability `creditReservationMode` из показанного
баланса. Включённый fixed5-сервер отклоняет платный запрос старого клиента
без этого признака до сохранения сообщения/квоты/попытки. Это техническая
совместимость, не замена согласия на передачу данных ИИ и не юридическая
сертификация условий сервиса. Старый мобильный bundle не умеет разбирать
отрицательный баланс: нужна новая сборка/экспорт, а не только серверный флаг.

## Подготовка безопасного обновления

На момент подготовки публичный сервер **не переключён**: там остаются
предыдущий выпуск, 23 миграции и полный резерв 60 ₽ CityGo. Проверки новых
сценариев выполняются только на синтетических данных.

Миграция `0024_ai_credit_overdraft.sql` добавляет новый учёт и сохраняет старые
режимы. Нельзя удалить прежние ограничения баланса без новых проверок долга.
API и Web должны обновляться совместно; технические разрешения выдаются
после миграции штатным `grants.sql`, без финансового доступа Worker.
После появления долга нельзя просто вернуть старый бинарник, рассчитанный на
схему 23 и неотрицательный баланс. При сбое нужен закрытый forward-fix либо
отдельно проверенное восстановление с учётом всех уже проведённых операций;
автоматический откат истории и денег не допускается.

Для нового режима предусмотрен отдельный закрытый startup-профиль **v7**:
`routerai-citygo-10x-yookassa-live-cn-fiscal-overdraft-v1`,
`AI_CREDIT_RESERVATION_MODE=fixed5_overdraft`. Профили v1–v6 не получают это
право автоматически. Название модели, country, ключи, прежний магазин,
фискальный профиль и ручной НПД-процесс не меняются. Постоянный автодеплой не
включается. Новый execution key требует свежего подтверждения денежного
правила: старое разрешение не превращается в согласие на частичную предоплату.

Перед выпуском нужны:

1. точный SHA, неизменный исходный снимок и полный Linux/Docker-прогон со
   всеми CI/Container smoke-проверками; локальные результаты не выдаются за
   GitHub Actions;
2. проверенные неизменяемые API/Web/Jobs-образы, отдельный migration-план
   **23 → 24**, приватный конфиг и новые разрешения preparation/start/finish;
3. свежая зашифрованная резервная копия с проверкой восстановления в отдельной
   временной БД; старый отчёт о копии не доказывает её текущую свежесть;
4. отдельное разрешение выпуска точного SHA, закрытие допуска/дренирование,
   штатный backup и миграция, затем readiness, проверка изоляции и учёта;
5. новая приёмка после переключения. Неизвестный результат выпуска оставляет
   доступ закрытым до разбора, без автоматического повтора или отката денег.

Текущее разрешение — **подготовить** обновление. Сам выпуск, миграция рабочей
БД, выдача подарков, новые настоящие оплаты и платные проверки этим документом
не объявляются выполненными. Старые release approvals не переиспользуются.

## Результаты проверок

На этапе подготовки выполнены:

- **39/39 проверок на настоящем локальном PostgreSQL**: числовой порядок,
  переход 23 → 24, прежние pending-резервы, точное ×10, долг/погашение,
  повторные уведомления и реальное ожидание блокировки между соединениями;
- **150/150 браузерных проверок без retries**: desktop и мобильная вёрстка,
  шесть последовательных ходов и перезагрузка, отрицательный остаток,
  бесплатная помощь человека, существующие сценарии оплаты;
- полный локальный `pnpm check`, TypeScript typecheck, сборка API/Web/Jobs,
  форматирование и diff-check;
- **67/67 защитных проверок** retirement/reset/SQL-grants: незакрытый долг
  блокирует retirement, любая долговая история блокирует destructive reset;
- независимое read-only ревью денежного учёта и отдельно истории/клиентов —
  блокеров в проверенных изменениях не найдено.

Временный PostgreSQL-контейнер с синтетическими данными удалён после проверки.
Ключи провайдеров не передавались, настоящих AI-запросов/платежей и изменений
сервера в этих проверках не было. Старые миграционные фикстуры исправлены для
честной подготовки исторической схемы; production-guards не отключаются.

Точный SHA и полный Linux/Docker-кандидат закрепляются отдельно после
замораживания исходников. Результат этого локального прогона не является
успешным GitHub Actions и не разрешает установку на сервер. Ранние RED-прогоны
порядка истории сохранены: они воспроизводили прежнюю ошибку, а не являлись
успешной приёмкой.

Первый точный Linux/Docker-прогон сохранился как неуспешный: Corepack не смог
скачать закреплённый pnpm при сборке образов. При проверке повторного запуска
также найдено устаревшее ожидание 23 миграций в основном Container smoke.
Оно исправлено на 24; добавлена ранняя регрессия, сравнивающая это ожидание
с полным списком SQL. Поэтому требуется новый SHA и новый полный набор
проверок. Старые успешные этапы не переносятся на изменённые исходники.

Финальная проверка ролей выявила ещё один блокирующий дефект выпуска: при
создании схемы настоящей ролью `citygo_migrator` штатный запрет `PUBLIC EXECUTE`
не позволял API вызывать `citygo_apply_credit_debt_repayments(bigint)`. Это
затрагивало допуск AI и invoker-триггер новых источников баланса даже без долга.
Прежние тесты прав создавали схему от superuser и не воспроизводили эти defaults.

В `grants.sql` добавлено только явное право исполнения этой функции для
`citygo_api`; Worker, backup и PUBLIC его не получают. Проверки должны создавать
миграции настоящей ролью migrator с теми же default privileges, затем выполнять
вызов и триггерные пути от роли API. Container smoke дополнительно проверяет
это на настоящем PostgreSQL. Исходники миграции 0024 и её checksum не меняются.
Кандидат `8e7ee2a` не устанавливается: для исправленного SHA нужны новые полные
проверки, образы, манифест и разрешения. Публичный сервер на схеме 23 не
переключался, чеки и существующий магазин ЮKassa не изменялись.
