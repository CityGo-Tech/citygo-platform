## Разбор сетевого сброса

В обычном прогоне `07e4a3b18594` сброс совпал с измеренным окном HUP:
`reusedSocket=true`, `ECONNRESET`, 0 отправленных байтов, нет заголовков ответа
и допуска в API. Nginx закрыл простаивавшее keep-alive соединение; клиентский
пул ещё не обработал закрытие и выбрал прежний сокет. Детерминированный тест с
задержкой клиентского event loop воспроизвёл тот же механизм одним GET, без
повтора. Свежий GET и ранее принятые POST/SSE завершились успешно.

Локальная запись байтов не равна допуску в API: отдельный контроль воспроизвёл
также вариант с локально записанными байтами, но без поступления запроса в API.
Счётчик server visits исключает скрытую повторную или позднюю доставку.
`keepalive_min_timeout 5s` используется только для тестового сравнения;
production-шаблон не меняется. Ограниченный таймаут не обещает сохранность
любого idle-соединения.

Отчёт сохраняет каждый сброс. Только reused GET тестового probe без заголовков
и тела ответа, с подтверждённым отсутствием допуска в API и временем внутри
наблюдаемого HUP попадает в `idleReuseResets`. Такой отчёт получает статус
`passed-with-idle-connection-closure`, а не утверждение «HTTP-ошибок нет».
Свежие соединения, POST/SSE, неизвестный допуск, ошибка принятого запроса и
любые другие сбои остаются провалом. Четыре теста защищают эту границу.
Повторов HTTP для сокрытия ошибок нет.

Для исторического `81ec102b8725` подробной телеметрии недостаточно. Объяснение
того сброса тем же механизмом — обоснованный вывод, а не восстановленный факт
о конкретном запросе. Его неуспешный журнал сохранён.

## Что проверено настоящим Host

Стенд вызывает production `verify`, `switch`, `retire` и повтор `retire` без
подмены Host/транспорта. Проверяются реальные protected files, flocks, Docker
inspect/health/ports, `nginx -T/-t`, pidfd HUP, системный CA, loopback TLS/SNI,
новое поколение workers, drain, SIGTERM, exit 0, отключение endpoint и удаление
pending. Два синтетических Web-образа имеют разные image ID и source SHA;
прежние файлы экспортированы из реальных контейнеров и сохранены в архиве.
API, реальный PostgreSQL, job и новый Web остаются прежними.

Финальный прогон `914a5e8f8197` получил 13 свежих TLS-ответов с интервалом
опроса 100 мс, без ошибок; максимальный промежуток завершения — 146,17 мс,
максимальная длительность запроса — 45,83 мс. Это дискретные измерения fixture,
не SLA нулевого простоя. Наблюдаемый signal marker подтверждает отсутствие
преждевременного SIGTERM и ровно один штатный сигнал после drain. Дополнительно
проверены реальные конфликты двух flock, несовместимый backend, небезопасные
права плана, изменение public manifest pin, неготовность кандидата, повреждение
архива, повтор switch и наличие прежних активных workers. `verify` создаёт
только advisory locks. Все шесть собственных ресурсов очищены и проверены;
ownership inventory завершён со статусом `cleaned`.

Это отдельный Docker-in-Docker host без внешнего Docker socket, host bind
mounts, публикуемых наружу портов и сети. Кандидаты не получают socket.
Применяется fixed public-image allowlist и отказ от remote Docker contexts.
Ownership inventory сохраняется до мутаций; cleanup сверяет точные ID/labels.
SIGINT/SIGTERM обрабатываются кооперативно, для SIGKILL/power loss остаётся
ручная проверка inventory. Независимое ревью wrapper закрыло замечания о
частичных тегах, stderr, preflight и прерывании.

API/Web в этом тесте синтетические, финансовые операции не проверяются.
Транспортный тест использует две копии одного проверенного Next-образа с
OCI revision `42ecf835ea8c7f1488d70453e203c1c3149e2f92`; это не тест двух
разных продуктовых версий. Его SSE молчал более 35 с, незаконченный POST
пересёк HUP при `client_body_timeout 15s`, 44 прежних Next-файла доступны
после остановки старого Web. Принятые запросы завершались один раз.

Бюджет внешнего fixture — 6 ГиБ; memory gate читает `/proc` Docker VM.
Это проверяет исполнение гейта, **не вместимость production VM на 4 ГиБ**.
До установки нужны отдельные bootstrap, аудит ресурсов и проверка совместимости
производственных образов. Новых миграций, ключей или прав БД нет.
