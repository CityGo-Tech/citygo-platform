# Проверяемый запуск контейнера миграции

Следующий блок CG-037 / §10.5 после транзакционного исполнителя (#57).
`deploy/backup/migration_job.py` — **внутренняя библиотека, не команда для ВМ**.
Она ещё не подключена к `prepare()`. Полный контроллер с независимым разрешением
миграции, переключением API/Web, health/mobile проверкой и завершением не реализован.
На рабочем сервере этот модуль пока не запускать.

## Требования к будущему вызывающему коду

Нужен настоящий активный объект release window, тот же процесс/поток и непрерывная
maintenance lock. После успешной новой копии в этом окне хранится внутренний checkpoint;
сохранённый JSON от предыдущего процесса не позволяет продолжить операцию.
Копия должна быть не старше 15 минут, связана с тем же operation ID и SHA цели.

Но ни checkpoint, ни `allow_migration=True`, ни Python-объект не являются одобрением
владельца. Доверенный контроллер обязан отдельно проверить конкретное разрешение,
выбранные manifest/SQL/ACL, закрытый ingress, завершение писателей и точную DB-сеть.
Он передаёт обязательную функцию `guard`, повторяющую эти проверки перед созданием,
перед стартом и после завершения. Нельзя передавать no-op guard в production.
Текущий preparation approval остаётся `allow_migration: false` и здесь не используется.
Это кооперативный протокол, не защита от root/Docker или произвольного Python-кода.

## Что выполняет библиотека

1. Отвергает повтор в том же окне, включая повтор после ошибки предварительной
   проверки. Host operation ID (32 hex) преобразуется в UUID с дефисами для задания
   #57 — те же 128 бит, без нового независимого идентификатора.
2. Проверяет структуру задания, исходную/целевую историю и привязку к операции.
   Проверяет jobs-образ через image gate: digest, tested/local/config ID и source SHA.
   Повторяет проверку на границах запуска. Скачивания и registry login нет.
3. Читает единственный секрет — JSON с DATABASE_URL для citygo_migrator,
   postgres:5432/citygo_pilot без дополнительных URL-параметров. Снимок создаётся
   в защищённой временной папке и монтируется read-only; исходный файл перепроверяется.
   Web/API/Worker, ключи ИИ и административный пароль БД контейнер не получает.
4. До первого Docker create сохраняет **эксклюзивную синхронизированную запись попытки**.
   Затем создаёт остановленный контейнер по проверенному локальному image ID.
   Фиксированы команда, пользователь 1000:1000, read-only root, init, no-new-privileges,
   dropped capabilities, лимиты 256 MiB памяти/128 процессов, DB network ID,
   единственный bind mount, отсутствие restart/auto-remove и открытых портов.
5. Проверяет created-контейнер и сохраняет его точный ID. Передаёт компактный JSON
   через stdin при `docker start --attach --interactive`, без shell и аргументов с ключами.
   Вывод ограничен 256 KiB через лимит файла, клиент — 180 секунд. Первый наблюдённый
   running **или уже exited** процесс фиксируется по StartedAt; итог обязан совпадать.
6. Требует сохранённый контейнер с теми же ID/image/StartedAt, без restart/OOM/ошибок,
   с exit 0. Отдельно проверяет точный типизированный квиток: operation/target/request
   hashes, список применённых миграций, ACL hash, committed=true, trafficAuthorized=false.
   Один exit 0 или один JSON-ответ недостаточен.
7. После повторных проверок и успешной очистки временной папки пишет защищённый
   квиток успеха. Контейнер и durable pending остаются, вход и Worker не открываются.

## Ошибки и ограничения

Не удалять записи попытки/контейнера или pending для повтора. Потерянный ответ,
timeout, ошибка Docker, неясный COMMIT, падение процесса, ошибка записи квитка либо
проверки после COMMIT означают **ручную сверку**, не доказательство rollback.
Завершение Docker-клиента не гарантирует остановку контейнера. Библиотека не делает
retry, kill/rm контейнера, resume после перезапуска, откат БД или открытие доступа.

Файлы в state_dir: `migration-<operation-id>.intent.json`, `.container.json`,
`.success.json`. В них нет URL БД, сырого stdout/stderr, SQL или health logs.
При отсутствии `.container.json` контейнер уже мог быть создан: точное имя заранее
содержится в intent. Проверенный успех не разрешает будущему контроллеру пропустить
health/mobile проверки. Чтение большого success-квитка следует ограничивать 256 KiB,
не старым 64 KiB пределом общих status-файлов.

## Проверки

Unit tests: контракт/типы/дубликаты JSON, fixed runtime, неверные DB credentials,
подмена/перезапуск/ошибка процесса, guard/backup/secret drift, неопределённый start,
неверный квиток, запрет повтора и сохранение lock/pending/intent.

Disposable CI: настоящий jobs-контейнер с stdin, реальная миграция 6 → 7,
контейнер exit 0 и квиток; затем отдельный ошибочный запуск с exit 1 и сохранением
pending/intent без успеха. Копии создаются настоящими pg_dump/age, S3 — MemoryStore;
registry binding в этой fixture синтетический, реальный image gate проверяется
отдельным registry smoke. Тест удаляет только свои два уже завершённых контейнера
после подтверждения сохранённых свидетельств. Production-библиотека их не удаляет.
Это ещё не тест полного обновления сервера или независимого разрешения выпуска.
