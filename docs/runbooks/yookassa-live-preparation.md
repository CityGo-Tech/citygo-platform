# Подготовка боевой оплаты ЮKassa и чеков НПД

CityGo планирует принимать оплату за собственный сервис AI-помощников через пополняемый
баланс. Тестовое пополнение проверено, но боевой приём денег пока закрыт.
Оператор сообщил о применении НПД. Для запуска нужны подходящий договор магазина,
выдача чеков НПД и завершённый учёт оплаченных средств и возвратов.

## Принятые денежные правила

- 100 оплаченных рублей дают 100 ₽ CityGo. Множитель ×10 не применяется к оплате.
- Подтверждённая себестоимость AI умножается на 10 при списании по сохранённому
  тарифу попытки. Себестоимость, выручка и комиссия эквайринга учитываются отдельно.
- Сначала расходуется подарок, затем оплаченные пополнения в порядке FIFO.
- Подарок 500 ₽ CityGo выдаётся один раз после подтверждения телефона. Пока
  SMS-провайдер не подключён, автоматическая выдача подарка закрыта.
- Подарочные средства не возвращаются настоящими деньгами.

Баланс CityGo — внутренний учёт предоплаты услуг, не банковский кошелёк и не
обещание вывода произвольной суммы. Условия услуги и возвратов должны соответствовать
этому описанию. Применимость НПД к конкретным договорам CityGo требует отдельной
проверки: нельзя подменять собственную услугу перепродажей прав или агентским
приёмом средств за партнёров. [Условия НПД ФНС](https://npd.nalog.ru/).

## Почему требуется отдельная схема чеков

Для плательщика НПД доход регистрируется и чек передаётся покупателю через
«Мой налог» либо уполномоченного партнёра. Настроенные «Чеки от ЮKassa» по 54-ФЗ
этот сценарий не заменяют; ЮKassa отдельно указывает, что эта услуга не подходит
для НПД. [Документация ЮKassa](https://yookassa.ru/docs/support/merchant/payments/implement/docs),
[порядок чеков для самозанятых](https://yookassa.ru/developers/payment-acceptance/receipts/basics).

В чеке отражается полная сумма оплаты покупателя, без уменьшения на эквайринг
или стоимость AI. Корректировка дохода при возврате — отдельное действие;
обычное расходование баланса не является основанием для аннулирования чека.
[Разъяснение ФНС](https://www.nalog.gov.ru/rn46/news/activities_fts/16536156/).

Для пополнения проектируем выдачу чека при получении оплаты, а не после расходования
баланса. Формулировку услуги и момент расчёта нужно согласовать с фактической схемой
эквайринга и договором: правила 54-ФЗ про аванс и зачёт нельзя автоматически
переносить на НПД. Для электронных средств платежа ФНС требует выдавать чек в момент
расчёта. [ФНС о формировании чеков](https://www.nalog.gov.ru/rn71/news/activities_fts/16645143/).

Владелец выбрал автоматическую выдачу через уполномоченного НПД-партнёра
18 октября 2026 года. Ручная выдача для платного пилота не является принятым
обходным вариантом. Конкретный партнёр и тариф ещё не согласованы.

После проверки ограничений ЮKassa владелец выбрал **проверить переход на Robokassa**.
Это разрешение на оценку совместимости, а не на смену действующего эквайринга,
создание магазина, принятие договора или включение платежей. Результат и порядок
перехода — в [оценке Robokassa для НПД](../implementation/robokassa-npd-assessment.md).

Нужны официальный договор, разрешение оператора, API регистрации дохода,
чтение статуса и ссылка на чек, доставка покупателю, обработка повторов и
возвратов. Доступ к личному кабинету ФНС и его cookies не используются как
неофициальный API. Подключение партнёра и передача ему полномочий требуют
отдельного подтверждения владельца.
[ФНС об уполномоченных партнёрах](https://www.nalog.gov.ru/rn60/news/activities_fts/16544244/).

Встроенная автоматизация ЮKassa для НПД прекращена с 29 декабря 2025 года.
Сохранить эквайринг ЮKassa можно только после подтверждения отдельным партнёром
совместимости с этим источником оплаты. Наличие API «для самозанятых» само по себе
этого не доказывает: API выплат исполнителям и чеков на такие выплаты не заменяет
регистрацию дохода самого оператора CityGo от его покупателей.
[История изменений ЮKassa](https://yookassa.ru/developers/using-api/changelog).

## Проверка совместимости партнёра

Проверенного сочетания «один ИП на НПД, собственная выручка, отдельный API чеков,
эквайринг ЮKassa» пока нет. Нельзя выбирать интеграцию по одному наличию метода
создания чека. Наличие организации в [перечне ФНС](https://npd.nalog.ru/aggregators/)
подтверждает статус партнёра, но не условия его конкретного продукта.

| Вариант        | Что подтверждено                                                                                      | Что требуется для CityGo                                                                                                               |
| -------------- | ----------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------- |
| MonetaNPD      | Есть отдельный метод регистрации дохода, статусы и ссылка на чек; опубликован onboarding маркетплейса | Письменное подтверждение обслуживания одного ИП и платежей ЮKassa без перевода денег через ЭСП Монеты; актуальные спецификация и тариф |
| Самозанятые.рф | API/виджет, приём оплаты и автоматические чеки в их схеме эквайринга                                  | Отдельный API чеков для внешней ЮKassa не подтверждён; свой эквайринг нельзя подключать как незаметную замену                          |
| Робочеки СМЗ   | Автоматические чеки на оплаты через Robokassa, в том числе для ИП на НПД после заявки в поддержку     | Это альтернативный эквайринг; нужны согласованные тариф, модель предоплаты и порядок полных/частичных возвратов                        |

Источники: [регистрация дохода MonetaNPD](https://docs.payanyway.ru/marketplace/samozanyatye/scenarii-ispolzovaniya-npd-api/8.-registraciya-dokhoda-v-fns-i-8.-pechat-cheka.md),
[подключение MonetaNPD](https://docs.payanyway.ru/marketplace/samozanyatye/samozanyatye.md),
[эквайринг Самозанятые.рф](https://xn--80aapgyievp4gwb.xn--p1ai/acquiring).

Сценарий Robokassa описан на [странице Робочеки СМЗ](https://robokassa.com/online-check/robocheck-smz/).

Метод Sber API регистрации чека описан для ранее проведённого B2C-перевода
самозанятому с его предварительной валидацией. Он не подтверждает регистрацию
собственной выручки CityGo через ЮKassa.
[Ограничения метода Сбера](https://developers.sber.ru/docs/ru/sber-api/specifications/self-employed/register-self-employed-receipt).

Если будет принято решение сохранить ЮKassa, кандидат для предметного уточнения —
MonetaNPD, не для немедленного подключения. Для такого варианта получить ответы:

1. Договор разрешает одному ИП на НПД регистрировать собственную выручку от
   физлиц за услуги, оплаченные через ЮKassa? Не требуется фиктивный маркетплейс,
   выплата самому себе или перенос эквайринга/открытие электронного кошелька?
2. Кто юридически является уполномоченным партнёром, как выдаются и отзываются
   минимальные полномочия в «Мой налог» и как проверяется действующая привязка?
3. Можно ли сохранить собственный ID операции до отправки? Как после timeout
   найти созданный чек без повторной регистрации дохода? В опубликованном
   `registerincome` клиентский ключ идемпотентности не указан, а `requestId`
   возвращается только в ответе — гарантии нельзя додумывать.
4. Как читаются окончательный статус, точная сумма, дата расчёта и ссылка на чек;
   как подтверждается доставка покупателю и защищаются уведомления?
5. Как корректируются доход и чек при полном и частичном возврате, в том числе
   нескольких? Одна только операция отмены целого чека недостаточна.
6. Есть ли тестовый контур без реального дохода и налоговых последствий, какие
   лимиты, сроки обработки, стоимость подключения, абонплата и цена операции?

На эти условия пока нет согласованного ответа поставщика. Чеки не отправляются,
ключи не запрашиваются, боевые платежи не включаются. Неопределённая регистрация
дохода не повторяется вслепую; автоматическая выдача требует долговечной сверки,
а не только HTTP-обработчика успешного платежа.

## Возможности подготовленного кода

| Компонент                                  | Что делает                                                                                         | Чего не делает                                                                            |
| ------------------------------------------ | -------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------- |
| `apps/api/src/yookassa-refunds.ts`         | Только sandbox: неизменяемая сумма/UUID, проверка исходного платежа, POST и отдельный GET возврата | Не резервирует и не списывает баланс; не принимает live-ключи                             |
| `apps/api/src/payment-live-readiness.ts`   | Называет незавершённые условия; различает НПД, иной и неизвестный режим                            | Всегда возвращает `readyForLive=false`; не подтверждает налоговое соответствие            |
| `apps/api/src/preview-payments.ts`         | Читает явно указанный операторский JSON и выводит подготовительный отчёт                           | Не загружает `.env`, БД или платёжный клиент; не является командой включения              |
| `packages/contracts/src/payment-fiscal.ts` | Точный ограниченный offline-preview профиля `54fz_non_npd`                                         | Не формирует чек НПД, не отправляет чек в налоговую и не задаёт оператору налоговый режим |

Для оператора НПД даже технически корректный профиль 54-ФЗ остаётся неподходящим:
проверка выдаёт `NPD_FISCAL_FLOW_NOT_IMPLEMENTED`. Наличие ключа или флага чеков
в кабинете этот запрет не снимает.

Пример несекретного файла подготовки:

```json
{
  "operatorTaxRegime": "npd",
  "sourcePolicy": "gift_first_paid_fifo",
  "merchantReceiptsReportedEnabled": true
}
```

```sh
pnpm --filter @citygo/contracts build
pnpm --filter @citygo/api build
node apps/api/dist/preview-payments.js --input /local/path/payment-preparation.json
```

Код завершения `2` означает «включение заблокировано»; `1` — некорректный ввод.
CLI не возвращает успешный допуск live. Используйте доверенный локальный обычный
файл до 16 KiB, без ключей, персональных данных и ссылок на сетевые папки/junction.

## Что завершить до включения оплаты

1. Подтвердить действующий статус НПД и допустимость фактической услуги CityGo.
   Отображение налогового календаря в ЛК ИП не заменяет справку о постановке на учёт.
2. Согласовать с ЮKassa магазин для сайта CityGo и режима НПД. В проверенном кабинете
   сайт магазина относится к прежней услуге, а услуга чеков 54-ФЗ уже включена.
   Ничего не отключать и не менять до согласования правильного договора/профиля.
3. Подтвердить совместимого НПД-партнёра и реализовать автоматический процесс чеков.
   Хранить его статус отдельно от оплаты: `payment=succeeded` не доказывает выдачу
   и доставку чека. До этого боевой приём денег остаётся закрыт.
4. Добавить оплаченные лоты с привязкой к платежам. AI-hold должен атомарно закреплять
   gift-first/FIFO-распределение, а возврат — конкурировать с ним за тот же остаток.
   Не менять уже применённую миграцию 0015: test/live-переход требует новой миграции.
5. Реализовать журнал возвратов. Сначала резервировать возвращаемые платные средства,
   затем вызывать провайдера вне транзакции. Сохранять UUID и тело до POST, provider ID
   после ответа; проводить окончательное списание только после проверенного GET.
6. Оставлять timeout/неизвестный POST на сверке без освобождения резерва и нового UUID.
   Транспорт запрещает повтор POST спустя 23 часа; окно идемпотентности провайдера
   ограничено 24 часами. Полные и частичные возвраты сверять с исходным платежом.
7. Обнаруживать возвраты из кабинета ЮKassa даже после начисления/расходования баланса.
   Недостаток оплаченных средств переводит аккаунт на разбор и блокирует новые расходы,
   а не стирает ранее оказанную услугу. Чек НПД корректируется отдельно; частичный
   возврат не должен автоматически аннулировать весь доход.
8. Завершить долговечную очередь уведомлений и фоновую сверку. Webhook и return URL
   сами по себе не подтверждают оплату или возврат.
9. После согласования магазина выпустить отдельный live-ключ с подтверждением владельца,
   сохранить только в закрытом серверном конфиге. Не ослаблять изоляцию тестовых денег.
10. Проверить чистый закрытый запуск, HTTPS, восстановление и блокирующие операции
    backup. Только затем отдельно согласовать включение live и первую реальную оплату.

Справочники: [возвраты ЮKassa](https://yookassa.ru/developers/payment-acceptance/after-the-payment/refunds),
[идемпотентность API](https://yookassa.ru/developers/using-api/interaction-format),
[чистый тестовый запуск](fresh-test-launch.md).

## Ограничение внешних обращений

Владелец запретил отправлять обращения поставщикам. Подготовленные ранее тексты
не отправлялись; писем, заявок и внешних черновиков нет. Проверять условия можно
по публичным материалам, не подменяя неизвестные условия предположениями.
