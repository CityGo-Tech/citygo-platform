# Завершение закрытого выпуска

`deploy/backup/finish.py` продолжает в одном процессе цепочку preparation →
backup → migration → start/health → config cutover. Это внутренняя библиотека,
не разрешение запустить выпуск на рабочей ВМ и не публичный deployment CLI.

## Что меняется

- Один канонический `backup.json`, полученный через `load_config`, атомарно
  заменяется новым v1 JSON. Файл расположен вне стабильного `state_dir`.
- Меняются только `source_sha`, `compose_file`, `compose_env`. База, проект,
  каталог блокировок, получатель шифрования и место хранения копий не меняются.
- В новом приватном `state_dir/release-<sha>` сохраняются фиксированный
  `compose.json`, пустое окружение и копия `dump.sh` установленного доверенного
  контроллера. Никакие команды из candidate Compose не исполняются.
- API/Web сохраняют уже проверенные настройки, AI disabled, loopback-порт и
  **restart=no**. Ops-профиль содержит только Worker нового jobs-образа и backup
  прежнего PostgreSQL-образа. Нет migrator, создания/удаления БД или volume.
- Worker и backup используют существующие отдельные секреты. Секреты не копируются
  в generation, approval или receipt; в привязках используются только SHA-256.
- Старые загруженные настройки после cutover отклоняются; все команды оператора
  обязаны заново читать тот же канонический файл и использовать новый runtime.

## Отдельное разрешение

Помимо preparation/migration/start approval нужен приватный независимый файл
`purpose=citygo-release-finish`, `profile=citygo-closed-release-v1`, `version=1`.
Он связывает SHA-256 start approval, абсолютный путь и точные байты прежнего
канонического config, SHA-256 новой generation (настройки, файлы, секреты).
Срок действия ограничен 24 часами. Разрешается только `allow_finish=true`;
`allow_traffic`, `allow_worker`, `allow_restart` должны быть `false`.

Отсутствующее/неподходящее разрешение обнаруживается **до остановки приложения,
резервной копии и миграций**. При исполнении перепроверяются все четыре approval,
их сроки и файлы. JSON из bundle не может одобрить собственный выпуск. Библиотека
не создаёт разрешений за оператора; синтетические writers существуют только в CI.

## Порядок фиксации

1. Дождаться успешной финализации preparation/migration/start и повторных health
   проверок. Живое продолжение остаётся в том же процессе под maintenance lock.
2. Взять также worker-admission lock, подтвердить закрытые ingress и Worker,
   прежний PostgreSQL/завершённые jobs, неизменные новые API/Web и их процессы.
3. Однократно записать `finish-approval-<hash>.used.json`, создать и синхронизировать
   generation; сохранить точные прежние настройки в `finish-<operation>.previous.json`.
4. Повторить проверки. Атомарно заменить канонический config и синхронизировать
   родительский каталог. Убедиться, что читаются ожидаемые новые байты/файлы.
5. Ещё раз проверить runtime/health, секреты и все разрешения; записать
   `active-release.json`, перечитать его и только затем убрать
   `operation-pending.json` с синхронизацией каталога.

Последняя проверка разрешений выполняется внутри `complete_operation` после
чтения pending, непосредственно перед его удалением. Сроки всех четырёх approvals
сверяются по общему времени после последних чтений файлов; отзыв при чтении active
или expiry при чтении pending оставляет барьер на месте.

`active_release(config)` принимает запись только при отсутствии pending и совпадении
источника/fingerprint с конфигурацией. Сам receipt не является разрешением на
повторную миграцию, запуск контейнеров или открытие доступа. Это статус фиксации,
не непрерывный мониторинг здоровья, секретов и ingress.

## Прерывание и восстановление

| Место отказа                             | Настройки        | Обязательное состояние                                         |
| ---------------------------------------- | ---------------- | -------------------------------------------------------------- |
| До замены config                         | Прежние          | Pending остаётся, новая generation может быть частичной        |
| После замены config                      | Новые            | Pending блокирует backup/Worker/следующий выпуск               |
| После записи active, до удаления pending | Новые            | Active **ещё не считается** завершённым                        |
| Ошибка fsync после удаления pending      | Требуют проверки | Не повторять выпуск автоматически; исход фиксации неоднозначен |

Нет автоматического rollback, retry, удаления partial generation или восстановления
живого продолжения по записанному startup receipt. Сохранённый прежний JSON —
свидетельство для оператора, **не команда отката схемы**. Нельзя вручную удалять
pending только потому, что процесс завершился или приложение отвечает.

Перед эксплуатацией ещё нужны отдельная процедура recovery/compatibility drill,
операторский CLI и проверенный допуск перезапуска. Автоматический restart, traffic,
Worker admission, расписания, DNS/TLS и AI этот этап не включает. Проверка живой
инфраструктуры и разрешение конкретной версии остаются отдельными действиями.

## Проверки

Linux unit-тесты моделируют прерывания до/после config swap и записи active,
изменение секретов, отзыв разрешения, повторное использование receipts и stale
config. Изолированный container smoke выполняет реальную цепочку, затем делает
новый `pg_dump → age` и отдельный Worker на сгенерированной конфигурации. Только
в disposable fixture Worker временно допускается и сразу снова закрывается;
облачные S3/ИИ не вызываются. Образы/approval в этом тесте синтетически связаны;
проверка digest/blob отдельно выполняется registry rehearsal.

Граница доверия прежняя: один оператор, стабильный каталог состояния и один config,
неизменяемые защищённые файлы. Root, прямые Docker-команды, старый runtime и
параллельное редактирование файлов вне протокола эта блокировка не изолирует.
