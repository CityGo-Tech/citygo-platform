# Контейнерная основа для Cloud.ru Free Tier

Первый этап плана размещения: собрать готовые Linux-образы в CI и проверить их
на одноразовой PostgreSQL. Это **не публичное развёртывание**: ВМ, платный IP,
домен, TLS, доступы, backup и публикация образов этим этапом не создаются.
Существующие локальные базы и ключи переносить не нужно.

## Образы

Все цели собираются из корня репозитория через `deploy/Dockerfile`:

| Цель   | Содержимое                                                     | Команда по умолчанию                 |
| ------ | -------------------------------------------------------------- | ------------------------------------ |
| `web`  | Next standalone, static и public, общие зависимости из tracing | готовый `apps/web/server.js`         |
| `api`  | API и production-зависимости из `pnpm deploy --legacy --prod`  | готовый `dist/server.js`             |
| `jobs` | Worker, DB CLI, SQL-миграции и production-зависимости          | `migrate`; переопределение: `worker` |

Сборка использует Node 24, pnpm 10.15.0 и frozen lockfile. На сервере не нужны
исходники, TypeScript, pnpm или повторная сборка. Миграции запускаются отдельно,
API не меняет схему автоматически. Образы запускаются от пользователя `node`.
До настоящего релиза нужно зафиксировать проверенные digest базовых образов и
выпустить образы приложения с тегом commit SHA; теги `latest` для релиза не нужны.

`CITYGO_WEB_STANDALONE=1` включает standalone только в Linux-сборке контейнера;
обычный локальный запуск остаётся прежним. `API_INTERNAL_URL=http://api:4000` —
**параметр сборки**, встроенный в Next rewrites. Его изменение требует нового
образа Web. Это адрес внутреннего сервиса, а не секрет. Снаружи Web использует
`/api/*`, а прокси снимает префикс `/api` перед Fastify.

`.dockerignore` исключает `.env*`, локальные БД, ключи, `.git`, node_modules и
старые сборки на любой глубине. Перед установкой зависимостей выполняется аудит
контекста. CI дополнительно подкладывает неработающий тестовый секрет в исключённые
файлы и проверяет, что он не попал в контекст. Это защита от случайного копирования,
не универсальный сканер всех возможных секретов в произвольном исходном коде.

## Окружение и границы безопасности

`scripts/container-runtime.mjs` принимает только `api`, `web`, `migrate`, `worker`.
Он запускает уже собранный код, принудительно устанавливает `NODE_ENV=production`
и не читает локальные `.env`-файлы. Переменные передаются из окружения контейнера
через существующие allowlist сервисов:

- API: только известные настройки API/провайдеров;
- Web: без базы и ключей моделей;
- migrator и worker: только параметры процесса и `DATABASE_URL`, без ключей AI.

Все DB-режимы требуют явно переданный PostgreSQL URL. PGlite и автоматическое
создание `.local/database` в контейнере запрещены. Режим development не может
обойти production-проверки. Защита RouterAI/GigaChat в production сохранена;
см. [AI-провайдеры](ai-providers.md). Smoke всегда использует `LLM_PROVIDER=disabled`.

Образы слушают 3000 (Web) и 4000 (API); healthcheck проверяет `/api/ready` и
`/ready` соответственно. Не меняйте эти порты без согласованной правки healthcheck
и маршрута Web. Мигратор/worker — одноразовые задачи, healthcheck им не нужен.

## Как выполнить контейнерную проверку

Нужны Linux, Docker Engine с Compose v2 и Node 24. Проверка не требует pnpm на
хосте: установка зависимостей и сборка выполняются внутри builder. На Windows без
Docker используйте workflow **Container smoke** в GitHub Actions; установка Docker
Desktop/WSL для этого PR не обязательна.

В чистом клоне, из корня:

```sh
node scripts/container-smoke.mjs --disposable
```

Скрипт работает только с локальным Docker по умолчанию. Он не передаёт Docker
унаследованные cloud/LLM-переменные и использует явный пустой `deploy/smoke.env`,
чтобы Compose не прочитал корневой `.env`. Создаётся случайный project name
`citygo-smoke-*`, отдельная сеть и отдельный том. По завершении удаляется **только
том этого одноразового проекта** и созданная им тестовая папка. При принудительном
убийстве процесса возможны оставшиеся тестовые ресурсы; сначала найдите точный
project через `docker compose ls --all`, не удаляйте общие тома командой prune.

Сеть smoke — `172.29.91.0/24`. При совпадении с локальной сетью выполняйте проверку
в CI или согласованно измените subnet, адреса и доверенный `/32`. Не расширяйте
доверие до всех прокси. Web доступен только на случайном порту `127.0.0.1`; API и
PostgreSQL не публикуют порты. Временный HTTP endpoint нужен для машинной проверки
через bearer-сессию, **не для входа пользователей**: production-cookie остаётся
Secure. `pilot.example.test` — фиктивное значение, DNS/TLS оно не настраивает.

Проверяются:

1. Сборка всех трёх образов и исключение тестового секрета из контекста.
2. Семь текущих SQL-миграций и повторное применение без дублей.
3. Разные роли API, worker и мигратора; отсутствие superuser/DDL у API.
4. Readiness через Web-прокси, главная страница и оба типа изображений.
5. Регистрация вымышленного пользователя, Secure-cookie, bearer-сессия,
   версия контракта, отклонение чужого Origin.
6. Одноразовый worker, запрет PGlite и production-включения RouterAI/GigaChat.
7. Работа от non-root с read-only корнем контейнера и отсутствие `.env`/dev-tools.
8. Сохранение аккаунта/сессии после перезапуска БД и пересоздания API/Web.

`deploy/fixtures/*.sql` и пароли `synthetic-*` предназначены **только для тестов**.
Не переносите их на сервер и не сохраняйте реальные данные в smoke-томе.
Схема выдачи прав проверяет текущие семь миграций; при добавлении таблиц нужно
пересмотреть права API/worker и smoke. Это ещё не production-bootstrap ролей.

Обычные локальные проверки:

```sh
corepack pnpm test:containers
corepack pnpm check
```

GitHub Actions собирает образы без публикации, без production secrets и без
живых запросов к моделям. Основной CI продолжает проверять приложение, E2E и Expo.

## Следующие этапы перед удалённым пилотом

1. Production Compose: ingress/TLS, постоянный том БД, настоящие отдельные роли,
   безопасный ввод секретов, ограничения RAM/logs для Free Tier.
2. После подтверждения итоговой стоимости — создать ВМ и нужный сетевой доступ,
   настроить SSH/firewall; не открывать 3000/4000/5432 наружу.
3. Обязательная внешняя резервная копия и проверка восстановления на отдельной БД.
4. Pipeline: PR → тесты → образы по SHA → закрытый registry → утверждённый release
   → pull на ВМ → backup → миграции → healthcheck. Rollback приложения отдельно
   от восстановления БД; нельзя автоматически откатывать новые данные.
5. Согласование получателей данных и production-проверки AI, закрытый набор
   участников, лимиты, пользовательские согласия и проверка Honor по HTTPS.

До этих этапов запуск 20 реальных пользователей не объявляется готовым. Free Tier
не делает IP, backup, домен и расходы моделей автоматически бесплатными.
