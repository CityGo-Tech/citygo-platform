# Разовый ручной выпуск без GitHub Actions

Это отдельный путь подготовки кандидата, а не отключение CI и не постоянное
разрешение на обновление. Он нужен при недоступности GitHub Actions. Изолированные
Hyper-V ВМ и GitHub runner для него не требуются. Проверки выполняет оператор в
локальном Linux/Docker на доверенном, предварительно просмотренном коде.

## Что обязательно сохранить

1. Точный commit SHA и дерево Git, полный перечень и хеши экспортированных исходников.
2. Все команды CI и Container smoke из `scripts/operator-release.mjs`, без пропусков,
   с настоящими exit code, отдельными журналами и хешами исходников до/после каждой команды.
3. Сборку и испытание конкретных production-образов Linux/amd64. После испытаний
   образы нельзя пересобирать: при публикации проверяются те же image ID и registry digest.
4. Неизменность первых миграций и текущего образа PostgreSQL. Обновление PostgreSQL
   не входит в выпуск приложения.
5. Свежую зашифрованную резервную копию и проверку восстановления отдельно от рабочей БД.
6. Отдельные ограниченные по времени разрешения на подготовку, миграцию, запуск
   и завершение закрытого обновления. У открытия доступа, AI и оплаты свои условия.

Нельзя создавать фиктивные GitHub run ID, зелёные статусы или выставлять
`GITHUB_ACTIONS=true`, чтобы пройти штатный издатель. GitHub-проверки и защита
обычного выпуска остаются включёнными.

## Формат доказательств

`checks.json` имеет тип `operator-local-linux-checks-v1`. В нём перечислены точные
команды, exit code, имена и SHA-256 сохранённых журналов. У каждой команды должны
совпасть полный digest исходников до и после запуска. Инструмент
`readLocalChecks()` проверяет сами файлы журналов, а не только заявления в JSON.
Node закреплён на 24.11.1, pnpm — на 10.15.0.

Кандидат имеет `version: 2`, тип `operator-local-candidate-not-deployed` и ID
`<sha>-local-<operation>`. В нём поле `local`, а не фиктивное поле GitHub `run`:
идентификатор операции, хеш `checks.json`, дерево и digest исходников, обе группы
проверок. Политика кандидата по-прежнему запрещает deployment и автоматический rollback.

Это метаданные происхождения, **не самостоятельное разрешение**. Контроллер принимает
их только с защищённым внешним разрешением `version: 3`, purpose
`citygo-operator-local-preparation`. В нём должны совпасть manifest, SHA, образы,
конфигурация, `artifact_id: local:<operation>` и `local_receipt_sha256`. Срок —
не более суток. Подготовка сама по себе не разрешает миграции и открытие сайта.

Штатный `autodeploy.py` явно отклоняет локальный кандидат даже при корректных
хешах. Старые GitHub-кандидаты и разрешения версий 1–2 сохраняют прежний формат.
Перенос этой возможности в установленный контроллер сервера — отдельный
проверяемый шаг, не побочный эффект подготовки кода.

## Граница текущей реализации

Реализованы проверка журналов, формирование типизированного manifest и серверная
проверка его связи с внешним разрешением. Это ещё не готовая команда публикации:
нельзя запускать штатный GitHub publisher с подставными параметрами. До выпуска
нужны настоящий полный Linux-прогон на окончательном SHA, публикация/обратная
проверка тех же образов, свежие серверные pins и закрытое обновление.

До публичного запуска отдельно проверяются реальный ответ RouterAI и его стоимость,
тариф ×10, пополнение 1:1, идемпотентность уведомлений, возврат и очередь НПД-чеков.
Проверка одной модели вне приложения не заменяет проверку списания через HTTP и БД.
