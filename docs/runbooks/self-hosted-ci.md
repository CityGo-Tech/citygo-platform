# Изолированный локальный CI

CityGo планирует выполнять проверки GitHub Actions в одноразовых Linux-ВМ на
локальном компьютере, сохраняя приватность репозитория и существующие условия
выпуска. Этот путь не требует покупки GitHub-hosted compute. Настройка не должна
давать коду из PR доступ к личным файлам, ключам или рабочему серверу.

## Текущее состояние

На 19 октября 2026 года Hyper-V включён владельцем. Read-only preflight
**успешно выполнен в отдельно подтверждённом административном процессе**.
Подпись и SHA-256 официального Ubuntu-образа проверены; создан выключенный
bootstrap-гость без подключения сети. Работающий CI и сетевая изоляция ещё
не подтверждены.

- Компьютер: Windows 11 Pro, 32 ГБ оперативной памяти. Подтверждены состояние
  компонента Hyper-V `Enabled` и службы `vmms` `Running`; это не проверка гостевой
  изоляции и не подтверждение отсутствия всех ожидающих перезагрузку изменений.
- Обычный процесс разработки остаётся без административных прав. Владелец лично
  подтвердил UAC для отдельного доверенного процесса. В нём успешно прочитаны
  инвентари Hyper-V и сети; подтверждены ресурсы для начального профиля 4 CPU,
  6 ГБ RAM, 96 ГБ диска с сохранением резерва хосту. Это не разрешение выполнять
  PR-код с повышенными правами.
- Windows PowerShell первоначально заблокировал локальный `.ps1`. После
  отдельного согласия владельца использован `RemoteSigned` только для одного
  административного процесса. Постоянные политики, корпоративные ограничения,
  группы Windows и службы не менялись; `Bypass`/`Unrestricted` не применялись.
- Ранее отменённый UAC при попытке DISM остаётся историческим фактом. Повторять
  установку, автоматически повышать права или подтверждать UAC за владельца
  нельзя; компонент уже включён вручную.
- Одноразовая Linux-ВМ, зарегистрированный runner и проверенная фабрика ВМ ещё
  не готовы. Описанный ниже жизненный цикл — требования к реализации, не
  действующая автоматизация.
- Bootstrap-ВМ — Gen2, 4 CPU, 6 ГБ static RAM, standalone VHDX 96 GiB,
  Secure Boot с шаблоном `MicrosoftUEFICertificateAuthority`. Независимое
  read-only считывание подтвердило `Off`, один отключённый NIC, выключенные
  автозапуск/checkpoints и точный хеш диска. Первый запуск ОС ещё не выполнен.
- Начальная попытка сохранила ВМ, но отклонила служебные ACL, добавленные
  Hyper-V к своей папке, при записи receipt. Исторический отказ сохранён;
  независимая проверка состояния не объявлена успешным выполнением всей попытки.
  Контрольные отчёты должны находиться в отдельной защищённой папке вне
  Hyper-V-managed каталога. Общие служебные права Hyper-V не переносятся
  на каталог контроллера или его будущие секреты.
- Workflows не перенесены: `CI`, `Container smoke`, publisher и deploy пока
  используют GitHub-hosted runners. Их отказ по billing не считается успешной
  проверкой и не обходится локальным отчётом.
- Покупки, оплаты GitHub, изменение видимости репозитория, выдача новых
  серверных прав и открытие приложения не входят в эту подготовку.

По [текущим правилам GitHub](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
вычисления self-hosted runners бесплатны. Это не отменяет отдельного учёта
хранилищ artifacts, caches и Packages. Здесь не разрешаются платные лимиты,
изменение тарифов или удаление существующих артефактов; собственный компьютер
также расходует электричество, диск и интернет.

## Что владельцу сделать в Windows

Повторно устанавливать Hyper-V не требуется. Эти действия выполняет владелец
вручную в удобное время. Доверенный launcher может запросить UAC только после
явного согласия владельца; подтверждение остаётся за владельцем. DISM и обход
Execution Policy не выполняются.

1. Выбрать доверенный контекст управления. Минимальный первый шаг — вручную
   открыть **Windows PowerShell → Запуск от имени администратора** и лично
   подтвердить UAC. Это временный контекст для проверки/управления хостом, не
   терминал для исполнения кода PR и не права будущего GitHub job.
2. В этом терминале перейти в проверенную копию репозитория и запустить только
   диагностику: `./deploy/ci/Test-CityGoRunnerHost.ps1`. Если локальная политика
   запрещает скрипт, остановиться: не применять `Bypass` или `Unrestricted`.
   При отдельном согласии владельца допустим `RemoteSigned` с областью
   `Process` только для доверенного административного окна; не менять
   `CurrentUser`, `LocalMachine`, `MachinePolicy` или `UserPolicy`.
   Проверить JSON: компонент/службу, доступные ресурсы, blockers. Поле
   `readyForVmProvisioning` не означает готовность CI или проверенную изоляцию.
3. В том же контексте выполнить read-only `Get-VM` либо открыть **Диспетчер
   Hyper-V** и проверить, что локальный хост доступен без ошибки прав. Не
   публиковать инвентарь личных ВМ. Это ещё не создание и не приёмка гостя.
4. Если нужна работа доверенного контроллера без постоянно повышенного
   терминала, владелец отдельно решает вопрос членства выбранной учётной записи
   в **Hyper-V Administrators / Администраторы Hyper-V** через **Управление
   компьютером → Локальные пользователи и группы → Группы**. Это широкое право
   управления Hyper-V, а не ограничение одной ВМ CityGo; его нельзя выдавать
   гостю, PR-коду или общему runner. Не добавлять учётную запись автоматически.
   Членство не меняет уже запущенный токен: после сохранения работы владелец
   сам завершает сеанс Windows и входит снова, затем повторяет пункты 2–3
   именно в новом контексте контроллера. Одна перезагрузка терминала не
   доказывает обновление токена.
5. Передать результат безопасной диагностики и сообщить, какой контекст получил
   управление. До подготовки и проверки точного базового образа, отдельного
   диска, сетевых запретов и внешнего удаления ВМ runner не регистрировать.
   Изменение токена управления не является разрешением открыть production,
   перенести privileged workflows или выдать гостю секреты.

Неповышенный участник Hyper-V Administrators может иметь право `Get-VM`, но
получить `admin_inventory_required` при полной инвентаризации Windows-компонентов.
В этом случае состояние компонентов проверяется отдельно в доверенной
повышенной консоли, а право управления — именно в токене контроллера. Не заменять
неизвестные поля на `Enabled` и не выдавать частичный снимок за полностью успешный
preflight.

Если Windows отдельно требует перезагрузку, владелец сохраняет работу и сам
выбирает её время. Автоматический reboot, отключение WSL/Docker и изменение
личных ВМ не входят в этот порядок. Скрипт не удостоверяет отсутствие всех
возможных pending-reboot состояний Windows.

Если Hyper-V отсутствует, пункты недоступны или установка завершилась ошибкой,
остановиться и сохранить только код ошибки. Не менять UEFI, корпоративные
политики, антивирус, правила firewall или политику исполнения скриптов без
отдельного решения владельца. Для read-only preflight использовать штатный
подготовленный инструмент `deploy/ci/Test-CityGoRunnerHost.ps1`; если его блокирует
локальная политика исполнения, не применять `Bypass` или `Unrestricted`.
Проверка состояний компонентов и служб не подтверждает отсутствие всех возможных
ожидающих перезагрузку изменений Windows.

Официальная инструкция Microsoft:
[включение Hyper-V в Windows](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/get-started/Install-Hyper-V#enable-hyper-v).

## Граница изоляции

Нужна полноценная отдельная Linux-ВМ со своим Docker Engine. Существующая рабочая
WSL с доступом к дискам Windows и общий Docker Desktop для этого не подходят.
Доступ к Docker socket позволяет коду контролировать Docker-хост; ограничение
пользователя внутри контейнера не заменяет изоляцию ВМ.

Для гостя запрещены:

- Windows/OneDrive/home mounts, общие папки, проброс дисков и clipboard;
- личный SSH-agent, Credential Manager, пользовательские `.env` и credentials;
- production БД, серверные конфиги, AI/payment/S3 keys;
- общий Docker daemon, build cache и сохраняющийся workspace от другого job.

Интернет нужен для GitHub, зависимостей, контейнерных образов и Playwright.
**NAT обеспечивает выход в сеть, но не изолирует гостя от LAN, Windows-хоста
или production endpoints.** До запуска кода PR отдельно настроить и проверить
ограничения на уровне доверенного хоста/гипервизора: запрет доступа к личным и
рабочим сетям, host services, metadata endpoints и production, при сохранении
необходимого DNS и внешнего HTTPS. Не использовать внешний bridged switch как
непроверенную замену изоляции. Проверять IPv4 и IPv6, а не только отсутствие
публичного входящего порта.

## Проверенные подготовительные инструменты

Эти инструменты не являются готовой фабрикой CI:

- `deploy/ci/Test-CityGoRunnerHost.ps1` — read-only инвентарь ресурсов.
- `deploy/ci/download-ubuntu-cloud-image.mjs` — два публичных metadata-файла,
  затем отдельная загрузка закреплённого образа. Внешняя проверка GPGV должна
  предшествовать загрузке диска; JSON-утверждение не заменяет проверку подписи.
  Исходный образ — generic amd64 Ubuntu 24.04, serial `20261017`, не Azure VHD.
  Используются неизменяемый release URL и точный полный fingerprint Canonical.
- `deploy/ci/Dockerfile.artifact-tools` — доверенный конвертер артефактов,
  **не** GitHub runner. Конвертация выполняется без сети, привилегий, Docker
  socket и личных mounts, с read-only исходником и единственным новым output
  directory. Увеличивать нужно отдельную QCOW2-копию **до** конвертации в VHDX:
  установленный qemu не поддерживает `resize` VHDX. Проверяются виртуальный
  размер 96 GiB и окончательный хеш VHDX.
- `deploy/ci/New-CityGoBootstrapVm.ps1` — по умолчанию только план; явный apply
  требует администратора, свежего приватного preflight с точным SHA-256,
  standalone VHDX ровно 96 GiB с точным SHA-256 и уникальной операции.
  Создаёт только новую выключенную ВМ с отключённым NIC. Не запускает гостя,
  не подключает switch, не регистрирует runner и не исправляет существующие ВМ.
- `deploy/ci/New-CityGoRunnerNetworkPlan.ps1` — только offline-предложение ACL.
  SHA-256 снимка и `planValid` не доказывают ни доверенность его источника,
  ни фактическое применение ACL. Неподтверждённые DHCP/NAT/классификация сетей
  блокируют план. Нужны отдельные enforcement/readback и реальные canary.

Запуск проверок: `pnpm test:ci-host`; он добавлен к `pnpm check`, существующие
проверки не удалены. Windows PowerShell behavioral tests выполняются на Windows;
при отсутствии подходящего PowerShell/Windows на Linux часть явно пропускается,
а не объявляется воспроизведённой. Локальные synthetic tests не заменяют CI
точного main SHA и не разрешают запуск PR-кода в непроверенном госте.

При первой реальной загрузке downloader сообщил общий отказ после передачи
данных. Независимая проверка файла подтвердила полный размер и точный SHA-256
из подписанного манифеста; исходный отказ не был переписан на success.
Причина того транспортного/finalize-сбоя не доказана. В downloader добавлены
безопасные коды этапов и сохранение первичной ошибки при последующем сбое close;
полный payload с ошибкой завершения потока по-прежнему считается отказом.

## Жизненный цикл одной проверки

Базовый образ содержит Ubuntu 24.04 amd64, Python 3.12, Node 24, pnpm 10.15.0,
Docker/Compose, Git, curl, OpenSSL, age, `systemd-analyze` и зависимости Playwright.
Версии и исходные загрузки проверяются до сохранения образа. В образе нет
регистрации runner, checkout, пользовательских данных или секретов. Ресурсы ВМ
подбираются по свободным ресурсам компьютера; 32 ГБ на хосте не являются обещанием
доступности всех 32 ГБ гостю.

Доверенный контроллер вне гостя должен обеспечивать следующий порядок:

1. Создать новую ВМ и отдельный диск из чистого базового образа, проверить сетевую
   изоляцию и отсутствие общих дисков.
2. Зарегистрировать runner на один job с `--ephemeral`. Учётные данные управления
   runners не передавать в job; ограниченный регистрационный материал не
   сохранять в образе или журнале.
3. Выполнить ровно один job. Для CI разрешены только временный read-only доступ
   к репозиторию и вымышленные тестовые данные.
4. Сохранить необходимые обезличенные диагностические журналы. Завершение
   определять по доверенному состоянию задания, не по строке в выводе гостя.
5. После успеха, ошибки, cancellation, timeout или обрыва удалить только точно
   принадлежащие этому запуску ВМ и диск. Повторный запуск получает новый клон.

`--ephemeral` снимает регистрацию после одного job, но сам не стирает гостевой
диск. Очистка внутри потенциально скомпрометированного гостя тоже не доказывает
чистоту. Удаление и контроль зависших ресурсов выполняет внешний контроллер.
Этот механизм ещё требуется реализовать и проверить; обычный постоянно работающий
runner не считается его заменой.
[Справочник GitHub о self-hosted runners](https://docs.github.com/en/actions/reference/runners/self-hosted-runners).

Компьютер должен оставаться включённым и иметь сеть до окончания задания. Не
менять глобальные настройки сна автоматически. Сбой компьютера не разрешает
повторять неизвестную серверную миграцию: для неё действуют обычные правила
durable pending и восстановления.

## Отдельные уровни доверия

| Назначение           | Допустимый код и доступ                                                                           | Где исполнять                                               |
| -------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| CI и Container smoke | PR и main, read-only repository token, синтетические БД                                           | Новый изолированный CI guest на каждый job                  |
| Publisher            | Проверенный main, временный `packages:write`, без SSH-key                                         | В будущем отдельный чистый guest, никогда не исполнявший PR |
| Deploy               | Доверенный main workflow, artifact проверенного publisher, ограниченный SSH-key только в этом job | В будущем ещё один чистый guest после publisher             |

**Publisher и deploy остаются GitHub-hosted до отдельной приёмки изоляции,
маршрутизации и разрешения их переноса.** Метки `runs-on` — не механизм
авторизации: PR может изменить YAML и запросить метку privileged runner.
Для такого пула нужна проверенная политика допуска точных workflow refs,
например runner group с ограничением на `deploy-main.yml@refs/heads/main` и
`release-candidate.yml@refs/heads/main`.

В read-only проверке интерфейса организации CityGo-Tech (Free) 19 октября
подтверждены кнопка `New runner group` и вариант `Selected workflows` в
`Workflow access`. Группа `Default` допускает все private repositories;
зарегистрированных runners нет. Никакие варианты не выбирались и не сохранялись,
группы и runners не создавались. Наличие пункта интерфейса **не означает**, что
ограничение уже настроено или доказано его применение. До переноса publisher/deploy
нужно отдельно проверить фактический запрет чужих workflow refs и PR. Если такую
политику применить или проверить нельзя, перенос остановить, а не заменять проверку
другой меткой или условием из изменяемого PR.
[Ограничения доступа runner groups](https://docs.github.com/en/enterprise-cloud%40latest/actions/how-tos/manage-runners/self-hosted-runners/manage-access).

Нельзя provision общий единственный runner сначала для publisher: тот может
занять слот и ждать CI/Container, которым негде исполняться. Фабрика сначала
обслуживает проверки. Привилегированные ВМ в будущем создаются только после
соответствующих gates либо получают отдельную ёмкость.

## Поэтапный перенос workflows

1. **Готовность хоста.** После ручного включения и перезагрузки повторно проверить
   Hyper-V и подготовить чистый guest. Пока готовность не подтверждена,
   `runs-on` не менять.
2. **Приёмка изоляции.** Синтетический локальный canary проверяет сеть, файловые
   границы, собственный Docker, порты и удаление ВМ после success/failure/cancel.
   Это ещё не успешный GitHub CI.
3. **Одноразовый CI canary в GitHub.** Зарегистрировать только непривилегированный
   ephemeral runner после проверки доступа. Не выдавать AI, оплату, S3 или SSH.
4. **CI и Container smoke.** Отдельным проверяемым изменением перенести только
   эти jobs. Сохранить workflow names `CI` и `Container smoke`, paths `ci.yml`
   и `container-smoke.yml`, jobs `verify` и `production-images`, события PR/push
   main, все шаги и assertions. Для checkout не сохранять credentials.
5. **Проверки точного main.** После merge получить новые успешные push-checks
   точного main SHA. Локальный лог, зелёный PR другого SHA или старый успешный
   attempt не заменяют их. Не добавлять `continue-on-error`, искусственный
   success, отключение обязательных тестов или fallback на платный runner.
6. **Отдельная приёмка privileged pools.** Только после проверки границы workflow
   access и внешнего удаления ВМ обсуждать перенос publisher/deploy. Сохранить
   `publish-candidate` → `deploy`, отдельные permissions и SSH только в deploy.

Существующие release gates остаются обязательными: текущий `main`, оба точных
push-checks, последний run/attempt, проверка repository/workflow, source labels,
digest/readback трёх образов, artifact ID/hash, backup и серверные разрешения.
`cancel-in-progress: false` для выпуска сохраняется. Серверный контроллер не
обновляется и не получает новых прав от одной смены runner.

См. [автоматическое обновление main](automatic-main-deployment.md),
[подготовку candidate](release-candidate.md) и
[действия оператора выпуска](release-operator.md).

## Особенности проверок CityGo

`Container smoke` требует настоящий Linux. Штатный стенд использует host
networking, 3000/80/443, а CI service PostgreSQL — 5432. В госте не должно быть
других job или личных сервисов на этих портах. Гостевой Docker должен работать
независимо от Docker Desktop.

Исторические ограничения WSL/Desktop и локальные overrides описаны в
[отчёте CG-009](../implementation/cg-009-plan-ownership.md). Тот адаптированный
локальный прогон не доказывает прохождение неизменённого современного workflow.
Не ослаблять host-network, identity, transactional rollback или role assertions
ради воспроизведения старого обхода.

Release harness создаёт `.local/release-candidate` и доказательства с `flag: "wx"`.
Повторно использованный workspace может остановиться на существующих файлах.
Новый guest решает это без удаления пользовательских каталогов. Не применять
общие `docker system prune`, `compose down -v` или очистку рабочей копии владельца.

Полнота CI включает typecheck, check, browser E2E, mobile export и проверку
артефактов окружения. Container-набор включает controller tests, release guards,
реальный PostgreSQL, образы и registry rehearsal. Python/age/systemd-зависимости
не заменяются увеличением числа skip. Диагностический canary не выполняет
реальные AI, платежи, возвраты, cloud backup или deploy.
