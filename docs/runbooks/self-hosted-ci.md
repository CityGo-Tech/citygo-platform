# Изолированный локальный CI

CityGo планирует выполнять проверки GitHub Actions в одноразовых Linux-ВМ на
локальном компьютере, сохраняя приватность репозитория и существующие условия
выпуска. Этот путь не требует покупки GitHub-hosted compute. Настройка не должна
давать коду из PR доступ к личным файлам, ключам или рабочему серверу.

## Текущее состояние: база подготовлена, offline-клон проверен, CI ещё не принят

На 19 октября 2026 года Hyper-V включён владельцем. Read-only preflight
**успешно выполнен в отдельно подтверждённом административном процессе**.
Подпись и SHA-256 официального Ubuntu-образа проверены. Владелец успешно выполнил
доверенное продолжение V3; Hyper-V подтвердил состояние ВМ `Running`. Затем
read-only проверка по SSH с закреплённым host key подтвердила загрузку Ubuntu
24.04, Python 3.12.3, `cloud-init: done`, отсутствие ошибок cloud-init и
`cloud-final: success`. Независимое повторение подтвердило Node 24.22.0,
pnpm 10.15.0, Python 3.12.3, native Linux Docker 29.1.3, Compose/buildx и
запуск Chromium на локальном data URI без внешних запросов. Это не запуск
контейнерного приложения и не доказательство browser/network isolation. Работающий CI и
сетевая изоляция не приняты; runner не зарегистрирован, workflows не перенесены.

Отдельная разрешённая подготовка базы удалила гостевой bootstrap-вход,
его sudo-строку, SSH host keys и persistent cloud-init копии; все гостевые
проверки очистки прошли. После штатного выключения независимый native-инвентарь
подтвердил `Off`, пустой DVD, отключённый NIC и отсутствие snapshots.
Первая попытка host-finalization сохранила отказ на readback DVD после операций;
этот отказ не переписан на success. После ограниченного ожидания свежего
readback отдельное продолжение завершило finalization: сохранён новый хеш диска
и `sealed-base.json` только для локального canary. Первая попытка копирования
клона остановилась до создания ВМ; независимая сверка подтвердила полное
совпадение копии с базой. Адресное продолжение той же попытки заново проверило
хеши, разные файловые идентичности исходника и копии, отсутствие внешних ссылок
и точное содержимое каталога; старый partial receipt сохранён без изменений.
Создана ровно одна ВМ-клон. На ней прошёл реальный offline scratch-контейнер
собственного Docker без загрузок, сети и mounts; подтверждены отсутствие
bootstrap-входа, новые machine-id/host key и версии Node/pnpm. После штатного
выключения удалены только этот клон, его диск и пустые принадлежащие ему каталоги.
Финальный native readback подтвердил отсутствие клона и диска, Off исходной базы
и неизменность её post-seal SHA. Отказы очистки из-за native-типа DiskIdentifier
и отдельного confirmation сохранены; исправления покрыты regression tests.
Обычный creator по-прежнему не принимает существующий каталог. Базовый образ
не объявлен принятым для CI: отключённый тест не проверяет connected isolation.

Следующий отдельный тестовый клон создан штатным creator и независимо проверен
в состоянии **Off / disconnected**. Для него сохранены полный creation manifest
и свежий закрытый снимок адресов, маршрутов, HNS и DNS production. Сетевые ACL
на этот клон не применялись, seed не подключался. Затем на нём начат реальный
offline early-startup stop: проверка graceful component отказала из-за отличия
native DeviceID от ожидаемого формата. Клон остался Running без сети; первоначальный
тест сохранён как **failed**, не объявлен пройденным после исправления кода.
Отдельная разовая reconciliation заново проверила immutable manifest и полный
native identity, закрепила исходные failure/intent по SHA и после истёкшего grace
выполнила один TurnOff. После независимого Off-readback удалены только этот клон,
его диск и пустые owned-папки. Подтверждены отсутствие ВМ/диска и прежний SHA
выключенной исходной базы. Это проверка адресного восстановления после сбоя,
а не прошедший без вмешательства timeout/watchdog сценарий.
Инвентарь хоста содержит VPN/туннельные маршруты: их нельзя автоматически
считать ни безопасным интернетом, ни целиком запрещённой LAN.

Добавлены отдельные инструменты CI-policy и остановки owned canary с
AST/mock-проверками. Это подготовка, а не результат испытаний на подключённой ВМ.
Для текущей схемы Default Switch ещё не доказаны L2/ARP/NDP, подмена источника и
stateful replies. Само наличие Hyper-V IP ACL не закрывает эти пункты.
Это **не утверждение об обнаруженной уязвимости Hyper-V**: Microsoft описывает
защиту виртуального коммутатора, но её действие в конкретной схеме ещё нужно
проверить. Владелец отдельно разрешил схему Private switch + доверенная ВМ-шлюз
с учётом смены внешних сетей. **Private-коммутатор создан**: native readback
подтвердил `Private`, ноль подключённых host/guest NIC и неизменность прежних
switch/NIC/NAT. Первый pre-creation отказ сохранён: у native management-NIC
VMId оказался null. Он допускается только при явном `IsManagementOs=true`;
пустой VMId гостя по-прежнему запрещён. ВМ-шлюз ещё не создана, IP forwarding
не включён; старые NAT, firewall, WSL, Docker и production не перенастраивались.

- Компьютер: Windows 11 Pro, 32 ГБ оперативной памяти. Подтверждены состояние
  компонента Hyper-V `Enabled` и службы `vmms` `Running`; это не проверка гостевой
  изоляции и не подтверждение отсутствия всех ожидающих перезагрузку изменений.
- Обычный процесс разработки остаётся без административных прав. Владелец лично
  подтвердил UAC для отдельного доверенного процесса. В нём успешно прочитаны
  инвентари Hyper-V и сети; подтверждены ресурсы для начального профиля 4 CPU,
  6 ГБ RAM, 96 ГБ диска с сохранением резерва хосту. Это не разрешение выполнять
  PR-код с повышенными правами.
- Windows PowerShell первоначально заблокировал локальный `.ps1`. После
  отдельного согласия владельца использован `RemoteSigned` только для одного
  административного процесса. Постоянные политики, корпоративные ограничения,
  группы Windows и службы не менялись; `Bypass`/`Unrestricted` не применялись.
- Ранее отменённый UAC при попытке DISM остаётся историческим фактом. Повторять
  установку, автоматически повышать права или подтверждать UAC за владельца
  нельзя; компонент уже включён вручную.
- Проверенная фабрика одноразовых ВМ и зарегистрированный runner ещё не готовы.
  Успешный локальный клон не заменяет описанный ниже жизненный цикл jobs — это
  требования к реализации, не действующая автоматизация GitHub.
- Bootstrap-ВМ — Gen2, 4 CPU, 6 ГБ static RAM, standalone VHDX 96 GiB,
  Secure Boot с шаблоном `MicrosoftUEFICertificateAuthority`. Независимое
  read-only считывание **при создании** подтвердило `Off`, один отключённый NIC,
  выключенные автозапуск/checkpoints и точный хеш диска. После продолжения V3
  подключён тот же NIC с проверенными существующими ACL, Ubuntu загрузилась и
  отчёт установки получен. Независимая проверка инструментов прошла;
  приёмка изоляции и одноразового жизненного цикла ещё не завершена.
- Начальная попытка сохранила ВМ, но отклонила служебные ACL, добавленные
  Hyper-V к своей папке, при записи receipt. Исторический отказ сохранён;
  независимая проверка состояния не объявлена успешным выполнением всей попытки.
  Контрольные отчёты должны находиться в отдельной защищённой папке вне
  Hyper-V-managed каталога. Общие служебные права Hyper-V не переносятся
  на каталог контроллера или его будущие секреты.
- Workflows не перенесены: `CI`, `Container smoke`, publisher и deploy пока
  используют GitHub-hosted runners. Их отказ по billing не считается успешной
  проверкой и не обходится локальным отчётом.
- Покупки, оплаты GitHub, изменение видимости репозитория, выдача новых
  серверных прав и открытие приложения не входят в эту подготовку.

По [текущим правилам GitHub](https://docs.github.com/en/billing/concepts/product-billing/github-actions)
вычисления self-hosted runners бесплатны. Это не отменяет отдельного учёта
хранилищ artifacts, caches и Packages. Здесь не разрешаются платные лимиты,
изменение тарифов или удаление существующих артефактов; собственный компьютер
также расходует электричество, диск и интернет.

## Что владельцу сделать в Windows

Повторно устанавливать Hyper-V не требуется. Эти действия выполняет владелец
вручную в удобное время. Доверенный launcher может запросить UAC только после
явного согласия владельца; подтверждение остаётся за владельцем. DISM и обход
Execution Policy не выполняются.

1. Выбрать доверенный контекст управления. Минимальный первый шаг — вручную
   открыть **Windows PowerShell → Запуск от имени администратора** и лично
   подтвердить UAC. Это временный контекст для проверки/управления хостом, не
   терминал для исполнения кода PR и не права будущего GitHub job.
2. В этом терминале перейти в проверенную копию репозитория и запустить только
   диагностику: `./deploy/ci/Test-CityGoRunnerHost.ps1`. Если локальная политика
   запрещает скрипт, остановиться: не применять `Bypass` или `Unrestricted`.
   При отдельном согласии владельца допустим `RemoteSigned` с областью
   `Process` только для доверенного административного окна; не менять
   `CurrentUser`, `LocalMachine`, `MachinePolicy` или `UserPolicy`.
   Проверить JSON: компонент/службу, доступные ресурсы, blockers. Поле
   `readyForVmProvisioning` не означает готовность CI или проверенную изоляцию.
3. В том же контексте выполнить read-only `Get-VM` либо открыть **Диспетчер
   Hyper-V** и проверить, что локальный хост доступен без ошибки прав. Не
   публиковать инвентарь личных ВМ. Это ещё не создание и не приёмка гостя.
4. Если нужна работа доверенного контроллера без постоянно повышенного
   терминала, владелец отдельно решает вопрос членства выбранной учётной записи
   в **Hyper-V Administrators / Администраторы Hyper-V** через **Управление
   компьютером → Локальные пользователи и группы → Группы**. Это широкое право
   управления Hyper-V, а не ограничение одной ВМ CityGo; его нельзя выдавать
   гостю, PR-коду или общему runner. Не добавлять учётную запись автоматически.
   Членство не меняет уже запущенный токен: после сохранения работы владелец
   сам завершает сеанс Windows и входит снова, затем повторяет пункты 2–3
   именно в новом контексте контроллера. Одна перезагрузка терминала не
   доказывает обновление токена.
5. Передать результат безопасной диагностики и сообщить, какой контекст получил
   управление. До подготовки и проверки точного базового образа, отдельного
   диска, сетевых запретов и внешнего удаления ВМ runner не регистрировать.
   Изменение токена управления не является разрешением открыть production,
   перенести privileged workflows или выдать гостю секреты.

Неповышенный участник Hyper-V Administrators может иметь право `Get-VM`, но
получить `admin_inventory_required` при полной инвентаризации Windows-компонентов.
В этом случае состояние компонентов проверяется отдельно в доверенной
повышенной консоли, а право управления — именно в токене контроллера. Не заменять
неизвестные поля на `Enabled` и не выдавать частичный снимок за полностью успешный
preflight.

Если Windows отдельно требует перезагрузку, владелец сохраняет работу и сам
выбирает её время. Автоматический reboot, отключение WSL/Docker и изменение
личных ВМ не входят в этот порядок. Скрипт не удостоверяет отсутствие всех
возможных pending-reboot состояний Windows.

Если Hyper-V отсутствует, пункты недоступны или установка завершилась ошибкой,
остановиться и сохранить только код ошибки. Не менять UEFI, корпоративные
политики, антивирус, правила firewall или политику исполнения скриптов без
отдельного решения владельца. Для read-only preflight использовать штатный
подготовленный инструмент `deploy/ci/Test-CityGoRunnerHost.ps1`; если его блокирует
локальная политика исполнения, не применять `Bypass` или `Unrestricted`.
Проверка состояний компонентов и служб не подтверждает отсутствие всех возможных
ожидающих перезагрузку изменений Windows.

Официальная инструкция Microsoft:
[включение Hyper-V в Windows](https://learn.microsoft.com/en-us/windows-server/virtualization/hyper-v/get-started/Install-Hyper-V#enable-hyper-v).

## Граница изоляции

Нужна полноценная отдельная Linux-ВМ со своим Docker Engine. Существующая рабочая
WSL с доступом к дискам Windows и общий Docker Desktop для этого не подходят.
Доступ к Docker socket позволяет коду контролировать Docker-хост; ограничение
пользователя внутри контейнера не заменяет изоляцию ВМ.

Для гостя запрещены:

- Windows/OneDrive/home mounts, общие папки, проброс дисков и clipboard;
- личный SSH-agent, Credential Manager, пользовательские `.env` и credentials;
- production БД, серверные конфиги, AI/payment/S3 keys;
- общий Docker daemon, build cache и сохраняющийся workspace от другого job.

Интернет нужен для GitHub, зависимостей, контейнерных образов и Playwright.
**NAT обеспечивает выход в сеть, но не изолирует гостя от LAN, Windows-хоста
или production endpoints.** До запуска кода PR отдельно настроить и проверить
ограничения на уровне доверенного хоста/гипервизора: запрет доступа к личным и
рабочим сетям, host services, metadata endpoints и production, при сохранении
необходимого DNS и внешнего HTTPS. Не использовать внешний bridged switch как
непроверенную замену изоляции. Проверять IPv4 и IPv6, а не только отсутствие
публичного входящего порта.

## Проверенные подготовительные инструменты

Эти инструменты не являются готовой фабрикой CI:

- `deploy/ci/Test-CityGoRunnerHost.ps1` — read-only инвентарь ресурсов.
- `deploy/ci/download-ubuntu-cloud-image.mjs` — два публичных metadata-файла,
  затем отдельная загрузка закреплённого образа. Внешняя проверка GPGV должна
  предшествовать загрузке диска; JSON-утверждение не заменяет проверку подписи.
  Исходный образ — generic amd64 Ubuntu 24.04, serial `20261017`, не Azure VHD.
  Используются неизменяемый release URL и точный полный fingerprint Canonical.
- `deploy/ci/Dockerfile.artifact-tools` — доверенный конвертер артефактов,
  **не** GitHub runner. Конвертация выполняется без сети, привилегий, Docker
  socket и личных mounts, с read-only исходником и единственным новым output
  directory. Увеличивать нужно отдельную QCOW2-копию **до** конвертации в VHDX:
  установленный qemu не поддерживает `resize` VHDX. Проверяются виртуальный
  размер 96 GiB и окончательный хеш VHDX.
- `deploy/ci/New-CityGoBootstrapVm.ps1` — по умолчанию только план; явный apply
  требует администратора, свежего приватного preflight с точным SHA-256,
  standalone VHDX ровно 96 GiB с точным SHA-256 и уникальной операции.
  Создаёт только новую выключенную ВМ с отключённым NIC. Не запускает гостя,
  не подключает switch, не регистрирует runner и не исправляет существующие ВМ.
- `deploy/ci/New-CityGoRunnerNetworkPlan.ps1` — только offline-предложение ACL.
  SHA-256 снимка и `planValid` не доказывают ни доверенность его источника,
  ни фактическое применение ACL. Неподтверждённые DHCP/NAT/классификация сетей
  блокируют план. Нужны отдельные enforcement/readback и реальные canary.
- `deploy/ci/Set-CityGoBootstrapNetwork.ps1` — отдельный **trusted bootstrap**,
  не политика допуска CI jobs. Только после явного apply на точной выключенной
  ВМ добавляет ACL её единственного NIC, полностью сверяет native readback,
  подключает существующий Default Switch и повторяет сверку. Не запускает ВМ,
  не меняет NAT, Windows firewall, switches или чужие адаптеры. При ошибке
  отключает только подтверждённый owned NIC; partial ACL и evidence сохраняются.
  Допускает лишь узкий SSH-вход с gateway Windows-хоста, публичные TCP 80/443,
  фиксированные DNS и DHCP 67/68; IPv6, специальные/локальные адреса и известные
  production IP запрещаются на vNIC до подключения сети.
  Второй точный путь `network-resume-inventory.json` позволяет построить план
  по новому hash-связанному снимку для сверки уже существующих ACL. Запрет
  повторного apply при наличии результата или ACL сохраняется; старый inventory
  и receipt не перезаписываются и не «освежаются» заменой даты.
- `deploy/ci/seal-bootstrap-guest.sh` — отдельная очистка доверенной bootstrap-ВМ
  после успешного повторения toolchain. По умолчанию только read-only plan;
  apply удаляет один известный bootstrap authorized key, его точную sudo-строку
  с сохранением остальных строк, стандартные SSH host keys и штатные cloud-init
  копии через `cloud-init clean --logs --seed --machine-id`. Пользовательские
  папки и произвольные логи не очищаются. Штатное выключение и отсоединение ISO
  являются отдельными действиями; содержимое tmpfs исчезает только после Off.
- `deploy/ci/Finalize-CityGoSealedBase.ps1` связывает приватные отчёты с raw SHA,
  проверяет фактический Off и оборудование точной ВМ, отсоединяет только её
  известный seed и NIC и закрепляет **новый** хеш остановленного диска.
  Полученный `sealed-base.json` разрешает только локальную проверку клона,
  а не GitHub jobs. Исходный предустановочный SHA после загрузки ОС уже не актуален.
- `deploy/ci/New-CityGoCanaryVm.ps1` создаёт только один новый Off/disconnected
  standalone-клон; при копировании исходник удерживается под read lock.
  Уникальный DiskIdentifier меняется только у проверенной новой копии.
  `Remove-CityGoCanaryVm.ps1` удаляет лишь Off-ВМ и диск из полного immutable
  creation manifest. Чужие ссылки, включая цепочки AVHDX, checkpoints,
  reparse points и посторонние файлы блокируют очистку. Нет общего prune,
  принудительного выключения или рекурсивного удаления; evidence сохраняется.
  Смена ID новой проверенной копии использует штатный неинтерактивный
  `Set-VHD -ResetDiskIdentifier -Force`; база не изменяется. После typed ack и
  повторных проверок exact ID/Off/диска `Remove-VM -VM ... -Force -Confirm:$false`
  подавляет дополнительный native confirmation, который не отключается одним
  `Confirm=false`. Это не разрешение выключать работающую ВМ или обходить guards.
  `Force` не применяется к `Remove-Item`; рекурсивной очистки нет.
  [Семантика Remove-VM](https://learn.microsoft.com/en-us/powershell/module/hyper-v/remove-vm).
  Строковый native DiskIdentifier нормализуется через GUID с отказом для нулевого,
  некорректного или чужого ID. Failed receipt содержит только фиксированные
  этап/код ошибки, без native exception text; успешный receipt сохраняет схему.
  Отдельный `canary-resume-creation.json` принимается cleanup только как новый
  COMPLETE manifest, связанный raw SHA с исходным pre-VM partial receipt
  старого формата и строгим `canary-resume-verification.json`. Оба файла
  read-locked до конца очистки. Сам partial по-прежнему не разрешает удаление;
  исходная история не переименовывается и не переписывается.
- `deploy/ci/render-offline-canary-seed.mjs` создаёт публичный NoCloud seed
  без аккаунтов, паролей и ключей, с отключёнными DHCP/RA/link-local.
  `offline-clone-canary.py` проверяет этот seed, отсутствие bootstrap-входа,
  выбранных checkout/runner путей и shared-host FS, отсутствие внешних адресов
  и маршрутов и запускает собственный scratch-контейнер из локально собранного
  статического бинарника: без pulls, сети, mounts и привилегий. Только точные
  новые container/image IDs удаляются после проверки.
  Для отчёта нужен штатный Ubuntu KVP daemon; опубликованный собственный ключ
  pool1 использует POSIX-блокировку и ограничен 1022 ASCII-символами с учётом
  преобразования Hyper-V в UTF-16. Хост разбирает это как недоверенные данные,
  не как команды. Этот отключённый тест **не** подтверждает connected CI ACL.
- `deploy/ci/Set-CityGoCanaryNetwork.ps1` готовит direct-IP политику только для
  одной Off-ВМ из полного creation manifest. Сверяет хеши reviewed helpers,
  свежие host IP / маршруты обеих семей / HNS / production DNS и native
  конфигурацию ВМ. До подключения owned NIC сверяет весь набор ACL, после
  подключения повторяет readback. Ошибка сохраняет evidence и отключает только
  тот же exact NIC. Bootstrap SSH и неподтверждённый DHCP candidate не допускаются;
  существующие ACL не заменяются. По умолчанию только plan, без применения.
  Даже successful apply не означает принятую изоляцию. Разрешённый внешний HTTPS
  не блокирует все возможные косвенные обращения через прокси/DoH; проверки
  прямых адресов нельзя объявлять доказательством такого запрета.
- `deploy/ci/Stop-CityGoOwnedCanaryVm.ps1` — отдельный элемент lifecycle,
  **не готовый внешний watchdog**. При apply удерживает manifest/helper/seed
  под read lock и повторно проверяет exact VM/NIC/диск, firmware и отсутствие
  чужих ссылок. Сначала durable intent, затем graceful shutdown через привязанный
  к этой ВМ CIM с `Force=false`; только после grace deadline допускается один
  `Stop-VM -TurnOff -AsJob` с отдельным durable dispatch intent. `Stop-VM -Force`
  не используется. Success требует фактического `Off`; `Stopping` разрешён
  исключительно в ограниченном read-only ожидании, а не для новой команды.
  При неоднозначном прерывании после dispatch повторный TurnOff не отправляется.
  Истёкшее окно, изменённая identity или неуспешный readback сохраняют отказ
  для адресного разбора, а не расширяют права очистки. VM-read ACE допускается
  только на exact seed и его каталоге; control/helper/evidence остаются private.
  Удаление выполняет другой helper только после независимого Off-readback.
  Реальные сценарии зависшего гостя, отмены job и обрыва host-контроллера ещё
  не пройдены; mocks не заменяют эти испытания.
  После native-отказа поддержаны оба ограниченных формата shutdown DeviceID:
  reference `Microsoft:VMGUID\GUID` и наблюдённый `Microsoft:GUID`. Ни один не
  считается доказательством владения: требуется ровно одна системная
  [CIM-связь Msvm_SystemDevice](https://learn.microsoft.com/en-us/windows/win32/hyperv_v2/msvm-systemdevice)
  с `Msvm_ComputerSystem.Name`, равным exact VM ID. Эта связь отдельно подтверждена
  на реальном клоне read-only запросом; исправленный полный stop workflow на новом
  госте ещё не воспроизведён. Отсутствующая/чужая/множественная связь запрещает
  dispatch, а не разрешает мгновенный poweroff.
- `deploy/ci/New-CityGoPrivateSwitch.ps1` создаёт только новый Private switch из
  operation-scoped имени. До native write записывает intent, повторно сверяет
  исходные switches/NIC/NAT, после — точный type/ID/notes и отсутствие любых
  подключений к новой сети. Нет host adapter, VM attach, NAT/firewall setters,
  удаления или автоматического adoption существующего коммутатора. Plan — без IO.
- `deploy/ci/private-gateway-policy.py` — **чистый генератор**, не installer.
  Готовит IPv4 default-drop filter/NAT и IPv6 drop для будущего доверенного шлюза;
  exact один CI IPv4, только публичный HTTPS и фиксированные DNS, узкий WAN DHCP.
  Special/LAN/host/production deny идут до established permits. Требуются hash
  host snapshot, фактические WAN/lease сведения, явная классификация префиксов;
  недопустимы широкий VPN `/0`, совпадение DNS с запретом или DHCP с production.
  Сейчас правила не применялись в Linux, forwarding не включался. Нужны installer,
  независимый readback, реальные canary и fail-closed контроль смены Wi-Fi/VPN.
  Свободный внешний HTTPS не является доказанным запретом всех косвенных прокси.
- Для самого первого доверенного boot возможен явно помеченный DHCP candidate:
  единственный `/32` адрес gateway из HNS ICS, **не** утверждение, что DHCP server
  уже наблюдался в lease. Это не широкое разрешение subnet и не допуск CI jobs.
  После boot нужно отдельно проверить фактический lease/server. В общей CI
  политике candidate-исключение не разрешается.
- `deploy/ci/bootstrap-user-data.template.yml` и `render-bootstrap-seed.mjs` —
  новый private NoCloud seed с уникальным instance-id, отдельным per-VM host key
  и только клиентским **public** key. Renderer не выполняет IO/процессы и не
  удостоверяет ключевую пару: вызывающая доверенная сторона отдельно сверяет
  `ssh-keygen -y` и public key. Все возвращённые строки считаются sensitive;
  не писать их в Git, Actions artifacts или общие логи.
- `deploy/ci/bootstrap-toolchain.sh` — установка только в доверенном Ubuntu 24.04
  guest: Python 3.12, native Docker/Compose из подписанных Ubuntu repositories,
  Node 24.22.0 с GPGV/full fingerprint и SHA-256, pnpm 10.15.0 и Playwright core
  1.63.0 с SRI. Используются отдельные пустые npm configs, без личных credentials,
  app checkout, install scripts приложения или runner registration. Exact dpkg
  versions фиксируются в отчёте; отдельный checksum Chromium здесь не закреплён.
  Успешная установка сама по себе не означает изоляцию или готовый golden image.

Ниже описаны **исторические отказы до успешного запуска V3**, а не текущее
состояние ВМ. До продолжения первый boot ещё не выполнялся: сетевые ACL были
применены и полностью сверены, но после отказа на следующем шаге owned NIC
отключили, сохранив ACL и отчёты.
Автоматические запросы запуска остановились **до исполнения команды** из-за
недоступности сервиса проверки разрешений инструмента. Затем владелец лично
выполнил hash-проверенную команду в административном окне: она остановилась
на `identity / directory-not-plain`, до сетевых изменений и попытки запуска.
Причина подтверждена: родительские каталоги исходников в OneDrive имеют
`ReparsePoint`. Это отказ защитной проверки пути, не ошибка гостевой ОС.

Повторная попытка не ослабляет plain-path guard: только два точных публичных
helper-скрипта читаются из OneDrive как ограниченные по размеру недоверенные
bytes, сверяются с утверждёнными SHA-256 и копируются через `CreateNew` в
отдельный protected control directory вне OneDrive. Выполняются только копии
после повторной проверки хеша и с удержанием read-lock. Control, исполняемые
копии и ISO по-прежнему не допускают reparse-предков. Старый failure остаётся
неизменным; та вторая попытка допускалась только по его точному хешу и строгим флагам
`networkApplied=false` / `bootAttempted=false`, новый результат записывается
под отдельным именем. Никакие прошлые отказы не переписываются на success.
Вторая ручная попытка прошла копирование, сетевой apply/readback и подключение
ISO, затем остановилась на `attach_private_seed / attached-seed-acl-unexpected`.
Hyper-V добавил на ISO известную Windows platform capability с `Read|Synchronize`.
Она не считается уникальной для ВМ. Продолжение допускает только точный полный
SID, exact readonly mask, explicit ACE без наследования на данном ISO с
проверенными хешем и owned attachment. Каталог seed и control не получают такого
исключения; служебные ACE не удаляются и не добавляются. Проверены ACL metadata,
а не содержимое seed. См. [пояснение Microsoft о capability SID](https://learn.microsoft.com/en-us/troubleshoot/windows-server/windows-security/sids-not-resolve-into-friendly-names).

Продолжение сначала получает свежий снимок сети и требует полного совпадения
существующих native ACL с новым планом. Оно не добавляет/удаляет ACL или DVD и
не вызывает старый apply повторно. Перед подключением и запуском повторяются
проверки owned Off/disconnected ВМ, диска, seed, IP/routes/DNS и срока снимка;
при отличии — остановка с отдельным результатом.

Владелец успешно выполнил это продолжение V3. Существующие ACL повторно сверены
со свежим планом и использованы **без изменения правил**; повторного сетевого
apply, добавления/удаления ACL или DVD не было. Проверка существующего ISO
допустила только описанную выше точную native platform capability, не добавляя
прав к seed-каталогу или control. Новый отдельный результат подтвердил
`vmState=Running`, `networkApplied=true` и повторное использование существующих
ACL; production не изменялся. Прежние отказы и receipts сохранены неизменными.

Последующая read-only проверка по SSH с host-key pinning подтвердила Ubuntu
24.04, Python 3.12.3 и успешное завершение cloud-init: состояние `done`, ноль
ошибок, результат `cloud-final` — `success`. Получен валидный отчёт установки:
Node 24.22.0, pnpm 10.15.0, Playwright 1.63.0 и пакеты native Docker/Compose.
Это отчёт установки, а не завершённая независимая приёмка запуска всех бинарных
инструментов, Docker и браузера: такой replay ещё идёт.

В systemd lease наблюдён фактический DHCP server, совпавший с ранее явно
помеченным HNS gateway candidate. Это не приёмка сетевой изоляции. Сетевые canary,
golden seal и одноразовый жизненный цикл ещё не приняты; GitHub runner не
зарегистрирован, кода PR в госте не выполняли.

Перед golden-образом необходимо удалить временные bootstrap authorized keys,
sudo-доступ, старые host keys, отсоединить seed и убрать cloud-init cached
user-data/seed copies. Каждый новый job получает собственную идентичность.
Клиентский private key остаётся только в защищённом host control directory;
существующие личные/production SSH-ключи для bootstrap не используются.

Запуск проверок: `pnpm test:ci-host`; он добавлен к `pnpm check`, существующие
проверки не удалены. Windows PowerShell behavioral tests выполняются на Windows;
при отсутствии подходящего PowerShell/Windows на Linux часть явно пропускается,
а не объявляется воспроизведённой. Локальные synthetic tests не заменяют CI
точного main SHA и не разрешают запуск PR-кода в непроверенном госте.

При первой реальной загрузке downloader сообщил общий отказ после передачи
данных. Независимая проверка файла подтвердила полный размер и точный SHA-256
из подписанного манифеста; исходный отказ не был переписан на success.
Причина того транспортного/finalize-сбоя не доказана. В downloader добавлены
безопасные коды этапов и сохранение первичной ошибки при последующем сбое close;
полный payload с ошибкой завершения потока по-прежнему считается отказом.

## Жизненный цикл одной проверки

Планируемый базовый образ должен содержать Ubuntu 24.04 amd64, Python 3.12, Node 24, pnpm 10.15.0,
Docker/Compose, Git, curl, OpenSSL, age, `systemd-analyze` и зависимости Playwright.
Версии и исходные загрузки проверяются до сохранения образа. В образе нет
регистрации runner, checkout, пользовательских данных или секретов. Ресурсы ВМ
подбираются по свободным ресурсам компьютера; 32 ГБ на хосте не являются обещанием
доступности всех 32 ГБ гостю.

Доверенный контроллер вне гостя должен обеспечивать следующий порядок:

1. Создать новую ВМ и отдельный диск из чистого базового образа, проверить сетевую
   изоляцию и отсутствие общих дисков.
2. Зарегистрировать runner на один job с `--ephemeral`. Учётные данные управления
   runners не передавать в job; ограниченный регистрационный материал не
   сохранять в образе или журнале.
3. Выполнить ровно один job. Для CI разрешены только временный read-only доступ
   к репозиторию и вымышленные тестовые данные.
4. Сохранить необходимые обезличенные диагностические журналы. Завершение
   определять по доверенному состоянию задания, не по строке в выводе гостя.
5. После успеха, ошибки, cancellation, timeout или обрыва удалить только точно
   принадлежащие этому запуску ВМ и диск. Повторный запуск получает новый клон.

`--ephemeral` снимает регистрацию после одного job, но сам не стирает гостевой
диск. Очистка внутри потенциально скомпрометированного гостя тоже не доказывает
чистоту. Удаление и контроль зависших ресурсов выполняет внешний контроллер.
Этот механизм ещё требуется реализовать и проверить; обычный постоянно работающий
runner не считается его заменой.
[Справочник GitHub о self-hosted runners](https://docs.github.com/en/actions/reference/runners/self-hosted-runners).

Компьютер должен оставаться включённым и иметь сеть до окончания задания. Не
менять глобальные настройки сна автоматически. Сбой компьютера не разрешает
повторять неизвестную серверную миграцию: для неё действуют обычные правила
durable pending и восстановления.

## Отдельные уровни доверия

| Назначение           | Допустимый код и доступ                                                                           | Где исполнять                                               |
| -------------------- | ------------------------------------------------------------------------------------------------- | ----------------------------------------------------------- |
| CI и Container smoke | PR и main, read-only repository token, синтетические БД                                           | Новый изолированный CI guest на каждый job                  |
| Publisher            | Проверенный main, временный `packages:write`, без SSH-key                                         | В будущем отдельный чистый guest, никогда не исполнявший PR |
| Deploy               | Доверенный main workflow, artifact проверенного publisher, ограниченный SSH-key только в этом job | В будущем ещё один чистый guest после publisher             |

**Publisher и deploy остаются GitHub-hosted до отдельной приёмки изоляции,
маршрутизации и разрешения их переноса.** Метки `runs-on` — не механизм
авторизации: PR может изменить YAML и запросить метку privileged runner.
Для такого пула нужна проверенная политика допуска точных workflow refs,
например runner group с ограничением на `deploy-main.yml@refs/heads/main` и
`release-candidate.yml@refs/heads/main`.

В read-only проверке интерфейса организации CityGo-Tech (Free) 19 октября
подтверждены кнопка `New runner group` и вариант `Selected workflows` в
`Workflow access`. Группа `Default` допускает все private repositories;
зарегистрированных runners нет. Никакие варианты не выбирались и не сохранялись,
группы и runners не создавались. Наличие пункта интерфейса **не означает**, что
ограничение уже настроено или доказано его применение. До переноса publisher/deploy
нужно отдельно проверить фактический запрет чужих workflow refs и PR. Если такую
политику применить или проверить нельзя, перенос остановить, а не заменять проверку
другой меткой или условием из изменяемого PR.
[Ограничения доступа runner groups](https://docs.github.com/en/enterprise-cloud%40latest/actions/how-tos/manage-runners/self-hosted-runners/manage-access).

Нельзя provision общий единственный runner сначала для publisher: тот может
занять слот и ждать CI/Container, которым негде исполняться. Фабрика сначала
обслуживает проверки. Привилегированные ВМ в будущем создаются только после
соответствующих gates либо получают отдельную ёмкость.

## Поэтапный перенос workflows

1. **Готовность хоста.** После ручного включения и перезагрузки повторно проверить
   Hyper-V и подготовить чистый guest. Пока готовность не подтверждена,
   `runs-on` не менять.
2. **Приёмка изоляции.** Синтетический локальный canary проверяет сеть, файловые
   границы, собственный Docker, порты и удаление ВМ после success/failure/cancel.
   Это ещё не успешный GitHub CI.
3. **Одноразовый CI canary в GitHub.** Зарегистрировать только непривилегированный
   ephemeral runner после проверки доступа. Не выдавать AI, оплату, S3 или SSH.
4. **CI и Container smoke.** Отдельным проверяемым изменением перенести только
   эти jobs. Сохранить workflow names `CI` и `Container smoke`, paths `ci.yml`
   и `container-smoke.yml`, jobs `verify` и `production-images`, события PR/push
   main, все шаги и assertions. Для checkout не сохранять credentials.
5. **Проверки точного main.** После merge получить новые успешные push-checks
   точного main SHA. Локальный лог, зелёный PR другого SHA или старый успешный
   attempt не заменяют их. Не добавлять `continue-on-error`, искусственный
   success, отключение обязательных тестов или fallback на платный runner.
6. **Отдельная приёмка privileged pools.** Только после проверки границы workflow
   access и внешнего удаления ВМ обсуждать перенос publisher/deploy. Сохранить
   `publish-candidate` → `deploy`, отдельные permissions и SSH только в deploy.

Существующие release gates остаются обязательными: текущий `main`, оба точных
push-checks, последний run/attempt, проверка repository/workflow, source labels,
digest/readback трёх образов, artifact ID/hash, backup и серверные разрешения.
`cancel-in-progress: false` для выпуска сохраняется. Серверный контроллер не
обновляется и не получает новых прав от одной смены runner.

См. [автоматическое обновление main](automatic-main-deployment.md),
[подготовку candidate](release-candidate.md) и
[действия оператора выпуска](release-operator.md).

## Особенности проверок CityGo

`Container smoke` требует настоящий Linux. Штатный стенд использует host
networking, 3000/80/443, а CI service PostgreSQL — 5432. В госте не должно быть
других job или личных сервисов на этих портах. Гостевой Docker должен работать
независимо от Docker Desktop.

Исторические ограничения WSL/Desktop и локальные overrides описаны в
[отчёте CG-009](../implementation/cg-009-plan-ownership.md). Тот адаптированный
