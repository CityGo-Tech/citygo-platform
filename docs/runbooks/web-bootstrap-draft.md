# Проверяемый проект конфигурации bootstrap

Статус: локальная подготовка после #191 (`main c27c61a`). Сервер не изменяется.
Компилятор создаёт проект конфигурации для [первичного подключения Web](web-switch-bootstrap.md),
но не устанавливает его. Команды установки, SSH, API провайдеров и автодеплой
в этот этап не входят.

## Что проверяется

Компилятор принимает точные байты канонического `compose.json` и отдельный
JSON-запрос с метаданными наблюдения. Он поддерживает ограниченный формат
канонического выпуска: API, Web, закрытые ops-сервисы worker/backup и две
существующие внешние сети. Неизвестный формат отклоняется; он не преобразуется
в подходящий автоматически.

Поддерживаемая структура проверена по producer и синтетическим примерам.
Реальные канонические байты рабочего сервера на этом этапе не читались;
их совместимость с компилятором ещё предстоит подтвердить по свежему снимку.

Первый кандидат использует прежние image ID и source SHA. В отдельной копии
канонической конфигурации разрешены только два изменения API:

- `TRUSTED_PROXY_CIDRS`: `172.30.92.10/32` →
  `172.30.92.10/32,172.30.92.20/32`;
- restart: `no` → `unless-stopped`, без ограниченного числа повторов.

Второй Web получает отдельный уникальный Compose project, прежний образ,
`172.30.92.20`, loopback-порт `3001` и `unless-stopped`. Межпроектный
`depends_on` удаляется; второй API, база, jobs, секреты и тома в новый project
не добавляются. Остальные ограничения Web сохраняются.

Новые адреса доверенного прокси и restart policy не меняют три режима ИИ,
×10, «Минимум» 3 ₽, списание после ответа без удержания, бюджетные счётчики,
чеки ЮKassa, подтверждение телефона и подарок 500 ₽. Runtime-секреты не читаются
и не копируются: используются только их пути и контрольные суммы.

## Входные данные и доверие

Полная исполняемая схема — `compile_draft` в
[`web_bootstrap.py`](../../deploy/backup/web_bootstrap.py), синтетический пример —
`fixture()` в [`test_web_bootstrap.py`](../../deploy/backup/test_web_bootstrap.py).
Тестовые ID, пути и хеши нельзя использовать как production-план.

Запрос связывает исходные байты Compose с их SHA256, прежние image/source,
контейнеры, внешнюю сеть, сохранённые конфигурации и secret pins. Наблюдение
должно быть полным по утверждению оператора и не старше часа; частичное,
просроченное или будущее наблюдение отклоняется. Запреты pending, открытого
worker admission и автодеплоя должны быть явно подтверждены.

**Проверка входного JSON не удостоверяет состояние сервера.** Метаданные,
включая полноту инвентаризации, передаёт оператор; компилятор не подключается
к Docker, Nginx или серверу для их подтверждения. Совпадение хешей также не
означает наличие разрешения владельца, свежей резервной копии или исключения
внешних reload. Эти условия остаются отдельными gates установки.

## Локальная команда

```sh
python -B deploy/backup/web_bootstrap_cli.py --plan
python -B deploy/backup/web_bootstrap_cli.py --draft --canonical <local-compose.json> --request <local-request.json>
```

Без аргументов и с `--plan` нет чтения входных файлов и записи. `--draft`
создаёт новый каталог `.local/web-bootstrap-drafts/<uuid>/` в текущей рабочей
копии на Linux. Запись использует дескрипторы каталогов и не следует
подменённым символическим ссылкам. На Windows доступны чистый компилятор и
`--plan`; `--draft` отказывает, поскольку равноценная защита записи не реализована.
CLI не принимает произвольный output-путь, не перезаписывает прежние проекты,
отклоняет ссылки, специальные файлы и слишком большие входы. Ошибки не выводят
содержимое входных файлов.

В каталоге находятся пять файлов:

| Файл                      | Назначение                                                 |
| ------------------------- | ---------------------------------------------------------- |
| `canonical.original.json` | Исходный Compose с сохранением точных байтов               |
| `request.original.json`   | Исходный запрос с метаданными; без значений секретов       |
| `canonical.prepared.json` | Отдельная копия с двумя указанными изменениями API         |
| `slot2.compose.json`      | Только второй Web в отдельном project                      |
| `draft.json`              | Хеши, разрешённые изменения и условия дальнейшей установки |

`draft.json` записывается последним. При прерванной записи отсутствие этого
файла означает неполный локальный пакет. Это не журнал состояния сервера.
Все допуски исполнения и `readyToApply` остаются `false`. Контроллер переключения
не принимает этот файл как свой V2 plan.

## Возврат и следующие этапы

Исходный Compose сохраняется побайтно. Обратные изменения восстанавливают
прежний CIDR и наблюдённую restart policy, а не предполагаемые defaults.
Это проект обратных изменений, **не автоматический rollback** работающих
контейнеров. После пересоздания API старые ID/StartedAt и approvals недействительны.

До установки по-прежнему нужны отдельное разрешение владельца, свежая
зашифрованная копия с проверкой восстановления, запас ресурсов, закрытие и
drain запросов, защита от внешних reload, сохранение Nginx symlink и исходных
прав, durable installer с аварийной репетицией и reconciliation возврата.
Фактический V2 plan строится по новому снимку после bootstrap. Старые
`backup.json`, `ACTIVE` и deployment receipts этим проектом не переписываются.

При неизвестном результате установки нельзя выводить успех из возраста файла,
повторять HUP/остановку контейнера, очищать pending или открывать доступ по этому
draft. Требуется новое наблюдение и разбор состояния по основному runbook.

## Проверки

```sh
python -B -m unittest discover -s deploy/backup -p 'test_web_bootstrap*.py' -v
python -B deploy/backup/web_bootstrap_smoke.py --disposable
```

Вторая команда работает только с синтетическим примером и локальным
`docker compose config`. Она не запускает контейнеры и не обращается к Docker
daemon. Она проверяет, что нормализованные Compose-конфигурации сохраняют
разрешённые изменения и изоляцию второго Web. Это не репетиция установки
на рабочий сервер и не доказательство восстановления после сбоя питания.
