# Постоянные копии пилота: 24 часа / 7 дней / 4 недели

Это отдельное операторское расписание, **не** прежний ограниченный пробный
режим `schedule.py`. Merge/push в GitHub сам по себе его не включает и не меняет.
Не устанавливать два расписания одновременно.

## Политика

- `citygo-backup-routine.timer`: каждый час в `:05`, задержка до 30 секунд,
  `Persistent=true`; после выключенного сервера выполняется одна догоняющая
  задача, а не все пропущенные часы. ВМ должна быть включена.
- `citygo-backup-routine-check.timer`: проверка свежести и результата очистки
  каждые 15 минут. Норма — успешный цикл и проверенная копия не старше двух часов.
- Сохраняются самые новые копии для 24 последних представленных часовых
  интервалов, 7 дней и 4 ISO-недель (UTC). При пропусках сохраняются более старые
  имеющиеся точки. Копии групп пересекаются: всего не более 35; как минимум две
  последние копии, если они существуют. Предрелизные копии входят в ту же ротацию.
- `pg_dump → age → S3`, затем скачивание и проверка SHA-256; локальный дамп
  существует только внутри приватной временной папки и удаляется при завершении.
  Открытого дампа и приватного ключа расшифровки на сервере нет.
- Удаление старых пар `.dump.age` / `.complete.json` начинается **после**
  успешной новой копии и проверки её маркера в хранилище.
- Другие объекты (например enrollment), неполные пары, изменённые получатели
  шифрования и некорректные манифесты не удаляются автоматически.

## Защита от заполнения и гонок

Одна общая `maintenance.lock` с выпуском приложения; занятость пропускает запуск,
а последующая проверка свежести обнаруживает длительную остановку. Незавершённый
`operation-pending.json` не очищается автоматически. Обычный запуск освобождает
временные каталоги; после аварийного убийства оператор сначала проверяет процессы
и pending-маркер, а не удаляет файлы по маске.

Ограничения существующего backup engine: до 1 ГиБ на зашифрованный дамп и минимум
8 ГиБ свободного диска. Новая регулярная загрузка запрещена, если уже есть
40 завершённых копий или объём объектов префикса достиг 1 ГиБ; это оставляет запас
под один максимальный дамп. Это предохранитель регулярного задания, **не квота
всего бакета**: отдельные ручные/предрелизные загрузки тоже требуют контроля.
Ошибка удаления не запускает бесконечные повторы. Она вызывает уведомление;
достигнутый предохранитель останавливает дальнейшее накопление.

S3-листинг полностью постраничный, с пределами числа объектов/страниц. Удаление
идёт только по точным именам проверенных старых пар. Прерывание между удалением
архива и маркера требует операторского согласования остатка; следующая проверка
инвентаря останавливает новые регулярные загрузки до разбора ситуации.

## Cloud.ru

Бакет остаётся приватным. Сервисный аккаунт получает только GetObject, PutObject,
DeleteObject внутри согласованного префикса, ListBucket с условием `s3:prefix`
и, если позволяет IAM, GetBucketVersioning. Список вне префикса запрещён.
**Не выдавать `s3e.admin`: эта роль обходит Bucket Policy.**

В консоли перед включением проверяется, что версионирование не включалось.
Cloud.ru дополнительно ограничивает GetBucketVersioning ролью IAM; Bucket Policy
не может заменить эту роль. Поэтому контроллер проверяет VersionId каждого
кандидата через HeadObject (доступен по GetObject), отказывается от версионных
объектов и проверяет, что DeleteObject не создал DeleteMarker. Изменение режима
версий требует отдельного плана очистки старых версий; они не удаляются этим
инструментом. Не считать delete marker освобождением места.

## Установка и включение

Требуются работающие `/etc/citygo/backup.json`, storage credentials, age,
AWS CLI, доступ к Docker и уже проверенный почтовый канал. Секреты не включаются
в исходники или архив установки.

1. Выполнить `python3 -B -m unittest discover -s deploy/backup -p 'test_*.py' -v`
   в Linux (Python 3.11+; age для криптографического теста).
2. Перенести `backup.py`, `notify.py`, `routine.py`, `install_routine.py` и четыре
   шаблона/таймера `systemd/citygo-backup-routine*` в новую root-owned staging
   папку. Проверить SHA-256 перед запуском; каталоги root-only, файлы без записи
   для группы/остальных. Не исполнять root-код из изменяемого пользовательского
   checkout.
3. После согласования выполнить `install_routine.py --allow-install-and-email`.
   Он создаёт неизменяемый по имени content-addressed каталог в `/opt/citygo`,
   конфиг `/etc/citygo/backup-routine.json`, units, включает существующий почтовый
   канал, но **не запускает** сервисы или таймеры. Повторная установка отказывается
   перезаписывать существующие настройки.
4. Выполнить `systemd-analyze verify` для четырёх units.
5. `systemctl start citygo-backup-routine.service`; проверить код выхода,
   `/var/lib/citygo-backup-routine/last-run.json` и отсутствие временных дампов.
6. `systemctl start citygo-backup-routine-check.service`.
7. `systemctl enable --now citygo-backup-routine.timer citygo-backup-routine-check.timer`.
8. Проверить `systemctl list-timers 'citygo-backup-routine*' --all`, свободное
   место, доступность приложения и наличие последней копии в S3.

Контроллер следует активному root-owned `/etc/citygo/backup.json` после новых
релизов, но закрепляет проект, каталог состояния, endpoint, бакет, префикс,
получателя шифрования и путь credentials. Их изменение требует оператора.
Слияние нового кода не подменяет уже установленный root-контроллер.

## Проверка и остановка

```sh
systemctl list-timers 'citygo-backup-routine*' --all
systemctl show citygo-backup-routine.service -p Result -p ExecMainStatus
journalctl -u citygo-backup-routine.service --since today --no-pager
cat /var/lib/citygo-backup-routine/last-run.json
df -h /
# Остановка будущих запусков без удаления копий:
systemctl disable --now citygo-backup-routine.timer
```

Проверка свежести останется включённой и сообщит о намеренной паузе. Для полного
обслуживания отдельно остановить check timer. Активный dump не прерывать без
причины; при принудительной остановке разбирать pending-состояние оператором.

Письма содержат только общий статус, без ключей и пользовательских данных.
Повторы ограничены: минимум 15 минут между попытками, напоминание через сутки.
Монитор на той же ВМ **не обнаружит собственное полное отключение**. Нужен
независимый внешний монитор для такого случая. Следить за сроком действия
ключа хранилища; расписание не продлевает ключ автоматически.

Readback проверяет доставку, но не заменяет периодический restore drill.
Восстановление выполнять только в отдельную тестовую БД по
[инструкции](encrypted-backup.md), не поверх работающего приложения.
