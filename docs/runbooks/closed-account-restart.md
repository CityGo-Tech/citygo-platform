# Закрытый переход тестовых аккаунтов к первому администратору

Операторский `ClosedAccountRestart` закрывает прежние тестовые аккаунты,
удаляет логины и переписку и создаёт первого `admin` в одной транзакции.
Финансовые записи сохраняются. Инструмент не выполняется при старте сервиса,
не имеет HTTP-маршрута и не является общей процедурой удаления реальных клиентов.

Эта поставка готовит код и синтетические проверки. Она не запускает очистку на
Cloud.ru и не разрешает открывать известный временный пароль публично.

## Какие данные меняются

Старые строки `users` сохраняют ID для финансовых связей, но получают
`status=deleted`, случайный новый `auth_subject`, пустой username и обычную роль.
Прежние credentials и все сессии удаляются. Это псевдонимизация: связь записей
учёта остаётся, физическое удаление всех следов не обещается.

Удаляются сообщения, handoff-контекст, профили, ответы, планы, жилищные ревизии,
пользовательские квесты/XP, согласия и персональная аналитика. У диалогов остаются
только необходимые связи: контекст очищается, статус становится `closed`.
Запросы и попытки сохраняются, чтобы не нарушить цепочку
`charge → attempt → request → thread → user`.

Не меняются суммы и остатки старых AI-балансов, проводки, исходные receipts,
идентификаторы генераций, бюджеты, общие и пользовательские счётчики,
маршрутизация, миграции и каталоги. Остаток старого аккаунта не передаётся новому
администратору. Исходные операционные записи routing/budget/credit аудита
сохраняются целиком; до применения оператор должен проверить их на личный контекст.
Резервные копии и внешние объекты этим инструментом не удаляются.

## Когда переход блокируется

- Первичный bootstrap уже был завершён. Флаг не сбрасывается ни при очистке,
  ни при смене пароля, ни при повторном запуске.
- Есть выполняющийся chat request, lease или неочищенная отметка `busy_until`.
- Есть удержанный баланс, неразрешённый hold либо charge без receipt.
  Отсутствие ответа модели не доказывает отсутствие расходов.
- Есть generated artifacts: сначала нужен отдельный внешний inventory.
- В аудите есть неизвестная пара action/type. Произвольный JSON не очищается
  и не признаётся безопасным автоматически.
- Состав таблиц отличается от проверенного inventory либо поменялся снимок.
- Более 1000 аккаунтов, 10000 строк или 8 MiB в одной таблице, 32 MiB в снимке.

Ненулевые подаренные/потраченные суммы сами по себе не мешают переходу: они
сохраняются, а не обнуляются. Неизвестную стоимость сначала нужно сверить.

## Подготовка закрытого окна

1. Согласовать целевую БД, фактически установленный релиз, maintenance и откат.
   Установленная версия должна поддерживать миграцию 0013 и новый CLI.
2. Закрыть внешний ingress, завершить текущие генерации, остановить API и Worker,
   не оставлять другие пишущие клиенты. Нельзя считать флаги CLI проверкой этого
   состояния: существующие фоновые операции не все проверяют deleted-статус.
3. Создать и проверить зашифрованную резервную копию через существующий backup
   процесс. Сохранить SHA-256 её квитанции. CLI принимает ссылочный отпечаток,
   но сам не читает хранилище и не доказывает пригодность копии к восстановлению.
4. В защищённом операторском контуре проверить сохраняемые audit payload и
   отсутствие недопустимого личного контекста. Не копировать их в чат или логи.
5. Передать `CITYGO_ACCOUNT_DATABASE_URL` только отдельному процессу оператора.
   Нужен ограниченный владелец `citygo_migrator`, не runtime API и не superuser.
   CLI не читает `.env`. Ожидаемая цель в аргументах не содержит credentials.

## Dry-run и применение

Из закреплённого checkout можно использовать исходник
`pnpm exec tsx apps/api/src/account-maintenance.ts`.
Сборка API также включает `dist/account-maintenance.js`; в API image он находится
по `/app/dist/account-maintenance.js`. Это отдельный операторский artifact:
штатный `container-runtime.mjs` не запускает его. Сборка файла не подтверждает
доставку конкретного image на сервер; перед использованием нужна проверка image
и отдельная one-shot команда с ограниченным окружением, не изменение CMD API.

Сначала только план, с условной целью:

```text
node dist/account-maintenance.js --restart-accounts \
  --expected-target=postgresql://DB_HOST:5432/citygo_pilot \
  --expected-environment=production --expect-users=5 \
  --maintenance-confirmed
```

План возвращает количества, blockers и `snapshotFingerprint`, без email, текстов,
паролей или ID аккаунтов. Отпечаток включает значения всех известных таблиц и
структуру колонок, ограничений, индексов, триггеров, функций и views. Изменение
переписки, receipt или схемы после проверки требует нового dry-run.

Применение — та же команда с дополнительными параметрами:

```text
--apply --expected-snapshot=SNAPSHOT_SHA256 \
--backup-receipt-sha256=BACKUP_RECEIPT_SHA256 \
--services-stopped-confirmed --retained-audits-reviewed
```

Оба значения должны быть настоящими 64-символьными строчными SHA-256, а не
строками-заглушками. Дополнительно требуется
`CITYGO_ACCOUNT_BOOTSTRAP_CLOSED=true`. Подтверждения и точная цель проверяются
до подключения; blockers и снимок повторно проверяются под блокировками в той же
транзакции, что очистка и bootstrap. Порядок: security singleton → users →
остальные таблицы. Блокировки короткие, с ограниченными timeout; сетевых вызовов
и вычисления хэша пароля внутри транзакции нет.
После последней записи выполняются все отложенные ограничения и constraint
triggers (`SET CONSTRAINTS ALL IMMEDIATE`), затем повторно проверяются финансовые
и приватные данные. После этого барьера инструмент больше ничего не записывает.

Прежний `--apply-reset` по-прежнему недоступен. Команда без `--apply` ничего не
удаляет. Нельзя совмещать `--restart-accounts` и `--bootstrap-admin`.

## Первый вход и ошибки

Квитанция успеха содержит `accountsRetired`, `accountsDeleted: 0`,
`mustChangePassword: true`, `accountingPreserved: true` и
`publicIngressMayOpen: false`. Новый `admin` имеет временный пароль `admin`.
Через закрытый доступ владелец обязан сменить его на новый пароль от 6 символов.
До смены доступны только необходимое чтение dashboard и сама смена пароля:
AI, админские операции и назначение ролей запрещены сервером. Старые пароли и
сессии больше не должны открывать доступ.

После смены отдельно проверить вход, права super admin, отзыв старых сессий и
health. Открытие пилота требует самостоятельной приёмки и разрешения.

При ошибке внутри транзакции изменения откатываются. При обрыве соединения во
время commit результат может быть неизвестен: не повторять bootstrap и не
сбрасывать security state. Сначала защищённо проверить
`closed-account-restart-completed` в `account-maintenance` аудите и фактическое
состояние аккаунтов. Повтор после завершённого bootstrap отклоняется.
Восстановление backup с прежними аккаунтами не даёт права открыть ingress;
повторный допуск данных и администратора решается отдельно.
