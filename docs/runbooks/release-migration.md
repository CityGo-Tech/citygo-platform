# Проверяемая миграция релиза: PostgreSQL и права в одной транзакции

Часть CG-037 / §10.5. В jobs-образ добавлен внутренний режим `migrate-release`.
Это **исполнитель для будущего контроллера, не команда выпуска на Cloud.ru**.
Он не открывает ingress/Worker, не снимает pending, не запускает API/Web,
не выполняет backup, не обращается к провайдерам и не меняет расписания.
Обычный `migrate` для начального развёртывания и локальной разработки сохранён.

## Что проверяет исполнитель

1. Принимает один ограниченный объект JSON через stdin, без SQL, URL или путей.
   Формат — `JSON.stringify(input)` и необязательный завершающий LF. Это
   намеренно исключает дубликаты ключей и неоднозначное декодирование.
2. Сверяет полный список миграций и SHA-256 **байтов** файлов внутри проверенного
   jobs-образа с заданием. Исходный список обязан быть точным непустым префиксом
   целевого. `grants.sql` теперь также упакован в jobs; его байты сверяются отдельно.
   Для него используется hash `deploy/postgres/grants.sql` из целевого manifest.
   SQL-файл ограничен 4 MiB, ACL и каждый runtime-файл — 256 KiB, как при чтении
   target bundle. Publisher проверяет эти размеры, число/порядок миграций и размер
   готового JSON **до Docker/registry login/push**, затем повторяет при формировании
   manifest. Превышение не обнаруживается впервые после закрытия сервиса.
   Общий объём всех SQL — до 8 MiB: publisher и executor сначала проверяют размеры
   всего набора, затем последовательно читают файлы и сверяют фактический объём.
   Это оставляет запас для декодирования/разбора в jobs-контейнере с 256 MiB RAM;
   лексер не сохраняет все токены большого выражения. Это не разрешение запускать
   тяжёлый SQL: семантика и ресурсоёмкость новых миграций всё равно требуют ревью.
3. До подключения к БД читает и проверяет весь SQL. Снимает только внешнюю пару
   `begin; … commit;`; отвергает внутренние команды управления транзакцией,
   psql-команды и неподдерживаемые команды. Комментарии, строки, quoted identifiers
   и dollar bodies учитываются при разделении выражений. Это защита от случайного
   разрыва транзакции, **не SQL sandbox**: содержимое миграций остаётся предметом ревью.
4. В одной транзакции проверяет PostgreSQL 17, БД `citygo_pilot`, текущую и исходную
   роль `citygo_migrator`, отсутствие superuser/createdb/createrole/replication/bypassrls.
5. Захватывает прежнюю строку `citygo_migration_lock` через `FOR UPDATE NOWAIT`,
   чтобы взаимодействовать с существующим мигратором. Отсутствующую строку/таблицу
   не создаёт. Блокирует запись в журнал миграций. Занятый мигратор — отказ,
   а не ожидание с последующим запуском устаревшего задания.
6. Требует **точного** равенства всей истории БД исходному списку: никакой лишней,
   пропущенной, изменённой или уже применённой целевой миграции. Сохранена совместимость
   со старыми checksum: БД исторически хешировала SQL с нормализацией CRLF → LF.
   При этом manifest и файлы сравниваются по исходным байтам, без нормализации.
7. Применяет новые SQL и записи журнала, затем обновляет права API/Worker/backup
   из того же образа, затем ещё раз сверяет историю. Всё — в одной транзакции.
   Ошибка любого шага откатывает и DDL, и журнал, и изменения прав.
8. Выдаёт минимальный JSON-результат только после подтверждённого COMMIT и закрытия
   соединений: ID операции, SHA цели, hash задания, применённые name/hash, hash прав,
   `committed: true`, **`trafficAuthorized: false`**. SQL, пароли и ошибки драйвера
   в вывод не попадают.

Ограничения времени: stdin 10 с, SQL statement 60 с, ожидание DDL-lock 3 с,
idle-in-transaction 10 с, вся транзакция 120 с, процесс 150 с. Нет повторных
попыток при lock/timeout/ошибке соединения. Транзакционные блокировки освобождаются
при завершении транзакции; это не глобальный запрет других клиентов или root.
См. [блокировки PostgreSQL 17](https://www.postgresql.org/docs/17/explicit-locking.html)
и [таймауты PostgreSQL 17](https://www.postgresql.org/docs/17/runtime-config-client.html).

## Задание не является одобрением

Закрытая схема задания: `version: 1`, `kind: citygo-release-migration`,
`operationId` (UUID), `targetSha` (40 hex), `currentMigrations`, `targetMigrations`
(упорядоченные массивы `{name, sha256}`), `grantsSha256` (64 hex).
Размер — до 512 KiB (два списка из manifest по 256 KiB), до 1000 миграций;
пустая исходная история не поддерживается.
SHA цели и UUID в результате — корреляция с заданием, не доказательство образа
или независимого разрешения владельца. Проверка происхождения образов остаётся
за [image gate](release-images.md) и доверенным вызывающим кодом.

**Нельзя подавать `release-prepared.json` или существующий preparation approval
как разрешение миграции.** Они по-прежнему имеют `migration_authorized: false`.
Этот PR не создаёт одобрения, CLI контроллера или обхода ограничения подготовки.
На сервере не запускать до реализации полного непрерывного пути:

- отдельное разрешение конкретной миграции/версии до окна обслуживания;
- проверка образов, закрытие входа, drain, свежая внешняя копия;
- ровно одна попытка исполнителя под тем же maintenance lock и durable pending;
- проверка ID/образа/exit сохранённого контейнера и согласованного результата;
- запуск API/Web, health и проверка контрактов, затем проверенное завершение.

Исполнитель сам по себе **не обеспечивает exactly-once после падения процесса**.
После неоднозначного COMMIT, потери квитка или timeout нельзя автоматически повторять
задание, снимать pending, открывать доступ или откатывать БД. Нужна ручная сверка.
Повтор старого задания после применённой новой миграции отвергается историей;
выпуски без нового SQL допустимы и требуют защиты от повтора в host-контроллере.
Привилегии и checksum не доказывают совместимость приложения/клиента с новой схемой.

## Проверки

Unit tests: строгий ввод, списки/hash, грамматика SQL, порядок действий, неверная роль,
БД/версия, история, ошибка прав/COMMIT, отсутствие retry и разрешения открыть вход.

Disposable container smoke выполняет **реальный** переход синтетической PostgreSQL
БД с 6 на 7 миграций через собранный jobs-образ и роль `citygo_migrator`.
Отрицательные сценарии: неверный hash образа/ACL-файла, лишняя/пропавшая/изменённая
история, занятый мигратор, DDL-lock timeout, SQL-ошибка после изменения схемы,
ошибка прав после REVOKE, внутренний COMMIT. Проверяет rollback схемы/журнала/прав,
отказ устаревшего повторного задания и выпуск без DDL. Затем существующий smoke
запускает API/Web и проверяет пользовательский сценарий, backup/restore и TLS/SSE.
Это последовательность тестового стенда, **не испытание полного host-контроллера**.
Тестовые подмены SQL/ACL и откат fixture не поставляются в runtime bundle.

Новые миграции базы проекта в этом PR не добавляются. Рабочая БД, Cloud.ru,
DNS, ИИ, секреты и расписания остаются без изменений.
