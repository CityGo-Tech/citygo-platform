# Worker и резервное копирование: общий операторский протокол

Часть CG-037, не полный deploy-controller. **Ничего не устанавливается/включается
этим PR.** Сервер, расписания, SMTP/S3, AI и пробный режим не меняются.

`deploy/backup/worker.py` запускает только готовый Worker через Docker Compose,
без shell, build/pull, миграций, новых зависимых сервисов и автоматического повтора.
Он использует тот же защищённый `backup.json`, что `backup.py` и `schedule.py`.
`upload_enabled` по-прежнему нужен только для загрузки backup, а не для Worker;
Worker не читает ключи хранилища/ИИ. Секреты БД получает контейнер из Compose secrets.

## Защита при смене активной конфигурации

Все команды должны читать **один канонический защищённый `backup.json`** через
`backup.load_config()`. Загрузчик сохраняет привязку к пути и точным байтам файла
в памяти; формат v1, fingerprint и записываемые JSON остаются прежними.
В основной конфигурации запрещены symlink/hardlink, доступ группы/остальных,
повторяющиеся JSON-ключи и размер свыше 64 KiB.

После будущего атомарного переключения этого файла новый процесс читает новые
source SHA/Compose/env. Уже загрузивший прежний файл процесс отказывается от
backup/Worker/open/pause/release при проверке перед действием и внутри блокировки.
Старый Worker **не удаляет новый admission marker** и не запускает контейнер.
`copy()`, `copy.copy()` и `copy.deepcopy()` сохраняют привязку и общий отказ:
после обнаруженного изменения возврат прежних байтов не оживляет этот объект.
Новый осознанный запуск требует нового `load_config()`.

При изменении основного файла во время dump загрузка копии не начинается;
при изменении во время Worker успешный receipt не создаётся. Pending сохраняется,
дополнительная задача/повтор/автоматическое снятие блокировки не выполняются.
Уже принятые внешние эффекты не откатываются. Изменение Compose/env после допуска
по-прежнему не меняет уже снятый снимок запуска; права на внешние secrets/mounts
этот механизм не расширяет и сами такие файлы не копирует.

Это защита потребителей конфигурации, **не реализация переключения/finish**.
Будущий контроллер обязан использовать тот же стабильный state_dir и общий lock,
закрытый ingress/Worker, отдельное разрешение, новую проверенную конфигурацию,
health/recovery проверки и только затем фиксировать выпуск. Не заменять файл
на рабочем сервере вручную ради проверки этого изменения.
Старый код, другие копии `backup.json`, обходные Docker-команды или root вне
протокола этой защитой не покрываются. Внутренние dict fixtures разрешены для
тестов/сборки конфигурации, но реальный загруженный объект нельзя превращать в
`dict(config)` или JSON round-trip: это потеряет непередаваемую привязку к источнику.
Расписания/допуски по старому fingerprint сами за новым релизом не следуют.

## Инварианты и ограничения

- Один **стабильный `state_dir` для этой БД на одном Linux-хосте**, независимо от
  релиза. Все три entrypoint должны использовать одну обновлённую версию протокола.
  Каталог принадлежит оператору, mode 0700, файлы 0600, без symlink/общей записи.
  Lock-файлы не удалять и не заменять: блокируется inode, а не строка пути.
- `maintenance.lock` удерживается на всём протяжении Worker или backup, включая
  проверку результата. Конкурирующий запуск отказывается, не ждёт и не повторяет.
- Worker закрыт по умолчанию. `worker-admission.json` появляется только после
  явной команды `open`; разрешение связано с fingerprint конфигурации/Compose/env.
  Изменение файла релиза/БД/настроек копии требует нового осознанного допуска.
  При обнаруженном несовпадении или недоступной/некорректной конфигурации прежний
  marker удаляется с fsync под admission lock: возврат старых файлов его не оживляет.
  После проверки и восстановления конфигурации нужен новый явный open.
- Worker читает ограниченные по размеру Compose/env один раз, сравнивает fingerprint
  именно этих байтов и запускает Compose из их временных копий mode 0600 в закрытом
  state_dir. Замена исходных файлов после допуска не меняет принятую операцию.
  В pending/receipt записывается тот же проверенный fingerprint, без повторного
  чтения исходных путей. Базовый каталог релиза сохраняется для относительных путей.
  Это снимок только двух файлов: внешние include/extends/env_file не поддерживаются
  операторским протоколом; использовать самодостаточный проверенный runtime-шаблон.
  Файлы bind mounts/Compose secrets не копируются. Релиз и секреты нельзя менять
  во время операции; будущий контроллер обновления обязан удерживать общий lock.
- `pause` закрывает только **новый допуск**, даже когда принятая операция ещё идёт.
  Короткий `worker-admission.lock` сериализует open/pause и момент принятия Worker.
  Успешная pause НЕ означает остановку всех процессов и не разрешает миграции.
- До первого внешнего действия на диск с fsync записывается `operation-pending.json`.
  После SIGKILL/перезагрузки освобождённый flock не означает успеха: оставшийся
  marker запрещает Worker, backup и повторное open, даже если JSON повреждён.
- Worker оставляет свой контейнер после exit. Проверяются точные ID/name/image,
  project/service/oneoff, init/grace/restart policy, тот же StartedAt, exit 0,
  отсутствие OOM/restart/engine error. Быстрый one-shot может уже завершиться к
  первому inspect. Успех Docker wait сам по себе недостаточен.
- Сначала сохраняется защищённый receipt, затем удаляется pending marker и
  синхронизируется каталог. При ошибке/таймауте marker не удаляется. Включая
  неудачный dump/upload/readback/manifest: следующая попытка копии требует проверки.
  Старый `last-success.json` не доказывает свежесть при незавершённой операции.

**Граница гарантии:** это протокол управляемых запусков, не ограничение полномочий
root/Docker и не распределённый lock. Прямые `docker compose run/up worker`,
`pnpm worker:once`, старые установленные скрипты, другой `state_dir` или второй
хост его обходят. Перед активацией нужно инвентаризировать и отключить такие пути,
перевести все worker-запуски на эту обёртку и проверить уже существующие контейнеры.
Сама обёртка не останавливает внешние таймеры и не сканирует/завершает чужие процессы.

## Ручное использование после отдельного допуска на сервер

Проверить происхождение релиза и владельцев всех файлов. Использовать только
доверенный защищённый Compose с фиксированными образами. В примерах намеренно
оставлен `APPROVED_SHA`; это не команда автоматической активации.

```sh
# Запретить новые управляемые Worker, не прерывая уже принятый.
python3 -E -s -B /opt/citygo/releases/APPROVED_SHA/deploy/backup/worker.py pause \
  --config /etc/citygo/backup.json --allow-pause

# Только после проверки состояния и отдельного решения: разрешить будущие запуски.
# Эта команда сама не запускает Worker и не создаёт расписание.
python3 -E -s -B /opt/citygo/releases/APPROVED_SHA/deploy/backup/worker.py open \
  --config /etc/citygo/backup.json --allow-open

# Одна операция, без автоматического повтора.
python3 -E -s -B /opt/citygo/releases/APPROVED_SHA/deploy/backup/worker.py run \
  --config /etc/citygo/backup.json --allow-worker
```

Повторный `open` отказывается, пока прежний marker существует; для изменения
разрешения сначала pause, затем проверка и отдельный open. Повторная pause безопасна.
Коды CLI: 0 — указанная операция подтверждена, 1 — отказ/неопределённость; содержимое
ошибок Docker/конфигурации не печатается. Нет команды «снять все блокировки».

## Сбой и восстановление управления

Не удалять pending по возрасту/PID и не запускать задание повторно автоматически.
Закрыть admission через pause. Под защищённым доступом прочитать pending и receipts;
проверить исходный релиз, точный контейнер и его exit/StartedAt/OOM, отсутствие ещё
работающих Worker/backup, сохранность БД и результаты загрузки. При неизвестном
результате оставить закрытым. Удаление только конкретного marker допустимо лишь
после отдельного решения оператора и записи результатов расследования; инструмент
не предоставляет автоматического сброса. Не удалять lock-файлы или каталог state.

Worker-контейнеры не удаляются автоматически. После проверки receipt их можно
убирать отдельно по подтверждённому точному ID; не использовать общий prune.
SIGTERM/SIGINT операторской обёртки прекращает ожидание, но не гарантирует остановку
контейнера. При таком прерывании pending остаётся. Если требуется штатная остановка
активного Worker, отдельно проверить target и дать ему grace из runtime-шаблона;
результат всё равно проверяется оператором. Таймаут ожидания — 900 секунд.

## Что нужно до миграций

Закрыть ingress, запретить все новые Worker-запуски (не только обёртку), дождаться
API drain и Worker, сверить результаты и отсутствие обходных исполнителей.
Будущий контроллер обязан удерживать общий запрет/lock от этой проверки через
**новую** внешнюю проверенную копию до конца обновления. Пока такого контроллера
нет: отдельные `pause` и `backup` не создают атомарного разрешения на миграцию.
Обычный свежий backup, снятый при работающем API, не является предрелизным допуском.

Библиотечное [release-окно](release-backup-window.md) теперь позволяет держать этот
lock до/во время/после новой копии. Оно пока не доказывает quiescence и намеренно
сохраняет pending даже при нормальном выходе: это ещё не завершённый контроллер.

Следующий библиотечный этап — [подготовка релиза](release-preparation.md).
Он закрывает ingress, проверяет контейнеры проекта и участников DB-сети, завершает
API/Worker и создаёт новую копию внутри окна. Внешние писатели/обходные запуски
по-прежнему требуют аудита оператора. Ни миграций, ни автоматического снятия
запрета этот этап не добавляет.

## Проверки

Linux unit tests используют реальный flock, файловые права и SIGKILL дочернего
тестового процесса; Docker/S3 заменены синтетическим transport. Проверяются обе
стороны взаимного исключения, pause при активном Worker, ошибка readback, повреждённый
pending и сохранение запрета после смерти владельца lock.
Disposable pilot smoke отдельно запускает реальный операторский CLI и jobs-образ:
закрытый допуск → явный open → проверенный exit 0/receipt → pause → отказ нового run.
S3 uploads в этом сценарии выключены. Это не испытание на ВМ пользователя.

Основание: [Python flock](https://docs.python.org/3/library/fcntl.html#fcntl.flock),
[Compose one-off run](https://docs.docker.com/reference/cli/docker/compose/run/),
[Docker wait](https://docs.docker.com/reference/cli/docker/container/wait/).
