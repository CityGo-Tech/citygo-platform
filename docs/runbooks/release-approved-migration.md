# Одобренная подготовка и миграция в одном окне

Продолжение CG-037 / §10.5. `deploy/backup/migrate.py` связывает проверенные
подготовку, свежую копию и one-shot migration job. **Это внутренняя библиотека,
не production CLI и не полный выпуск. На рабочем сервере пока не запускать:**
запуск API/Web, health/mobile, finish и rollback drill остаются отдельным этапом.

## Независимое разрешение

Прежний preparation approval не изменён: `allow_migration: false`.
Миграция требует другого защищённого файла вне обоих bundle, не совпадающего
с preparation approval. Корень доверия ручной: оператор независимо проверяет
artifact/manifest, SQL и ACL, текущее состояние, окно обслуживания и явно разрешает
изменение именно этой БД. Библиотека не создаёт approval и не проверяет подпись GitHub.
Файл из кандидата, PR или чата не является разрешением.

Строгие поля отдельного документа:

- `version: 1`, `purpose: citygo-release-migration`.
- `preparation_sha256`: hash точных байтов уже проверенного preparation approval.
  Через него связаны repo/org/artifact ID, оба выпуска, images и настройки.
- `target_manifest_sha256`, `configuration_sha256`, `project`, `origin`:
  точно совпадают с текущей проверенной Selection/конфигурацией.
- `network_id`: полный Docker ID проверенной сети PostgreSQL, не имя.
- `approved_at`, `expires_at`: целые Unix seconds, максимум 24 часа, без будущего
  начала и с проверкой срока после длительных чтений.
- `allow_migration: true`, `allow_start: false`, `allow_traffic: false`.

Оба approval перечитываются на границах остановки/копии/запуска. Первое успешное
чтение фиксирует байты; обнаруженные изменение, отзыв или expiry инвалидируют
объект. Возврат старого файла не восстанавливает разрешение.

## Непрерывная операция

1. До downtime проверяются отдельное одобрение, manifests, местные образы и формат
   migrator-секрета. SQL inventories и ACL hash берутся только из выбранных manifests,
   не из произвольного задания вызывающего кода.
2. Закрывается допуск Worker; одна maintenance lock удерживается через закрытие
   ingress, подтверждённый drain API/Worker, новую pg_dump/age копию и миграцию.
   Старый `prepare()` остаётся подготовкой без миграции; JSON-квиток не возобновляет окно.
3. После копии конкретный guard повторно проверяет оба одобрения, все прежние
   контейнеры/процессы/образы, закрытый TLS ingress и точную DB-сеть.
4. Отдельное одобрение резервируется один раз: защищённый, эксклюзивный и fsynced
   `migration-approval-<hash>.used.json` связывает его с operation/request hash.
   Запись не удаляется при ошибках; её изменение запрещает продолжение.
5. Задание передаётся библиотеке #58. Guard допускает только один новый контейнер
   из её сохранённого container-record, привязанный к операции, request и jobs image.
   Иные новые контейнеры/сетевые участники, вновь запущенный API/Worker, изменённый
   секрет, открытый ingress или отозванное разрешение прекращают операцию.
6. Сохраняется доказательство exit 0/точного квитка. Общая функция возвращает результат
   только после финальных проверок и очистки временной папки подготовки.

Pending, закрытый ingress и запрет Worker сохраняются даже после успеха. Ни один
полученный JSON не разрешает запуск сервисов или открытие доступа. Preparation receipt
по-прежнему имеет `migration_authorized: false`; отдельный migration receipt доказывает
завершение задания, **не всего выпуска**. Ошибка поздней проверки после COMMIT означает
ручную сверку, а не rollback, автоматический повтор или возможность снять pending.
Consumed approval запрещает повтор даже при ручном удалении pending. Без начала
миграции pending всё равно запрещает автоматический повтор подготовки.

Протокол кооперативный, не защита от администратора Docker/root. Содержимое runtime,
bind/secret файлов и управляющий процесс должны оставаться доверенными/неизменными.
Нет сетевой публикации образов, CLI, автоматического обновления, расписаний и AI.

## Проверки

Linux unit tests используют настоящие lock/protected files, синтетические approvals,
контейнеры и encrypted bytes. Проверяют scopes/bindings/revocation/expiry, запрет
повтора, изменение ingress/network/secret/writers и отказ после COMMIT.

Disposable CI связывает настоящие TLS ingress, остановку API/Worker, pg_dump/age,
подтверждение копии в MemoryStore и сохранённый jobs-контейнер одной операцией.
В ней выполняется настоящая транзакция проверки истории/ACL **без новых DDL**;
отдельный существующий smoke продолжает проверять реальный upgrade 6 → 7 и rollback.
Approvals и registry bindings синтетические; живые Cloud.ru/S3/ИИ не используются.
Удаляются только проверенные завершённые контейнеры тестового проекта — production
библиотека их не удаляет. Это ещё не проверка start/health/finish или recovery.
