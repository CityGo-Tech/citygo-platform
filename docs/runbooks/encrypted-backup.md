# Зашифрованные копии пилота: инструмент, ещё не включённая услуга

Продолжение [серверной конфигурации](cloudru-runtime.md). Подготовлен Linux-инструмент
`deploy/backup/backup.py`: ограниченная DB-роль → `pg_dump` → `age` → приватный
Cloud.ru Object Storage через AWS CLI. ВМ, бакет, ключи, расписание, retention и
канал уведомлений этим PR **не создаются и не включаются**. Допуск пользователей
остаётся закрытым до реального restore drill и остальных критериев R1.

Для следующего этапа подготовлены [ограниченное расписание и email-оповещения](backup-operations.md).
Их шаблоны по умолчанию выключены и не устанавливаются автоматически.

## Гарантии и границы инструмента

- Работает от оператора на Linux с Python 3 (стандартная библиотека), Docker Compose,
  `age` и AWS CLI v2. Сборочные инструменты приложения/Node на ВМ не нужны.
- Запускает только сервис `backup` из проверенного Compose, без build, pull образов
  и без автоматического запуска других сервисов. БД должна уже работать.
- Не пишет открытый дамп на диск: между `pg_dump` и `age` — поток в памяти ОС.
  На диске временно находятся только шифротекст и несекретные метаданные.
- На ВМ хранится только native X25519 **открытый** ключ `age1…`. Приватный ключ
  восстановления не нужен ни backup-сервису, ни GitHub, ни хранилищу.
- Не наследует DB/AI/storage credentials, прокси, Docker host или AWS config из
  окружения. У Docker/age нет ключей S3; у AWS CLI нет ключей БД/AI.
- До отправки обязаны успешно завершиться **оба** процесса: `pg_dump` и `age`.
  Ошибку выгрузки нельзя замаскировать успешным шифрованием неполного потока.
- Отправляет уникальный `.dump.age`, затем скачивает его обратно и проверяет
  размер/SHA-256. После этого отправляет и проверяет `.complete.json`. `ETag`
  или пользовательская metadata не используются как доказательство целостности.
- Только после обеих проверок атомарно обновляет `last-success.json`. Ошибка не
  обновляет успех; журнал содержит только код стадии, без stderr поставщиков.
- Проверка свежести учитывает возраст **начала снимка**, ошибки последней попытки,
  изменения получателя/хранилища/Compose/его env-файла. Старше 2 часов — отказ.
- Один запуск через общий `maintenance.lock`; будущие deploy/worker-обёртки должны
  использовать этот же lock. Сейчас их автоматической координации ещё нет.
- Выгрузка/шифрование ограничены 15 минутами, каждая операция хранения — 10 минутами.
  Шифротекст ограничен 1 GiB; перед попыткой требуется минимум 8 GiB свободного места.
  Для большей БД нужен отдельно проверенный multipart/ресурсный профиль.
- Не создаёт бакеты, не меняет ACL/политики и не удаляет удалённые объекты. При сбое
  могут остаться незавершённые зашифрованные объекты; это не повод удалять весь префикс.

Это **не** гарантия RPO/RTO или защиты от компрометации root/облачного владельца.
Контрольная сумма не заменяет аутентичность релиза и не доказывает наличие правильного
ключа восстановления у владельца. Настоящий restore drill обязателен.

## Подготовка — только после согласования размещения и стоимости

1. Подтвердить регион, стоимость хранения, операций и обратного скачивания, лимиты
   и срок хранения. Каждая успешная попытка читает всю копию обратно: учитывать
   этот трафик. Предложение 24 часовых + 7 дневных + 4 недельных копии пока не
   реализовано; таймер без согласованной retention приведёт к накоплению данных.
2. Создать отдельный **приватный** бакет и узкий префикс. Проверить отсутствие
   публичного чтения извне. Потребуются PutObject/GetObject только внутри этого
   префикса. List/Delete, управление бакетом и общие admin-ключи инструменту не нужны.
3. Проверить доступные Cloud.ru механизмы versioning/immutability и защиту от
   удаления/перезаписи со стороны backup-аккаунта. Сам по себе уникальный ключ
   объекта не защищает от компрометации аккаунта. Непроверенную совместимость
   Object Lock/условных S3-запросов этот инструмент не предполагает.
4. На отдельном доверенном устройстве создать ключ `age-keygen`, сохранить приватную
   часть в защищённом месте **вне ВМ**, проверить возможность восстановления и
   независимую резервную копию ключа. Значения приватного ключа в чат/Git не передавать.
   На сервер переносится только публичный recipient; сверить его вне канала передачи.
5. Установить проверенные версии Python 3, Docker Compose, age, AWS CLI v2 из
   доверенных источников. Не запускать скачанные скрипты через `curl | sh`.
6. Разместить immutable каталог одобренного релиза. Для backup указать прямой путь
   к нему, **не** символическую ссылку `current`. Каталоги/Compose принадлежат
   оператору (на сервере root), не доступны группе/остальным на запись.
7. Создать `/var/lib/citygo-backup` с владельцем root и правами `0700`.
   Создать `/etc/citygo/backup.json` по `deploy/backup/config.example.json`, права
   `0600`, заполнить все placeholders и точный SHA одобренного релиза. Env-файл
   Compose тоже `0600`; в нём только согласованные метаданные, не общий `.env`.
8. Создать `/etc/citygo/backup-storage.json` (`0600`) с **ровно** двумя полями:
   `access_key_id` и `secret_access_key`. Это отдельные storage credentials,
   не ключи моделей или Cloud.ru administrator. Вводить защищённо без shell history.
   Для Cloud.ru access key ID имеет формат tenant:key; регион `ru-central-1`,
   endpoint строго `https://s3.cloud.ru`. Варианты без TLS инструмент не принимает.
9. Только после проверки затрат/приватности/ключей поставить `upload_enabled: true`.
   Дополнительный `--allow-upload` защищает от случайного запуска команды.

Пример ручного запуска на **подготовленном сервере**, не на ноутбуке с рабочей БД:

```sh
python3 -B /opt/citygo/releases/APPROVED_SHA/deploy/backup/backup.py backup --config /etc/citygo/backup.json --allow-upload
python3 -B /opt/citygo/releases/APPROVED_SHA/deploy/backup/backup.py check --config /etc/citygo/backup.json
```

Код возврата `0` — проверенный успех/свежесть; `1` — отказ. `check` не обращается
к облаку и не проверяет, что объект не удалён после записи локального квитка.
Не считайте его независимым мониторингом. Нужен внешний наблюдатель, отдельная
проверка существования/восстановления копий и согласованный канал уведомлений.

При прерывании обычным сигналом инструмент пытается остановить свои дочерние
процессы и контейнер с уникальным именем. После отключения питания/SIGKILL оператор
проверяет остатки `.attempt-*` и конкретные `citygo-backup-*` контейнеры. Не применять
общий prune или рекурсивное удаление всего каталога данных. Остатки локальных
попыток — зашифрованные, но занимают диск.

## Восстановление

Автоматической команды восстановления поверх рабочей БД намеренно нет.

1. Выбрать конкретные `.complete.json` и `.dump.age`, скачать в отдельную защищённую
   среду. Сверить размер/SHA-256 и соответствие source SHA проверенному релизу.
   Manifest содержит идентификаторы/хеши, **не** пароли, grants или файлы конфигурации.
   Развёртываемые файлы ролей/grants берутся из проверенного Git SHA; серверные
   секреты, env-метаданные и TLS имеют отдельную защищённую копию у оператора.
2. Расшифровать `age` и дождаться успешного завершения **до** импорта. Нельзя
   напрямую направлять непроверенный поток расшифровки в рабочую БД: ошибка в
   конце повреждённого архива не должна оставлять частично изменённую базу.
3. Для реальных данных использовать защищённый зашифрованный диск/ограниченный
   tmpfs с `umask 077`; не переносить их на ноутбук без отдельного разрешения.
4. Создать отдельную PostgreSQL 17, воспроизвести ограниченные роли и импортировать
   от migrator через `pg_restore --no-owner --no-acl --exit-on-error`. Применить grants.
   Выбор target, расходы новой среды и удаление открытого временного дампа —
   явные операторские действия, не скрытая часть этой утилиты.
5. Проверить аккаунты, сессии, миграции, XP, согласия и денежные резервы. AI/уведомления
   остаются отключёнными. Сверить расходы с провайдером до возможного включения AI.
6. Зафиксировать время восстановления и результат. Только затем согласовывать
   расписание/retention/оповещения и отдельный допуск реальных пользователей.

## Что проверяется в CI

- Unit/отказные тесты: подмена конфигурации, утечки окружения, права/символические
  ссылки, блокировка, нехватка диска, ошибки dump/upload/readback/manifest, давность
  квитка и смена назначения; без реального облака.
- Настоящий age: шифрование/расшифровка, ошибка производителя после частичного
  вывода, таймаут, повреждённый архив. Приватные ключи только временные тестовые.
- Контейнерный smoke: реальная ограниченная backup-роль PostgreSQL → age →
  **локальная имитация S3-транспорта** → обратное чтение/расшифровка → отдельная
  БД. Проверяются миграции, сессии, XP и денежный резерв.

Совместимость команд основана на документации Cloud.ru/AWS CLI; живая загрузка
в ваш бакет, доставленное уведомление, расписание и retention **ещё не проверены**.
На Windows выполняются только переносимые unit-тесты; Linux-проверки идут в CI.

## Координация с Worker

Новая версия `backup.py` использует общий операторский lock и устойчивый pending
marker. При ошибке после начала внешних действий следующий backup/Worker блокируется
до проверки оператором; предыдущий «успех» не скрывает незавершённую операцию.
Правила установки, единый state_dir, pause и ограничения описаны в
[протоколе Worker/backup](worker-coordination.md). Это не включает расписание и
не является разрешением миграции или автоматическим восстановлением.
