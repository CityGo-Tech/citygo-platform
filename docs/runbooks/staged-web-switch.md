# Обновление Web с минимальным перерывом

Статус на 9 ноября 2026: отдельный opt-in механизм в коде, **не установлен на
сервере**. Текущий maintenance-контроллер и автодеплой не изменены. Этот документ
не разрешает серверные операции.

## Граница первого этапа

Новый Web заранее запускается рядом со старым. После проверок Nginx направляет
новые соединения к новому Web; прежний Web продолжает обслуживать уже принятые
запросы. API, PostgreSQL, роли, runtime-профиль и фоновые задания остаются
единственными и неизменными. Три режима ИИ, тариф ×10, «Минимум» 3 ₽, постоплата
после ответа без денежного удержания, чеки ЮKassa, телефон и подарок 500 ₽ не
меняются.

Это путь для совместимых изменений Web. Изменения API, схемы, runtime, политик,
получателей данных или существующих публичных ресурсов требуют прежнего
закрытого выпуска. На маленьком сервере две полные пары Web/API также удвоили
бы пул соединений и память API. Поэтому второй API здесь не запускается.

Нулевой простой при любом сбое не гарантируется. Прерванные клиентом соединения,
сбой машины и несовместимые изменения требуют обычного восстановления. Цель —
не прерывать работающие соединения при плановом совместимом обновлении Web.

## Файлы и доверенная основа

- `deploy/render-web-switch.mjs` печатает отдельный шаблон Nginx; ничего не
  устанавливает. Прежний `render-pilot.mjs` остаётся прежним.
- `deploy/backup/web_switch.py` выполняет только `verify`, `switch`, `retire`
  и `inspect` для **двух уже подготовленных** контейнеров Web.
- `deploy/backup/web_switch_assets.py` проверяет манифесты и добавляет неизменяемые
  Next-ресурсы в архив. Нет удаления старых файлов или автоматического GC.
- `scripts/web-switch-smoke.mjs` — одноразовая локальная транспортная репетиция;
  без аргументов и с `--plan` только печатает план.

Нужен отдельный согласованный bootstrap. В этом PR **нет** автоматического
установщика, генератора production-допуска или изменений allowlist старого
публикатора. Нельзя просто скопировать новый файл поверх установленного
контроллера или вызвать прежний `finish` на двух Web-контейнерах.

Bootstrap должен отдельно проверить и закрепить:

1. Root-owned Linux-код контроллера, `backup.py`, модуль ресурсов, Python с
   `pidfd_open`/`pidfd_send_signal`, Nginx и все реально подключённые конфиги.
   Запуск — из защищённого каталога, с очищенным окружением, без пользовательских
   Python-модулей (`python3 -E -s -B`). Символические ссылки и изменяемые чужими
   пользователями предки запрещены.
2. Один прежний API и PostgreSQL, точные ID/образы/время старта/runtime-хеши,
   закрытый допуск фоновых заданий и отсутствие работающих jobs. API уже должен
   доверять **только двум** Web-адресам `172.30.92.10/32` и `172.30.92.20/32`.
   Эти права не добавляются командой переключения.
3. Два Web с loopback-портами `127.0.0.1:3000` и `127.0.0.1:3001`, адресами `.10`
   и `.20` той же сети и единственным прежним DNS-именем `api`. Не добавлять
   второй alias `api`. Контейнеры должны пройти штатный healthcheck.
4. Отдельный шаблон Nginx с include
   `/var/lib/citygo/ingress/web-upstream.conf`, сертификатом настоящего origin
   и прежним `traffic-open`. Include содержит ровно одну строку `proxy_pass`
   на один из двух разрешённых loopback-портов. Не задавать ненулевой
   `worker_shutdown_timeout`: он может принудительно оборвать старые соединения.
5. Архив `/var/lib/citygo/web-assets/_next/static`, доступный Nginx для чтения и
   прохода по каталогам, но изменяемый только root. Права и SELinux/AppArmor,
   если они используются, проверяются отдельно. Локальная проверка слота
   `/__citygo_web_slot` закрыта для внешних клиентов.
6. Проверенные source/backend/schema-проекции двух релизов, фактические
   манифесты **готовых образов**, включая сгенерированный `/characters`, свежую
   проверенную резервную копию и отдельный план восстановления ingress.

План и проекции — доверенное решение оператора, **не автоматически полученная
аттестация исходников**. Равные хеши проекций доказывают только равенство
утверждённых входов; подготовка обязана связать их с проверенными образами и
исходниками. Контроллер не определяет сам, совместимо ли изменение приложения.

## Манифесты и план

Статический манифест — JSON-объект `относительный/путь` →
`{"sha256":"64 hex","size":123}`. Пути считаются от `/_next/static`; для
public-манифестов — от `/`. Модуль принимает только обычный несжатый USTAR,
ограничивает число/размер файлов и отклоняет traversal, ссылки, устройства,
PAX/GNU extensions и неожиданные файлы. При необходимости подготовка отдельно
нормализует Docker-архив, проверяя исходные байты; нельзя отключать проверки.

Новый архив — union уже сохранённых Next-файлов и новых. Один URL с другими
байтами запрещён. Все прежние unversioned public-файлы должны сохраниться с
прежними байтами; разрешено только добавление. В отличие от Next-чанков,
unversioned public обслуживается новым Web, поэтому подмена старого ресурса
сделала бы открытые вкладки несовместимыми.

Точная схема плана закреплена функцией `validate` и синтетическим примером
`fixture()` в `test_web_switch.py`. В production нельзя использовать этот
пример. План содержит origin, случайный operation ID, срок до 24 часов, все
file pins, ID сетей, baseline API/PG/jobs, старый и новый Web, манифесты,
совместимость, PID+starttime master/worker Nginx и защищённые пути состояния.
Неизвестные поля, повторы JSON-ключей, истёкший или изменённый план отклоняются.

Контроллер требует не менее 3840 МиБ общей памяти, 512 МиБ доступной памяти,
неиспользованный swap, `memory full avg10 ≤ 1.0` и 256 МиБ свободного места
состояния. Это минимальные гейты; bootstrap также проверяет реальные cgroup
лимиты и запас для конкретного приложения. Недостаток ресурсов означает отказ
от этого пути, а не увеличение лимитов или остановку старого Web.

## Порядок будущего ручного переключения

После отдельного разрешения на bootstrap и точный выпуск:

1. Подготовить оба слота, архив, защищённый план и резервную копию. Проверить
   неизменность baseline и закрытый допуск jobs. Длительные HTTP/SSE запросы не
   переотправлять и не включать retry на POST.
2. Выполнить `web_switch.py verify --plan /защищённый/plan.json` в установленной
   защищённой среде. Проверяются файлы, инвентарь, сеть, память,
   готовность `/api/ready`, JSON-контракт неавторизованного API и действующий
   маршрут. Команда берёт advisory locks и при первом запуске может создать
   их фиксированные файлы; ingress, runtime, данные и receipts не изменяются.
   Нет переключения, миграций и остановки контейнеров.
3. Выполнить `switch --plan … --allow-switch`. Общие блокировки maintenance и
   worker admission предотвращают параллельную управляющую операцию. Сначала
   fsync сохраняет pending, затем атомарно меняется include. После `nginx -t`
   повторно проверяется baseline; HUP отправляется через pidfd после повторной
   проверки личности root master. Новое поколение workers и новый upstream
   подтверждаются свежим loopback TLS-запросом с проверкой настоящего CA/SNI.
4. Выполнить `retire --plan … --allow-stop`. Пока существует хотя бы один
   **прежний PID+starttime** worker Nginx, старый Web остаётся жив. Это защищает
   и тихий SSE, и POST, который Nginx ещё принимал до HUP. Предел ожидания 330 с
   не является разрешением убить процесс: при превышении возвращается отказ.
5. Только после полного drain повторно проверяются route и baseline. Точному
   старому Web посылается SIGTERM один раз, без эскалации SIGKILL. Проверяются
   exit 0, отсутствие OOM и удаление старого сетевого endpoint. Подтверждённая
   запись `web-active.json` сохраняется до удаления pending.

Команды выше показывают аргументы, а не готовый production launcher. Контроллер
не запускает контейнеры, не создаёт права, не переносит бюджеты и не записывает
результат в legacy `active-release`. Для следующего закрытого backend-релиза
нужен отдельный reconciliation инвентаря/активного слота со старым контроллером.

## Отказ и возобновление

- При HUP Nginx может закрыть простаивавшее HTTP/1.1 keep-alive соединение.
  Клиент с задержанной обработкой событий способен повторно использовать уже
  закрытый сокет и получить `ECONNRESET` до поступления запроса в API. Запись
  байтов клиентом сама по себе не доказывает, что API принял запрос. Свежему
  соединению доступен новый Web; принятые POST/SSE завершаются прежним Web.
  Не считать любой сетевой сбой признаком отсутствия списания и не переотправлять
  POST автоматически: сначала проверить сохранённую попытку и историю.
- Неподготовленный кандидат, drift API/PG/config/assets, нехватка памяти или
  неизвестный сосед сети: отказ до изменения ingress.
- Неуспешный `nginx -t`: восстанавливаются старые байты include без HUP;
  pending сохраняется для разбора.
- Ошибка HUP, неизвестный результат probe или сбой записи состояния: оба Web
  сохраняются, pending не стирается, автоматического rollback/повтора нет.
- Живой старый worker, зависший Web или неполный exit: старый контейнер не
  удаляется. Повторный `switch` не посылает второй HUP.
- `inspect` выводит только operation ID, hash плана и фазу. Если процесс упал
  между durable `stop-requested` и сигналом, возобновление не посылает сигнал
  повторно: требуется отдельный ручной разбор. Не удалять pending ради обхода.

Архив ресурсов не очищается этим механизмом. Его размер и число файлов надо
контролировать; план расширения или GC потребует отдельного изменения.

## Что именно проверяется

Unit-тесты Linux проверяют протокол, отказы, replay, порядок durable-записей,
pidfd, argv и безопасность архива. Отдельные Node-тесты проверяют новый шаблон
и неизменность прежнего. Транспортная репетиция запускает две копии одного
проверенного Next-образа, TLS Nginx и **синтетический** API: непрерывные новые и
keep-alive запросы, тихий SSE дольше обычного 30-секундного Web grace, медленный
POST, сохранение синтетической сессии и единственного dispatch/debit, drain
старых workers и доступ к прежним чанкам после остановки старого Web.

Репетиция не вызывает production-контроллер, настоящий API, БД или оплату и не
является проверкой двух различных релизов. На Docker Desktop API/Web находятся
только во внутренней сети; Nginx дополнительно подключён к одноразовой edge-сети
для loopback TLS. Все данные вымышленные, provider credentials отсутствуют.
Отчёт и логи сохраняются в `.local/web-switch-smoke/`, ресурсы удаляются по
точным собственным ID. Новый workflow только проверяет этот fixture и не имеет
прав на публикацию или выпуск.

Режим `--disposable --idle-reuse-regression` отдельно и без HTTP-повторов
воспроизводит гонку закрытого idle-сокета: один запрос на прежнем соединении,
серверный admission ID, свежий GET и уже принятые POST/SSE. Сравнение с
`keepalive_min_timeout 5s` относится только к тестовой конфигурации Nginx:
ограниченное время защиты не гарантирует сохранность любого idle-соединения.
Production-шаблон этим сравнением не изменяется.

Обычная транспортная репетиция сохраняет каждый HTTP-сброс в отчёте. Только
`ECONNRESET` у повторно используемого GET-сокета тестового `/api/rehearsal/probe`,
без заголовков/тела ответа, в измеренном окне HUP и с подтверждённым отсутствием
допуска в API относится к `idleReuseResets`. Свежие соединения, POST/SSE,
неизвестный допуск, потеря принятого запроса и любые другие ошибки завершают
прогон неуспешно. Если idle-сброс был, отчёт явно получает статус
`passed-with-idle-connection-closure`, а не утверждение «HTTP-ошибок нет».

Результаты локальной подготовки и непроведённые проверки перечислены в
[датированной записи](../operations/web-switch-rehearsal-2026-11-09.md).
`scripts/web-switch-controller-smoke.mjs --disposable --allow-privileged-fixture`
проверяет настоящий `Host` с двумя различными синтетическими Web-релизами,
реальным PostgreSQL и системным TLS в отдельном network-none Docker-in-Docker.
Нет внешнего socket, host bind mounts, внешних портов и provider credentials.
Полная цепочка `verify → switch → retire → повтор retire` исполняется без DI;
отрицательные сценарии проверяют сохранение старого Web. Для чистого CI runner
есть явный `--pull-public-bases`, разрешающий только пять фиксированных
официальных образов. Путь без флагов и `--plan` остаётся инертным.

Этот стенд проверяет OS/transport-контракт контроллера, не финансовые операции и
не вместимость production VM: `/proc` относится к Docker VM, внешний fixture
ограничен 6 ГиБ. До применения нужны отдельные bootstrap, аудит ресурсов и
проверка совместимости именно производственных образов. При SIGKILL невозможно
гарантировать выполнение JavaScript `finally`; сохранённый ownership inventory
используется для ручной проверки и очистки только собственных ресурсов.

Основание поведения: [graceful HUP Nginx](https://nginx.org/en/docs/control.html),
[worker_shutdown_timeout](https://nginx.org/en/docs/ngx_core_module.html#worker_shutdown_timeout),
[keepalive_min_timeout](https://nginx.org/en/docs/http/ngx_http_core_module.html#keepalive_min_timeout)
и [self-hosting Next.js 15](https://nextjs.org/docs/15/app/guides/self-hosting).
