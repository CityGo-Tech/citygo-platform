# Непрерывная блокировка вокруг предрелизной копии

Часть CG-037 / §10.5. Это библиотечный механизм будущего контроллера, **не готовая
команда обновления и не разрешение миграции**. На сервер ничего не устанавливается.
CLI, таймер, фоновый deployment, автоматическое открытие трафика и сброс запрета
не добавлены. Пробный режим не включается.

## Зачем отдельное окно

Последовательность из отдельных команд «backup завершён → начать обновление»
оставляет промежуток, в котором другой управляемый Worker мог начать запись.
`release.release_window(config, target_sha)` удерживает тот же `maintenance.lock`,
что Worker и обычное резервирование, до, во время и после создания копии.
Это позволяет будущему контроллеру проверять завершение записей и выполнять
следующие разрешённые шаги, не отпуская блокировку между ними.

Условие входа — защищённая валидная конфигурация, явный полный SHA цели,
разрешённая загрузка копии, отсутствие незавершённой операции и уже закрытый
допуск Worker. Само окно Worker не останавливает и не закрывает его допуск.
До передачи управления вызывающему коду записывается durable pending с уникальным
ID, исходным fingerprint и SHA цели. SHA здесь — связь с выбранной целью,
**не проверка происхождения или одобрения релиза**.

## Что гарантирует механизм

- Под одной непрерывной блокировкой можно ровно один раз вызвать `window.backup()`.
  Нельзя использовать предыдущий fresh receipt вместо новой попытки. После сбоя
  автоматического или повторного вызова в этом окне нет, даже если ошибку перехватили.
- Используется прежний путь dump → age → upload → readback → completion manifest
  → повторный readback. Обычный backup продолжает брать собственную блокировку;
  новый внутренний путь не пытается повторно захватить уже удерживаемый lock.
- Compose/env читаются в ограниченный снимок и копируются в временные файлы 0600;
  backup запускается из этих байтов с исходным project-directory. Изменение живой
  конфигурации до подтверждения результата приводит к отказу. Внешние mount/secret
  файлы не копируются; самодостаточный доверенный Compose и неизменяемые внешние
  файлы на время окна — требования оператора, как в Worker-протоколе.
- Проверенная копия связана с ID текущей операции в manifest и локальном
  `release-backup.json`. Квиток содержит `migration_authorized: false`.
  Содержимое квитка не является пропуском для другого процесса или следующего запуска.
- Объект окна действует только внутри исходного процесса/потока и контекста.
  После выхода, в том числе нормального, он больше не может создавать копию.
- **Даже нормальный выход сохраняет pending.** Создание копии не означает успешного
  релиза. После сбоя/SIGKILL kernel lock освобождается, но pending продолжает запрещать
  новый Worker, backup, open и новое release-окно. Ошибка очистки временных файлов
  также не создаёт новый успешный checkpoint.
- Нет методов finish/resume/unlock и команды удаления pending. До реализации
  проверяемого завершения контроллера этот модуль нельзя применять как рабочий deploy.

Один стабильный защищённый state_dir на одном хосте обязателен. Это кооперативный
протокол, не граница полномочий root/Docker. Внутренний `_backup_in_operation`
предназначен только для доверенного кода, уже удерживающего lock и pending;
не вызывать его отдельно и не экспортировать через CLI/HTTP.

## Что пока НЕ реализовано

Поверх этого примитива теперь есть [подготовка релиза](release-preparation.md):
закрытие ingress, инвентаризация Compose/DB-сети, остановка API/Worker и новая копия
под тем же lock. У неё тоже нет CLI, миграций и пути завершения; её квиток не
разрешает продолжение из другого процесса. Ограничения ниже относятся к самому
`release_window`, который можно использовать независимо от подготовки.

Окно не проверяет/не меняет ingress, не останавливает API, не перечисляет чужие
one-off контейнеры, не доказывает отсутствие активных соединений/писателей,
не проверяет доверенность целевого manifest, миграции, health или совместимость
старого мобильного клиента. Успешная копия при работающем API может быть обычной
согласованной копией PostgreSQL, но **не является предрелизным допуском**.

Следующий контроллер должен в том же окне закрыть все точки нового допуска,
подтвердить drain API/всех Worker и отсутствие обходных запусков, затем создать
новую проверенную внешнюю копию, выполнить только одобренный переход, проверить
результат и лишь после этого иметь отдельный путь завершения. До такого пути
сохранённый checkpoint не разрешает продолжение из нового процесса.

При неопределённости — [ручная сверка Worker/backup](worker-coordination.md),
без удаления marker по времени/PID и без автоматического повторения операции.

## Проверка

Linux unit tests проверяют блокировку до/внутри/после backup, все отказы upload и
readback, отсутствие retry, drift/snapshot, замену pending, потерю процесса после
успешной копии, права файлов, активность объекта и запрет передачи другому потоку.
Существующая изолированная контейнерная репетиция выполняет настоящий pg_dump/age
внутри окна, проверяет конкурирующие отказы и сохраняет pending после выхода;
затем расшифровывает и восстанавливает копию в отдельную синтетическую БД.
S3 здесь — локальная имитация транспорта. Реальное облако, пользовательские данные
и запросы к моделям не используются. Репетиция не выдаётся за проверку всего deploy.

Семантика окна опирается на [contextmanager Python](https://docs.python.org/3/library/contextlib.html#contextlib.contextmanager)
и явный [project-directory Docker Compose](https://docs.docker.com/reference/cli/docker/compose/).
