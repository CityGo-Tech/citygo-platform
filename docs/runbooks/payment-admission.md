# Допуск боевой оплаты и фоновая сверка

Выбранные оператором реквизиты чека и новый runtime v6 описаны в
[профиле чеков ЮKassa](yookassa-receipt-profile.md). Новый live POST требует этого
явного профиля; его изменение инвалидирует старую привязку допуска, не мешая
проверке и сверке ранее созданных заказов.

Это описание подготовленного кода, не разрешение открыть сервер. Новая миграция
`0022_payment_admission.sql` создаёт **закрытый** допуск; применение миграции,
наличие ключа ЮKassa или успешный CI не включают приём денег автоматически.

## Как разделены переключатели

- Runtime разрешает конкретный live-магазин, HTTPS-origin, тариф и режим чеков.
  API вычисляет стабильный `runtimePolicyId`; браузер не может выбрать магазин
  или прислать собственную привязку. Секретный ключ в эту идентичность не входит.
- Текущий `super_admin`, уже сменивший временный пароль, отдельно разрешает
  новые пополнения в панели «Допуск оплаты». Обычного `admin` недостаточно.
- Фоновая сверка включается независимо. Выключение новых пополнений **не**
  отменяет уже выданные ссылки ЮKassa, обязательства по ним, возвраты или чеки.
- Новый checkout доступен только при свежей успешной сверке, совпадающем
  runtime-профиле и действующем режиме допуска. Без этих условий API отвечает
  отказом до создания новой оплаты у провайдера.

Пользовательский `topUpAvailable` — подсказка для интерфейса, не доказательство
допуска. Сервер проверяет состояние внутри короткой транзакции создания заказа
и повторно перед provider POST. При гонке с закрытием может остаться локальный
заказ без provider ID; он не означает оплату или начисление.

## Режимы работы оператора

**Ограниченное окно** (`lease`) привязано к сессии оператора и времени БД.
Истечение окна, выход или удаление сессии закрывают новые checkout.

**Круглосуточный приём** (`continuous`) требует отдельного подтверждения
ответственности за ручные НПД-чеки. Оператору не нужно держать браузер открытым:
обычный logout не закрывает этот режим. Однако блокировка владельца допуска,
снятие его `super_admin` или обязательная смена пароля делают checkout недоступным.
Эта отметка — заявление оператора, **не** доказательство оформления/передачи
НПД-чека, налоговой регистрации или соблюдения сроков.

Панель показывает незавершённые регистрации, передачи, корректировки и review.
Дата самого старого наблюдения — диагностическая дата, не вычисленный законом
срок. Email аккаунта не выдаётся за контакт, подтверждённый источником оплаты.
Реестр и действия оператора описаны в [инструкции НПД](manual-npd-receipts.md).

## Сверка платежей и возвратов

1. API получает DB lease для одного цикла, связанный с revision и runtime.
2. Ограниченный scanner ставит известные pending-платежи/возвраты в inbox.
   Неизвестный provider ID не восстанавливается догадкой или новым POST.
3. Цикл API делает независимые server GET вне транзакций БД. Отдельный Worker
   приложения не получает финансовых прав.
4. Проводки возникают только после проверки магазина, режима, владельца,
   идентичности заказа, точных RUB-сумм и статуса. Webhook и переход по return URL
   не являются финансовым подтверждением.
5. Успешный цикл обновляет здоровье. Ошибка, неподтверждённое несоответствие или
   устаревшее здоровье закрывают новые checkout. Нормальный `pending` не означает
   сам по себе ошибку платежа.

Цикл обрабатывает до 10 записей; следующая попытка — через 60 секунд после
завершения, без бесконечного немедленного retry. Свежесть здоровья — 120 секунд.
Очень медленный batch может временно закрыть checkout: доступность не ставится
выше денежной целостности. Устаревший runId/revision не может перезаписать
здоровье после закрытия, повторного включения или смены профиля.

При остановке API цикл сначала завершается/освобождает свой допуск, затем
закрывается соединение БД. Это не отдельный постоянно работающий процесс в Web.
Тестовый `buildApp` по умолчанию не запускает таймеры и внешние операции.

## Идемпотентность и права

Команда содержит UUID и ожидаемую revision. CAS-конфликт требует обновить
состояние; клиент не придумывает новый UUID для автоматического повтора записи.
Повтор не продлевает окно и не переоткрывает закрытый допуск. Текущие права и
сессия проверяются до обработки повтора.

API может менять только необходимые колонки singleton. Журналы команд и
результатов сверки доступны API на SELECT/INSERT, backup — на SELECT; Worker
не получает к ним доступ. UPDATE/DELETE/TRUNCATE истории запрещены, включая
защиту триггерами. Общий порядок блокировок: account security → admission →
плательщик/заказ. Внешних API-вызовов под этими блокировками нет.

Полный сброс старых аккаунтов требует schema 22. Связанное/активное состояние
допуска или его история блокируют сброс: нельзя удалить связи или отключить
триггеры ради очистки. Неиспользованный singleton сохраняется неизменным.

## Перед открытием

- Установить проверенный точный SHA через штатный release gate и проверить
  миграции/grants. CI не заменяется вручную выставленным зелёным статусом.
- Проверить актуальную зашифрованную копию и согласованный способ восстановления.
- Закрыто проверить регистрацию, смену bootstrap-пароля и актуальные роли.
- Согласовать рабочий AI-маршрут/уведомление получателей и проверить реальный
  ответ с независимой стоимостью: CityGo ×10, неизвестная стоимость в резерве.
- В закрытом операторском контуре временно включить сверку, дождаться здоровья
  и открыть ограниченное окно `lease`. Это не открытие публичного ingress.
- В этом окне провести разрешённый владельцем живой платёж 100 ₽, убедиться в единственном
  начислении 100 ₽ CityGo, выполнить полный возврат и проверить денежный журнал,
  НПД-обязанность и её корректировку. Карта вводится владельцем.
- После приёмки проверить сверку, затем явно открыть выбранный публичный режим допуска.
  Проверить пользовательскую доступность, закрытие новых checkout и завершение
  ранее созданного платежа после закрытия.

Подарок 500 ₽ остаётся выключен до подключения проверки телефона. Тестовые
начисления не переносятся в live-БД. Технические проверки не заменяют решение
оператора о публичном запуске и его работу с реальными НПД-чеками.
