# Подготовка релиза: закрытый вход → остановка писателей → новая копия

Часть CG-037 / §10.5. `deploy/backup/prepare.py` — библиотека для будущего
проверенного контроллера, **не команда для рабочего сервера**. Нет CLI, миграций,
скачивания образов, удаления контейнеров, перезапуска, открытия доступа или снятия
pending. На Cloud.ru ничего не устанавливается; расписания и пробный режим
не включаются.

## Предварительные условия

- Один Linux-хост, один проверенный Compose-проект и стабильный защищённый
  `state_dir` для Worker, backup и release. Все управляемые исполнители используют
  общий протокол [worker-coordination](worker-coordination.md).
- Оператор заранее исключил старые cron/systemd/ручные обходные запуски,
  сторонние DB-клиенты и прямой доступ к Web/API в обход ingress. PostgreSQL
  не опубликован наружу. Это кооперативная блокировка, не защита от root/Docker.
- Установлен проверенный default-closed Nginx-шаблон; известны его защищённая
  папка `traffic-open` и точный ASCII HTTPS origin (IDN — в punycode). Локальный
  порт 443 обслуживает именно этот ingress с действительным доверенным сертификатом.
  Библиотека не устанавливает Nginx и не проверяет hash его конфигурации.
- Compose/env, bind mounts и секреты проверены и неизменяемы на время операции.
  Expected images — шесть заранее проверенных **текущих** Docker image ID
  (`sha256:…`) для api/web/postgres/worker/migrator/backup, не теги и не доказательство
  происхождения целевого релиза. Backup использует проверенные Compose/env текущего
  проекта. [Выбор целевого manifest](release-target.md) проверяется отдельным
  защищённым approval до любых изменений; это ещё не одобрение миграции/перехода.
- Разрешены остановка и новая внешняя копия. Доверенный вызывающий код обязан
  передать ровно `allow_stop=True, allow_upload=True`; сама конфигурация backup
  также должна разрешать upload. Это не замена пользовательскому одобрению.

Не запускать библиотеку в production до реализации и проверки полного пути
завершения/ручной сверки: после успешной подготовки сервис намеренно останется закрыт.

## Последовательность

1. Проверить [одобренную цель](release-target.md), оба bundle, hashes, срок approval
   и связь с конфигурацией. Затем закрыть допуск новых управляемых Worker.
   Если другой Worker/backup уже держит
   maintenance lock, отказ без ожидания и прерывания этой операции. Уже работающий
   API в этом случае не останавливается; квитка подготовки нет.
2. Войти в [непрерывное release-окно](release-backup-window.md), сохранить pending
   с уникальным ID операции и SHA цели. Lock остаётся захвачен до конца подготовки.
3. Удалить только обычный защищённый `traffic-open`, синхронизировать каталог.
   Проверить `/` и `/api/ready`: HTTPS через **127.0.0.1:443**, SNI/Host по origin,
   обычная проверка сертификата, без DNS, прокси, redirect или `verify=False`.
   Нужен именно maintenance JSON 503 с contract version, no-store и request ID,
   а не произвольная ошибка недоступности API.
4. Перечислить **все**, включая завершённые и one-off, контейнеры проекта.
   Требуются ровно по одному API/Web/PostgreSQL, известные роли и image ID,
   ожидаемые one-off/restart/init/grace параметры, отсутствие рестартов/OOM/ошибок.
   Работающий migrator или backup, неизвестный сервис, реплика, пропавший контейнер
   или предыдущий неуспешный exit блокируют продолжение.
5. Проверить ID и Compose labels сети `<project>_database`. Все её участники должны
   принадлежать известному набору, а работающие DB-сервисы — присутствовать в ней.
   Неизвестный участник, даже без Compose labels, блокирует подготовку.
6. Отправить SIGTERM только точным полным ID проверенных API/Worker: Docker grace
   330/90 секунд. Проверять тот же ID/image/StartedAt/RestartCount после остановки,
   требовать exit 0, отсутствие OOM/error и корректное время завершения. SIGKILL,
   timeout или неясный результат не считаются успешным drain. Контейнеры сохраняются.
7. Повторить инвентаризацию и проверку закрытого ingress. API и все Worker должны
   быть завершены; PostgreSQL остаётся healthy, Web — running. Web может стать
   unhealthy из-за остановленного API: это ожидаемо, а не основание его перезапускать.
8. Перепроверить цель и вызвать ровно одну новую копию внутри того же lock: pg_dump → age → upload →
   readback архива → manifest → readback manifest. Старого статуса fresh недостаточно.
9. Ещё раз проверить те же контейнеры, закрытый ingress и неизменную DB-сеть.
   После очистки временных файлов и проверки pending/config/целевого approval сохранить защищённый
   `release-prepared.json` с ID операции, краткими свидетельствами и ссылкой на копию.
   Ни environment, ни health logs, ни содержимое секретов в квиток не попадают.

## Границы результата и обработка отказа

Квиток всегда содержит `migration_authorized: false`. Это свидетельство подготовки,
**не пропуск для миграции, нового процесса или повторного запуска**. После выхода
kernel lock освобождается, но durable pending остаётся. Управляемые Worker/backup/open
и новое release-окно отказываются работать до отдельно проверенного завершения.
Библиотека не очищает pending ни по времени, ни по PID, ни даже при успехе.

Ошибку не исправлять автоматическим retry, открытием marker или удалением контейнеров.
Если отказ произошёл после закрытия ingress, он остаётся закрытым; уже завершённые
сервисы не запускаются обратно. Если остановка дала неопределённый результат,
другие писатели могут ещё работать — нельзя объявлять quiescence по одному 503.
Нужна [ручная сверка](worker-coordination.md), а не удаление pending наугад.

Инвентаризация охватывает Compose-проект и участников его DB-сети. Она **не доказывает
отсутствие всех PostgreSQL-сессий**, процессов на хосте или root, запускающего новый
контейнер между проверками. Поэтому аудит обходных исполнителей и неизменяемость
runtime обязательны. Проверка локальных образов нового релиза, миграции, health после обновления,
совместимость мобильного клиента и управляемое открытие доступа ещё не реализованы.

## Проверки без сервера пользователя

Unit tests проверяют порядок и взаимное исключение, неправильные image/реплики,
нечистый exit, замену процесса/сети, нового DB-peer/one-off, открытие ingress во время
копии и ошибку readback. Успех и отказ сохраняют pending; повтор запрещён.

Disposable CI использует настоящие API/Web/PostgreSQL, Nginx TLS с тестовым CA,
сохранённый jobs one-off, pg_dump и age. Полученный архив читается обратно и
расшифровывается; S3 заменён локальным transport. Jobs может завершиться до команды
остановки — сохранённый контейнер всё равно должен пройти проверку. Активный drain
Worker отдельно проверяет существующий container smoke. Другой прежний сценарий
проверяет восстановление резервной копии в синтетическую БД. Это не реальный
Cloud.ru/S3 и не испытание полного обновления production.
