# Проверка контролируемого перезапуска закрытого стенда

Статус: **одноразовая CI-репетиция**, не серверная команда и не разрешение
перезапустить Cloud.ru. `restart_smoke.py` не входит в runtime bundle, не имеет
операторского CLI и импортирует только тестовый транспорт резервного хранилища.
Не копировать этот сценарий на рабочую ВМ и не заменять его метки/адреса на реальные.

## Что проверяется

В существующем Container smoke после двух закрытых выпусков на одной синтетической
БД выполняется следующий сценарий:

1. Проверяются случайный `citygo-pilot-test-<12 hex>` project, вымышленный origin,
   синтетический source SHA, расположение временных файлов, отсутствие незавершённой
   операции, закрытый Worker и TLS maintenance. Берутся оба локальных lock.
2. Фиксируются точные container IDs, образы, процессы, сети, volume PostgreSQL,
   generation/config/secret bindings и исторические JSON-файлы. API/Web обязаны
   соответствовать прежнему production-профилю с `LLM_PROVIDER=disabled`.
3. Останавливаются API → Web → PostgreSQL. Сохраняется **результат остановки до
   нового старта**: тот же процесс, exit 0, без OOM/engine error/Dead. Grace periods
   330/30/60 секунд. При ошибке запуск не выполняется; SIGKILL не считается успехом.
4. Запускаются **те же ID** PostgreSQL → API → Web, каждый один раз. Образ, настройки,
   volume и сети не заменяются, pull/build/migration не выполняются. Ожидание health
   ограничено 120 секундами на сервис. Неуспех прекращает сценарий без retry.
5. У каждого сервиса должен появиться новый `StartedAt`, позже чистого завершения
   прежнего процесса. Образы/ID/runtime остаются прежними. Все сохранённые jobs
   должны остаться теми же завершёнными процессами; они не запускаются и не удаляются.
6. Проверяются TLS maintenance до, между и после операций, включая фазу, когда все
   три сервиса остановлены. Проверяются readiness, API-контракт, изоляция контейнеров,
   неизменность данных конфигурации, секретов и закрытый Worker.
7. Старые процессные доказательства **не принимаются** как доказательство нового
   запуска: прежний same-process guard должен отклонить новый `StartedAt`.
   `active-release.json` остаётся неизменной историей фиксации версии, не справкой
   о текущем здоровье и не новым разрешением перезапуска.
8. Создаётся новый настоящий `pg_dump → age` с тестовым S3-транспортом в памяти.
   Через прямой loopback Web/API проверяется прежняя пользовательская сессия,
   анкета, квесты, история чата, `+60 XP` и доступность следующего квеста. Повторное
   завершение старого квеста не начисляет XP заново. Ответ в чате — явно синтетическая
   запись фикстуры, не вызов или ответ живой модели.

Сценарий не создаёт аккаунт заново после перезапуска и не заполняет заново потерянные
данные. Проверки сравнивают исходный результат с чтением после двух выпусков и
перезапуска. Существующие проверки резервного восстановления и TLS/SSE сохраняются.

## Чего этот результат не доказывает

- Это **graceful stop/start контейнеров**, не перезагрузка ВМ, Docker daemon или
  внезапное отключение питания. Прерывание посреди миграции и crash recovery БД —
  другие сценарии.
- Повторяется один набор проверенных бинарников/SQL-журнал. Совместимость и откат
  конкретного будущего кандидата с новой схемой БД всё ещё требуют отдельной проверки.
- Пробный и production AI не включаются; внешних писем, S3/GHCR публикаций и платных
  запросов к моделям нет. Правила SSH, DNS и сертификаты рабочего сервера не меняются.
- Политика `restart=no` остаётся прежней. CI не устанавливает systemd unit и не даёт
  разрешения на автозапуск, открытие трафика, Worker или расписаний.

## Перед отдельным перезапуском рабочей ВМ

Это перечень условий, **не разрешение выполнять их прямо сейчас**:

1. Согласовать точную установленную версию, окно, остановку PostgreSQL и план
   восстановления. Проверить свежую внешнюю копию и доступ к аварийной консоли.
2. Отдельно определить поведение после boot и порядок запуска. Нельзя просто менять
   `restart=no` на `always` или запускать все services/profiles Compose: это может
   запустить мигратор/Worker либо обойти закрытый допуск.
3. Подтвердить отсутствие pending-операции, закрытый трафик, Worker и расписания.
   Сохранить фактическое состояние процессов до остановки; при нештатном завершении
   остановиться, не стирать доказательства перезапуском.
4. После одобренного старта заново проверить процессы, БД/volume, сети, readiness,
   конфигурацию/секреты, закрытый TLS и пользовательские данные. Старые receipts не
   являются разрешением на новую операцию или подтверждением текущего состояния.
5. Создать новую резервную копию. Открытие доступа пользователям согласовывается
   отдельно, после остальных launch gates.

Текущий [операторский выпуск](release-operator.md) и commit-only recovery не
расширяются этим тестом. Если процесс изменился во время незавершённого commit,
recovery по-прежнему откажет; этот тест не разрешает обходить такой отказ.
