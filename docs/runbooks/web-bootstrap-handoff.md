# Проверка готовности к передаче Web после закрытой подготовки

Этот этап связывает результат [закрытой подготовки API и второго Web](web-runtime-stage.md) с новой сводкой. Команда принимает уже экспортированные данные и печатает JSON для ревью. Время и источники сводки указывает оператор. Успешный отчёт фиксирует согласованность переданных доказательств. Живое состояние, установку, открытие входа и снятие блокировок проверяет отдельный исполнитель.

```sh
python3 -B deploy/backup/web_bootstrap_handoff.py --plan
python3 -B deploy/backup/web_bootstrap_handoff.py --review /path/to/exported-evidence
```

Каталог должен содержать следующие документы. Используйте только метаданные и хеши.

| Файл                    | Источник                                                                |
| ----------------------- | ----------------------------------------------------------------------- |
| `stage-plan.json`       | Точные байты плана, с которым завершился stage                          |
| `draft.json`            | Манифест исходного проверенного проекта конфигурации                    |
| `prepared.json`         | Квитанция `prepared-closed` от stage или adopt                          |
| `pending.json`          | Защищённый журнал stage с исходными подтверждениями команд и готовности |
| `legacy-barrier.json`   | Точные байты старого `operation-pending.json` этой операции             |
| `stage-inspection.json` | Результат свежего `web_runtime_stage_cli.py inspect` для того же плана  |
| `observation.json`      | Новая закрытая сводка оператора по схеме ниже                           |

Штатный stage сохраняет шесть подтверждений команд и готовность обоих сервисов.
После потери ответа на запуск Web или остановки перед закрытием журнала в нём
может остаться пять или шесть подтверждений и только pin готовности API.
Для такого случая дополните экспорт двумя файлами с точными исходными байтами:

- `adopt-approval.json` из защищённого `adopt-<sha256>.json`.
- `adopt-state.json` из соответствующего `adopt-state-<sha256>.json`.

Проверка связывает допуск с исходным журналом по SHA-256 и с текущим по
операции, плану и допустимому изменению только `phase` и `intent`. Если
квитанция содержит хеш допуска, он должен совпасть с точными байтами экспортированного
допуска. При шести подтверждениях может сохраниться первоначальная квитанция
без хеша допуска. Исторический допуск сверяется на момент его выдачи, а свежий
inspect подтверждает готовность обоих сервисов. История подтверждений сохраняется.

В `observation.json` указываются версия `1`, `purpose=citygo-web-bootstrap-handoff-observation-v1`, тот же `operation_id`, целое время Unix `observed_at`, SHA-256 точных файлов `inspection_sha256` и `prepared_sha256`. Срок для ревью составляет 120 секунд после наблюдения. Для перехода понадобится свежий допуск.

- `runtime` содержит полные pins `api`, `old_web`, `new_web`, `postgres`, `jobs` и `networks` по схеме первого плана и квитанции. API и новый Web сверяются с результатом stage, старый Web, PostgreSQL, jobs и сети — с исходным baseline.
- `canonical_file_pins_sha256` — digest канонического `web_switch.wire` от заново наблюдённого объекта `originals` той же формы, что в `draft.json`. Сверяются исходные Compose, env, backup config, active release и autodeploy current.
- В `gates` значения `traffic_open`, `worker_admission_open` и `autodeploy_enabled` равны `false`, `external_reload_excluded` равно `true`.
- `ingress` включает дескриптор `enabled_link` (`path`, `target`), pin байтов `legacy_config` (`path`, `sha256`), `candidate_config_sha256`, `tls_evidence_sha256`, `initial_upstream_sha256`, pins `master` и `workers` (PID и `starttime`). Исходный symlink указывает с `sites-enabled/citygo-pilot` на `sites-available/citygo-pilot`. Первый include направляет в прежний слот на `3000`, canary останется на `3001`.
- `assets` содержит `public_manifest_sha256`, `static_manifest_sha256` и `archive_observation_sha256` для экспорта same-image Web, в том числе старых Next-ресурсов. Эти хеши являются ссылками на доказательства. Для применения содержимое и защищённые пути нужно проверить отдельно.

Пример синтетического набора находится в `test_web_bootstrap_handoff.py`. Он подходит для проверки схемы. До открытия доступа будущий исполнитель должен снова сверить каждый pin под общими блокировками, исключить посторонний reload, подготовить архив, установить ingress и проверить TLS и оба слота. Передача канонического active state и снятие барьеров требуют отдельного исполнительного этапа с проверкой восстановления. Для возврата сохраняются исходный symlink, байты его target и исходные API-параметры. После пересоздания API для возобновления нужны свежие разрешения, привязанные к новым процессам.

## Стендовая проверка Nginx

На Linux с Nginx и OpenSSL запустите от обычного пользователя:

```sh
python3 -B deploy/fixtures/web-switch-ingress-handoff.py --disposable
```

Проверка запускает свой Nginx на высоких loopback-портах с тестовым TLS-сертификатом. Используются оба шаблона CityGo и два синтетических Web-слота. Шаблоны адаптируются только к временному каталогу, адресу, портам и имени стенда.

Стенд устанавливает переключаемый ingress при закрытом трафике. После открытия выполняет переход со слота A на B и обратно с реальным HUP. Уже начатые SSE и POST завершаются по одному разу. Затем стенд снова закрывает трафик и восстанавливает прежнюю ссылку на конфигурацию. Отчёт содержит время смены поколений процессов Nginx в этом стенде. Применение на сервере, согласование рабочего состояния и снятие барьеров остаются отдельными этапами.

## Журнал закрытого переключения

Стенд записывает намерение до замены конфигурации и перед отправкой HUP. При установке переключаемый конфиг становится обычным файлом на месте исходной ссылки. При возврате восстанавливаются точный текст прежней ссылки и маршрутизация по сохранённому конфигу. Трафик остаётся закрытым во время обеих операций.

Проверяются два сбоя. После потери ответа на HUP восстановление сверяет метку загруженного профиля, прежний master и новое поколение workers, затем сохраняет квитанцию без второго сигнала. После остановки сразу после замены файла или ссылки журнал позволяет продолжить с проверки конфига. Если после записи намерения HUP результат нельзя подтвердить, журнал сохраняется для диагностики.

Отдельный include Nginx создаёт сокет `/run/citygo-nginx-epoch/epoch.sock` в каталоге с правами `0700`. Контроллер читает ответ по свежему соединению и проверяет PID и UID владельца сокета через `SO_PEERCRED`. Метка записана непосредственно в конфигурации. Она привязана к операции, направлению, байтам сайта и проверенному пакету. Поэтому старое и восстановленное поколения получают разные метки даже при одинаковых байтах сайта.

Файл сайта и include готовятся под одним намерением до `nginx -t` и HUP. При восстановлении после частичной записи недостающий include можно подготовить, пока загружены прежняя метка и прежнее поколение. После HUP проверка требует новую метку, завершение прежних workers, точные байты на диске и сохранённый публичный 503. TCP-маршрут `/epoch` остаётся закрытым.

На стенде include загружается тем же Nginx при первом запуске. До применения на сервере нужно отдельно подготовить исходную метку при точных проверенных байтах текущего legacy, закрепить root-owned каталог сокета и путь include, связать его с полной проверкой `nginx -T` и исключить посторонние reload под общими блокировками. Существующий legacy без загруженной исходной метки не может начать этот протокол. Стендовая квитанция не разрешает открытие трафика или снятие барьера.
