# Закрытая подготовка API и второго Web

Статус: код и изолированный стенд; рабочий сервер не изменяется.
Этап следует за [установкой неактивного контроллера](web-controller-install.md)
и использует [проект конфигурации #192](web-bootstrap-draft.md).
Он готовит runtime, но не открывает приложение и не переключает Nginx.

## Что меняется

Первый API и второй Web используют прежние утверждённые image ID и source SHA.
У API разрешены только два изменения: доверенные CIDR `.10/32,.20/32` и restart
`unless-stopped`. Секреты и все остальные настройки приложения сохраняются.
Второй Web находится в отдельном project, получает `.20`, loopback-порт `3001`
и restart `unless-stopped`. Старый Web `.10:3000`, PostgreSQL и исторические
jobs сохраняют свои идентификаторы и настройки.

Контроллер один раз отправляет SIGTERM точному старому API и ждёт подтверждённого
выхода с кодом 0 без OOM. Затем удаляет только этот остановленный контейнер
без force и без удаления томов. Он создаёт API из проверенной отдельной проекции
Compose и запускает точный полученный ID; затем так же создаёт второй Web.
Команд `compose up`, автоматического recreate, загрузки образов и миграций нет.

Обычный `docker stop` не используется: по окончании timeout он мог бы отправить
SIGKILL. При неподтверждённом завершении этап останавливается с сохранённым
журналом. Ответы модели и платёжные запросы не переотправляются.

Три режима ИИ, ×10, «Минимум» 3 ₽, постоплата после ответа без денежного
удержания, бюджетные счётчики, чеки ЮKassa, подтверждение телефона и подарок
500 ₽ не меняются. Ключи не перевыпускаются и не копируются в новые файлы.
Реклама и автодеплой не включаются.

## Условия и доверие

До запуска должны быть закрыты публичный marker и worker admission, закончены
посторонние операции и активные jobs. Реальный loopback TLS должен возвращать
штатный maintenance-контракт. Точный план закрепляет исходные контейнеры,
полную инвентаризацию project, сети, канонические файлы и secret pins.
Проверяются реальные байты и состояние; неизвестный сосед или дрейф означает отказ.

Сравнение runtime учитывает один подтверждённый вариант Docker:
`OomKillDisable: null` и `false` означают включённый OOM killer. В
[коде Moby](https://github.com/moby/moby/blob/master/daemon/daemon_unix.go)
значение по умолчанию — `false`, а неподдерживаемое поле может стать `null`.
Контроллер приводит только эти два явных значения к `false`; `true`, пропуск
поля и неверный тип запрещены. Остальные поля сравниваются без такой подстановки.

План также связывает файлы свидетельств свежей резервной копии и проверки
восстановления с заявлением оператора о предварительном drain. Эти root-owned
сведения — **утверждение оператора, а не автоматически полученная аттестация**.
Этот этап не загружает копию из S3 и не повторяет restore-проверку. Они должны
быть выполнены отдельно штатной процедурой до допуска на runtime.

Закрытый marker и чистый выход API не доказывают отсутствие уже принятых,
но ещё буферизуемых запросов Nginx. Контроллер сохраняет graceful drain
запросов, уже принятых API; предварительное завершение всего ingress-трафика
остаётся явным условием оператора. Нельзя обещать бесшовность первого bootstrap
или сохранность всех принятых Nginx запросов только по результату этого этапа.

Для первой операции требуются свежие план и отдельный root-owned допуск
`allow_stage`, связанные точными operation ID и SHA плана. Draft, manifest
и старое разрешение на merge сами по себе не дают этого допуска.
Исторические сведения сохраняются для просмотра после истечения срока;
новые изменения не получают разрешение задним числом.

## Команды

```sh
python -B deploy/backup/web_runtime_stage_cli.py --plan
python -B deploy/backup/web_runtime_stage_cli.py stage --planfile <protected-plan.json> --approval <stage-cap.json> --allow-stage
python -B deploy/backup/web_runtime_stage_cli.py inspect --planfile <protected-plan.json>
python -B deploy/backup/web_runtime_stage_cli.py adopt-prepared --planfile <protected-plan.json> --approval <fresh-adopt-cap.json> --allow-adopt
```

Без аргументов и с `--plan` нет операции или чтения сервера. Рабочие маршруты
требуют Linux root и защищённого проверенного launcher. Произвольные команды,
пути назначения, подмена времени, flags открытия доступа и автоматического
возврата через CLI не принимаются. Схема плана и допусков определена в
[`web_runtime_stage.py`](../../deploy/backup/web_runtime_stage.py).

Установщик #193 намеренно сохраняет контракт ровно трёх неактивных модулей:
его receipt не подтверждает установку этого нового executor. Перед серверным
применением ещё требуется отдельный проверенный launcher для шести файлов:
`web_runtime_stage.py`, `web_runtime_stage_cli.py`, `web_bootstrap.py`,
`web_switch.py`, `web_switch_assets.py` и `backup.py`, с закреплёнными байтами
в защищённом root-owned каталоге и изолированным Python-окружением. Этот PR
не устанавливает такой launcher и не даёт разрешения запускать код на сервере.

## Журнал и неопределённость

Все изменения проходят под общими maintenance/worker locks. До первого
Docker-изменения создаются собственный журнал и соответствующий legacy barrier.
Исходные допуски и pins остаются связаны с этой операцией.

Перед каждой из шести команд durable intent фиксирует действие: `api-term`,
`api-remove`, `api-create`, `api-start`, `web-create`, `web-start`.
После команды результат подтверждается фактическим наблюдением.
Потерянный ответ, timeout или остановка контроллера не разрешают повтор.
Повторный `stage` при существующем pending отклоняется.

`inspect` только описывает наблюдаемое состояние. `adopt-prepared` с новым
допуском и точным SHA pending принимает **только полностью готовую здоровую
целевую топологию**, повторно проверенную в этот момент. Он не создаёт,
не запускает и не удаляет контейнеры. Частично выполненная операция остаётся
для отдельного разбора или будущего явно разрешённого обратного плана.

## Завершение этого этапа

Успех имеет статус `prepared-closed`: прежние API image/source/config и
PostgreSQL сохранены, работают новый API и два Web, доступ закрыт.
Legacy barrier намеренно **остаётся**, канонические `ACTIVE`, текущие receipts
и Compose не переписываются. Старые startup/resume approvals, привязанные к
прежним ID/StartedAt, не применяются.

Это не готовность к вызову обычного `web_switch`: тот правильно отказывает,
пока существует legacy pending. Следующая фаза должна отдельно проверить
свежий baseline, ingress, архив статических ресурсов и правила возврата,
а затем явно передать управление. В этом PR нет HUP, смены конфигурации Nginx,
открытия доступа, удаления барьера или автоматического rollback.

## Изолированная репетиция

```sh
sudo env TMPDIR=/root python3 -B -m unittest discover -s deploy/backup -p 'test_web_runtime_stage*.py' -v
node scripts/web-switch-controller-smoke.mjs --disposable --allow-privileged-fixture --runtime-stage
```

Репетиция использует настоящий production Host внутри отдельного Docker-in-Docker
контейнера. У внешнего контейнера нет сети, host socket, provider credentials
или директорий рабочего сервера. API/Web поведение синтетическое; Docker,
PostgreSQL, TLS и graceful shutdown настоящие. Проверяются точные команды,
потерянный результат, явное принятие уже готового runtime и неизменность
конфигураций, секретов, бюджетных данных и остальных контейнеров.
Это не живая проверка моделей, не перенос пользовательских данных и не
доказательство восстановления после потери питания.

Локальная проверка 9 ноября 2026: **190/190 Linux-тестов** без пропусков
(155 прежних и 35 новых), **121/121** тест контейнерных и релизных скриптов,
ESLint, Prettier и `git diff --check`. Настоящая DinD-репетиция production Host
завершилась успешно: шесть runtime-команд, один SIGTERM, по одному завершённому
POST и SSE; новый допуск принятия результата не выполнил Docker-изменений.
Ответ последнего `web-start` намеренно потерян после принятия команды.
Все шесть внешних ресурсов стенда удалены с проверкой принадлежности.

Истечение исходного допуска проверено unit-тестами; физическая репетиция
не ждала истечения его 600 секунд. Backup/restore evidence и бюджетные строки
на стенде синтетические. Это не проверка реальных AI-ответов или платежей.
Первоначальные неуспешные прогоны сохранены рядом с успешным: выявлены
разрешённый пустой env, представление OOM-параметра и гонка готовности тестовой
БД; исправления не расширяют допуск на произвольный дрейф runtime.
