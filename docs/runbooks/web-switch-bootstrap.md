# Первичное подключение переключения Web

Статус: **подготовка, сервер не изменён**. Это проект отдельной ручной операции,
а не разрешение её выполнить. [Основной протокол](staged-web-switch.md) находится
в main после #190. Обычный publisher этот механизм не устанавливает.

## Результат и границы

Первый canary использует **тот же утверждённый образ и source SHA Web, который
уже работает**. Это подключение инфраструктуры без нового продуктового выпуска.
Образ API, PostgreSQL, схема, runtime-профиль и ключи сохраняются. Три режима ИИ,
×10, «Минимум» 3 ₽, списание после ответа без денежного удержания, чеки ЮKassa,
телефон и подарок 500 ₽ остаются прежними. Лимиты и счётчики бюджета не меняются:
профиль и образы сохраняются. Реклама и автодеплой не включаются.

Первое подключение требует короткого закрытого окна: единственный API нужно
пересоздать для двух доверенных Web-адресов. Нельзя обещать бесшовность bootstrap
или запускать второй API. Последующие совместимые Web-выпуски используют drain
старого слота; backend/schema/runtime-изменения проходят обычный закрытый выпуск.

Для следующего Web-цикла будущий стейджер должен под общими locks заранее
перевести прежний active Web из `unless-stopped` в `no`, а кандидата подготовить
с `unless-stopped`, затем закрепить новые runtime pins. V2 этого не делает.
До такой подготовки повторное переключение будет отклонено; автоматического
стейджера для последующих выпусков этот пакет не добавляет.

## Локальный пакет

```sh
node scripts/web-bootstrap-preparation.mjs --plan
node scripts/web-bootstrap-preparation.mjs --prepare --host=pilot.xn--c1ajazlh.xn--p1ai
```

Вторая команда только создаёт новый каталог `.local/web-bootstrap-preparation/`:
три Python-модуля, отрендеренный Nginx, четыре документа с сохранёнными
относительными ссылками и `review.json` с SHA256 каждого файла.
Открывать `docs/runbooks/web-switch-bootstrap.md`. SSH, Docker, сеть, БД,
провайдеры и запись за пределами `.local`
не вызываются. По умолчанию скрипт инертен; команды `apply` нет.

`review.json` — **не production-план и не допуск**: `readyToApply`,
`productionPlan`, `deploymentAuthorization` всегда `false`. Он перечисляет ещё
не подтверждённые условия. Контроллер его не принимает. Хеши фиксируют байты,
но сами по себе не удостоверяют проверку, установку или согласие владельца.
В пакет не входят реальные runtime/compose/receipts, сертификаты или ключи.

## Условия будущей установки

1. Зафиксировать точный commit и SHA256 пакета, результаты Linux и whole-host
   проверок. Получить отдельное разрешение владельца на перечисленные ниже
   изменения; допуск на слияние #190 не является допуском на установку.
2. Повторить свежую полную инвентаризацию: канонический release, образы и source
   SHA, единственные API/PG, все jobs и сети, отсутствие pending и открытого
   worker admission. Частичный обзор не заменяет это условие. Не создавать
   production-план из устаревших container IDs, PID или времени старта.
3. Проверить место для **свежей зашифрованной копии, проверки восстановления,
   статического архива и возврата**. `backup.MIN_FREE` остаётся 8 ГиБ. Порог
   контроллера 256 МиБ не заменяет порог backup. Увеличивать лимиты или удалять
   старые контейнеры/копии ради обхода проверки нельзя.
4. Проверить память/cgroup для PG 1024 МиБ, API 768 МиБ и двух Web по 768 МиБ,
   отсутствие swap pressure/OOM. Минимум контроллера 3840 МиБ общей и 512 МиБ
   доступной памяти не доказывает вместимость под нагрузкой.
5. Экспортировать public и `/_next/static` именно готового live-образа, включая
   сгенерированный `/characters`. Проверить архив без ссылок, traversal и TAR
   extensions. Подготовить root-owned append-only архив и манифесты; список
   исходных файлов Git не заменяет фактические байты образа.
6. Сохранить канонические compose/env, config, исходные restart policies и
   ingress **с проверенными байтами, правами и описателями ссылок**. Не менять
   `backup.json`, `ACTIVE` или старые deployment receipts.
7. Исключить внешние reload Nginx на всё окно до завершения pending. Активный
   `certbot.timer` недостаточно остановить: нужно дождаться уже запущенного
   renewal/service/hooks и проверить другие timers/cron/manual-триггеры.
   После этого захватываются финальные конфиги, TLS metadata и worker PID.
   `maintenance.lock` не защищает от произвольного `systemctl reload` или HUP.
   Если исключение не доказано — отказ; существующие lock/гейты не ослаблять.

## Предлагаемые изменения bootstrap

Это перечень для будущего допуска, **пока не исполненные команды**.

| Объект           | Изменение                                                                                | Что закрепляется                                                                     |
| ---------------- | ---------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------ |
| Единственный API | `TRUSTED_PROXY_CIDRS=172.30.92.10/32,172.30.92.20/32`; restart `unless-stopped`, retry 0 | Прежний image/source, все остальные Env, secret mounts, лимиты, роли, profile и сети |
| Старый Web       | Прежние `.10`, `127.0.0.1:3000`, restart `no`                                            | Точный наблюдённый контейнер и runtime                                               |
| Новый Web        | Тот же image/source; `.20`, `127.0.0.1:3001`, restart `unless-stopped`, retry 0          | 768 МиБ, read-only, UID 1000, init, no-new-privileges, cap-drop ALL, прежний API     |
| Nginx            | Opt-in template, include upstream, append-only static archive                            | Прежние origin/TLS, traffic marker, запрет retry POST, private slot probe            |
| Контроллер       | Отдельный root-owned versioned каталог трёх модулей                                      | Все реально используемые конфиги и runtime pins, V2 plan, очищенное окружение        |

Новый Web получает отдельный уникальный Compose project, чтобы штатный
канонический project не содержал два сервиса `web`. Он подключается только к
прежней Web/API-сети с `.20`, без второго alias `api`. Все project IDs и все
их контейнеры включаются в точную инвентаризацию плана; неизвестный сосед
означает отказ. Канонический Compose не должен автоматически управлять новым
слотом.

При наблюдении restart API/Web был `no`; PostgreSQL — `unless-stopped`.
Изменение политики API названо отдельно, оно **не выполняется V2**. Возврат
обязан восстановить наблюдённые исходные значения. V2 строго требует
`old=no`, `new=unless-stopped`, retry 0; сам политики не меняет. V1 сохраняется.

Текущий `/etc/nginx/sites-enabled/citygo-pilot` — символическая ссылка на
`sites-available/citygo-pilot`. Контроллер требует regular files у config pins.
Будущий installer должен сохранить ссылку и её target, затем установить
отдельный regular opt-in файл в enabled-путь, оставив прежний target неизменным.
Нельзя исключать подключённый конфиг из pins ради обхода проверки. Это пока
не автоматизировано. Certbot live-ссылки сертификата/ключа сохраняются;
private key на компьютер не выгружается. Нужно подтвердить доверенный путь,
актуальность TLS и отсутствие ротации внутри окна операции. Nginx 1.24.0 не
поддерживает `keepalive_min_timeout`; эта директива не добавляется.

## Порядок будущей операции

1. В согласованное окно исключить reload и фоновые управляющие операции;
   закрыть новые запросы штатным marker и дождаться принятых API-запросов/jobs.
   Не завершать запросы по таймауту ради перехода и не переотправлять их.
2. Сделать свежую зашифрованную S3-копию и проверить изолированное восстановление
   штатной процедурой. Сохранить evidence и прежнее состояние timers/доступа.
3. Под общими locks подготовить отдельный overlay. Пересоздать только API с
   двумя названными дельтами, запустить same-image Web на `.20:3001`. Проверить
   единственность API, cgroup, mounts, health и JSON-контракт.
4. Подготовить архив, versioned controller и ingress. Исходный upstream — 3000.
   Проверить root-owned пути, `nginx -t`, TLS/SNI, локальный probe и публичный
   запрет probe. Все внешние reload остаются исключены.
5. По **новому** post-bootstrap снимку сформировать ограниченный V2 plan с
   правильными PID/starttime, network/container/file pins и сроком до 24 ч.
   Выполнить `verify → switch → retire → повтор retire` по основному runbook.
   Probe контроллера требует marker: вернуть прежний доступ лишь после
   readiness API/обоих Web и проверки ingress, до switch, по явному этапу допуска.
   При неизвестном результате не открывать доступ и не удалять pending.
6. Проверить old Web stopped/no и active Web running/unless-stopped, отсутствие
   старых workers, единственный API/PG, точный runtime, archive, health, бюджет,
   оплату и worker admission. Сохранить отдельные bootstrap/web-active receipts;
   legacy receipts остаются историческими.
7. Вернуть исходное active-состояние timers лишь после settled pending, не меняя
   enablement; пропущенный renewal может запуститься сразу. При ошибке сохранять
   оба Web и pending, отдельно разобрать безопасное восстановление timer.

Реальный reboot проверяется отдельной согласованной репетицией. Наличие restart
policy не подтверждает boot ordering Docker/Nginx/PG/API. При неизвестной фазе
нет автоматического rollback, SIGKILL, сброса pending или повторного AI/платёжного
запроса. При живых старых workers старый Web не останавливать.

## Возврат и следующий backend-выпуск

До исполнения нужен точный обратный план: закрыть/drain, остановить новый слот
после проверки соединений, восстановить прежний ingress и descriptor symlink,
единственный API с прежним CIDR/restart и Web `.10:3000` из сохранённых образов.
Проверить новые container IDs, readiness/TLS и лишь затем вернуть прежний доступ.

Нельзя вызвать старый `resume/recover/startup approval`: он связан с прежними
container IDs/StartedAt. Нельзя переписать `ACTIVE`, выдавая новое состояние за
старое. Требуются свежие runtime-доказательства и новый обычный допуск. Перед
закрытым API/schema/runtime-выпуском reconciliation обязателен; legacy `finish`
не принимает двухслотовую топологию. Автоматический installer/reconciliation
и его аварийная репетиция остаются отдельным этапом.

## Приёмка подготовки

Готовы offline kit, Linux/V1/V2 проверки, перечень изменений, условий и возврата.
Это **не** статус «готово применить»: production-план, installer, свежая копия и
финальные runtime pins создаются на этапе отдельно согласованной установки.
Сервер не меняется этим PR.
