# Установка неактивной версии Web-контроллера

Статус: код и изолированная репетиция, рабочий сервер не изменяется.
Это следующий инкремент после [проекта конфигурации bootstrap](web-bootstrap-draft.md),
а не завершённая установка двух Web-слотов.

## Результат и границы

Установщик записывает в новый каталог
`/opt/citygo/web-switch-controller-<полный SHA256 manifest>` ровно три модуля:
`backup.py`, `web_switch.py`, `web_switch_assets.py`, а также `manifest.json`
и собственную квитанцию `installed.json`. Файлы принадлежат root, имеют режим
`0444` и одну жёсткую ссылку; завершённый каталог — `0755`. При совпадении имени
существующий посторонний каталог не перезаписывается и не принимается за результат.

Новая версия остаётся **неактивной**: установщик не импортирует её модули,
не создаёт current-ссылку и не меняет запуск прежнего контроллера. У него нет
команд Docker, systemd, Nginx, SSH, миграций или вызовов провайдеров.
Конфигурации, секреты, сертификаты, admission и legacy receipts не заменяются.

Три режима ИИ, ×10, «Минимум» 3 ₽, постоплата после ответа без денежного
удержания, бюджетные счётчики, чеки ЮKassa, телефон и подарок 500 ₽ сохраняются.
Реклама и автодеплой не включаются. Наличие этого кода в PR не разрешает
выполнить установку на сервере.

## Входы и отдельный допуск

Источник содержит строго четыре regular-файла: три модуля и `manifest.json`.
Манифест задаёт SHA256 и размер каждого модуля; полный SHA256 его исходных
байтов определяет версию каталога. Состав, размер, байты, владелец, права,
число ссылок и доверенные родители проверяются до записи payload.
Код из источника не исполняется для проверки.

Установка требует отдельного root-owned приватного JSON-допуска с точными
operation ID, SHA манифеста, временем не более часа и явным `allow_install`.
`bootstrap_draft_sha256` — ссылка для аудита на подготовку #192; сам draft
не становится разрешением на установку. Схемы и названия операций определены
в [`web_controller_install.py`](../../deploy/backup/web_controller_install.py).

Для завершения прерванной операции нужен свежий допуск reconciliation:
те же operation ID, manifest и draft, плюс точный SHA сохранённого pending.
Прежний допуск сохраняется для аудита и не переписывается для продления срока.
Просроченный допуск не разрешает новые записи. Read-only inspection позволяет
разобрать состояние и после истечения срока.

Установщик исполняется только на Linux под root из проверенного защищённого
каталога. Кандидатный образ и его содержимое не являются доверенным launcher.
Без аргументов и с `--plan` он инертен. На рабочем сервере ни одна из операций
этого документа в рамках текущего PR не выполняется.

Маршруты CLI после отдельного допуска:

```sh
python -B deploy/backup/web_controller_install_cli.py --plan
python -B deploy/backup/web_controller_install_cli.py install --source <protected-package> --approval <install-cap.json> --allow-install
python -B deploy/backup/web_controller_install_cli.py inspect --manifest <manifest-sha256>
python -B deploy/backup/web_controller_install_cli.py reconcile --source <protected-package> --approval <fresh-reconcile-cap.json> --allow-reconcile
```

CLI не принимает флагов активации, изменения runtime, произвольного destination
или подмены времени. Он не создаёт допуски за владельца.

## Журнал и сериализация

Порядок блокировок: существующие `maintenance.lock`, `worker-admission.lock`,
затем собственная блокировка установщика. Существующие legacy pending-маркеры
вызывают отказ. Они не создаются, не удаляются и не исправляются этим механизмом.
Открытое admission установщик не закрывает: он копирует только неактивный код.

Собственное состояние находится в `/var/lib/citygo-web-controller-install`.
Pending записывается и синхронизируется **до создания каталога версии**.
Его точные байты предварительно сохраняются в неизменяемом transaction archive.
Исходный допуск и новые допуски reconciliation хранятся отдельно в режиме `0400`.
Проверка готового результата сверяет также эту цепочку: raw-хеши, operation ID,
manifest, draft и SHA прежнего pending. Истечение исторического допуска не
продлевает его разрешение на новые записи.
Каждый файл сначала полностью записывается во временное имя и синхронизируется,
затем публикуется без замены существующего final-файла. Родительские каталоги
открываются через дескрипторы без следования symlink.

Квитанция завершения записывается последней. Установщик сверяет полный состав
и метаданные дерева, синхронизирует запись и только затем завершает собственный
pending. Наличие каталога или исчезновение процесса не считается успехом.
Отдельный pending не оставляет legacy barrier, который после сбоя мешал бы
обычным backup и release-процедурам.

## Прерванная операция

| Состояние                                                 | Допустимое действие                                    |
| --------------------------------------------------------- | ------------------------------------------------------ |
| Pending отсутствует, версия не создана                    | Новая явно разрешённая установка                       |
| Pending durable, каталога ещё нет                         | Проверка и reconciliation той же операции              |
| Записана часть известных файлов                           | Проверка каждого файла и только разрешённое завершение |
| Квитанция durable, pending остался                        | Полная сверка результата и завершение matching pending |
| Результат завершён, ответ CLI потерян                     | Идемпотентная проверка без повторной установки         |
| Неизвестные файлы, другой inode, hash, владелец или права | Отказ; данные сохраняются для ручного разбора          |

Reconciliation не означает rollback приложения. Он завершает только эту
транзакцию копирования неактивных файлов. Нельзя удалять чужие файлы, заменять
посторонний каталог, очищать произвольный pending или автоматически выбирать
другую версию. Потеря соединения также не разрешает повторять runtime-запросы.

Если прерывание оставило временную квитанцию с другими метаданными прежней
попытки reconciliation, установщик может консервативно отказать. Такой partial
сохраняется для ручного разбора; режим force и автоматическая перезапись
не предусмотрены.

## Изолированная проверка

Синтетические unit-тесты и репетиция используют только собственные временные
каталоги Linux. Фиксированные серверные roots переопределяются внутри закрытой
тестовой функции; публичного флага смены серверных путей нет.
Репетиция запускает дочерний установщик и останавливает только этот процесс
через SIGKILL на именованных барьерах. После этого проверяются inspection,
явный reconciliation, полный состав версии и неизменность контрольных
canonical/config/runtime/Nginx/receipt/budget файлов.

Команды для изолированного Linux-стенда:

```sh
sudo env TMPDIR=/root python3 -B -m unittest discover -s deploy/backup -p 'test_web_controller_install*.py' -v
sudo env TMPDIR=/root python3 -B deploy/backup/web_controller_install_smoke.py --disposable
```

Локально прошли 46 проверок установщика/CLI и 109 прежних Web/Bootstrap-проверок
в одном Linux-прогоне: **155/155, без пропусков**. Репетиция проверила восемь
реальных SIGKILL: до каталога, после его создания, пустой и записанный temp,
два имени одного inode, готовое дерево, durable receipt и уже удалённый pending.
В последнем случае inspection подтвердил результат без новых записей.

Это проверка сбоя процесса и порядка fsync на настоящей файловой системе.
Она не имитирует потерю питания, reboot сервера или установку активного runtime.
Следующими этапами остаются API/Web staging, сохранение и смена ingress,
фактические V2 pins, восстановление канонического runtime и отдельно разрешённое
первое подключение после свежей резервной копии с проверкой восстановления.
