# RouterAI: точный production-допуск, без автоматического включения

Этот этап добавляет техническую возможность согласовать **одну конкретную
политику получателя**. Он не утверждает юридические тексты, расходы, готовность R1
и не меняет действующий сервер. Прямой OpenAI сохранён; GigaChat пока остаётся
заблокированным в production. Автоматического fallback нет.

## Условия запуска

Для RouterAI в production нужны все обычные настройки провайдера и две новые:

- `ROUTERAI_DATA_NOTICE`: публичное уведомление оператора, до 4000 символов.
  Его полностью увидят пользователи Web/Expo. **Не помещать сюда ключи или
  персональные данные.** Текст дополняет, а не скрывает существующее описание
  передаваемого контекста и маршрута.
- `ROUTERAI_PRODUCTION_POLICY_ID`: SHA-256 точного публичного snapshot после
  независимого одобрения владельцем. Пустое значение сохраняет блокировку.
  Это не секрет и не флаг `true`. Не вычислять/подставлять автоматически при старте.

Идентификатор связывает модель, RouterAI, upstream, фильтр страны, техническое
описание данных, версию и уведомление. Изменение любого из этих полей делает старый
допуск непригодным. Ротация API-ключа не меняет получателя/согласие.

Текст хранится в существующем `policy.data`; меняется версия snapshot на
`ai-recipient-v2`. Поля API не меняются, текущие Web и Expo уже показывают весь текст.
Политики без нового уведомления и политики других провайдеров сохраняют прежние ID.

## Подготовка без ключей и запросов к модели

1. Уточнить фактический маршрут, передаваемые данные, условия обработки/хранения,
   удаление и контакт оператора. Владелец отдельно утверждает публичный текст и
   получателей. Фильтр страны RouterAI сам по себе не доказывает регион хранения.
2. В API-настройках задать модель, upstream, при необходимости country и
   `ROUTERAI_DATA_NOTICE`. Ключ для предварительного просмотра не нужен.
3. В рабочей копии после сборки общих пакетов выполнить `pnpm ai:policy:preview`.
   Команда выводит только публичный JSON snapshot, не создаёт адаптер, не подключает
   БД и не пишет approval. Это просмотр, **не юридическое одобрение** и не проверка
   доступности модели. Не запускать его с секретом, ошибочно вставленным в notice.
4. Передать владельцу полный JSON для проверки. Только после его явного решения
   записать поле `id` в `ROUTERAI_PRODUCTION_POLICY_ID` серверного API-окружения.
   Все реплики должны получить одинаковые настройки после контролируемого drain.

Провайдер с отсутствующим/устаревшим допуском не запускается как bootstrap.
Если bootstrap — OpenAI, неподтверждённый RouterAI отсутствует среди доступных
вариантов; `production_blocked` сохраняется и при попытке подставить адаптер.

## Что НЕ разрешает этот допуск

- `LLM_PROVIDER=disabled` по-прежнему сильнее серверного approval и выбора в БД.
- `/admin` по-прежнему требует существующий allowlisted аккаунт. Права никому
  автоматически не выдаются. Выбор в существующей БД не меняется при рестарте.
- Смена policy ID требует нового выбора администратором и согласия пользователя;
  старые ответы/согласия не удаляются и не считаются согласием на новый текст.
- Денежный бюджет остаётся отдельным: нужно одобрение точного execution ID,
  общего дневного и суммарного лимита и верхней оценки одной попытки. Новая policy
  даёт новый execution ID; прежний денежный допуск не переносится.
- Решение владельца от 2026-09-27: **разовые бесплатные 500 ₽ на пользователя,
  затем пополнение**, без ежедневного восстановления. Существующий суточный
  резерв не реализует такой баланс; до включения нужен отдельный кошелёк/ledger
  и проверка оплаты. См. [решение о балансе](../product/ai-credit.md).
  В этом изменении нет тарифов, положительного бюджета или разрешённого live-теста.
- Публичное открытие Web не включает AI и не завершает privacy/аккаунты/R1.

## Развёртывание — отдельное согласованное действие

Новые поля разрешены только API scope. Они не передаются Web/build/mobile/worker
как переменные окружения; публичный snapshot доставляется через существующий API.
Секреты остаются в защищённом API JSON/хранилище. Набор разрешённых секретных полей
не расширяется.

Текущий `deploy/compose.pilot.yml` и протокол release-controller намеренно запускают
`LLM_PROVIDER=disabled`. Этот PR **не меняет** данный профиль и не содержит команды
обхода его проверок. Для live-выпуска нужен отдельно проверенный профиль deployment
с этими API-параметрами, согласованными получателями, ключом и денежными ограничениями.
Не переводить сервер в development, не очищать ledger и не расширять secret allowlist
вручную для включения AI.

Перед live-проверкой: проверить права администратора, настройку бюджета и согласие;
отдельно согласовать один синтетический запрос и сумму; затем подтвердить настоящий
stream, историю и аварийное отключение. Офлайн-тесты не доказывают live-доступ.

## Офлайн-проверки

Конструктор/реестр, production control с подставленным адаптером, устаревший hash,
пустое уведомление, смена получателя и hard-disable; изоляция env; production-mode
API с синтетическим провайдером: отказ без пользовательского согласия/бюджета,
сохранение ответа и требование нового согласия и бюджетного approval после смены
уведомления. Миграций и изменений реальных данных нет.
