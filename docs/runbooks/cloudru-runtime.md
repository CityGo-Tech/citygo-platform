# Cloud.ru: серверная конфигурация (ещё не развёрнута)

Продолжение [контейнерной основы](container-foundation.md). Подготовлены runtime
Compose, роли/секреты, Nginx и логический dump. **ВМ, IP, DNS, сертификат ACME,
registry и внешнее хранилище копий ещё не созданы.** Конфигурация не означает
готовность к допуску реальных пользователей или включению AI.

## Что запускается

`deploy/compose.pilot.yml` использует только готовые образы — без build, исходников
и pnpm на ВМ. `deploy/pilot.env.example` содержит только несекретные метаданные.
Укажите проверенные digest образов одного выпуска; шаблон намеренно нерабочий.
Образы приложения ещё не опубликованы: их отдельный ручной выпуск описан в
[release candidate](release-candidate.md). Готовый кандидат не запускает сервер.

| Сервис        | Лимит RAM | Секреты                   | Доступ                              |
| ------------- | --------- | ------------------------- | ----------------------------------- |
| PostgreSQL 17 | 1024 MiB  | пароли пяти DB-ролей      | только внутренняя сеть БД           |
| API           | 768 MiB   | только `api.json`         | сеть Web/API + сеть БД              |
| Web           | 768 MiB   | нет                       | `127.0.0.1:3000`, только host Nginx |
| migrator      | 256 MiB   | только `migrate.json`     | одноразово, сеть БД                 |
| worker        | 256 MiB   | только `worker.json`      | одноразово, сеть БД                 |
| backup        | 256 MiB   | только пароль backup-роли | одноразово, сеть БД                 |

Это начальный бюджет памяти для 4 GiB, не результат нагрузочного теста Free Tier.
Не запускайте все служебные задачи одновременно. Три постоянных сервиса имеют
суммарный потолок 2560 MiB; оставшаяся память нужна ОС, Docker, Nginx и служебной
задаче. Следите за OOM, CPU throttling, диском и задержками. Docker logs ограничены
3 файлами по 10 MiB на сервис. Для Nginx на хосте отдельно нужен logrotate.

PostgreSQL: 40 соединений, shared_buffers 256 MiB, work_mem 4 MiB. Пул API остаётся
10, роль API допускает 12 соединений, worker/backup — по 2, migrator — 3. SQL и
значения параметров не логируются. Корень приложений read-only, пользователь
`node`, без capabilities и Docker socket; запись разрешена только в tmpfs/cache.

Сети `172.30.92.0/24` и `172.30.93.0/24` нужно проверить на пересечения с сетью
ВМ/VPN. При изменении согласованно исправьте IP Web и доверенный `/32` API.
Web не состоит в сети БД; у PostgreSQL, API и jobs нет опубликованных портов.
Не добавляйте к этой схеме CDN/load balancer без пересмотра доверия адресам.

## До первого запуска — защищённые секреты

Эти действия выполняются **на выбранной новой ВМ после разрешения её создания**,
не на текущем рабочем компьютере. Нужны root/SSH-доступ и проверенная версия Docker.
Не копируйте локальный `.env`, PGlite или ранее раскрытые общие ключи ботов.

1. Создать каталог `/etc/citygo/secrets`, владелец root, режим `0700`.
2. Сгенерировать пять разных криптографически случайных паролей: по 32 байта в
   lowercase hex (64 символа). Сохранить без вывода/попадания в history в файлы
   `db_admin_password`, `db_api_password`, `db_migrate_password`,
   `db_worker_password`, `db_backup_password`. Значения в Git/чат не передавать.
3. Создать JSON-файлы с единственным начальным полем `DATABASE_URL`:

| Файл           | Логин URL         | Пароль из файла       |
| -------------- | ----------------- | --------------------- |
| `api.json`     | `citygo_api`      | `db_api_password`     |
| `migrate.json` | `citygo_migrator` | `db_migrate_password` |
| `worker.json`  | `citygo_worker`   | `db_worker_password`  |

Формат URL: `postgresql://<логин>:<hex-пароль>@postgres:5432/citygo_pilot`.
Host/имя БД обязательны именно эти. API должен работать ограниченной ролью,
не postgres или migrator. Админские ID впоследствии добавляются только в API-файл.

Compose secrets — **read-only bind mounts**, не зашифрованное хранилище.
Файлы должны быть читаемы соответствующим пользователем контейнера. Безопасный
простой вариант: файлы root-owned `0444` внутри root-only каталога `0700` — на
хосте доступ закрыт каталогом, внутри контейнера смонтирован только разрешённый
файл. Более строгий вариант — `0400` с владельцем, совпадающим с проверенным UID
конкретного образа. Не рассчитывайте на `uid/mode` Compose для file-backed secret:
проверяйте фактические права. Не делайте родительский каталог общедоступным.
Пользователь Docker/root всё равно имеет доступ ко всем секретам этого хоста.

Контейнерный launcher читает фиксированное `/run/secrets/<mode>.json` только при
`CITYGO_MOUNTED_CONFIG=1`. Произвольные поля, неподходящий сервис, ошибочный JSON,
пустые значения и конфликт с тем же ключом окружения останавливают запуск без
вывода содержимого. Web не умеет читать такие файлы. `LLM_PROVIDER=disabled`
задан отдельно в Compose; секрет не может его переопределить.

## Первая БД и запуск (операторская последовательность)

Используйте новую БД; автоматического импорта старой истории нет. Сначала проверить
cloud disk encryption, доступное место, приватность порта и утверждённые images.

1. Выбрать и **явно создать** постоянный Docker volume `citygo_pilot_data`.
   Он `external: true`: обычный `compose down` не управляет его жизненным циклом.
   Никогда не применять `docker volume prune` для обновления сервиса.
2. Зафиксировать каталог релиза с `deploy/` и проверенные метаданные в
   `/etc/citygo/pilot.env` (не исходники/сборка). Для всех следующих команд один
   project name, один compose file и явный `--env-file`; корневой `.env` не читать.
3. Запустить только PostgreSQL и дождаться его готовности.
4. На пустом томе `init.sql` создаёт роли, SCRAM-пароли и права схемы. На существующей
   БД init-скрипты повторно **не исполняются**. Изменение secret-файла не меняет
   пароль роли. Частично неудавшийся bootstrap требует диагностики; не удаляйте
   реальную БД ради повторного запуска.
5. Запустить jobs-образ с `migrate`. Он не скачивает пакеты и не собирает код.
6. После миграций применить `deploy/postgres/grants.sql` **как citygo_migrator**,
   передав его пароль безопасно через защищённый файл/процесс, не аргумент CLI.
7. Запустить API, проверить readiness, затем Web. До настройки TLS не давать
   пользователям прямую HTTP-ссылку: production-cookie Secure.

Набор безопасных команд Compose (после подготовки файлов/образов):

```sh
docker compose --env-file /etc/citygo/pilot.env -p citygo-pilot -f /opt/citygo/current/deploy/compose.pilot.yml up -d --wait postgres
docker compose --env-file /etc/citygo/pilot.env -p citygo-pilot -f /opt/citygo/current/deploy/compose.pilot.yml --profile ops run --rm --no-deps migrator
# Здесь оператор применяет grants.sql как migrator. Не пропускайте этот шаг.
docker compose --env-file /etc/citygo/pilot.env -p citygo-pilot -f /opt/citygo/current/deploy/compose.pilot.yml up -d --wait api web
```

Для рабочего обновления сначала backup и проверка совместимости, затем drain,
миграции/grants и healthcheck. Это ещё не автоматический release pipeline.
Worker запускать `run --rm --no-deps worker` по расписанию с `flock`, чтобы задания
не пересекались; установка таймера относится к настройке ВМ.

### Остановка API перед обновлением (часть CG-037)

API обрабатывает `SIGTERM`/`SIGINT` как необратимый drain текущего процесса.
Публичной HTTP-команды для включения или отмены drain нет.

1. После сигнала новые обработчики `/v1/*` и `/ready` получают HTTP 503 с кодом
   `SERVICE_UNAVAILABLE`, `retryable: false` и обычными заголовками контракта.
   Проверки CORS, версии, формата и rate limit могут отклонить запрос раньше.
   Новые операции не доходят до БД, записи анкеты, резерва денег или провайдера.
   `/health` остаётся доступен, пока сервер ждёт текущую работу; это **не** readiness.
2. Уже принятые обработчики получают до 270 секунд на завершение. Учитывается
   время всей операции, включая сохранение SSE после разрыва соединения клиентом.
   Обычный собственный timeout провайдера продолжает действовать.
3. По истечении 270 секунд API отменяет оставшиеся AI-потоки. Они проходят прежний
   путь сохранения прерванного ответа/освобождения lease; деньги автоматически
   не возвращаются, запросы не переотправляются, запасной провайдер не включается.
4. Только после завершения обработчиков закрываются HTTP-сервер и БД. Общий
   предел ожидания, включая закрытие, — 300 секунд. При зависшем обработчике,
   ошибке закрытия или неподтверждённом сохранении прерванного чата процесс завершается
   с кодом 1, а не сообщает об успешном drain. Ошибка сохранения запоминается до конца
   жизни процесса, даже если произошла до сигнала остановки или после неё были
   успешные запросы. API дожидается других обработчиков и закрытия ресурсов, но не
   считает нулевое число активных операций доказательством сохранения истории.
   Клиент получает сообщение о неподтверждённом сохранении без обещания «История
   сохранена», без внутренних ошибок БД и с `retryable: false`.
   В этом случае сохранность незавершённой операции не гарантируется: проверить
   историю, leases и резервы перед продолжением релиза; не повторять чат автоматически.
   Сам по себе перезапуск процесса не подтверждает восстановление: флаг ошибки
   хранится в памяти, а последствия в БД требуют отдельной проверки оператором.
5. Compose даёт API 330 секунд до принудительной остановки. Не сокращать этот
   интервал параметром `stop --timeout`/`down --timeout`. Для обновления останавливать
   **только API**, не общий стек: PostgreSQL нужен до окончания сохранения.
   Повторный сигнал не запускает второе закрытие и не ускоряет принудительное завершение.

Это ещё не общий maintenance-режим и не обновление без простоя. При одной реплике
клиенты временно увидят 503/недоступность. Перед сигналом оператор отдельно закрывает
новый пользовательский трафик, останавливает задания Worker и проверяет backup и
совместимость; после него проверяет exit code/логи. Миграции нельзя запускать,
пока старая API/Worker ещё работает. Автоматический deploy-controller, проверка
сохранения при остановке реального контейнера с длинным AI-запросом, старый мобильный
клиент и все остальные критерии CG-037 остаются отдельными этапами.

Тесты используют только синтетическую БД/провайдер и короткие тестовые интервалы:
блокировка новых операций, завершение и отмена чата, отсутствие повторного резерва,
разрыв реального HTTP-соединения, повторные сигналы и предельное время остановки,
сбой сохранения до/во время drain и ненулевой exit code без ложного сообщения об успехе.
Эти изменения сами не развёртывают новую версию на Cloud.ru и не включают AI,
DNS/TLS, резервное расписание или почтовые уведомления.

### Контейнерная репетиция остановки (CI, только синтетические данные)

`scripts/container-smoke.mjs --disposable` также запускает
`container-drain-smoke.mjs` на только что собранном API-образе. Не запускайте
этот набор на сервере пилота: он намеренно останавливает и аварийно завершает
свой одноразовый API. Имя проекта генерируется самим набором; перед сигналами
проверяются метки проекта/сервиса и полные ID контейнеров.

Проверяется штатная цепочка Docker init → container launcher → API, без подмены
entry point и без test-only настроек в production-коде:

- Тестовая транзакция удерживает одну строку синтетического пользователя. Ожидание
  уже принятой анкеты подтверждается через `pg_stat_activity`/`pg_blocking_pids`,
  а не предположением после фиксированной паузы. Удержание ограничено таймаутами;
  таймауты приложения и схема БД не меняются.
- `compose stop api` использует заданные 330 секунд, не сокращённый CLI timeout.
  До освобождения строки `/ready` и новая запись получают 503; `/health` ещё
  отвечает. Повторные SIGTERM/SIGINT не прерывают сохранение.
- После снятия блокировки первая анкета возвращает 200 и сохраняется ровно один
  раз. Проверяются код 0, отсутствие OOM/ошибки Docker, неизменность ID, image,
  времени старта и счётчика перезапусков. В логах ровно одно начало и завершение
  drain. Сессия/профиль доступны после пересоздания только API; PostgreSQL работает.
- Отдельный отрицательный сценарий отправляет SIGKILL только одноразовому API.
  Команда Docker завершается успешно, но итоговый код 137 отклоняется проверкой
  `container-stop-check.mjs`. Unit-тесты также отклоняют код 1/143, OOM, restart,
  другой контейнер и отсутствующие/неоднозначные свидетельства.

AI остаётся `disabled`; попытки моделей и денежные резервы не появляются.
Это подтверждает контейнерную остановку с активной **записью анкеты**, не длинный
AI-поток. Сохранение SSE/ошибка сохранения покрываются отдельными API-тестами;
проверка SSE в реальном контейнере остаётся отдельным этапом. Проверка exit code
здесь — тестовая, не установленный deploy-controller и не разрешение миграции.
Maintenance, Worker coordination, предрелизная внешняя копия, совместимость старого
мобильного клиента и ручное одобрение выпуска ещё нужны для полного CG-037.

Основание: [Docker stop](https://docs.docker.com/reference/cli/docker/container/stop/)
после grace period может принудительно завершить контейнер;
[Docker kill](https://docs.docker.com/reference/cli/docker/container/kill/)
отправляет сигнал, но успех команды не подтверждает сохранение данных приложением.

Роли API/worker не могут менять схему/миграции. Audit, consent и попытки AI для API
append-only; удалять можно только сессии. Права новых таблиц API/worker выдаются
явно при разработке миграции. Backup получает чтение новых объектов через default
privileges **citygo_migrator**. Добавление RLS или другого владельца требует новой
проверки dump, а не выдачи backup-роли superuser/BYPASSRLS.

## Nginx, DNS и TLS

1. Выбрать домен, создать согласованную A-запись; не добавлять неработающую AAAA.
2. Установить host Nginx. Удаление/замена default-site — только после проверки
   существующих сайтов. Не использовать этот шаблон вслепую на общем сервере.
3. Через отдельный HTTP-only bootstrap получить настоящий сертификат ACME
   webroot `/var/lib/letsencrypt`. HTTPS-шаблон требует уже существующие
   `fullchain.pem` и `privkey.pem`; с отсутствующими файлами nginx не запустится.
4. На машине с Node отрендерить `node deploy/render-pilot.mjs pilot.<ваш-домен>`.
   Команда печатает только конфигурацию. Передать результат в host Nginx внутри
   `http {}`; `CITYGO_ORIGIN` должен совпадать с `https://<этот-host>`.
5. Выполнить `nginx -t`, reload и проверку снаружи по HTTPS. Настроить автообновление
   сертификата с reload hook и тестом renewal. Шаблон хранит challenge-location.
6. Убедиться, что извне открыты только согласованные SSH/80/443. Проверить также
   Docker firewall: одного UFW недостаточно, хотя Web дополнительно привязан к
   loopback. Проверить IPv6 отдельно. Сервер не должен служить открытым прокси.

Nginx заменяет X-Forwarded-For/Host/Proto и удаляет Forwarded. API доверяет только
адресу Web `/32`. Подменённый клиентом XFF не создаёт новый лимит; CI проверяет
два независимых socket-адреса. Per-IP limiter всё ещё объединяет пользователей
за NAT и не является account-aware ограничителем нескольких реплик.

Nginx и Next external rewrite имеют конечный timeout 300 секунд; buffering для
ответа выключен, автоматический retry upstream запрещён. Проверка CI пропускает
искусственный SSE после 35 секунд молчания и подтверждает выдачу первого фрагмента
до завершения ответа. Это проверка транспорта, не реальный вызов AI и не доказанный
нагрузочный/240-секундный тест Free Tier. Параметр Next `experimental.proxyTimeout`
проверен для установленного Next 15; при обновлении пересмотреть smoke.

## Копия и восстановление: что готово, что ещё нет

Добавлен отдельный [инструмент шифрования и проверенной загрузки](encrypted-backup.md).
Он не включает услугу автоматически; ниже описан низкоуровневый источник дампа.

`backup` выдаёт бинарный `pg_dump --format=custom --no-owner --no-acl` в stdout
через отдельную read-only роль. **Не запускайте его без перенаправления stdout
в защищённое хранилище/шифратор.** Дамп содержит персональные данные и хеши сессий.
Нужны `umask 077`, проверка exit code и исключение частичного файла при сбое.
Локальная незашифрованная копия на том же диске — не допустимый конечный backup.

В CI дамп хранится только в памяти и восстанавливается в отдельную вымышленную
`citygo_restore_check`; проверяются аккаунт, сессия, миграции и денежный резерв.
Production restore-команды, автоматическая ротация и таймер пока не поставляются.
Шифрование и загрузка подготовлены отдельной обёрткой. Ещё нужны настоящее внешнее
хранилище, согласованная retention, alerts и реальный restore drill. Публичный запуск
до этого закрыт.

`--no-owner --no-acl` означает: роли и grants нужно воспроизвести отдельно. Секреты
и TLS требуют отдельной защищённой копии. Не восстанавливать поверх работающей
БД без явного решения. После восстановления AI остаётся отключённым до сверки
исторических резервов с фактическими расходами провайдера.

## Проверки и источники

`corepack pnpm test:containers` — локальные unit-тесты; `node scripts/container-smoke.mjs
--disposable` на Linux — оба изолированных стенда. Второму нужны свободные loopback
порты 3000/80/443, `openssl`, `curl`, Python 3 и `age`; он не подходит для общей рабочей машины с
уже запущенными сервисами. Предпочтительно запускать в GitHub Actions.

Новые тесты создают только случайно именованные test volumes/контейнеры и удаляют
только их. Ни cloud, ни SSH, ни реальные ключи в CI не требуются.

- [Compose secrets](https://docs.docker.com/compose/how-tos/use-secrets/).
