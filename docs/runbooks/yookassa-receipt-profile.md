# Чеки ЮKassa для пополняемого баланса CityGo

## Принятое решение и границы

Владелец 20 октября 2026 года сохранил пополняемый баланс и существующий магазин
с включёнными «Чеками от ЮKassa», явно выбрав «Без НДС», «Услуга», «Полный расчёт».
Это техническая настройка транспорта по решению оператора, **не заключение о
налоговой корректности** пополнения баланса и не подтверждение условий договора.
НПД оператора не переименовывается в УСН кассового агента. НПД-чеки оформляются
и передаются вручную отдельно; запись в реестре не утверждает, что чек оформлен.

100 оплаченных ₽ по-прежнему дают 100 ₽ CityGo. Расходы AI списываются по тарифу
×10, сначала подарок, затем оплаченные лоты FIFO. Чек пополнения не превращает
неиспользованный баланс в уже израсходованную AI-услугу и не отменяет возвраты.
Новый магазин, отключение чеков и автоматическое начисление подарка не нужны.

## Точный технический профиль

`YOOKASSA_FISCAL_PROFILE=citygo_service_full_payment_v1` выбирается явно в API.
Единственная позиция чека:

| Реквизит             | Значение                               |
| -------------------- | -------------------------------------- |
| Описание             | `Пополнение баланса CityGo`            |
| Количество и единица | `1.000`, `piece`                       |
| Сумма                | Точная сумма пополнения в RUB, без ×10 |
| `vat_code`           | `1` — Без НДС, не ставка 0%            |
| `payment_subject`    | `service` — Услуга                     |
| `payment_mode`       | `full_payment` — Полный расчёт         |

`tax_system_code` не передаётся: режим кассового агента из чужого чека нельзя
выдавать за систему налогообложения оператора CityGo. Нельзя прислать произвольные
реквизиты чека из браузера или заменить этими настройками проверку магазина.
Значения перечислены в [официальном справочнике ЮKassa](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/parameters-values).

Перед новым пополнением покупатель явно вводит настоящий email. CityGo не
подставляет технический `admin@citygo.invalid` и не утверждает, что адрес подтверждён.
ЮKassa получает адрес в `receipt.customer.email` для отправки чека, как описано
в [сценарии платежа с чеком](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/payments).

## Неизменяемость, повторы и возвраты

Миграция `0023_payment_receipt_snapshots.sql` добавляет версию снимка заказа.
До внешнего POST сохраняются весь запрос, email, профиль и ключ идемпотентности.
Триггеры запрещают замену снимка. Повтор прежнего request ID с другой суммой или
email получает конфликт, а не ещё один платёж. Изменение email аккаунта не меняет
контакт в прежнем чеке или связанной задаче ручного НПД-чека.

В браузерном хранилище остаются только идентификаторы и сумма, не email или чек.
После потери ответа исходный заказ можно восстановить через авторизованный
`GET /v1/payments/topup-attempts/:requestId`: он проверяет владельца, не вызывает
ЮKassa, не создаёт заказ и не начисляет деньги. Если заказ не найден, интерфейс
не начинает новый платёж автоматически: исходный запрос мог ещё выполняться.

Старые заказы версии 1 не переписываются и не получают чек задним числом.
Их GET/сверка сохраняются при исходных магазине, режиме и return URL. Новый live
POST без выбранного фискального профиля закрыт. Нельзя повторять старый
неоднозначный receipt-free POST с добавленным чеком под тем же ключом.

При возврате всей исходной суммы объект `receipt` **не отправляется**: ЮKassa
берёт данные исходного платежа. Для частичного возврата сохраняется отдельный
неизменяемый чек на точную возвращаемую сумму с исходным email и реквизитами.
Остаток после предыдущих частичных возвратов всё ещё считается частичным
относительно исходной оплаты. См. [официальный сценарий возвратов](https://yookassa.ru/developers/payment-acceptance/receipts/54fz/yoomoney/refunds).
Начисление и окончательное списание возврата по-прежнему требуют независимого
server GET. Статус регистрации чека не заменяет денежный статус платежа.

## Выпуск и приёмка

Для mounted production используется новый профиль
`citygo-api-web-routerai-citygo-10x-yookassa-live-cn-fiscal-v2`, startup approval v6,
маркер `routerai-citygo-10x-yookassa-live-cn-fiscal-v2`. Он сохраняет CN-маршрут
DeepSeek Pro и ограничения v5, добавляя только закреплённый профиль чека.
Прежние v1–v5 и их разрешения не переиспользуются для этого изменения.

Смена фискального профиля меняет `runtimePolicyId` допуска оплаты. Нужны свежие
резервная копия, проверенные SHA/образы/миграция/grants, закрытый выпуск и новый
явный допуск. Наличие ключа, миграции или успешных тестов само не открывает оплату.
Постоянная защита выпуска и достоверность статусов GitHub сохраняются.

До заявления «оплата работает» проверить владельцем один настоящий платёж,
ровно одно начисление 1:1, чек в кабинете ЮKassa и его передачу покупателю,
полный возврат, денежный журнал и задачу корректировки ручного НПД-чека.
Карту и её подтверждение вводит владелец. Тестовый оплаченный лот не тратить на AI.
При сбое регистрации чека проверить кабинет отдельно; нельзя объявлять
подтверждённую оплату отменённой или автоматически возвращать деньги из-за статуса чека.
