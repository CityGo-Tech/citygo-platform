# Разовый баланс 500 ₽ — основа, не подключённый биллинг

Историческое описание основы из PR #67. Актуальное подключение чат-списаний,
режимы, миграция `0009` и восстановление описаны в
[RouterAI: списание без наценки](ai-credit-charging.md); этот раздел сохраняет
описание исходных примитивов `0008`, но не текущего статуса интеграции.

Решение владельца: [500 ₽ один раз, затем пополнение](../product/ai-credit.md).
Этот этап не разворачивает сервер, не выдаёт реальные бонусы и не подключает
платёжный сервис. Весь запуск ИИ, его получатели, согласия и общий бюджет остаются
под прежними независимыми ограничениями.

## Что реализовано

- Миграция `0008_ai_credit.sql` создаёт пустые `ai_credit_accounts` и
  `ai_credit_entries`. Не начисляет существующим/новым пользователям средства,
  не переоценивает прежние ответы и не изменяет суточный бюджет.
- `POST /v1/admin/ai/credit/welcome`: только существующий allowlisted администратор,
  с `userId` и `confirmOneTime500Rub: true`. Сумма всегда 500 000 000 микрорублей,
  валюта RUB. Другую сумму/валюту передать нельзя. Повтор и параллельное
  подтверждение возвращают прежний бонус, без второго начисления и второго аудита.
- `GET /v1/ai/credit` и `dashboard.aiAccess.credit`: только свой аккаунт,
  доступный остаток, резерв, подтверждённые списания и последние 20 операций.
  ID другого аккаунта в query-параметре не переключает владельца ответа.
- Web показывает остаток, историю и ID для сверки с оператором. Expo использует
  общий контракт и показывает остаток. Admin подтверждает бонус по сверенному ID.
- Внутренние операции `AiCreditLedger.hold/resolve` проверяют целые суммы,
  владельца, остаток и уникальный ID операции. Резерв удерживается до подтверждённого
  завершения; списание не может превышать резерв. Повтор завершения с тем же ID
  идемпотентен, другое завершение того же резерва отклоняется.

На серверном пути чата эти операции **пока не вызываются**. API честно возвращает
`chargingStatus: not_connected`, `topUpAvailable: false`. Нулевой остаток этого
нового баланса пока НЕ является блокировкой чат-запросов; действуют старые общие
ограничители. Не включать публичный AI, считая этот этап готовым платным тарифом.

## Транзакции и доступ

Блокировки берутся в порядке `users` (числовой ID) → баланс. Сеть не вызывается
в транзакции. Журнал и агрегированные суммы меняются вместе, ошибка аудита
отменяет начисление. Чтение сумм/истории — один SQL snapshot.

Уникальные индексы защищают один бонус на аккаунт, ID операции и одно завершение
резерва. Ограничения БД запрещают отрицательные суммы и превышение выделенных 500 ₽.
API может читать/добавлять записи журнала, но не менять/удалять их; Worker не имеет
доступа. Backup читает их вместе с остальными таблицами. Сам runtime API не является
границей против полного компрометационного доступа к собственной БД.

Физическое удаление аккаунта с журналом запрещено FK; политика архивирования/
анонимизации денежных записей требует отдельной реализации. Несколько аккаунтов
не распознаются как один человек. Пока нет подтверждённого автоматического допуска,
бонус выдаётся только оператором конкретному участнику, не каждой регистрации.

## Условия установки

1. Отдельно разрешённый выпуск: backup, остановка/закрытие старых API и Worker.
2. Применить миграции до `0008` и обновлённый `deploy/postgres/grants.sql` через
   существующий migration job. `/ready` новой версии требует `0008`.
3. Обновить API/Web и проверить пустой баланс, запрет чужого чтения и запрет
   начисления обычным аккаунтом. Согласованному тестовому участнику оператор
   подтверждает бонус один раз; повтор не увеличивает сумму.
4. Не включать AI/платёжные ключи. Миграция добавочная, но обратное приложение не
   учитывает баланс: старые версии нельзя использовать для последующего платного AI.
   Журнал не удалять и миграцию не редактировать; исправления — новой миграцией.

## Следующее подключение списаний

Нужны выбранный тариф/округление, сопоставление подтверждённой стоимости с точной
попыткой модели, общая транзакция резерва баланса и лимитов оператора, восстановление
после сбоя и проверка отсутствия повторного списания. Не округлять защитный потолок
попытки в «фактическую стоимость». Ошибка/таймаут не доказывают отсутствие расхода.
На неопределённом результате удержать резерв до сверки, не делать повторный вызов
и не освобождать деньги вслепую.

Оплата потребует отдельной проверенной серверной интеграции: уникальный платёж,
проверка статуса у провайдера, повторные события, возвраты и сверка. В этом этапе
нет HTTP-методов произвольного пополнения, списания или возврата. Решение о тарифе,
бонусном допуске и платёжном провайдере не заменяется техническим умолчанием.
