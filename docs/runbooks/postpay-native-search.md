# Подготовка закрытого профиля веб-поиска v17

5 ноября 2026. `citygo-api-web-postpay-native-search-v1`, версия **17**,
маркер `CITYGO_AI_PROFILE=postpay-native-search-v1`, схема **49**.
Это описание подготовленного кода, а не установленной серверной конфигурации
или разрешения на выпуск, открытие доступа и модельные расходы.

## Контракт профиля

Профиль наследует фиксированные настройки v16 и добавляет единственное поле:

```json
{
  "AI_MAXIMUM_WEB_SEARCH": "routerai_native_postpay_v1"
}
```

Сохраняются память выбранного диалога, лимит входа 8 МиБ, выход RouterAI 4096,
`medium` для «Максимума», три режима, фактическое списание ×10 после ответа,
«Минимум» 3 ₽, фискальный профиль ЮKassa, email, телефон и подарок 500 ₽.
`fixed5_overdraft` остаётся полем совместимости: постоплата не удерживает 5 ₽.
Профили v1–v16 сохраняют прежние наборы полей; флаг в окружении не заменяет
новый API-only приватный JSON и его точный хеш в разрешении версии 17.
Worker, Web и мигратор не получают этот флаг или AI-ключи.

«Максимум» использует точный Sol/OpenAI/us Chat Completions, native-плагин
с `max_results=5`, один нестриминговый запрос, без fallback и повторной отправки.
У него отдельные policy/catalog/execution ID и политика чтения полного чека.
Фабрика создаёт настоящий адаптер только при корректном production policy ID
и наличии нужного ключа. Запуск профиля не открывает маршрутизацию, бюджет,
приём платежей, публичный доступ или автодеплой.

## Ответ и цена

Корректный завершённый текст без аннотаций принимается. Отсутствие источников
не означает ошибку диалога или подтверждённый бесплатный запрос. Каждая
присутствующая аннотация проходит прежнюю строгую проверку; некорректные ссылки
прерывают попытку, а текст Markdown не становится метаданными источника.
Панель источников появляется только при сохранённых аннотациях провайдера.

В полном чеке `/generation` обязательны исходные generation/reference,
Sol/OpenAI/Chat Completions, source=api и булевый `has_web_search`.
Допустимы оба значения флага: цена всегда берётся из точного `total_cost`.
Признак поиска и число ссылок не используются для вычисления цены, добавления
надбавки или доказательства того, что поисковый вызов действительно выполнен.
Например, `7.39182831114` ₽ превращается в 73.918283 ₽ CityGo после ×10
и округления ledger. Завершённый ответ и положительный идентичный чек допускают
однократное списание. Ноль, неизвестная стоимость, прерывание и несовпадение
идентичности обрабатываются существующей постоплатной машиной состояний.
Поздняя сверка делает GET исходной генерации, а не повторный POST вопроса.

Денежный допуск остаётся захваченным доступным балансом CityGo ÷10 с прежними
операторскими остановками и лимитами. `max_results=5` и локальный расчёт текстового
контекста не гарантируют жёсткий предел счёта или места для добавленного поискового
контекста провайдера. Ошибка переполнения окна сохраняет историю, не списывает
плату за незавершённый ответ и не запускает автоматический повтор.

## Проверяемый порядок будущего выпуска

1. Зафиксировать точные SHA/tree, три испытанных образа и свежие результаты
   Linux CI и Container smoke. Результаты предыдущего `dbf6497` не являются
   проверками добавленного production-профиля.
2. Проверить без внешних расходов штатную фабрику с production-конфигурацией,
   полный HTTP-путь, позднюю цену, replay, остановки бюджета, 100 тыс. символов,
   память и offline preview, ответы с источниками и без них. Моки не заменяют
   отдельную разрешённую живую приёмку, если она понадобится.
3. Подготовить сведения о внешнем поиске и утвердить точный notice/policy ID.
   Сохранённые согласия не переписывать задним числом. Использовать существующий
   механизм новой редакции; новая анкета и постоянный раздел согласий не нужны.
4. До переключения инвентаризировать все старые pending-попытки по исходным
   policy/execution/protocol. Сверять их старым профилем либо отдельно реализованным
   и проверенным read-only читателем с точной прежней идентичностью. Новый
   Chat-профиль не подставляется к старому Maximum/Responses. Ни повторного POST,
   ни выдуманной нулевой цены, ни автоматического rekey попыток нет. Если
   исходные попытки нельзя безопасно сверить, переход не готов к выпуску.
5. Получить решение владельца на точный выпуск по
   [процессу ручной постоплаты](postpay-actual.md). Кратко закрыть доступ и новые
   операции, дождаться текущих работ, создать свежую зашифрованную копию и
   проверить восстановление. Для сервера на схеме 47 применять последовательно
   **47 → 48 → 49**; применённые SQL не редактировать. Миграция 49 меняет только
   узкое правило функции существующего триггера, без новых прав и переписывания данных.
6. Подготовить новый приватный JSON v17 и hash-bound startup/finish разрешения.
   Старое разрешение v16, старый JSON, постороннее поле и флаг из окружения
   должны отклоняться. Закрытый старт сам по себе не открывает ingress, AI,
   платежи, Worker, restart или автодеплой.
7. Подготовить явный CAS-переход правил бюджета для всех изменённых execution ID.
   Смена общего notice может менять также ID «Баланса» и «Минимума», даже если
   их транспорт прежний. Сохранить счётчики и финансовые ограничения; старый
   допуск Maximum/Responses не разрешает native Chat. Автоматического повышения
   лимитов, сброса счётчиков или включения выключенного бюджета нет.
8. Проверить схему 49 и физический активный invoker-триггер с обеими допустимыми
   native-версиями. Затем восстановить отдельно разрешённые доступ, AI и оплату
   по установленной процедуре и зафиксировать фактическую приёмку.

Тестовая фикстура содержит отдельный синтетический notice и ненастоящие ключи.
Она нужна для проверки границ конфига и не является операторским уведомлением,
production seed, согласованием тарифа или разрешением использовать бюджет.
Обновление APK с карточками источников и исходные PDF/изображения в этот профиль
не входят. Установленный старый APK игнорирует необязательные метаданные источников.
