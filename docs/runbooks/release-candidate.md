# Ручной кандидат релиза: GitHub → приватные образы → Cloud.ru

Этот этап готовит **кандидат**, а не развёртывание. Слияние PR не публикует образы
и не меняет сервер. Workflow не получает SSH-ключей, паролей БД, ключей ИИ или S3.
На ВМ остаются прежние данные и доступы; SSH по IP этот этап не ограничивает.

## Перед первым выпуском

1. Слить PR с этой инструкцией. Дождаться зелёных **CI** и **Container smoke**
   на новом коммите `main` (не только на PR). Скопировать полный 40-символьный SHA.
2. Проверить доступный лимит GitHub Actions и расходы организации. Один ручной
   выпуск заново собирает и тестирует Linux-образы; это расходует минуты Actions.
   Платные минуты/хранилища не разрешаются автоматически этим workflow.
3. Проверить политику Packages организации CityGo-Tech: новые container packages
   должны быть private, связаны с `citygo-platform`, доступны его Actions.
   Имена: `citygo-platform-api`, `citygo-platform-web`, `citygo-platform-jobs`.
   Существующие public/internal или связанные с другим репозиторием пакеты
   останавливают выпуск; workflow не изменяет видимость/доступы.
4. Только после отдельного разрешения публикации добавить repository variable
   `CITYGO_RELEASE_PUBLISH_ENABLED=true`. Это переключатель возможности запуска,
   **не замена review/branch protection/двухстороннего approval**. Никаких новых
   секретов для публикации создавать не нужно: используется краткоживущий
   `GITHUB_TOKEN` с `contents:read`, `actions:read`, `packages:write` в ручном job.
   Код job выполняется только из доверенного `main`; token передаётся явно лишь
   проверке GitHub и публикации, Docker build/runtime его не получают.

GitHub документирует [ручной запуск workflow](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/manually-run-a-workflow)
и [аутентификацию/приватность Container registry](https://docs.github.com/en/packages/working-with-a-github-packages-registry/working-with-the-container-registry).
Наличие environment с названием production само по себе не гарантирует approval:
доступность защит зависит от настроек/тарифа. Этот workflow такую защиту не обещает.

## Выпуск

1. Actions → **Release candidate (manual)** → Run workflow → ветка **main**.
2. `expected_sha`: полный текущий SHA; `confirm`: `PUBLISH_PRIVATE_IMAGES`.
   Ввод передаётся через окружение, не подставляется в shell-команды.
3. Проверяется приватность репозитория, совпадение checkout/current main/SHA,
   последние успешные push-проверки обоих workflow именно для этого SHA.
   Более новый неуспешный/незавершённый run не маскируется старым зелёным.
4. Node 24 bookworm-slim и PostgreSQL 17 alpine скачиваются для linux/amd64 и
   фиксируются по digest **до сборки**. Выполняются обычные тесты контейнеров,
   ограничений ролей, TLS-прокси, SSE и зашифрованного backup/изолированного restore.
   Только синтетические данные, `LLM_PROVIDER=disabled`; реальных запросов ИИ нет.
5. Только после успешных тестов и cleanup сохраняются ID проверенных API/Web/jobs.
   Worker и migrator обязаны использовать один jobs-образ. Перед публикацией
   выполняется push/pull тех же образов во временный registry на loopback CI runner.
   Проверяется настоящий Docker transport; GHCR login и package API в этой
   репетиции подставные, их доступность она не подтверждает. Registry и его volume
   удаляются, release manifest не создаётся. Затем
   main/CI/приватность проверяются снова. Если main успел измениться — новый запуск
   с новым SHA, а не разрешение устаревшего кандидата.
6. **Те же** проверенные образы, без повторной сборки, публикуются с тегами
   `sha-<полный SHA>-<run ID>-<attempt>`. `latest` не используется. Каждый образ
   читается обратно по registry digest и сравнивается с проверенным локальным ID.
   Ещё раз проверяется private-видимость и связь с репозиторием.
7. Получить artifact `citygo-candidate-<SHA>-<run ID>-<attempt>` из этого успешного
   запуска. Хранится 7 дней. В нём только `release.json` и явный список публичных
   runtime-шаблонов/инструкций; нет исходного `.env`, БД, приватных ключей и логов.

Содержимое `release.json`: source SHA, run/check IDs, точные image digests и IDs,
base digests, SHA-256 миграций и runtime-файлов. `deploymentApproved=false`,
`automaticRollback=false`, совместимость схемы требует отдельной проверки.
JSON — не подпись и не самостоятельное разрешение запуска. При передаче оператор
должен проверять происхождение artifact из успешного доверенного workflow,
SHA/ID/attempt и хеши файлов. Автоматического обработчика сторонних manifest нет.

## Сбой и повтор

- Ошибка API GitHub, нехватка прав или неоднозначные проверки закрывают выпуск.
- Журнал указывает текущую операцию и роль API/Web/jobs. Для внутренних проверок
  выводится фиксированная причина отказа, для GitHub — HTTP-статус. Не выводятся
  raw stdout/stderr Docker, тела HTTP-ответов, заголовки, токены, assertion diffs
  или произвольные сообщения исключений. Ошибка в проверке равенства image ID
  не разрешает отключать readback; сначала воспроизвести её в loopback-репетиции.
- Публикация трёх пакетов **не атомарна**. Если второй/третий push, readback или
  upload-artifact не прошёл, отдельные образы могут остаться в GHCR. Это не релиз:
  сервер их не получает. Не удалять автоматически, не устанавливать по тегам.
- Повторный запуск имеет новый attempt/tag. Старый неполный набор не перезаписывается.
- Нет credentials fallback: не выдавать workflow admin SSH, общий PAT или ключи ИИ
  для исправления ошибки Packages. Сначала проверить repository/package access.
- Проверка приватности идёт до и после push; администраторы организации должны
  сохранять приватность между проверками. Workflow не заменяет контроль доступа.
- Concurrency запрещает одновременные candidate-job, текущий выпуск не отменяется
  новым запуском. Другие администраторы всё ещё могут изменить main/Packages.

## Доставка на сервер — следующий отдельный шаг

**Этот PR не подключает автоматический deploy и не выдаёт ВМ registry credential.**
После успешного кандидата и согласования доставки:

1. Подготовить отдельный ограниченный, срочный доступ ВМ только на чтение нужных
   private packages (`read:packages` classic PAT согласно GHCR), без права публикации
   и без администраторского SSH-ключа в GitHub. Ввод локально, не в чате/репозитории.
2. Передать проверенный runtime bundle в новый `/opt/citygo/releases/<releaseId>`.
   Сравнить хеши с manifest из доверенного artifact; не выполнять полученные
   произвольные команды/URL/compose override из непроверенного файла.
3. Заполнить защищённый `/etc/citygo/pilot.env`: три digest из manifest и
   `POSTGRES_IMAGE` из `bases.postgres`, согласованный домен, secret directory,
   постоянный volume. Ни одного плавающего image tag.
4. Для первой установки подготовить новые DB-роли/секреты, TLS и DNS. Для обновления
   проверить backup с restore, место и совместимость SQL; держать общий maintenance
   lock. Не запускать миграции одновременно с резервным копированием/другим релизом.
5. Следовать [runtime runbook](cloudru-runtime.md) с проверкой здоровья. Не откатывать
   образ после несовместимой миграции автоматически. Приложение/БД/AI и публичный
   доступ включаются отдельными операциями; готовый кандидат не снимает эти условия.

Для выключения будущих выпусков убрать/сменить `CITYGO_RELEASE_PUBLISH_ENABLED`.
Это не удаляет уже выпущенные образы и не останавливает уже работающий job/сервер.

## Проверки разработчика без публикации

```sh
pnpm test:release
# Только одноразовый Linux Docker, без облачных/провайдерских credentials:
node scripts/release-candidate.mjs prepare
node scripts/container-smoke.mjs --disposable --release-candidate
# Только на одноразовом Linux CI runner (CI=true):
node scripts/registry-smoke.mjs --disposable
```

`prepare` создаёт `.local/release-candidate/build-inputs.json`, smoke — evidence
только при полном успехе. Файлы создаются с отказом от перезаписи. Для повторной
локальной репетиции используйте свежий disposable checkout/runner, не удаляйте
общую `.local` с пользовательскими БД. CI проверяет весь build/smoke/evidence-путь
и настоящий push/pull в одноразовый `registry:3`, доступный только через
`127.0.0.1:<случайный порт>`. Используется отдельный пустой Docker config, без
учётных данных. Все GHCR-имена перехватываются тестовым transport; внешний push
невозможен по штатному пути. Это не проверка политики доступа GHCR. Unit-тесты
дополнительно проверяют отказы и отсутствие секретов в диагностике.

Первый ручной выпуск `35814148398` (main `615f098`) остановился после загрузки
private API package; Web/jobs и artifact не созданы. Из старого общего сообщения
нельзя установить точную причину. Этот неполный набор не устанавливать и не
считать готовым релизом; исправление диагностики само по себе не доказывает
исправление исходного сбоя.
