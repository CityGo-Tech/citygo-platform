# План дальнейшей разработки

Обновлено **4 октября 2026**, после PR #75. Это доступная в GitHub версия
очереди из «CityGo_Очередь_реализации_2026-09-14» и
«CityGo_Технический_план_2026-09-14», с учётом поздних решений о постепенной помощи.
Номера CG сохранены. Это порядок работ, **не обещание сроков и не разрешение
на запуск пилота, новые расходы или изменение production**.

## Цель и отправная точка

Полный CityGo сопровождает человека по пути:
идея переезда → оценка возможностей → план → жильё и работа → поездка и вещи →
первые недели → городские сервисы и своё окружение.

Первый релиз R1 сознательно уже: **подготовка поиска и просмотра жилья в Москве,
Web, до 20 допущенных участников, реальная помощь владельца**. Неизвестные
бюджет/срок/тип жилья не должны блокировать первую пользу. Полная анкета не
возвращается под видом обязательной цепочки коротких вопросов.

Baseline CG-001–008 уже создан; CG-009 поставлен в PR #74, CG-010 — в PR #75.
У CG-010 готовы правила и контракты, не новый пользовательский сценарий.
Существующие AI-адаптеры, денежный учёт, дизайн, CI и Cloud.ru-контур сохраняем
и развиваем, а не создаём заново. [Текущее состояние](project-status.md).

## 1. Ближайший основной блок

| Задача                                          | Результат для проекта                                                                                       | Когда можно принять                                                                                                                                       |
| ----------------------------------------------- | ----------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **CG-012 — хранение результатов и команды API** | Частичные ответы, бриф и чеклист сохраняются как версионированные ресурсы                                   | Проверены владелец, план, ревизии, происхождение действий, изменения отдельных полей и конкурентные команды; чужие и устаревшие подтверждения отклоняются |
| **CG-013 — постепенный Web-путь**               | Полезная карточка после малого объёма контекста, следующий добровольный вопрос, исправления и подтверждение | Видны неизвестное/пропущенное/предложение/факт; можно вернуться позже; подтверждается именно показанная ревизия; нет повторного цикла вопросов            |
| **CG-014 — содержательное завершение и XP**     | Награда за подтверждённый полезный результат, а не за факт ответа модели                                    | Сервер проверяет содержание и актуальность; completion/receipt/XP/unlock/outbox согласованы; гонки и повторы не дают лишних XP                            |

Порядок: **CG-012 → CG-013 и CG-014 → их совместная E2E-приёмка**.
Серверную часть CG-014 можно делать после CG-012 параллельно UI, если согласованы
контракты и разделены файлы. Нельзя включать пересоздание планов до защиты
однократной награды `(user, r1-pilot, questSlug)`.

CG-012 следует дробить на проверяемые изменения: хранение/миграции,
owner-scoped чтение и редактирование, происхождение/подтверждение, затем
интеграционные отрицательные тесты. Для JSON-результатов достаточно PostgreSQL;
файловое хранилище CG-034 не является блокером. Минимальная outbox-схема
согласуется с CG-031: не создавать две очереди событий.

Первый инкремент — [CG-012A: история частичных ответов](implementation/cg-012-answer-history.md).
В текущей ветке подготовлено внутреннее хранилище без публичного API и включения
в Web/Expo. Это кандидат для ревью, не закрытие CG-012: полезные результаты,
привязка к квесту, зависимости и подтверждения ещё впереди.

Критерии награды и раннего чеклиста не изобретаются повторно: источник —
[принятая спецификация CG-010](implementation/cg-010-housing-criteria.md).
Старые XP сохраняются; нельзя задним числом приписать им несуществующие
подтверждения или считать их доказательством прохождения нового R1.

## 4. Эксплуатация и критерии допуска R1

Cloud.ru, контейнеры, HTTPS, миграционные роли, релизный pipeline и backup уже
имеют реализацию. Здесь задача — проверить и дополнить существующее.

| ID                       | Что проверить или добавить                                                                                                             |
| ------------------------ | -------------------------------------------------------------------------------------------------------------------------------------- |
| CG-029 / CG-030 / CG-032 | Текущий сервер, изоляция сред, регионы данных, минимальные роли БД, безопасные миграции, закрытые origin-порты и HTTPS                 |
| CG-031                   | Delivery worker с lease, retry, deduplication и видимыми ошибками для нужных R1-уведомлений; существующий housekeeping этого не делает |
| CG-033                   | Общий account/IP rate limiter до нескольких API-реплик; одна реплика допускается только после проверки её возможностей                 |
| CG-034                   | Приватные файлы и ограничения доступа перед появлением настоящих uploads; не блокирует JSON-бриф                                       |
| CG-035                   | Свежая шифрованная копия и восстановление непустой БД в изолированном окружении; измеренные потери данных/время восстановления         |
| CG-036                   | Внешняя проверка недоступности VM, уведомления владельцу, контроль расходов и аварийное отключение AI                                  |
| CG-037                   | Релизные разрешения функций, совместимость клиентов, проверка SHA/digest и порядка обновления; существующий deploy не переписывать     |
| CG-039, часть R1         | Исправление ответов, устаревание только зависимого результата и повторное подтверждение без потери прогресса                           |
| CG-043, часть R1         | Доступ к истории старше последних 100 сообщений либо явно согласованное ограничение без обещания полной истории                        |
| CG-044, часть R1         | Клавиатура, узкий экран, крупный текст, диктор; отдельно WebKit/Safari. Наличие токенов не доказывает доступность                      |
| CG-059, часть R1         | Измерение начала/подтверждения/завершения/обращения/ошибок и стоимости результата без текста чата в аналитике                          |
| CG-063, часть R1         | Согласованная малая нагрузочная проверка 1/3/5 синтетических сессий с mock AI, ресурсы и восстановление после сбоя                     |

**CG-028 — отдельная приёмка и набор людей.** До неё должны пройти:

- новый жилищный путь, содержательное подтверждение и защита повторных XP;
- независимая помощь и готовность реального оператора;
- допуск участников, восстановление доступа, согласия и lifecycle данных;
- источники, guardrails, предметная оценка Housing и сквозные тесты;
- бюджет, restore, внешние alerts, совместимость, доступность и малая нагрузка.

После согласования — малая группа, затем расширение до 20 по результатам.
Критическая ошибка, перерасход или необслуживаемые обращения — основание
остановить расширение. Зелёный CI, merge и доступная страница не запускают пилот
автоматически. «20 участников» не означает «20 одновременных модельных запросов».

## Как двигать задачу по очереди

Для каждой задачи фиксируем границы файлов и данных, зависимые контракты,
результат для человека и проверяемые критерии. Затем отдельная ветка, тесты,
документация и PR. После принятия обновляем [статус](project-status.md), но не
помечаем весь R1 готовым по одному успешному инкременту.

Параллельная работа допустима в отдельных рабочих копиях с разделённым владением
файлами. Общие контракты, миграции и lockfile требуют координации. Read-only
ревью не даёт права менять файлы, а merge не является разрешением на новые расходы.
