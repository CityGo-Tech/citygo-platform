# Участие в разработке CityGo

Начните с [документации](docs/README.md), [статуса](docs/project-status.md) и
[очереди задач](docs/roadmap.md). Для текущего R1 обязательны принятые
[правила постепенных результатов](docs/implementation/cg-010-housing-criteria.md).

## Подготовка

1. Получите доступ к приватному репозиторию и клонируйте его в свою рабочую папку.
2. Используйте Node.js 24 LTS и pnpm **10.15.0** из `packageManager`.
3. Выполните `corepack pnpm install --frozen-lockfile`, затем `corepack pnpm dev`.
   Подробности и варианты БД — [локальный запуск](docs/runbooks/local-development.md).
4. Работайте на вымышленных данных. Для обычных тестов не нужны ключи AI,
   production-БД или подключение к серверу.

Если в вашей согласованной рабочей копии предусмотрен локальный безопасный
launcher, используйте его по инструкции владельца окружения. Его путь и
наличие не являются требованиями к чистому клону: `.local` не поставляется в Git.

## Одна задача — отдельная ветка и понятный PR

- Начинайте от актуального `main` в чистой или выделенной рабочей копии.
  Не сбрасывайте чужие незакоммиченные изменения и не копируйте поверх них файлы.
- Укажите номер CG, цель, что не входит в задачу, изменяемые контракты/файлы
  и критерии приёмки. Большую задачу разделяйте на проверяемые инкременты.
- Если работают несколько людей или AI-инструментов, используйте отдельные
  ветки и рабочие копии. Общие контракты, миграции и lockfile согласуйте заранее.
- Read-only ревью заканчивается замечаниями, не изменениями. Доступ к серверу
  или ключам не является разрешением их использовать в любой задаче.
- Не пишите напрямую в `main`, не объединяйте PR и не включайте платные вызовы
  без соответствующего решения владельца.

## Где менять код

Общие схемы — `packages/contracts`, правила — `packages/domain`, хранение и
транзакции — `packages/db`, API — `apps/api`, клиентский транспорт —
`packages/api-client`. UI не должен решать, кому принадлежат данные или сколько
выдать XP. Модель не имеет права подтвердить пользовательское действие.

При изменении API учитывайте одновременно Web и Expo:
[политика совместимости](docs/architecture/api-compatibility.md).
Применённые миграции не редактируются; новые проверяются на чистой БД и
переходе с предыдущей схемы. Не превращайте фикстуры/кандидатные схемы в
production seeds без отдельной реализации и проверки.

## Проверки

| Изменение               | Минимальная проверка перед PR                                                                                  |
| ----------------------- | -------------------------------------------------------------------------------------------------------------- |
| Только Markdown         | Prettier изменённых файлов, `git diff --check`, относительные ссылки/якоря, команды и утверждения по коду      |
| Контракты / домен / API | Целевые положительные и отрицательные тесты; `pnpm check`; проверка обоих клиентов                             |
| БД / команды            | Предыдущее плюс PostgreSQL integration: чужой owner, replay, гонка, rollback транзакции и upgrade миграции     |
| Web-сценарий            | Предыдущее плюс `pnpm browser:install` и `pnpm test:e2e`; узкий экран, клавиатура и ошибки                     |
| Mobile / общие пакеты   | `pnpm mobile:export`, проверка на устройстве по риску; export не заменяет APK/device QA                        |
| Контейнеры / релиз      | Тесты соответствующих scripts и отдельный Container smoke; серверные операции только по согласованному runbook |

`pnpm check` запускает lint, typecheck, unit/integration-тесты, тесты контейнерных
и релизных скриптов, build и startup. Это **не** сам Docker smoke и не Playwright:
они проверяются отдельно. Для server-PostgreSQL тестов используется только
выделенная тестовая БД в `TEST_DATABASE_URL`, никогда production.

Тестовые entrypoints используют детерминированный провайдер. Зелёные тесты
не доказывают качество живой модели или актуальность её сведений. Живой тест
требует отдельного согласования получателя данных и предела расходов.

Пример форматирования одного документа:

```sh
pnpm exec prettier --check README.md
git diff --check
```

Не запускайте массовое форматирование всего репозитория ради одного документа.
Если проверка недоступна, напишите причину и что именно осталось непроверенным;
не заменяйте результат фразой «должно работать».

## Что писать в PR

1. Номер задачи и пользовательский/технический результат.
2. Изменённые области и явные исключения из scope.
3. Выполненные команды проверок и их результат; непроведённые проверки отдельно.
4. Совместимость, миграции, feature gates и операционные последствия, если есть.
5. Обновлённые документы и известные ограничения.

CI запускается и для документационных PR. **Merge в `main` может запустить
автоматическое обновление Cloud.ru**, в том числе после изменения только
Markdown: фильтра по документационным путям в текущем deploy-процессе нет.
Порядок — [runbook обновления](docs/runbooks/automatic-main-deployment.md).

## Как поддерживать документацию

- `README.md` — короткая точка входа; `docs/README.md` — навигация.
- `docs/project-status.md` — состояние с датой, коммитом, PR и доказательствами.
- `docs/roadmap.md` — следующие результаты и зависимости, не отчёт об исполнении.
- `docs/product/` — решения; `docs/implementation/` — датированные спецификации
  и отчёты; `docs/runbooks/` — инструкции выполнения операций.
- Обновляйте связанные документы в том же PR. Отличайте «контракт готов» от
  «функция работает», а «проверено в CI» — от «развёрнуто и принято на сервере».

Никогда не включайте реальные ключи, cookies, токены, `.env`, дампы, анкеты,
тексты диалогов или персональные данные в коммиты и отчёты.
